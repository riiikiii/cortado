How Terraform works

Terraform manages infrastructure from declarative configuration. You describe the end state in HashiCorp Configuration Language (HCL), and Terraform builds a dependency graph and works out the actions needed to reach it.

Provider
A plugin that knows how to work with an API or platform. The AWS provider, for example, can manage S3 buckets.
Resource
An object Terraform manages. A resource has a Terraform address such as aws_s3_bucket.lab and typically an ID assigned by the platform.
Data source
A lookup that reads information such as the current account ID or an existing network. Its result can feed other blocks.
Module
A directory of Terraform configuration. Your working directory is the root module. Any modules it calls are child modules.

Configuration, state, and live infrastructure can differ. The HCL describes your intent. State records which remote IDs belong to which Terraform addresses and retains information Terraform needs to manage them. During a normal plan Terraform refreshes its view of managed objects through providers, then computes changes. Apply calls the APIs and writes updated state.

References usually determine order. If a bucket policy uses aws_s3_bucket.lab.id, Terraform knows that the policy depends on the bucket even if the policy block appears first. Use depends_on for a dependency Terraform cannot infer, such as a service that requires permissions established by a separate policy attachment.

Install and verify

Use Terraform CLI 1.10 or a later 1.x release. A terminal and a plain-text editor are enough for the local lab.

Windows

  1. Download the Windows ZIP from the official install page. Pick AMD64 for most Intel or AMD PCs and ARM64 for Windows on Arm. Windows lists the processor architecture under Settings → System → About → System type.
  2. Extract terraform.exe into a folder such as C:\Tools\Terraform. In Edit environment variables for your account, edit the user Path and add that folder.
  3. Open a new PowerShell window. Run the verification commands below. Make sure your editor saves .tf files with that extension, since some Windows editors append .txt by default.

macOS

Linux

Use the official package repository instructions for your distribution, or download and extract the matching Linux binary. For a user-local binary install, place the executable at ~/.local/bin/terraform, give it execute permission with chmod +x ~/.local/bin/terraform, and make sure the directory is on your PATH.

If the terminal cannot locate Terraform, check Get-Command terraform in PowerShell or command -v terraform in Bash or Zsh. If a different version appears, use that path to find the earlier install. For manual downloads, use HashiCorp’s published checksums and signature verification instructions.

Read and write HCL

A block has a type, sometimes labels, and braces. In resource "terraform_data" "release", the labels identify the resource type and local name. Inside the block, an argument assigns a value with =. Expressions include references, function calls, conditionals, and comprehensions.

PatternExample and meaning
Input variablevar.environment is an input. Declare its type, description and validation where appropriate. Without a default, the caller supplies a value.
Local valuelocal.release.label references a named expression inside this module, such as a computed name or collection.
Managed resourceterraform_data.release.id references a resource attribute. The expression can also create a dependency.
Data sourcedata.aws_caller_identity.current.account_id reads an attribute from a declared lookup named current.
Module outputmodule.release.label reads an output exposed by a child module. Use root outputs to display or publish values produced by a stack.

Input precedence in the local CLI. From lower priority to higher, Terraform uses variable defaults, TF_VAR_* environment variables, terraform.tfvars, terraform.tfvars.json, *.auto.tfvars and *.auto.tfvars.json in lexical order, then explicit -var and -var-file flags in the order provided. For named environment files such as stage.tfvars, supply -var-file=stage.tfvars when planning.

Give repeated resources stable keys

count creates numbered instances such as terraform_data.service[0]. Use it when an index is the intended identity. for_each creates instances identified by a key, so removing api from the map below leaves worker at its existing address. The full set of keys must be known during planning.

Run terraform plan and look for terraform_data.service["api"] and terraform_data.service["worker"]. In HCL, try a conditional like var.environment == "prod" ? 3 : 1 or a list transformation like [for name in ["api", "worker"] : upper(name)]. Type constraints such as list(string) and map(number) catch shape errors at module boundaries.

Modules and versioning

Start with a single root module. Extract a child module when a group of resources forms a reusable unit with a clear contract, such as a network with subnet outputs. Every .tf file in a directory forms one module, so splitting a large file into main.tf, variables.tf and outputs.tf leaves resource addresses intact.

In a new directory, create these two files. Run terraform init, terraform validate and terraform plan from the directory containing the root file. If you apply it, terraform output -raw release_label returns atlas-dev. Use a reviewed destroy plan to clean up.

  • Terraform CLI. required_version declares compatible Terraform versions. Pin an exact CLI version in CI so colleagues and automation use a known runtime.
  • Providers. required_providers declares each provider’s source and version constraint. The lock file, .terraform.lock.hcl, records selected provider versions and checksums. Commit it for each root module. For example, ~> 6.0 allows compatible 6.x releases and excludes 7.0.
  • External modules. Pin Registry modules with a version argument and Git modules with a version tag or commit ?ref=.... The dependency lock file tracks providers. Module versions come from the module source and its version constraint.
  • Upgrades. Read release notes, update constraints as needed, run terraform init -upgrade, then review lock-file changes and a fresh plan before applying an upgrade.

State, backends, and secrets

State is Terraform’s record of ownership. A backend determines where that record is kept. For a shared stack, use a remote backend with access control, encryption, version recovery, and locking. Locking coordinates writers if the backend supports it.

Choose a boundary for each stack

Use separate root configurations and state locations for environments that need different credentials or access controls. A CLI workspace gives one configuration multiple state snapshots under the same backend configuration. It can be useful for temporary copies of a stack. HCP Terraform workspaces are a different concept. They can bundle state, variables, permissions and run settings.

Example remote backend on S3

Create the state bucket separately with versioning, encryption, and restricted IAM permissions. Substitute its name and use a distinct key for each stack. This example uses S3 lockfiles. Review the backend docs for the permissions on the state object and its .tflock file. The backend has its own authentication, which runs during init and is separate from provider setup.

Backend blocks take literal settings and cannot reference var.* or local.*. Keep credentials in your environment or workload identity. For an existing stack, pause writers, take a protected backup, and use terraform init -migrate-state to copy state to the new backend. Verify the target with terraform state list and a fresh plan before resuming applies. init -reconfigure refreshes the backend settings without copying the previous state. For an existing S3 setup with DynamoDB locking, consult the migration guidance because that locking method is deprecated.

State and plan files can contain secrets. sensitive = true redacts normal human-readable output. Values can still be stored in state and saved plans, and some output commands can reveal them. Use short-lived credentials, tightly restrict access to state and plan artifacts, and keep both out of Git. Ephemeral values (Terraform 1.10+) and provider write-only arguments (1.11+) can keep supported values out of state and plans.

Commit the .tf sources, test files, and any generated .terraform.lock.hcl. The ignore example assumes variable files may contain secrets. Teams can track deliberate non-secret files by name or publish sanitized .tfvars.example templates. Store any saved plan under a restricted path and expire it when the run ends.

Drift, imports, and refactors

Resolve drift

Drift is a difference between what Terraform expects and what exists, for example when a tag changes in the cloud console. Start with a normal terraform plan. If the configuration is still correct, review the change that restores it. If the live change is intentional, update HCL and plan again. Use terraform plan -refresh-only to preview updates to state and root outputs that reflect live objects. Applying a refresh-only plan records the observation. Update the configuration too if you want later normal plans to preserve the live change.

Adopt an existing resource

Find the provider’s import ID format and check that the object has no other Terraform owner. In the intended root module, declare a resource that matches the existing object and add an import block. The following example belongs in a properly configured AWS root for a bucket you already own.

Tests and team workflow

Test configuration behavior

In the original lab, save this file as tests/release.tftest.hcl and run terraform test from the root. If you completed the rename exercise, change the assertion to use terraform_data.record. The assertion checks the planned input, which is already known. A provider-computed output may only be available after apply.

terraform validate checks configuration consistency. terraform test checks behavior expressed as assertions. Tests default to apply unless you specify command = plan. Apply-mode tests can create infrastructure and incur cost. Run those in an isolated test account or use provider mocks where they fit your goal. Check cleanup if a real test fails.

Move a change from pull request to apply

  1. On the pull request, run terraform fmt -check -recursive, initialize for validation with terraform init -backend=false -input=false, then run terraform validate and the tests appropriate to that runner. Review configuration, dependency upgrades, and the intended targets. Keep deployment credentials out of untrusted pull-request jobs.
  2. From the approved revision, initialize against the real backend. Use short-lived credentials, verify the identity and environment, then generate a plan with terraform plan -input=false -lock-timeout=5m -out=deploy.tfplan. Review additions, access changes, replacements, and deletions. If a release affects a database or other durable data, review the backup, restoration, and maintenance steps too.
  3. After approval, apply the saved plan in the same stack using compatible Terraform and provider versions. Keep one active deployment per state. If the plan is stale or the revision, inputs, identity, or intended environment changes, generate a fresh plan and review it again.
  4. After apply, verify service health and record the result. If apply fails partway through, inspect the error and current state, fix the cause, and run a fresh plan before retrying. Terraform can leave successfully completed changes in place. Reverting a commit may propose further changes and needs its own review.

terraform plan -detailed-exitcode returns 0 for no changes, 1 for an error and 2 for changes. Handle 2 explicitly when the shell or runner treats any nonzero exit as a failure.

Troubleshooting

What you seeWhat to check
Terraform command missing or wrong versionResolve the executable path and reopen the terminal. Check terraform version against required_version.
Provider fails to installCheck the source address, version constraints, OS/architecture support, and registry connectivity. Run terraform providers to see which modules impose constraints.
Authentication errors or unexpected accountCheck the effective identity, credential expiry, region, and permissions. Backend and provider authentication can fail independently. With AWS, start with aws sts get-caller-identity.
State lock is heldLook for an active run and wait or use -lock-timeout=5m. Use terraform force-unlock only for your own confirmed stale lock after ensuring no writer is active.
Plan shows many unexpected creates or deletesCheck the working directory, backend key, workspace, variable file, resource addresses, and account. Compare terraform state list with the expected stack.
A change requires replacementRead which attribute forces replacement. Check the provider documentation and the service impact. create_before_destroy can change the order when both objects can coexist, and may require additional capacity or a different name.
for_each keys are unknownDrive the key set from configuration or inputs known at plan time. Use computed resource attributes in the map values where the keys are available independently.
Saved plan is staleCheck for another deployment or a state change, then generate and review a new plan from the correct revision and environment.

Check your understanding

What should you check before approving a plan with 30 unexpected creates?

Start with the directory, backend key, workspace and account. An empty or wrong state can make Terraform propose new objects for infrastructure that already exists. Compare the plan’s addresses with the intended state.

When does a Terraform rename need a moved block?

Use it when the state address changes and you want to keep the existing object. Moving a block between .tf files in the same module keeps the address the same.

Someone intentionally changed a tag in the console. How do you keep it?

Update the HCL to represent the intended tag, then review a normal plan. A refresh-only apply by itself only updates Terraform’s record of what exists.
