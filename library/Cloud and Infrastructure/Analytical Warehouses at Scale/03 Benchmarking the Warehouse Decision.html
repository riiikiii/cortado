Build a workload card before booking capacity

The decision is whether a platform can publish a correct corrected position and keep it fast during a burst while history gets restated. Start with two implementations of the same report. Design A keeps full history in S3/Iceberg, uses Athena to derive facts and publishes a book/day mart. Design B uses the most relevant managed warehouse from the previous guide, with equivalent ingestion, history and BI output. Add Trino reading the same Iceberg snapshot as a controlled engine comparison if its operational model is a serious candidate.

Use agreed business targets when available. The following invented workload is a starting contract. Record the exact region, engine or service tier, edition, client and driver, table layout, file counts, entitlement rules, auto-scaling range and pricing agreement. A service name alone cannot reproduce a measurement.

Input to the pilot Example Why it changes the answer
History and growth 1 PB compressed over 1,000 days, 1 TB/day steady, a 3 TB catch-up day Backfills, file compaction and retention change both storage and compute.
Distribution One book contributes 35% of recent facts. Test it alongside small books. Uniform random data hides skew, memory pressure and hot keys.
Updates 2% corrected trades, exact replays, late older revisions and book transfers Measure correctness, target scan, amplification and publication lag.
BI arrivals 120 users open one eight-visual page within 10 seconds Roughly 96 visual requests/s before caching, batching or retries. Observe actual fan-out.
API Book/day lookup p99 ≤250 ms. Return batch, watermark and amount. A precomputed primary-key lookup has a fundamentally different work budget from ad hoc SQL.
Freshness Corrected event visible to all entitled consumers within 60 s at p95 A fast stale cache fails. Measure source commit to visible output.
Batch and exploration Two-hour restatement overlapping reporting, analyst filters with a long tail Exposes noisy neighbours and oversubscription.

In steady state Little's law gives average in-flight work ≈ arrival rate × average end-to-end time. At 96 requests/s and 1.5 s mean residence time, about 144 requests are in flight. This is a sizing check, not a p95 calculation or a count of physical workers. A ten-second opening burst is transient. Drive the recorded arrival trace, watch the queue drain, and size for the deadline observed by the last users.

Run four query families on the same publication

  1. Point read. Bind batch, book and date and retrieve a single exposure row through the real API. Measure client, pool wait, database and serialisation time. Run already-open and newly established connections separately.
  2. Dashboard. Replay the eight real visual queries or the BI page itself against the same publication. Vary filters by role, hot book, small book and date. Record complete page-ready time and individual query IDs.
  3. Interactive slice. On current trade facts, aggregate a week by book, then drill into a selective book/day and fetch a bounded number of rows. Vary date width and sort order. Test one unforeseen grouping missing from the mart.
  4. Historical recompute. From raw revisions, select the latest valid trade per ID at a pinned source cut, join the effective-dated reference set and aggregate five years. Persist the output and reconcile. Include the write and publish step in batch duration.

Use three data scales when feasible: a hand-checkable fixture, a representative time slice with genuine skew and file sizes, and a production-scale or contractually realistic rehearsal. If only 1% can be tested, state which thresholds remain untested. A join fitting in memory at 1% can spill at full scale and a broad scan can hit source throttling. Never extrapolate p99 linearly from row count.

Event or failure Expected published observation

Publisher stops after loading a new batch and before promotion Readers remain on the last verified batch. Retry publishes once and retains the reconciliation trail.

For the full run compare keyed counts and decimal totals at book/date/currency plus deterministic samples of trade lineage. An invariant such as “global sum unchanged” misses a trade posted to the wrong portfolio. Measure correction visibility for a viewer of the old book and one of the new book. Measure all counters at a fixed cut. Rows moving while candidates are sampled create false differences.

Collect timing evidence you can explain

For Athena record the query ID, engine version, workgroup, output row count and execution statistics. Given AWS CLI access to inspect a completed query, replace the ID below. The command reads metadata for an existing execution.

Separate queue, engine execution, planning, bytes scanned, total service elapsed time and the result-reuse flag. Planning is a component of engine execution time. Adding both double counts. The service total does not include all client fetch and rendering time. Explicitly disable result reuse for the fresh-run baseline. Athena may otherwise serve a prior eligible result within the configured age. Record reuse separately as a legitimate production case only if its staleness contract meets the business target. Run each candidate in four labelled states: idle or suspended startup, warm compute with varied predicates, eligible repeated result, and the opening burst during a backfill. Some managed caches cannot be forcibly emptied. Describe the controls used and label uncontrolled cache state. Use identical source cuts, query answers, time windows and cost boundaries. Report both equally tuned native implementations and a shared-file scan where relevant. The first compares viable solutions. The second isolates engine and connector effects. A precomputed mart versus a raw recomputation answers a different architecture question.

Use an open-loop driver that schedules requests against the intended arrivals. A client that waits for each slow reply before firing the next quietly reduces offered load when the system struggles. Preserve intended start, actual start, finish, timeout and cancellation in the log. Use enough client workers to avoid making the driver the bottleneck. Repeat across multiple opening windows, keep timed-out requests in the denominator, and show success rates and latency percentiles by query family. A p99 from 30 queries says little about the tail. Also report requested vs achieved throughput, the maximum queue age and time to recover after the burst.

Put pounds against the service target

Use current contract rates in GBP for the deployment region, with the same VAT treatment and exchange-rate assumption for every vendor. The figures below are deliberately hypothetical, use decimal TB and GB, and exclude tax. They illustrate break-even arithmetic rather than vendor pricing.

Illustrative month, 30 days Calculation Result
On-demand scans 2,000 requests/day × 5 GB × 30 ÷ 1,000 300 TB/month
Assumed scan charge 300 TB × £4/TB £1,200/month
Preaggregate construction 1 TB/day × 30 × £4/TB £120/month
Serving tier plus build scans £650/month + £120 £770/month
Equal cost in this simplified model £770 ÷ (£4 × 0.005 TB/query) ÷ 30 About 1,284 queries/day

At 2,000 queries/day the simplified saving is £430/month. If the average scan falls from 5 GB to 0.5 GB, the original reports cost £120/month at the same volume, reversing the comparison. If the serving tier is mandatory for the latency target, a lower scan bill alone cannot win. If the build processes 1 TB each minute to meet freshness, its cost changes by orders of magnitude. Benchmark an incremental refresh, and count compaction, writes, reads and late-data repair. Athena pricing dimensions

For each candidate add storage and retained snapshots, requests, replication, network and cross-cloud transfer, catalog, compute for transformations and maintenance, BI licences, idle or reserved capacity, support and realistic engineering time. For self-run Trino include worker and coordinator hours, HA design, upgrades and incident cover. For managed Postgres include IOPS, HA, backups and restore drills. For Snowflake multiply metered credits by the contracted GBP rate. For Fabric attribute incremental capacity and show shared-cost allocation separately. For Databricks distinguish serverless billing from configurations that also charge cloud infrastructure. Quote cost per 1,000 successful, timely, fresh business requests plus the complete monthly budget. Show both peak-capacity cost and quiet-hour cost.

Interpret failure and make a decision

Observation First experiment How the decision changes
SQL fast, page slow Correlate visual waterfall, data transfer, model calculation and last rendered visual. Tune the model, bound results or precompute report grain before adding SQL compute.
Query fast alone, high queue during burst Isolate BI and backfill, then rerun identical arrivals. If queues disappear, buy isolation or schedule capacity. If a single query still misses, optimise its plan.
Low scan bytes, high planning time Compact the same logical dataset and retest with unchanged filters. Better file layout can remove the need for a larger cluster.
Worker tail and huge exchange Measure largest key and task input, reduce build side or preaggregate before joining. Increase capacity after checking skew. Doubling workers may leave the hot key on one worker.
Warm results fast, correction invisible Disable reuse, pin the new batch and time publication, replica catch-up and BI refresh independently. Shorten or version caches, change refresh mode or move publication to the incremental path.
Protecting p99 is expensive under ad hoc load Route fixed lookups to the mart and retain a warehouse for flexible slicing. A hybrid can win if recovery and policy parity also pass.

Apply hard gates before scoring: correct as-of results and entitlements, freshness, p95 page and p99 API under the agreed burst, batch deadline, restore objective and budget ceiling. Record each as pass, fail or unmeasured with a link to the run. Compare monthly GBP and operational work only among candidates that clear the gates. Under a near tie, test the assumption most likely to reverse the choice, such as doubling concurrent users, a new grouping dimension or moving the source to another cloud.

A defensible initial architecture for this example keeps full history on S3/Iceberg, uses Athena for research and rebuilds, and serves the book/day dashboard from a versioned aggregate. Benchmark managed Postgres if interactions remain bounded lookups. Benchmark Fabric with the real report if Power BI owns the experience, or Redshift/Snowflake/Databricks SQL when users routinely invent large new groupings. Replace Athena with warm Trino only after demonstrating a gain in the query classes or controls that matter. Promote the simplest architecture meeting the hard gates. The decision record should name the losing workload for each rejected design and the change that would justify revisiting it.

Verification boundary. The portable revision query and the replay, stale-revision and book-transfer cases were checked locally with SQLite. AWS, Trino, PostgreSQL and managed-warehouse examples target the documented interfaces. The service targets, dataset sizes, rates and timings used for sizing are illustrative.
