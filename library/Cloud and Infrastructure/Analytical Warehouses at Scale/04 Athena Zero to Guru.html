From an empty workgroup to a reliable data product

Your first task is to answer “what was the GILT book's GBP exposure yesterday?” from files in S3. Your final task is to publish the answer with a reproducible source snapshot, bounded cost and a recovery procedure. Athena SQL engine version 3 is the target throughout. The SQL belongs to Athena's supported dialect. Commands for standalone Trino appear in the following guide.

You need an AWS account, a chosen Region, permission to use Athena and Glue, and an S3 bucket with dedicated lab prefixes. This guide uses London, eu-west-2. The examples create resources and run chargeable queries in your account. Choose a new database and empty output prefixes for each first run. Replace YOUR-BUCKET everywhere before executing. The Python client requires Python 3.11+ and boto3 installed in a virtual environment. Authentication comes from your normal AWS profile or workload role.

Athena supplies managed query execution. You still own the structure and quality of the data, publication rules, permissions, retention and workload limits. Athena also offers a Spark execution experience, with a different programming and execution model. Here we use SQL because our deliverable is an analytical table and its reporting query. Create the workgroup and first dataset

In the Athena console create a workgroup named athena-learning, choose SQL and engine version 3, configure a customer-owned result location such as s3://YOUR-BUCKET/athena-learning/results/, and enforce the workgroup configuration. Enable query metrics and set a lab-appropriate per-query scan limit. The examples assume this customer-owned result configuration. If your organisation uses managed query results, use that mode's documented access and retention behaviour.

Turn raw strings into a business contract

Create a typed view as the boundary between physical input and domain values. TRY_CAST lets you count invalid fields explicitly. It must be paired with a publication gate. SUM ignores null amounts, so quietly continuing after conversion failures can understate a report.

This returns zero rows for the fixture. Next reject conflicting payloads for the same logical version. The exact duplicate of A is harmless after DISTINCT. Two versions with identical identity and revision but different values indicate a conflict requiring a declared resolution policy.

Materialise Parquet and understand the scan

CSV requires parsing row text. A columnar format groups values by column and records useful statistics. Selecting three columns from a wide Parquet file can avoid loading the remaining columns. Predicates may skip partitions, files or row groups. Projection and pruning act at different levels, so measure actual input bytes for the intended query.

Use CTAS to create a compact immutable baseline. The destination must be empty for this first creation. Partition columns appear last in the SELECT for this Hive-style table.

Compare the date-filtered aggregate against the view and the Parquet table. Confirm identical rows before comparing bytes. Five rows are too small for a performance result. Repeat the same experiment on a representative slice with real column widths and partition sizes. A LIMIT without a selective predicate does not guarantee a cheap scan. A COUNT(*) may use optimisations that your real report cannot use.

Run Athena safely from an application

Execution is asynchronous. Submit, retain the query ID, poll to a terminal state, then page through results. A timeout in your application does not automatically cancel the service query. A durable job should store its request token and query ID before acknowledging work to its caller.

The following complete script executes a small SELECT using the enforced workgroup settings. Install boto3, save as report.py and set ATHENA_REQUEST_TOKEN to a fresh UUID for a new logical request. Reuse that token and identical arguments after a submission retry. Change it for an intentional fresh report. The script targets a customer-owned result location configured on the workgroup.

The polling loop accepts QUEUED and RUNNING until a terminal state. A distributed job should poll with backoff and jitter and retain recoverable status externally. This small script demonstrates a deadline and cancellation request. Observe the final state before considering cancellation complete in an orchestrator. Keep errors and query IDs correlated with the caller's batch.

For user-supplied values, use Athena execution parameters or prepared statements within their documented constraints. They use positional placeholders and are subject to statement and placement restrictions. Identifiers such as table names need an allowlist. Never concatenate arbitrary user SQL into an API endpoint. Query result cells are strings, so decode dates and decimals explicitly using metadata for general-purpose clients. The header handling above applies to this SELECT result. DML and manifest results need their own interpretation. StartQueryExecution and request tokens · Parameterised queries

Export large results without a giant client response

The report API should return a compact result or an asynchronous job handle. If the business wants a large file, write a dataset to S3 and return the governed export location. Use a new empty export prefix for an unpartitioned UNLOAD.

Expect multiple objects when output is parallelised. An ORDER BY cannot establish a global ordering across separate files. Consume the manifest or a completed-export record, then reconcile rows and totals. If execution fails, inspect partially created objects before retrying into a new prefix. Use a completion marker only after validation. Keep export expiry separate from table retention. UNLOAD behaviour and limits

Tune the measured bottleneck

Record queue time, planning time, execution time, bytes scanned, result reuse, client fetch and page-ready time. Planning is included in engine execution time in Athena statistics. Sum components only when their definitions do not overlap. A warm result-reuse hit has a different freshness contract from an executed scan.

Observation First action Evidence of improvement
Broad scan for a narrow report Check partition predicate, selected columns and implicit casts Physical scan falls with identical output
Many tiny files, long planning Compact a representative partition Lower planning overhead and fewer file opens
Huge joined intermediate Filter dimensions, validate uniqueness and aggregate at the correct grain Fewer rows entering the exchange and equal business totals
One expensive distinct or sort Bound the requested detail, evaluate approximate functions only if business tolerance allows Lower peak work and explicitly documented approximation error
Queued morning reports Inspect quotas, concurrent jobs and workgroup capacity assignment Queue age and page-ready p95 fall under the same arrivals
Fast old answer Inspect reuse age and publication watermark The new correction becomes visible within the freshness objective

A window over every revision is useful for learning and full reconstruction. Re-running that window over a petabyte on every click is expensive. Maintain the current fact incrementally, materialise repeated aggregates, and retain raw history for restatement. Do not hide precision changes in a performance tweak. Approximate distinct counts may suit exploration. Monetary totals and exact trade counts need the specified semantics.

On-demand Athena scales execution for eligible workloads but has service quotas, admission limits and practical query resource limits. Capacity reservations give another allocation model to benchmark. Workgroups organise usage but do not by themselves establish unlimited independent capacity. The smallest fast query still consumes planning, authorisation and result handling. Test the real morning burst with unrelated research queries running. Own maintenance and recovery

Compaction rewrites small data files and applies accumulated deletes into a more efficient layout. Snapshot expiration shortens the recoverable history and can remove files. Schedule them as distinct operations with explicit retention. The following compacts the lab table. At large scale choose supported partition predicates for bounded work.

Configure retention from your longest reader, failed-job retry horizon and audit policy before running VACUUM. Preserve source history separately if it must outlive snapshot retention. A seven-day example is a policy choice, not a universal default.

Execute VACUUM only after confirming that policy is acceptable. Check its output and the remaining snapshots. File deletion also requires relevant storage permissions. Test recovery by rebuilding a scratch table from raw input and comparing the expected £60.00 on 27 November at the matching correction cut. Maintain a last-good published snapshot pointer so readers can be restored quickly. Snapshot rollback and data reconstruction solve different recovery cases. Iceberg maintenance

Track raw-to-curated lag, latest source watermark, invalid rows, version conflicts, duplicate rates, file counts and publication age alongside query latency and spend. Alert on a stale correct result as well as a failed query. Tag workloads and preserve query history in your own operational record for the required period. Use separate identities for ingest, maintenance and BI. Test with a restricted reader, because an administrator's successful query cannot establish the viewer's access.

Know the boundaries before promising a service

Athena is suitable for object-store analytics, historical inspection, curated SQL transformations and exports. Row-oriented application updates with strict millisecond deadlines need a different access path. Federation can expose other sources, with source connection, permission and latency constraints. Athena uses its own federation mechanism. An arbitrary standalone Trino connector cannot simply be installed into an Athena workgroup.

Document limits for your selected Region and engine before production. Examples include CTAS and UNLOAD partition fan-out limits, query text size, result-row size, timeout and concurrent-query quotas. Divide backfills into controlled batches with idempotent output and reconciliation. Constraints differ between Hive-style external tables and Iceberg. Read the table-format-specific documentation for write operations. Athena limitations · Federated queries

Alternative Prefer it when What to benchmark against Athena

There is no universal “Athena versus Snowflake speed” number. One candidate can answer a cached summary while another reconstructs raw revisions. Compare both the best viable business design and a controlled equivalent scan. Include licensing, storage, transforms, capacity, data transfer and the people required to operate the system. Graduate the lab into a production contract

You have the whole lifecycle once you can land a new batch, reject invalid and conflicting records, preserve replay, publish a current fact, retrieve an old snapshot, measure a real report and recover after an interrupted publication. Run the book-transfer case with the publisher stopped just before promotion. Readers should retain the last verified cut. On retry, verify the existing staged output or build a fresh version before promoting it. The business should see a complete before or after view with an explicit watermark.

The teaching fixture's arithmetic and revision rules are validated locally. SQL, AWS API and maintenance examples are checked against official documentation but require execution in your AWS account for service-level verification.
