Start with one corrected trade

At 09:00 a portfolio manager opens a dashboard. Yesterday's GBP exposure changed after a booking correction. The manager wants the right figure immediately. A researcher wants to explain the change across five years of trades. Both need the same history, but the amount of work each request should trigger is radically different. This series assumes familiarity with SQL, object storage and a BI client. You will build a small ledger, trace a distributed query, choose a serving design and specify an acceptance test.

A warehouse needs a defined grain (what one row means). Here a raw row is an immutable revision of a trade. A current fact is one accepted revision per trade. A business aggregate is one signed GBP amount per book and trade date. Amounts are integer pounds for the lab. A production cross-currency report needs exact decimal amounts, identified FX rates and a valuation timestamp. Summing mixed currencies silently gives a meaningless answer.

Run this read-only query in the Athena SQL editor on engine version 3, or in a Trino SQL client. A configured Athena workgroup needs a usable query-results destination. The example uses literals so you can validate the rule before provisioning tables.

The answer is GILT £60. Summing the arrivals gives £250. Removing the identical replay still gives £160 if you retain the superseded revision. A reversal at revision 3 with a zero amount would leave the book at −£30. Two different rows for the same ID and revision are a source conflict. Reject the batch or quarantine that key before ranking. Arrival time alone cannot resolve it. The highest-revision rule assumes the source assigns monotone versions and sends complete replacement records.

What persists after the compute stops?

Layer Concrete object What its presence proves
S3 object storage Immutable objects under a table prefix The bytes exist. Listing files cannot tell you which revision belongs in a report.
Parquet file format Column chunks grouped into row groups A reader can project columns and may skip groups using statistics. A file alone provides no table transaction.
Iceberg table format Metadata, snapshots, manifest lists and manifests A committed snapshot identifies the live data and delete files. Old files may still be needed by a reader.
Glue Data Catalog Named table and metadata pointer A compatible engine can discover the table and resolve the committed metadata. Permissions still govern access.
Query engine Athena workgroup or Trino cluster Plans and executes SQL. A second engine can open the same compatible table without duplicating all its data.
Business contract Published batch, as-of time, metric definition and entitlements A user can identify what the number means and what data they are authorised to see.

With a Hive-style external table over a directory, the path and partition registrations tell the engine where to look. With Iceberg, the committed metadata determines membership. Copying a Parquet file into an Iceberg directory does not add rows to its snapshot. Conversely, deleting a file by hand can break perfectly valid time-travel queries. Make retention and compaction table-aware. Athena engine v3 integrates work from Trino and Presto. Upstream Trino has its own releases, connector configuration, SQL coverage and operational controls. Treat multi-engine writing as a compatibility contract covering the catalog, concurrency mechanism, table-format version, precision and delete-file support. Build the smallest shared lake table

Use a scratch Glue database named wh_lab in the same AWS Region as the workgroup. In the Athena editor select that database and the AWS data catalog. Create the database first with CREATE DATABASE wh_lab if authorised. Substitute a new empty prefix in an S3 bucket you control. The lab identity needs catalog create/update, S3 data and results access, encryption-key access where applicable, and any Lake Formation grants your setup requires. Run the next statements individually. Cloud queries and retained files can incur charges.

Expected report before the merge is two trades and £70. Afterwards it is two and £60. Rerunning the merge keeps the report at £60. Test an older revision arriving afterwards. Its version predicate fails and the published values survive. Inspect snapshot history, capture the pre-correction snapshot ID and read it with SELECT * FROM wh_lab.trade_current FOR VERSION AS OF <snapshot_id>, substituting the integer. Time travel reconstructs the table as recorded then. A separate effective date is still needed to answer “what was yesterday's position, restated using today's corrections?”

For a real microbatch, stage the raw deliveries durably, deduplicate exact replays, reject conflicting versions, then select one newest revision per key across the batch before the merge. Iceberg does not enforce a trade-ID uniqueness constraint. Serialise overlapping writes to the same business keys or reconcile after a conflicting commit before retry. The query's equality on trade ID can require a large target scan. Add a date predicate only when the source contract guarantees it cannot hide an existing row. A correction moving a trade between dates or books requires rebuilding both affected aggregates. Clean up the disposable table only after verifying ownership of its dedicated prefix. Follow the bytes through a distributed query

In self-operated Trino the coordinator parses SQL, resolves catalog metadata and creates a plan. Workers execute tasks for the stages. A split represents a portion of source work. A local aggregation can reduce many input rows to partial sums per book. An exchange sends partial groups to workers responsible for completing them. The client consumes the final rows. A thousand workers cannot remove the cost of returning ten million detailed rows through a BI client. Use an export or paginated drill-down when the deliverable really is detail. Trino execution terminology

Imagine 1 PB of compressed facts across 1,000 equally sized days. A one-day predicate can reduce candidate data to 1 TB. If the requested columns occupy 12% of those bytes, the simple model gives 120 GB before row-group skipping, metadata or deletes. At a hypothetical sustained aggregate read rate of 6 GB/s, those reads alone occupy about 20 s. This is a sizing illustration with decimal units. Network exchange, planning, skew, caching and overlap alter elapsed time. Storing a petabyte says almost nothing about a dashboard that reads one precomputed row.

Operator decision Why it helps How to distinguish the failure
Partition pruning Skip entire time slices using a predicate the connector recognises. Compare input and scan plan for a single aligned day and a wide range. A highly selective filter applied after a scan changes output rows without saving the input read.
Row-group skipping Sorted or clustered values tighten file statistics. Projection avoids reading unused columns. Compare sorted and shuffled layouts with the same predicate, columns and cache state. Compare physical bytes, not final row count.
Broadcast join Replicate a small filtered dimension to each worker to avoid repartitioning a large fact. Measure build-side bytes after filtering. A dimension that outgrows per-worker memory changes the preferred plan.
Partitioned join Hash both sides on the join key and send matching keys to the same partition. Inspect exchange bytes and the slowest task. One dominant key can leave most workers idle near completion.
Dynamic filtering Eligible joins can feed build-side values into the probe-side scan. Inspect the real plan and connector support. A filter that arrives after most splits have been read saves little.
Partial aggregate Group locally before the exchange. Compare partial rows out to rows in. Grouping by a near-unique trade ID offers little reduction.

Start with EXPLAIN on the date-filtered report. Then run EXPLAIN ANALYZE on a bounded slice in Trino to inspect actual rows, timings and task variability. It executes the statement. In Athena capture query statistics and bytes scanned from the result details. Compare with a wider date range using the same selected columns. Two tiny fixture rows establish business logic only. Use production-shaped partitions, file counts and key skew for plan conclusions.

Keep the lake fast after month six

A batch writing 100 tiny objects each minute creates 144,000 objects a day. At constant data volume, opening these files and planning splits can dominate reading them. Compact active partitions using table-aware maintenance. Test file sizes in the hundreds of MiB against real parallelism and update frequency. One vast file for a tiny daily slice can also limit available work. Choose a coarse time transform first, then measure whether a second dimension improves pruning enough to offset smaller files. A partition per trade creates a metadata problem.

Corrections can leave delete files and fragmented data. Monitor planning time, file counts and bytes per file, delete-to-data ratio, actual filtered rows, queue time and p95 execution separately. Rewriting files consumes capacity, while expiring snapshots reduces the recovery horizon. Retain snapshots for your longest reader and investigation window, and store durable raw history when audit retention exceeds snapshot retention. Separate maintenance windows or capacity from the opening dashboard burst.

Athena workgroups organise settings, limits and accounting. Check regional active-query quotas and queue age. Use scan limits and workgroup-level metrics, and evaluate capacity reservations where a predictable burst warrants allocated compute. In Trino, choose your deployment and worker size, keep catalog credentials and object access consistent across workers, govern admission via resource groups, monitor coordinator pressure and test worker loss during a large scan. Task retries require the relevant fault-tolerant configuration, exchange storage and connector support. Separate clusters give stronger failure isolation at additional idle cost. When federation earns its keep

A Trino catalog can expose Postgres reference data alongside an Iceberg fact. On a small lookup, predicate and projection pushdown can make a cross-source query convenient. On a broad join, the database may transfer millions of rows, consume its connection budget and read at a different instant from the lake snapshot. Look at both the Trino plan and the source database's observed query. If the join is recurring or audited, land a versioned dimension in the lake and join by business key and validity interval. Verify each fact matches exactly one dimension row. Two overlapping intervals would double exposure even with flawless trade deduplication.

Choose Athena as the first lake baseline when the sources live in S3 and bursts are irregular. Pilot a warm Trino cluster when connector control, admission policy or sustained load justify owning the cluster. If most questions are identical aggregates with a strict response deadline, move that work off the request path. The next guide designs that boundary.
