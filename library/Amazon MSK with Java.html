Kafka fundamentals

Apache Kafka stores streams of records in an append-only, partitioned log. Producers append records, and consumers read at their own pace. Multiple applications can read the same topic independently. Consuming a record leaves it in the log until its retention or compaction policy removes it.

Topic

A named stream such as orders.v1. A record has a key, value, timestamp and optional headers.

Partition

A topic shard with ordered offsets. Partitions determine ordering boundaries and how much work a conventional consumer group can do in parallel.

Broker and replica

A broker serves Kafka traffic. In the usual path, the partition leader serves requests. Follower replicas copy the log, and eligible followers can become leaders.

Kafka controllers manage cluster metadata such as partition leadership. Modern Kafka uses the KRaft controller quorum for this coordination. Your Java clients connect to broker listeners and discover partition leaders and coordinators through Kafka metadata.

Keys, offsets and groups

Use a stable business key when related events require ordering. For a producer using Kafka’s default key-aware partitioning with a fixed partition count, records keyed by the same order ID go to the same partition. Kafka orders appends within each partition. A consumer group normally assigns each partition to one member at a time, and different groups keep independent positions.

Partition 017 · order-1042 · placed18 · order-1042 · paid
Partition 191 · order-715 · placed92 · order-806 · shipped
Partition 28 · order-912 · placed

Offsets are positions within a partition. After handling partition 0 through offset 18, the consumer commits 19 as the next position. That commit belongs to the group. A group with four members and three subscribed partitions has at least one idle member. Group membership or subscription changes can trigger a rebalance.

Retention, compaction and replication

  • Delete retention. Kafka removes eligible log segments by age or size. Size-based retention applies per partition. Set the window to cover the longest expected outage, recovery or replay.
  • Log compaction. Kafka eventually keeps the latest value per key in the compacted part of the log. A keyed record with a null value is a tombstone. A compacted topic works for rebuilding current state. Use delete retention for a bounded event history and check product support before combining policies.
  • Durable acknowledgments. A replication factor of three, min.insync.replicas=2 and producer acks=all are a common three-AZ Standard baseline. The leader waits for all current in-sync replicas (ISR). If fewer than two are in sync, Kafka rejects the write until the ISR recovers.

Choose an MSK deployment model

Amazon MSK manages the Kafka broker infrastructure. Your team owns event contracts, partitioning, client behavior, access policies, capacity planning and application recovery.

OptionChoose it whenPlan for
Provisioned StandardYou need flexible broker settings, EBS capacity controls or supported tiered storage features.Size brokers, partitions, EBS storage and throughput. Watch free space and rebalance data when needed.
Provisioned ExpressYou want provisioned capacity with MSK-managed storage and fewer broker settings to tune.Size throughput, partitions and connections. AWS manages several durability settings, including topic replication factor.
ServerlessYou want automatic capacity management and the workload fits Serverless quotas and supported features.Use IAM authentication. Check partition, throughput, connection and topic-configuration limits. Use the Serverless pricing model for estimates.

Check regional availability, Kafka versions, quotas and pricing before choosing. For the lab, use Provisioned Standard in three availability zones or follow the Serverless variant below. The Java example uses basic Kafka APIs and the classic consumer group protocol, so its client dependency version can differ from the broker version. Validate any newer protocol features on your exact MSK engine version and broker type.

Create a private MSK cluster

Use a sandbox AWS account or environment where you have permissions to create MSK, IAM and VPC resources. Have an existing VPC with three private subnets in distinct availability zones for the Standard walkthrough, a client security group, and a host that can reach the broker network. Install JDK 17 or newer, Maven 3 and AWS CLI v2 on the client host. The shell examples use Bash unless labelled PowerShell.

AWS resources in the lab can incur charges while they exist. Use the cleanup steps when finished.

Provisioned Standard walkthrough

  1. In the Amazon MSK console, choose the Region, Create cluster, then the custom creation workflow. Name the cluster orders-lab and choose Provisioned and Standard.
  2. Choose a supported engine version. For this lab, 3.9.x is a suitable Standard example if available. Use three availability zones and one broker per zone. Select a compatible lab-sized broker and storage allocation within the account budget. Keep the default broker configuration for the walkthrough.
  3. Select the VPC, three private subnets and the broker security group. Set up the security-group rules in network and IAM.
  4. Enable IAM role-based authentication and TLS client-to-broker traffic. Keep public access disabled and select the appropriate at-rest KMS key option for your environment.
  5. For the lab use the default CloudWatch monitoring level. Create the cluster. Wait until its status becomes ACTIVE and copy the cluster ARN from the cluster details.

Serverless variant

Choose Serverless instead, use the offered VPC and private subnets with your broker security group, and use IAM for authentication and authorization. Wait until ACTIVE. Continue with the private IAM endpoint and the same Java lab. For configuration changes, check the Serverless topic configuration list.

Connect the client and grant IAM access

Make the broker endpoints reachable

Run the lab from an EC2 instance, ECS task or other workload in the same VPC for the simplest path. For EC2, use an instance profile and a management path such as Systems Manager Session Manager if your environment supports it. Give the broker security group inbound TCP 9098 from the client security group for standard private IAM connectivity. Allow client egress and ensure routing, DNS resolution and any restrictive network ACLs let TCP and its return traffic through. Kafka discovers brokers from cluster metadata, so the client must be able to reach the advertised broker endpoints after bootstrap.

For cross-VPC or cross-account access, use a supported private network path. With MSK managed multi-VPC private connectivity on supported Provisioned clusters, enable the correct authentication scheme, authorize the connection in the cluster policy, create the managed VPC connection and use the VPC connectivity bootstrap string and its returned ports. Cross-account access also requires the relevant principal permissions. Keep the endpoint returned for your network path intact.

Design for retries, duplicates and replay

GoalImplementationFailure behavior
At least onceFinish durable processing, then commit the next offset. Make the operation idempotent.Failure between the business write and the offset commit can replay records.
At most onceAdvance the committed offset before work where dropping a record is acceptable.A crash after the commit can lose work.
Kafka-to-Kafka exactly onceUse Kafka Streams exactly-once processing or a transactional producer that commits output and input offsets in one transaction. Downstream readers use read_committed.Aborted output is hidden from committed readers. External effects need their own consistency controls.
  • Idempotency at the sink. Insert a stable event ID under a unique constraint in the same database transaction as the business update. On replay, recognize the existing ID and commit the Kafka offset. Advance the offset only after the durable transaction succeeds. Where a database update must also publish an event, use a transactional outbox and retain the event ID when forwarding the outbox entry.
  • Producer retries. Idempotent producer retries suppress duplicate writes for retried sends within the producer protocol. Re-submitting an event at the application level, including after a timeout with an unknown outcome, can still produce a duplicate. Reuse the same event ID across application-level retries. In the lab, every invocation intentionally generates a new test event ID.
  • Poison records. Define a bounded retry policy. Retry transient errors with backoff. For terminal errors, fail the partition or route the record with controlled access to a dead-letter topic. Preserve the original topic, partition, offset, event ID and error context. Advance the input only once the dead-letter write succeeds. If strict order matters, account for later records before routing failures away.
  • Replay. Use a separate group and isolated sink for safe backfills. To rewind a production group, stop its members, preview the reset, agree on the target and execute during an approved window. auto.offset.reset=earliest applies only if a usable committed offset is absent. The retention window limits what can be replayed.

With Kafka transactions, give each live producer instance its own stable transactional.id and plan for fencing when a logical instance is replaced. A Java consume-transform-produce loop uses initTransactions(), beginTransaction(), sends output, passes the next offsets and consumer group metadata to sendOffsetsToTransaction(), then commits or aborts. On MSK, verify broker version and IAM transaction support first. AWS documents IAM support for WriteTxnMarkers on Kafka 3.8 and later.

Java client tuning

Client settingWhat to do
Producer reliabilityUse acks=all and enable.idempotence=true. Keep retries enabled and max.in.flight.requests.per.connection at five or below. Bound total send time with delivery.timeout.ms, at least request.timeout.ms + linger.ms. Handle terminal errors and timeouts in the application.
Producer batchingKeep one producer per process or configuration and share it across threads. Use asynchronous send with callbacks for throughput, control outstanding work and benchmark batch.size, linger.ms and compression. The synchronous send in the lab makes acknowledgment visible.
Consumer progressChoose a stable group.id for each independent application. Disable auto-commit when coordinating offsets with work. The Kafka consumer is generally thread-confined. Commit only the highest contiguous completed position per partition when parallelizing work.
Poll and fetchSize max.poll.records so even a slow batch fits within max.poll.interval.ms, including commit time. For heavier work, keep polling and use partition-aware queues and pause/resume with rebalance handling. Tune fetch.min.bytes and fetch.max.wait.ms when balancing latency and throughput.
Offset resets and isolationUse earliest for a new group that should read retained history, latest to start from new arrivals, or none to surface missing offsets. Use read_committed where aborted transactions must be hidden. Open transactions can delay visible progress.

Operate MSK in production

Schema and event contracts

Use a serializer and a schema registry where consumers need a reliable contract. AWS Glue Schema Registry offers Java integration for Kafka. Choose a compatibility policy and test schema changes with old and new consumers. Make event identity, key, event type, event time and business meaning explicit. Document who owns the topic and its retention policy. Keep sensitive content out of keys and logs, and give dead-letter topics appropriately restricted access and retention.

Capacity and monitoring

Size for peak ingress, consumer fan-out, partition skew, replanning after an AZ or broker failure and replay traffic. On Standard, a rough retained-storage estimate for delete-only topics is compressed ingress bytes per second × retained seconds × replication factor. For 5 MiB/s and three days at RF 3, that is about 3.7 TiB cluster-wide before overhead, headroom and uneven distribution. Benchmark with representative record sizes, keys, compression and network paths. Review broker, partition and connection quotas before adding consumers or increasing deployment churn.

SignalWhat to check
Consumer progressCloudWatch MaxOffsetLag, SumOffsetLag and EstimatedMaxTimeLag where available, plus application event age, records processed per second and downstream errors. Offset lag measures distance in offsets. An absent metric may indicate an unstable group, a missing committed offset or other emission constraints. Pair it with health and progress checks.
Broker healthOffline and under-replicated partitions, ISR changes, request latency, throttling, broker CPU and connection rates where exposed. On Standard, watch storage usage and forecast exhaustion. Match alarms to the cluster type’s metric list.
Java applicationsAcknowledgment latency, send errors and timeouts, retries, poll-to-poll delay, rebalance count, commit failures, sink latency, duplicate rate and dead-letter volume. Set helpful client IDs and correlate alerts by topic and group.

Change, scale and recover

  • Use infrastructure as code for clusters and policies and a versioned workflow for topics and schemas. Review supported versions and end-of-support dates. Exercise broker rolling updates, producer or consumer restarts, IAM credential refresh and a replay before relying on those paths.
  • When lag grows, look at lag per partition before scaling. Correct key skew or downstream bottlenecks and add group members only up to usable partition parallelism. Confirm the effect of partition-count changes on key routing. For Standard broker expansion, plan how partitions move to the added brokers and validate balance after the operation.
  • Replication within one Region gives availability across broker failures and availability zones. For a regional recovery objective, evaluate MSK Replicator and measure replication lag, offset synchronization and duplicate tolerance. Write down RPO, RTO, endpoint changes and failback. Rehearse with a staging workload.
  • Use MSK Connect for supported connector workloads and Kafka Streams for keyed joins, aggregates or stateful transformations when those suit the application. Each workload still needs its own identity, network path and operational checks.

Troubleshoot in connection order

SymptomFirst checks
No IAM bootstrap stringConfirm Region, cluster ARN, ACTIVE state, operator permission and IAM listener. Use BootstrapBrokerStringSaslIam for the walkthrough. Use the returned endpoint field appropriate to a managed multi-VPC or other connection path.
DNS or connection timeoutTest from the application host. On Linux, try getent hosts BROKER and nc -vz BROKER PORT if installed. On Windows use Test-NetConnection -ComputerName BROKER -Port PORT. Check advertised brokers, routes, security groups and network ACLs. A successful TCP connection proves socket reachability only.
TLS handshake failureCheck that the port matches the configured listener, that the JVM trusts the broker CA chain and that the hostname matches the certificate. Keep host verification enabled. Check for a traffic-inspection proxy changing certificates.
SASL authentication failureConfirm SASL_SSL, AWS_MSK_IAM, the IAM login module and callback class, an available credential source, the intended principal and correct host clock. Verify the endpoint belongs to the expected Region and that the principal can connect.
Topic, group or cluster authorization failureMatch the denied operation to its IAM action and ARN type. Check the cluster UUID, topic and group names, policy boundaries or explicit denies, and the cluster-scoped idempotent-write grant. If using assume-role credentials, check which role the process actually obtained.
No messages or unexpected replayCheck topic and partition, producer acknowledgment, exact group ID and committed offsets. Check auto.offset.reset, retention, open transactions, commit outcomes and rebalance frequency.
Write timeouts or growing lagCorrelate ISR and leader health, broker throttle and throughput, and client retries. Check hot keys, sink latency, consumer poll timing and recent deploys. Restore capacity or reduce load while preserving processing and ordering guarantees.

Clean up the lab

  1. Stop the consumer and any remaining test producers. Save the data first if you need it. Deleting a topic or cluster removes its retained data.
  2. If you created a disposable MSK cluster, delete that cluster in the MSK console and monitor the status until it disappears. On a shared cluster, delete only lab-owned resources you are authorized to remove.
  3. Remove any lab-only client instance, EBS volumes, IAM role or policy, monitoring alarms, log groups, endpoints and security groups that you created. Check for retained resources in the same Region. A local Docker broker started with --rm is removed when stopped.
