Stage 1 of 5

Model the stream

Follow one order through a partition and two independent readers.

The log underneath the order screen

A producer writes an immutable record to a topic, a named stream such as oms.fills.v1. A topic is split into partitions. Each partition has an ordered sequence of records, and the broker assigns each record an offset within that partition. A record carries a key, a value, a timestamp and optional headers. The broker stores bytes. Serializers translate application values into those bytes, and consumers must agree on how to interpret them.

Use the order ID as the key. With Kafka’s ordinary keyed partitioning, identical serialized keys map to the same partition while the partition count and partitioning scheme stay fixed. This gives one append order for the fills of an order. Two producers can still race. An exchange timestamp or venue sequence can reveal that the first record received was the second fill executed. Capture those fields if the application must reconstruct venue order. Offset 17 in one partition has no temporal relationship to offset 17 in another.

A consumer group is a named subscription with a durable checkpoint per topic-partition. In the classic group model used here, Kafka assigns each partition to at most one active member of that group at a time. Six partitions allow six members to do useful partition-level work. A seventh can wait for an assignment. A second group gets independent assignments and checkpoints over the same data. Acknowledging a RabbitMQ work item is a helpful analogy up to one specific point. Here, committing progress leaves the original record available to other groups and future replays.

State Who owns it What it tells you
Partition log Broker leader and replicas Which events remain available
Current position Running consumer Where the next fetch continues after records returned by poll
Committed offset Kafka group coordinator, persisted in an internal topic Where a replacement group member resumes
Fill ledger Application database Which business events have actually affected the projection

The boundary between the last two rows explains most replay bugs. Kafka has no visibility into a JDBC transaction. A zero-lag dashboard cannot prove that your order screen contains the right answer. Reconcile an independent business measure such as fill count and quantity against the source of executions. Kafka design and delivery semantics

Design the event before the topic

Our event means “the source recorded a fill”. It carries a stable source-generated event ID, a positive integer number of shares, and an order ID. For the lab, UTF-8 key ORD-7 and UTF-8 value F-101|40 are sufficient. The next fill is F-102|60. IDs cannot contain the vertical bar. There is one venue, one order namespace and one unit of measure. The producer must reuse the same ID on resubmission. Generating a fresh UUID on each retry would defeat every duplicate check downstream.

A real multi-venue contract also needs source namespace, instrument, execution timestamp, price, currency and quantity scale. Corrections and busts deserve their own event IDs and references to the original fill. Overwriting F-101 from 40 to 35 loses the distinction between a genuine correction and a producer reusing an ID. The lab treats that conflict as an error. Decide explicitly who can issue corrections and how consumers handle a correction that arrives before its original.

JSON makes an incident easy to inspect. Avro or Protobuf with a schema registry gives you schema IDs and compatibility checks across deployments. For a rolling upgrade that deploys readers first, test the new reader against retained old events. For deployments where old readers also see new messages, test the reverse direction. A schema can preserve the integer type while changing “shares” to “lots”. Encode units and include semantic fixtures in CI. Retained events lengthen the period for which old meanings matter.

Choose a delete-retained topic for fills. A compacted topic keyed by order can represent the latest order snapshot. Compaction eventually removes superseded values for a key. Rebuilding a fill ledger from that stream could leave you with only F-102. A null value on a compacted topic is a tombstone, used to signal deletion. Compaction is asynchronous and a reader can see multiple versions. A snapshot reader must still apply them in order. On Serverless, choose the cleanup policy at topic creation. Read the acknowledgements

Illustrative output on a fresh partition is ack pN @0, then ack pN @1, where N is the actual partition number. At this point the broker has both fills and the ledger has applied neither. The group appears when you start its consumer.

Expect two acknowledgements for the same partition and successive offsets on a fresh topic with no other writes. The producer waits for each acknowledgement so the second send follows the first. Reuse a long-lived producer in a service. Sending asynchronously and handling each completion lets the client batch records and overlap network round trips. A fire-and-forget HTTP endpoint that returns success before a failed send completes can quietly lose fills.

The project has three runtime components. The Apache client implements the Kafka protocol, the AWS IAM library authenticates the same clients on MSK, and SQLite persists the effect independently of the consumer process. The local properties file contains just the bootstrap address and PLAINTEXT protocol. Keep that listener bound to the loopback interface. Read the complete Java client

Trace one call through send, then follow the matching record through poll, apply and commitSync. JDBC defaults to auto-commit here. The INSERT is the entire durable business effect, and the primary key is its duplicate guard. The displayed quantity is a sum over these immutable rows. A design that also updates a separate order totals table must put both writes in one database transaction.

Fills.java
import java.nio.file.*;
import java.sql.*;
import java.time.Duration;
import java.util.*;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.serialization.*;

public class Fills {
    static final String TOPIC = "oms.fills.v1";
    static final String INSERT = """
        INSERT INTO fills(event_id, order_id, qty) VALUES (?, ?, ?)
        ON CONFLICT(event_id) DO NOTHING
        """;

    public static void main(String[] args) throws Exception {
        Properties p = new Properties();
        try (var in = Files.newInputStream(Path.of(args[1]))) {
            p.load(in);
        }
        if (System.getenv("BS") != null)
            p.put("bootstrap.servers", System.getenv("BS"));

        switch (args[0]) {
            case "send" -> send(p, args[2], args[3], args[4]);
            case "consume" -> consume(p, args[2], args[3]);
            default -> throw new IllegalArgumentException("send or consume");
        }
    }

    static void send(Properties p, String order, String id, String qty)
            throws Exception {
        p.put("acks", "all");
        p.put("enable.idempotence", "true");
        try (var producer = new KafkaProducer<>(p,
                new StringSerializer(), new StringSerializer())) {
            var record = new ProducerRecord<>(TOPIC, order, id + "|" + qty);
            var ack = producer.send(record).get();
            System.out.printf("ack p%d @%d%n", ack.partition(), ack.offset());
        }
    }

    static void consume(Properties p, String group, String file)
            throws Exception {
        p.put("group.id", group);
        p.put("enable.auto.commit", "false");
        p.put("auto.offset.reset", "earliest");
        p.put("max.poll.records", "20");
        try (var db = DriverManager.getConnection("jdbc:sqlite:" + file);
             var consumer = new KafkaConsumer<>(p,
                 new StringDeserializer(), new StringDeserializer())) {
            try (var ddl = db.createStatement()) {
                ddl.executeUpdate("""
                    CREATE TABLE IF NOT EXISTS fills(
                      event_id TEXT PRIMARY KEY NOT NULL,
                      order_id TEXT NOT NULL, qty INTEGER NOT NULL)
                    """);
            }
            consumer.subscribe(List.of(TOPIC));
            while (true) {
                var batch = consumer.poll(Duration.ofSeconds(1));
                if (batch.isEmpty()) continue;
                for (var record : batch) {
                    System.out.printf("read p%d @%d%n",
                        record.partition(), record.offset());
                    apply(db, record);
                    if ("1".equals(System.getenv("STOP_AFTER_WRITE")))
                        throw new IllegalStateException("lab crash point");
                }
                consumer.commitSync();
            }
        }
    }

    static void apply(Connection db, ConsumerRecord<String,String> record)
            throws SQLException {
        var fields = Objects.requireNonNull(record.value()).split("\\|", -1);
        String order = Objects.requireNonNull(record.key());
        if (fields.length != 2 || fields[0].isBlank() || order.isBlank())
            throw new IllegalArgumentException("invalid fill");
        int qty = Integer.parseInt(fields[1]);
        if (qty <= 0) throw new IllegalArgumentException("invalid quantity");
        try (var insert = db.prepareStatement(INSERT)) {
            insert.setString(1, fields[0]);
            insert.setString(2, order);
            insert.setInt(3, qty);
            if (insert.executeUpdate() == 1) {
                System.out.println("applied " + fields[0]);
                return;
            }
        }
        try (var check = db.prepareStatement("""
                SELECT order_id, qty FROM fills WHERE event_id = ?
                """)) {
            check.setString(1, fields[0]);
            try (var row = check.executeQuery()) {
                if (!row.next() || !order.equals(row.getString(1))
                        || qty != row.getInt(2))
                    throw new IllegalStateException("conflicting event ID");
            }
        }
        System.out.println("duplicate " + fields[0]);
    }
}

A conflicting payload terminates the consumer before it can commit the poll. An identical ID, order and quantity produces a duplicate diagnostic and allows processing to continue. In a multi-instance service use a shared durable database, for example PostgreSQL on RDS. A SQLite file on each ECS task would split the ledger on a rebalance and lose the duplicate guard on task replacement. The SQL pattern transfers directly, but the connection lifecycle, concurrency and deployment need to change.

SQLite
-- sqlite3 fills.db
SELECT order_id, COUNT(*) AS fills, SUM(qty) AS filled_qty
FROM fills GROUP BY order_id;
-- Expected: ORD-7 | 2 | 100
Moment on the selected partition Durable rows Next group offset
Both sends acknowledged on a fresh topic None Unset
Poll returns offset 0, SQLite inserts F-101, process exits F-101 Unset
Restart starts at earliest, reads 0 again F-101, unchanged Unset until poll completes
Offset 1 processed and its poll committed F-101 and F-102 2

The table assumes both records are available in the restarted poll for its third row. Smaller polls can add an intermediate commit of 1. In both cases the committed value after processing offset 1 is 2. It names the next position to consume. There may be gaps in offsets in other workloads. Group position is a coordinate, not a count of business events.

If you reverse the order and commit the poll before writing SQLite, a crash can leave a missing fill that normal restart skips. With database-first processing, a crash can repeat work, but a stable event ID and unique constraint absorb the repeat. Two fresh producer sends with F-101 also yield two genuine Kafka records at different offsets. Producer idempotence protects a producer’s protocol-level retries. Only the business ID connects those two independent sends.

What survives the crash?

Assume both records arrived in one poll. Expand each observation in sequence.

1 · Immediately after poll()

The consumer can return both records and advance its in-memory position to 2. Its loop has yet to call SQLite. There is no committed offset for this fresh group.

2 · After the first insert and forced exit

SQLite holds F-101 and the displayed quantity is 40. The in-memory position disappears. On restart there is still no checkpoint, so the configured earliest policy selects the first retained record.

3 · After replay and commitSync()

The second insert attempt for F-101 hits its primary key. The consumer compares the stored payload, accepts the exact duplicate and applies F-102. SQLite now holds 100 shares across two rows. Kafka records 2 as the next offset. A third start with this group waits for new data.

Operate and rebuild

Set the processing budget, measure lag and rebuild beside the live group.

Tune the client for the failure you can tolerate

Kafka batches per partition. Increasing linger.ms gives a partially filled batch more time to accumulate records. More batching can improve compression and throughput at the price of waiting under light load. In Kafka 4.0 the producer default linger is 5 ms. Compare producer queue time, broker request latency and end-to-end latency separately. Compression such as LZ4 or Zstandard trades CPU for lower network and storage use. Large individual messages still need compatible producer, topic and fetch limits. For a PDF or a large source file, publish an immutable object reference, checksum and schema version instead.

Setting or choice Effect Decision for this service
acks=0, 1 or all No broker acknowledgement, leader acknowledgement, or acknowledgement from the in-sync replicas Use all and check the future. A timeout can leave the outcome ambiguous.
enable.idempotence Producer sequences suppress duplicates from retried batches Explicit true. Requires all acknowledgements, retries enabled and at most five in-flight requests per connection.
enable.auto.commit Java default true allows the client to advance checkpoints as polling progresses False. Commit only after all records returned by the poll are durably handled.
auto.offset.reset Applies when there is no valid checkpoint. Java default latest begins at the end. Earliest for lab and rebuilds. Consider none for a critical production group so missing history raises an incident.
max.poll.records / max.poll.interval.ms Bound records delivered per poll and time available between polls for group membership Begin with small batches. Include downstream tail latency and retry time in the processing budget.

Suppose 20 records each take 400 ms sequentially in the database. That batch occupies the consumer for about eight seconds before Kafka commit overhead. At five seconds per database call under stress it takes 100 seconds. A retry on every row can double that. If a consumer exceeds the poll interval, another member may take its partitions and the first one’s commit may fail. Its database writes survive. The duplicate guard now also protects against overlapping attempts. Keep the consumer on one thread. If delegating work, pause or bound intake, track the completed prefix for each partition, and commit only that prefix. Committing offset 13 while offset 11 is still running can skip 11 after a crash. Replay without disturbing live orders

For a repaired projection, use a fresh group and an empty destination. Run java -cp "$CP" Fills consume "$CFG" ledger-rebuild-v2 rebuild.db in a second shell with the same environment. Both groups read the topic independently. The original application can continue serving queries. If you reuse its database, the event-ID constraint will absorb the very inserts you wanted the new calculation to perform. For a live cutover, identify a vector of end offsets, one per partition. Wait for the rebuild to reach those offsets, reconcile counts and quantities at a comparable boundary, then switch reads while the new group continues tailing.

A rebuild has one target per partition

Suppose you capture end offsets P0=120 and P1=80. A rebuild checkpoint of (120,75) still leaves positions 75 through 79 on P1 to cover. A checkpoint of (125,75) gives the same total as the target and is still behind on P1. Compare each component. If you need an exact point-in-time reconciliation, bound both projections to the same cut or compare their ledgers filtered by source partition and offset. The sample SQLite schema would need those extra columns.

To rewind the same group, record the current offsets first, stop all group members and disable their automatic restart. Use the following on the AWS client with the earlier Bash variables. For local use, run the same Kafka tools inside the broker container with --bootstrap-server localhost:9092 and omit the MSK command-config. The reset changes Kafka checkpoints. The downstream database and any external notifications keep their existing state.

Run it as a service

Use an ECS service on Fargate for a long-running Java consumer if the team wants explicit control of polling, database batches and shutdown. Use its task role for broker access. The ECS execution role handles platform tasks such as image pulls. Put replicas in private subnets that can reach all brokers and the same durable ledger. Give a terminating task time to stop intake, finish or abandon the current batch, commit completed work and close the client. The example exits safely through redelivery, but has no orchestrator-specific draining hook. A service restart must tolerate a repeated batch.

Spring for Apache Kafka is an alternative when the team already operates Spring Boot. A listener container owns polling, partition assignment and commits. Configure its acknowledgement and error handling modes around the same database boundary. With a record listener, an exception must reach the container if processing failed. Catching it, logging and returning normally can turn a poison fill into a silently skipped one. AWS Lambda’s MSK event source mapping is another option for short batch handlers. The mapping owns polling and checkpoints. Account for batch retry, execution time limits and database connection pressure. EKS gives fine control if a Kubernetes platform already exists. The choice of deployment changes operational responsibility, while the event-ID constraint remains necessary.

For an existing OMS database, the publishing side has its own crash window. If the OMS commits the fill and then the process dies before publishing, Kafka never receives it. Insert an outbox row with the fill in the same database transaction, giving it the durable event ID. A relay or change-data-capture connector such as Debezium publishes the committed row. If the relay crashes after Kafka acknowledges but before it records progress, it republishes the same event ID. Test both sides of that failure. MSK Connect can host compatible Kafka Connect source or sink plugins. Examine each connector’s own checkpoint and delivery guarantees, alongside what the destination does on retries. Estimate time to recover

In an append-only partition, suppose 24,000 fills are waiting, 200 arrive each second and the consumer durably applies 320 per second. The backlog shrinks by 120 per second, so recovery takes about 200 seconds. Dividing by 320 gives 75 seconds and ignores arrivals. At 180 applied per second the backlog grows by 20 per second. A spare consumer in the same group cannot take half of this partition. Measure sink latency and key skew before scaling the service.

Alert on oldest unprocessed event age against the business freshness target, sustained per-partition lag, failed sends, commit failures and DB latency. Label logs with group, topic, partition, offset and event ID. Avoid putting event IDs in metric dimensions where every fill would create a new time series. On provisioned brokers also track offline or under-replicated partitions, storage headroom where applicable and broker saturation. The metric set depends on cluster type and monitoring level. For app-level latency, measure event time to durably applied time and check clock synchronisation. MSK lag metrics and emission conditions

A broken record needs a policy. For an authoritative order projection, stop and alert on an unparseable fill or conflicting ID. Skipping one fill could make a completed order appear tradable. For an analytics feed that can tolerate a gap, quarantine the original bytes with topic, partition, offset, error and schema ID. Make quarantine durable before advancing the source checkpoint, deduplicate quarantine entries by source coordinate and expose a redrive process. Moving failures to a retry topic allows later records to overtake them. That is acceptable only when the downstream business rule permits it.

A broker replica protects against some infrastructure failures. It also replicates accidental application writes. Keep deletion permissions separate, version topic definitions, rehearse restoring the archive, and test a consumer deployment through a rebalance. Before increasing partitions, remember that a hash modulo a new partition count can place future events for an existing order on a different partition. When per-order sequence is strict, drain and cut over to a versioned topic with a defined boundary or introduce an explicit sequence and reconciliation design.

Move the commit boundary

Compare a database projection with a Kafka-to-Kafka transaction.

Change the destination, change the guarantee

Suppose the risk team wants a derived Kafka topic of accepted fills. The source and destination are now both in Kafka. With the ledger approach a worker can publish a derived fill, die before committing its source offset and publish it again on restart. A unique row in SQLite cannot protect another team’s Kafka consumer. This is where a Kafka transaction changes the outcome.

Assign a stable, distinct transactional ID to each logical producer instance, initialise its transactions and disable consumer auto-commit. Begin a transaction, publish derived records, then call sendOffsetsToTransaction with the next offsets for each completed partition and the consumer’s group metadata. Commit the transaction. Configure downstream readers with isolation.level=read_committed. If the transaction aborts, discard or rewind the consumer’s in-memory position to the committed offsets before retrying. A fenced producer must close. Kafka Streams can coordinate these steps with processing.guarantee=exactly_once_v2. Check broker support, permissions and internal topic configuration for the chosen MSK type.

Choose the identity that survives a retry

A source coordinate such as (topic, partition, offset) identifies one physical record. F-101 identifies the business fill across independent submissions. A group offset records progress for one reader. Use the coordinate to find the incident, the business ID to protect the ledger and the group checkpoint to resume.

Trace offset 17 producing derived event D17. Before commit, a read-committed downstream reader cannot consume D17 and the source group’s durable position still points to 17. A successful commit makes the output eligible for that reader and moves the checkpoint to 18 atomically. If the process dies and its transaction aborts, a replacement starts at 17 and can emit D17 again. Only the committed attempt is visible to read-committed readers. An HTTP request or JDBC update issued within this code path still requires its own duplicate and recovery design. Kafka transactions and Streams semantics

Kafka Streams also provides keyed aggregations, joins, windows and recoverable local state stores. For example, grouping fill deltas by order builds a running quantity, while a windowed aggregate can compute executed volume by instrument over five minutes. A change of key can require a repartition topic. A state-store changelog allows a new worker to restore its state after assignment moves. Set event-time and lateness policies explicitly for delayed executions. Two separately published copies of F-101 are two distinct source records even under exactly-once processing. A business-level deduplication stage still matters.

Choose the commit boundary from the destination. For this order screen, SQLite owns the durable fill and the primary key makes replay safe. For a Kafka-to-Kafka derivative, the broker can commit output and input offsets together. For a broker API, email or payment instruction, start with the recipient’s idempotency and reconciliation contract before promising a delivery guarantee.
