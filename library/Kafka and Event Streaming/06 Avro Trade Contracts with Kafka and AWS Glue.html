One batch, three contracts

A booking service submits batch B-17 containing a gilt purchase and an FX trade. A risk service needs to recover both as Java objects and replay the same Kafka partition after an upgrade. What information must survive for that to work? Start with three independently owned contracts.

The Java producer uses a serializer to turn the batch into a Kafka value. The AWS serializer adds a small prefix inside that value containing a header version, compression indicator and 16-byte schema-version ID. Kafka can retain and replicate those bytes without contacting Glue. On a cache miss the consumer looks up that ID, recovers the exact writer schema and decodes the payload. The outer named record gives the batch an identity and somewhere to put future metadata. The location of the union is crucial. With an array whose items are a union, each trade picks its own branch. A union outside the array would select one shape for the whole field. Avro also disallows two anonymous array branches in one union.

Each nested definition introduces a named type in example.wire. Its full name identifies the record during resolution. On the wire, the selected branch is encoded using its zero-based index in the writer’s union, followed by the branch data. For this schema the bond selects index 0 and FX selects index 1. Their Avro long encodings are the bytes 00 and 02 respectively. Field names and Java class names take up no space in the datum. A decoder needs the writer schema even when it already has the correct Java classes. Avro binary encoding and unions

These deliberately small records illustrate dispatch. The bond amount means whole GBP pounds of face value. The FX fields show direction only. A booking contract would also need amounts, settlement dates and agreed rounding conventions. For fractional monetary amounts, define explicit scaled integers or use Avro decimal with a documented precision and scale. An unchanged field type cannot protect consumers from a change in economic meaning.

Publish v1 and promote v2

The .avsc in Git is the reviewed source. Glue holds the runtime lookup copy. The generated JAR is a build artefact. Keep their identifiers distinct: a Git tag identifies source, a Maven version selects a Java dependency, a Glue version number orders definitions within one named schema, and a Glue version UUID identifies the definition referenced by a message. Record their mapping in the release output. Register the same definition separately in each AWS environment and use the UUID issued there.

Run the initial creation in a new registry, or reuse the existing trading registry. Use an AWS identity authorised to manage these resources. To publish a subsequent definition keep the same schema name and record full names. For v2 add an optional execution desk to the outer batch. A null branch and a default solve different problems

The union allows a writer to put null in the field. The default supplies null when a reader asks for executionDesk in a v1 record where the field is absent. A writer using v2 still encodes a union branch for executionDesk. If historical absence means “unknown”, a default such as “London” would invent business data.

A release pipeline can own CreateSchema and RegisterSchemaVersion while producer roles only look up the approved definition (GetSchemaByDefinition) and consumers fetch definitions by UUID (GetSchemaVersion). The sample disables automatic registration and pins a logical schema name. Auto-registration is convenient for a sandbox with write permissions. Read the compatibility matrix in both directions

For a proposed release, put the writer on one axis and the reader on the other. Backward compatibility asks whether the new reader handles old data. Forward compatibility asks whether the old reader handles new data. Full requires both. Avro matches record fields by name, ignores writer fields absent from the reader, and requires a reader default for reader fields missing from the writer. Glue applies its configured admission rule when a version is registered. BACKWARD, FORWARD and FULL express direction; their _ALL variants extend checks across the applicable version history. Inspect the Glue checkpoint as well as the mode: it starts at the first version and can change through UpdateSchema or a console edit. NONE admits changes without compatibility checks. DISABLED freezes the schema against new versions. Keep old definitions available as long as Kafka retention, archives or disaster recovery may require replay. A green registry check can precede a broken reader

Under BACKWARD_ALL, adding SwapTrade can pass because a new reader can read old bonds and FX. Deploy that reader to every affected consumer group, including replay jobs, before enabling swap production. FULL_ALL is appropriate when independent old consumers must accept every new payload; a new branch then requires a coordinated migration or a separately versioned contract.

Choose the Kafka record boundary

QuestionBatch as one Kafka valueOne Kafka value per trade
What is ordered?The array preserves the submitted sequence. Broker ordering also applies across records in a partition.A stable tradeId key can keep revisions for that trade in the same partition under a stable partitioning scheme.
What can be retried?The whole offset. Application writes for each trade still need an atomic database transaction or idempotency.Each trade has its own offset. A batchId field can correlate trades across offsets.
What if FX and bonds have different users?Every subscriber reads the batch to discover its branches. Filtering after decoding still pays that cost.A shared topic with a union suits common subscribers. Separate topics allow independent retention, permissions and rollout.
What if a batch grows?Bound encoded size and count. Producer, broker and consumer limits matter; reject or split oversized submissions.Kafka can still batch records internally for throughput. Producer batching preserves individual record boundaries.

For B-17, choose the array when the submitted batch itself is the business event and a consumer should validate it as a unit. Choose individual records for independent trade lifecycles. If downstream must observe completion of a split batch, define a completion event and an expected count or manifest of trade IDs. A shared batchId alone gives a reader no way to know the final trade has arrived.
