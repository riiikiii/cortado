Read one trade twice

At 09:00 a trade is booked for £100. At 09:01 its value is corrected to £120. The live blotter needs £120, the audit reader needs both events, and a new risk calculation needs to replay yesterday without submitting a second order. All three can use the same Kafka cluster. They need different keys, history policies, checkpoints and side-effect boundaries.

This field guide targets Apache Kafka 4.4.0, its Java client and a KRaft cluster. The lab assumes a shell, Docker and familiarity with Java. The design examples assume three brokers spread across failure domains. Use the one-broker lab to observe records and offsets. Replication and failover require the three-broker topology. For managed Kafka, inspect the deployed broker version, feature levels and service limits before adopting a setting.

Apache Kafka quick start · Record delivery and replication design

Where a configuration takes effect

A producer starts with bootstrap addresses, discovers partition leaders and sends batches to them. Brokers store and replicate partition logs. KRaft controllers maintain cluster metadata and coordinate leadership. Consumers discover brokers and fetch from explicit positions. A group coordinator manages group membership and offsets. Changing a producer property cannot retroactively change stored records, and changing a consumer property cannot extend topic retention.

Design the log and the key

A record has a key and value expressed as bytes, optional headers and a timestamp. Serializers translate Java types into bytes. Use a key whose serialized form remains stable over the contract lifetime. A change from UTF-8 trade IDs to schema-wrapped key bytes can move the same logical trade to another partition. Null values have deletion semantics on a compacted topic. An empty byte array encodes a real value.

A producer can choose a partition explicitly, use a custom partitioner, or let the default partitioner route serialized keys. Unkeyed traffic can be batched on a partition before the producer switches. Per-partition order is append order. Two services racing to amend T17 can arrive in the opposite order from their business versions. Carry an event ID, business version, effective time and ingestion time when these distinctions matter.

Candidate key Good operation Cost paid elsewhere
Trade ID Enforce an ordered state machine per trade Portfolio totals require grouping many trades again.
Portfolio ID Process one portfolio serially A large book becomes a hot partition.
Unique event ID Spread append-only events Corrections to a trade may land on different workers.
Explicit shard or salted key Spread an exceptionally hot entity Reassembly needs an ordering or merge rule and additional state.

Increasing partitions can change the mapping of existing keys. Old records stay in their original partition. If continuous per-key order is an invariant, migrate to a versioned topic at a known cutover or use an explicit, stable routing scheme. Consumer instances above the number of assigned partitions provide no additional partition owners in a conventional consumer group.

Sizing example. Suppose measurements show one partition worker can project 4,000 events/s at acceptable latency and peak arrival is 14,000/s. Four evenly loaded partitions cover the arithmetic minimum. At a target 70% utilisation, the estimate becomes ceil(14,000 / 2,800) = five. If one key alone generates 5,000/s, adding partitions leaves that key above the single-worker limit. Measure key skew, recovery time and the effect of losing a broker before fixing a partition count.

Use separate topics for immutable trade events, latest trade state and execution commands. Set schemas and compatibility rules for values and keys. JSON is easy to inspect, Avro and Protobuf can use registry-backed schema IDs, and Kafka itself stores bytes. Keep old writer schemas available as long as history can be replayed. Test old bytes with the new application, including tombstones and unknown fields. Headers are useful for tracing and schema metadata. Broker fetches do not filter by arbitrary header or business key.

What a successful send guarantees

Follow one partition with leader A and followers B and C. The replication factor is three. Its in-sync replica set (ISR) changes as followers fall behind and catch up. Set the topic minimum ISR to two and keep unclean election disabled. A producer future completing successfully answers a specific question determined by its acknowledgement policy.

Producer setting When the producer can report success Failure that remains possible
acks=0 The client hands off the request without waiting for a broker response. No confirmed offset. Network loss or broker rejection can go undetected. A send can still fail locally during serialization or buffering.
acks=1 The leader has appended the batch. Leader loss before a follower copies it can lose an acknowledged write. Acknowledgement can precede consumer visibility.
acks=all or -1 Kafka fulfils the replication condition for the current ISR, subject to the minimum ISR. A lost response leaves the client uncertain. Correlated loss of all safe copies, retention and operator deletion remain separate risks.
Stable ISR at write Minimum ISR Result with all acknowledgements
A, B, C 2 All three participate. Two is an admission floor, not a request for the fastest two.
A, B 2 The two replicas can complete the write. C must catch up before returning to the ISR.
A 2 The write cannot be acknowledged successfully. An ISR change during an in-flight append can produce an after-append error.
A 1 A can acknowledge alone. The same producer config now provides weaker fault tolerance.

These rows assume stable membership during each example. Followers fetch data; the leader infers their progress. The high watermark is the exclusive replication visibility boundary. On 4.4 with strict minimum ISR, it cannot advance for a data partition while ISR size is below the minimum. A leader-only acknowledgement may therefore precede both replication and visibility. With eligible leader replicas enabled, the controller can remember an out-of-ISR replica known to contain committed data and elect it safely under defined conditions. An unclean election can select a stale replica and lose acknowledged history. Inspect feature levels when comparing upgraded clusters.

An acknowledgement does not imply an fsync of each replica for each record. Kafka uses the operating system's page cache and replication across machines. For power or zone failures, place replicas across independent failure domains using rack awareness, allow sufficient remaining capacity and verify placement. Controller quorum members protect metadata availability. Adding more controllers does not add copies of the trade log.

Use a replicated topic with this producer. With three brokers, create it with --replication-factor 3 --config min.insync.replicas=2. The one-broker lab deliberately cannot demonstrate that policy. Configure the replication and minimum ISR of internal transaction topics, and the offsets topic replication factor, when provisioning a cluster. A healthy data topic alone cannot make dependent coordinators available.

Retries, ordering and transactions

An application sends evt-002. The leader stores it and the acknowledgement disappears. The producer retries. With idempotence enabled, producer IDs, epochs and per-partition sequence numbers let Kafka recognise an internal retry and avoid a duplicate append. Explicitly enabling idempotence makes conflicting settings fail configuration validation. It requires all acknowledgements, retries enabled and at most five requests in flight per connection. Without idempotence, multiple in-flight requests and retries can reverse batch order if a later batch succeeds first.

Application-level resubmission is a different operation. A user clicks twice, a restarted process reads its outbox again, or a timeout handler constructs another record with the same payload. Kafka may validly append both. Give the business event a stable ID and make its effect idempotent. A producer callback or future is where the caller learns the asynchronous delivery result. Calling Java's send().get() on every record serialises the application and defeats much of the batching opportunity. Bound outstanding work and handle both synchronous exceptions and asynchronous failures.

Timer or buffer What it bounds Diagnostic use
max.block.ms Time waiting for metadata or buffer allocation in relevant producer API calls A thread stuck inside send may be waiting before the delivery timer does the work you expect. User serializer and partitioner time is separate.
request.timeout.ms Wait for a particular broker response One timeout may trigger a retry. A timeout alone cannot establish whether an append happened.
delivery.timeout.ms Overall record delivery budget including batching, transmission and retries Set it at least as large as request timeout plus linger. Size it against the application's real deadline.
buffer.memory / batch.size Producer buffering budget / batching target per partition Many active partitions increase partially filled buffers. Compression, requests and JVM objects add memory overhead.

Atomically publish output and advance input

For a Kafka-to-Kafka transform, a producer transaction can cover output to multiple topics/partitions and input offsets for a consumer group on the same cluster. Set a stable transactional.id unique to the active logical writer, call initTransactions() on startup, turn off consumer auto-commit and consume with isolation.level=read_committed where aborted data must be excluded. If the transaction aborts, staged output is hidden from read-committed consumers and the transactional checkpoint does not advance. The live consumer's position already moved during poll. On a recoverable abort, restore the input positions to the last committed offsets or restart the consumer before processing the next batch. If fenced, stop that writer. A commit timeout can have an uncertain outcome; follow the Java client's operation-specific retry rules. Blindly aborting or starting the next transaction can break recovery. Bound transaction duration and handle rebalances and ownership loss.

A transaction cannot roll back a wire transfer, email or independently committed PostgreSQL transaction. For a relational sink, save the event identity or partition progress in the same database transaction as the projection; for a database source, write an outbox row alongside the business mutation and relay it. A relay can repeat publication. Retain the event identity through the entire path.

Batches, compression and the network

Four units frequently get called a “batch”. A producer record batch belongs to one partition and can compress several records together. A produce request to one broker may contain batches from several partitions. A fetch response returns record batches beginning at requested partition offsets. A poll result is an application-facing selection from fetched data, and a database batch is an independent choice of transaction size. Ten calls to poll might consume data delivered by one network response.

Java 4.4's default producer linger is 5 ms. A full batch can go immediately. A short wait can lower latency under load if it reduces queueing and request overhead. Under sparse traffic a higher linger can add visible delay while barely improving compression. Try a representative key distribution, compare p50/p99 delivery time, records per request, bytes per record and CPU. Compressing each tiny JSON payload inside the application sacrifices redundancy across records and can prevent the broker/client codec from helping.

Codec or policy Useful starting workload What to measure
none on producer / uncompressed on topic Already-compressed or low-volume payloads Network and disk bytes versus CPU saved. Encrypted payloads often have little remaining redundancy.
lz4 / snappy High-throughput streams with a tight CPU or latency budget Compression ratio and producer/consumer CPU on real batches.
zstd Repeated field names or similar records, large retention footprint Storage and network savings versus compression level and decompression throughput.
gzip Interoperability or workloads where its measured size reduction pays CPU per MB and latency tails at peak.
Topic compression.type=producer Preserve the producer's chosen codec Mixed producers can create mixed-codec segments. Consumers transparently decode each batch with supported codecs.
Topic forces a codec Standardise the on-disk format for new batches Incoming batches encoded differently can require broker recompression. Budget broker CPU.

Compression changes bytes stored and transferred. It leaves keys, offsets, record count and retention policy semantics intact. Compaction instead removes obsolete values for a key and can create offset holes. A compacted topic can simultaneously hold compressed record batches. A codec change applies to newly written batches; existing segments are not synchronously rewritten.

Suppose 100 similarly sized trades total 100 KiB uncompressed and a producer batch occupies 25 KiB compressed. Disk and fetch bandwidth may approach the smaller size plus overhead. A reader decoding thousands of such records must still allocate for the expanded payload and Java objects. Set heap and processing queues from measurements after decompression. A byte-oriented fetch setting is an incomplete heap budget.

How history survives, expires or changes shape

Each partition is an append-only sequence spread across segment files, with sparse offset and timestamp indexes. The active segment receives appends. Segment rolling creates closed units that deletion, cleaning and remote copying can operate on. A lookup uses an index to approach the requested position, then scans batches. Kafka can serve a sequential scan efficiently, but it does not provide an arbitrary predicate index for “all T17 trades between two business dates”.

Topic model Settings What an old reader can recover
Event journal cleanup.policy=delete, size/time sized for the SLA Retained individual events, including superseded amendments. A reader can fall behind the earliest retained offset.
Latest value per key cleanup.policy=compact The latest retained value for each live key, plus earlier versions still awaiting cleaning. A fresh full scan can reconstruct current state under the tombstone timing constraints.
Bounded keyed cache cleanup.policy=compact,delete Obsolete versions can be cleaned and age/size retention can remove even the final value. An inactive key may disappear entirely.

Audit archive Independent immutable export with schemas, manifests and reconciliation History beyond Kafka retention if the export is complete. Restore and query are separate operations that require verification.

Segment deletion and capacity

retention.ms governs age; retention.bytes sets a limit per partition. With both enabled, either can make old closed segments eligible. segment.bytes and segment.ms influence rolling. Cleanup checks, active segment lifetime and deletion delay mean the physical file removal time can differ from the configured retention age. Short segments improve deletion granularity but increase files, index overhead and remote object count. Long segments can leave infrequent topics retaining records longer than a simple age calculation predicts. Consumer progress never pins these segments.

For an evenly loaded 12-partition topic receiving 12 MiB/s after compression, seven days of leader data occupies roughly 12 × 604,800 MiB = 6.92 TiB. At replication factor three, that is 20.76 TiB of cluster disk before indexes, spare capacity, temporary cleaner output, reassignments and other topics. Averaging across all partitions hides the hot one. A 100 GiB per-partition cap at 2 MiB/s covers only 14.2 hours for that partition, even with seven-day time retention. Use the larger of planned outage plus recovery time and the business replay obligation as the required horizon. Check size caps and actual log starts against it.

Compaction is asynchronous, so a reader must also work when it sees all four rows. A consumer maintaining an old external map can retain a ghost T42 if it misses the tombstone. Rebuild from an empty map when the incremental checkpoint no longer has reliable deletion coverage. A fresh scanner also needs sufficient time to finish before tombstones it needs can vanish. Size delete.retention.ms against the worst bootstrap scan. This is different from the delay before unlinking an expired segment file.

min.cleanable.dirty.ratio affects when cleaning becomes worthwhile. min.compaction.lag.ms can preserve a period of recent revisions; max.compaction.lag.ms limits how long data can remain ineligible, subject to cleaner throughput. A saturated cleaner cannot promise an exact per-record erasure deadline. Compaction uses the serialized key within one partition. A key that moves partitions after expansion has two independent histories. A latest-value topic should publish full state or a reconstructible snapshot per key. If the final record says only “increase by £20”, cleaning away the starting value destroys the reconstruction.

Hot and remote history

Tiering separates local local.retention.ms/bytes from the topic's overall retention.ms/bytes. Self-managed deployment requires broker support, a remote storage manager implementation and its metadata management, plus per-topic enablement such as remote.storage.enable. Check backend storage, credentials, quotas, upload lag, previous feature levels and supported cleanup policies on the selected distribution. A remote tier participates in the cluster's lifecycle policy; deletion and retention can propagate. An independent archive has a different failure boundary. On a cold backfill, monitor remote-fetch rate and request latency separately from live broker disk reads.

Who owns consumer state?

An ordinary Java consumer groups work by partition. With subscribe, group coordination assigns ownership and can move it when instances join, leave or fail. With assign, the application specifies partitions itself. Two manually assigned readers can independently read the same partition. Position is local to a consumer instance. Durable restart progress needs a group commit or an external checkpoint. KafkaConsumer is not thread-safe; keep poll, seek, assignment and commit operations on its owning thread. Use the supported wakeup mechanism to interrupt a blocking poll for shutdown.

At p0 after a poll of offsets 0, 1, 2 Next offset Owner What it proves
Consumer position 3 Local client All three have been handed to the application.
Only offset 0 durably applied 1 Projection/database Processing may safely restart at 1 if this progress is made durable with the effect.
Previous group commit 0 Kafka group coordinator, backed by offsets topic A restarted group member will replay 0, 1 and 2 if all remain readable.
End for a read-committed scan, assuming no open transactions or later writes 3 Broker The first three offsets are within the captured boundary. It says nothing about the database.

Offset commits always identify the next position. Committing 3 while offset 1 remains unprocessed can skip a trade on restart. If worker completions arrive in order 2, 0, 1, hold the durable frontier at the first outstanding delivered record. Advance to 3 after all earlier delivered work is durable. Offset gaps are legitimate. Track ordered delivered records and the next offsets supplied by the client, rather than waiting forever for integers removed by compaction or control records.

A group offset can expire independently of the data it refers to. An inactive group can lose its checkpoint while its topic still retains years of data. Conversely a healthy checkpoint can point below the start because size retention advanced during an outage. Inspect group history, group ID, broker offset-retention policy and actual partition starts before applying a reset. Renaming a group creates an independent progress namespace. Deleting records from a topic, deleting a group and resetting its offsets are three different operations.

Four ways to couple progress to work

Pattern Where the durable acknowledgement lives Crash behaviour
Commit first, process second Group offset committed before effect A crash between them skips work (at-most-once processing attempt).
Process first, commit second Group checkpoint after effect A crash between them repeats work. An idempotent sink can absorb repeats.
Store output and next offset in one database transaction Database row per projection version, topic identity and partition Rollback leaves both unchanged. On restart seek from the database. Fence stale owners before updates.
Kafka-to-Kafka transaction Broker transaction includes output and group offsets Read-committed downstream readers see committed output; aborted attempts can be retried.

Auto-commit periodically records progress as the consumer runs and can be convenient for synchronous, disposable processing. Handing records to an asynchronous queue then continuing to poll can commit past unfinished work. Disable it for explicit boundaries. commitSync waits for success or error. commitAsync can reduce delay but an application retry of an older failed commit can rewind progress. In batch processing, pass the offsets actually finished; the no-argument commit uses the consumer's poll progress. A revoked partition requires a coordinated hand-off. On lost ownership, abandon stale work or fence it at the sink.

Database implementation. Give each projection version its own checkpoint row. In one SQL transaction, lock or conditionally update that row using the expected previous checkpoint and current ownership token, apply ordered events, then advance the row. On conflict, roll back business changes too. Alternatively insert stable event IDs into an inbox with a unique constraint and update business state only for newly inserted IDs inside the same transaction. A unique row for the Kafka offset deduplicates delivery of that exact record; a unique business ID can also catch republished duplicates at a different offset. Design the scope of that uniqueness, e.g. per projection version. Otherwise rebuilding v2 can suppress every event already handled by v1.

Rebalancing and liveliness

With the classic group protocol, assignment strategy, session timeout and heartbeat interval are client settings subject to broker limits. Eager assignment can revoke all partitions; cooperative assignment moves ownership incrementally when supported by the group. With group.protocol=consumer, the broker manages assignment and heartbeat/session policy, with group overrides where supported. Kafka 4.4's Java consumer config still lists classic as the default. Check the actual client and protocol before tuning. A stable, unique group.instance.id can reduce churn on short restarts, but can delay reassignment of genuinely failed members.

max.poll.interval.ms bounds the time between poll calls for group-managed processing. Healthy heartbeats alone do not excuse a stalled application. If a 500-record batch can take 400 seconds and the interval is 300 seconds, shrink max.poll.records, speed up the sink, or decouple work with bounded partition-aware queues. Pause assigned partitions under backpressure, keep polling for group participation, and resume them as capacity returns. Pausing affects future delivery; records already returned still belong to the application. Track in-flight work and rebalance callbacks. Slow processing, session loss and stop-the-world GC have different remedies.

Consumer positions, commits, threads and rebalances · Classic and consumer protocol controls

Request history in bulk

Yes. Send Kafka a starting offset for each partition, then fetch sequential batches. The Java consumer issues fetch requests and buffers responses as you call poll. There is no requirement to make a network round trip per message. There is also no single “return the whole topic” response. A terabyte backfill streams through bounded memory. Most engineering effort goes into selecting a defensible start and stop, keeping the sink consistent and protecting live traffic.

Freeze a range, then consume it

At 09:10 capture a stop offset of 3 on p0. A new event at offset 3 arrives at 09:11. One poll can return offsets 0 through 3 together. Filtering with offset < 3 keeps the three intended records. Stopping at the first empty poll instead can finish too early. Re-reading the end continuously can make the job chase a live stream forever.

From a backfill to a live projection

Start v2 in an isolated table with outbound actions disabled. Capture the range, bulk-write rows in idempotent transactions, checkpoint each partition and compare counts and totals against the source at a common cut. Then tail from the captured stops, reconcile again at a later barrier, and switch the read alias when the agreed lag is met. Keep v1 advancing until rollback is no longer needed. Restart a failed job from its durable manifest. Capturing new ends when resuming silently changes the job's contract.

Throughput calculation. A frozen 360 GiB backlog at sustained 60 MiB/s takes 6,144 s, about 1 h 42 min. Catching the live head while it grows at 20 MiB/s takes about 2 h 34 min at the same service rate (360 × 1,024 / 40 seconds). At 20 MiB/s service there is no catch-up margin. These calculations assume comparable byte measurements and ignore warm-up, retries and key skew. Parallelise across partitions, batch sink writes and limit replay bandwidth per client/user so the live workload meets its latency budget.

Limits from producer memory to sink capacity

Kafka has no single maximum history query size expressed in records. A backfill can read many fetches until retention or the saved stop boundary. The limiting quantities have different units and scopes. Selected upstream Java/broker defaults below are a reference for 4.4; inspect topic overrides and managed-service ceilings.

Control Upstream default or scope What happens at the boundary
Producer batch.size 16,384 bytes per partition batch target A large individual record can get its own batch. This is a batching target, not a record admission limit.
Producer max.request.size 1,048,576 bytes Limits request size and effectively the maximum uncompressed record batch the producer will send. Include keys, headers and framing.

Worked tuning decision. The client fetches roughly 8 MiB of compressed data across four partitions. The application polls 100 records at a time. Raising max.poll.records to 1,000 reduces application loop overhead only if the client has records waiting. It may increase database transaction duration and risk max.poll.interval.ms. If network round trips dominate a cold backfill, look instead at fetch sizes, latency and the remote tier. If the database saturates at 10,000 upserts/s, increasing fetch buffers just moves the queue.

For multi-megabyte documents, a common design stores the object once and publishes an immutable URI, version, byte size and content hash. Ensure the object exists before sending the event, retain it for the full replay horizon, and grant readers access to that exact version. For large inline records verify the producer's pre-compression check, broker compressed/decompressed checks, follower catch-up, consumer heap and any Connect/Streams paths. Test the largest poorly compressible record as well as the average case. Java strings, JSON trees and application queues often dominate compressed bytes in memory.

Select the consumption and integration model

Consumer groups and share groups

A conventional group gives an application partition ownership and an ordered cursor. It fits T17's lifecycle because the same worker can serialise updates and checkpoint a contiguous prefix. A share group provides queue-like delivery using acquisition locks and record acknowledgements. Several share consumers can work on the same partition, and worker count can exceed partition count. In 4.4 a share consumer can accept completed work, release it for retry, reject an unprocessable record or renew its acquisition as supported by the API. Locks expire and delivery attempts are tracked. A worker can finish a side effect after its lock expires and another worker can then attempt it too.

Use a share group for independent jobs such as rendering completed trade confirmations with idempotent job IDs. Use a conventional assigned or subscribed consumer for a deterministic historical range scan. A share acknowledgement concerns one group's delivery lifecycle. Producer acks concerns replicated writes. Neither action removes the record for other readers. Check that the managed service, client and cluster feature levels support share groups before choosing the model.

Kafka Streams

Streams embeds processing in a Java application. A KStream models events; a KTable models a changing value per key. For full-state trade updates, materialise a table keyed by trade ID. To sum exposures by portfolio, a trade amendment must retract its old portfolio contribution before adding its replacement. A plain sum over update events counts £100 and £120 for T17. A table aggregation with subtraction/addition can produce the intended £120. If the input consists of deltas instead, an event aggregation can be appropriate.

Grouping by a new key can trigger a repartition topic. Stateful tasks keep local stores, commonly RocksDB-backed, and changelog topics support recovery where logging is enabled. application.id scopes consumer identity and internal resources. state.dir chooses local storage; num.standby.replicas trades resources for faster failover; num.stream.threads increases local processing concurrency up to the available tasks. processing.guarantee=exactly_once_v2 coordinates Kafka outputs, state changelogs and consumed offsets. A REST call inside a processor still has its own failure semantics.

Windowed joins and aggregations require event-time rules, window size, grace for late records and enough state retention. A late amendment beyond grace may need a correction path or a separate backfill. Order and co-partition keys consistently for keyed joins; inspect Topology.describe() to see repartition boundaries. Rebuilding a Streams app means coordinating group offsets, local stores, intermediate topics and downstream consumers. For a versioned rebuild, give the new application fresh state and output namespaces and compare both at the same business cut.

Kafka Connect and data movement

A source connector reads an external system and produces records; its connector-specific source offset is a coordinate such as a database log position. A sink connector consumes Kafka and writes externally; restart semantics depend on the connector and destination. Distributed workers share configuration, offset and status topics and redistribute tasks. Standalone workers suit development. tasks.max caps parallelism; a connector supporting one source cursor may still run only one task. Converters define key/value wire representations, and single-message transforms handle lightweight per-record changes.

A CDC source can bootstrap with a database snapshot and follow the transaction log. Verify how the snapshot boundary joins the log, how deletes and schema changes are represented, and what happens when the source log expires. A sink writing files can have both a Kafka offset and a file-commit protocol. Measure restart behaviour by failing it between file upload and checkpoint. Exactly-once support is connector- and system-specific. Error tolerance and dead-letter routing can preserve availability at the price of skipped business records. Monitor the quarantine stream and retain original topic, partition, offset, schema and failure reason.

MirrorMaker 2, federation and disaster recovery

MirrorMaker 2 uses Connect to replicate selected topics asynchronously across clusters. Configure source and target aliases, inclusion rules, replication policy and checkpoint/heartbeat functions. Partition offsets in the two clusters can differ. Consumer group offset translation and synchronisation need explicit configuration and verification. A disaster runbook needs the last replicated business event and tested restart coordinates; the existence of the destination topic proves neither completeness nor a zero recovery-point objective.

For active/passive trading, establish one write authority, fence the old writer before failover, measure the replication gap, and reconcile against the source ledger. For active/active, define key ownership, conflict rules and replication-loop avoidance. Internal Kafka transactions and offsets belong to their cluster; a replicated record does not automatically retain an atomic relationship with an external side effect or the original cluster's group checkpoint.

Operate and observe the cluster

Metadata quorum, storage and upgrades

KRaft separates controller quorum membership from broker replica placement. A three-voter quorum tolerates one voter being unavailable; five tolerate two under majority assumptions. Combined controller/broker mode is convenient for the local lab. Separate roles and failure domains allow independent capacity and recovery decisions. Configure unique node IDs, process roles, storage paths, controller listener names and quorum bootstrap or voter settings appropriate to the quorum type. Format new storage with the intended cluster identity once. Reformatting a failed production node as a new cluster is not recovery.

A broker can host leaders and followers across many partitions. More partitions add file handles, metadata, leader elections and recovery work; more replicas add network and disk load. To change replication factor of existing data, plan partition reassignment with target replicas, throttle migration, check completion and remove temporary throttles. Leader balancing changes where clients send traffic; it need not move all replicas. Distribute leaders as well as bytes. Measure disk headroom during broker loss and rebuild, not only during steady operation.

Binaries, metadata feature levels and client protocol support can move on different schedules. Before an upgrade inspect supported versions and features, use rolling procedures for the installed quorum type, verify replication and client interoperability, then advance feature levels according to the release procedure. Restore tests should include topics, configs, schemas, authorisation, group checkpoints and external application state.

Listeners, identity and isolation

listeners controls broker bind endpoints; advertised.listeners contains the addresses handed to clients through metadata. A TCP connection to the bootstrap host can succeed while every produce/fetch afterwards fails if those advertised names are unreachable from the client network. Use routable endpoints for each audience, correct certificates and separate controller/inter-broker listener roles. Supply more than one bootstrap broker for resilience.

Configure security.protocol and the matching listener mechanism. TLS protects transport and verifies the server, mTLS can authenticate clients, and SASL mechanisms such as SCRAM or OAuth can authenticate over TLS. Authorisation is separate. Grant the writer rights to its output topics and transactional ID as required, the consumer appropriate topic and group permissions, and the replay principal read access plus its isolated output permissions. Keep command-topic write rights away from reporting jobs. Control schema registry, remote tier and external sink access independently. Record audit identities with meaningful principals and client.id values; a client ID is an observation/quota label and is user-configurable.

Quotas can limit producer/consumer byte rates and request utilisation for client/user entities; administrative mutation and replication throttles serve different purposes. Give backfills a recognisable identity and observe throttle time. A larger poll interval cannot cure a saturated disk, and extra broker threads will not speed up a slow PostgreSQL index.

Deciding which metric to inspect

Observation Discriminating evidence Action to verify
Send timeout while brokers appear healthy Compare metadata resolution, buffer wait, throttle time, request latency, retry count and ISR per partition Verify advertised addresses; inspect a single affected leader and the delivery deadline. Reconcile ambiguous event IDs.
Writes fail after one broker outage Compare RF, ISR and minimum ISR; inspect internal transaction topics if only transactional writes fail Restore the missing safe copy or capacity. Observe ISR return and a replicated probe acknowledged on the intended topic.
Consumer appears caught up, dashboard remains stale Compare group offset, consumer position, durable DB checkpoint and business event age Look for auto-commit ahead of processing, a blocked work queue or filtered amendments. Validate a known event end to end.
Lag rises on one partition Compare per-key arrival distribution with per-partition processing latency Identify a hot key or a poison record before adding group members.
Stable group lag but read-committed jobs stall Compare high watermark, last stable offset and open transaction lifetime Find the long-running producer transaction and verify its commit or abort.
Rebalance loop after deploy Poll gaps, GC, task duration, duplicate static IDs, member assignments Reduce work per poll or bound queues. Expect sustained ownership and successful commits after recovery.
Backfill starts too late or returns fewer rows Compare requested and available starts, cleanup policy, aborted transactions, timestamp basis and isolation Reconcile business IDs against the archive. Offset subtraction is a distance, not an exact row count.
Healthy live reads, slow historical reads Compare hot/cold fetch latency, tier upload/read metrics, quotas, cache, network and sink flush time Benchmark a fixed range with a disposable fast sink, then repeat with the real sink.
Consumers see duplicates after crash Compare duplicate business IDs and actual Kafka coordinates Same coordinate suggests redelivery; a new coordinate suggests re-publication. Check which transaction committed first.

For an intentional reset, record the prior per-partition checkpoints and sink state, stop all group members, verify the preview, then replace --dry-run with --execute. Restart and verify effects as well as group offsets. Reverting a checkpoint does not reverse SQL updates or messages previously sent. For day-to-day observation, track under-replicated and offline partitions, ISR changes, disk and controller health, bytes in/out, request queues and latency, produce errors/retries, client throttling, poll interval, commit latency, group lag, business freshness and sink checkpoint age.

A release test using the three trade events

  1. Run the one-partition lab. Read it independently as audit and risk. Record offsets 0 through 2 and confirm the final £170 projection manually.
  2. Run the Java backfill and compare its three rows with the console output. Repeat with a future start timestamp. Expect zero output rows and a completed empty range.
  3. For a production rehearsal, capture stops in a manifest. Append a fourth trade after capture. Verify its offset is excluded from that run and included when tailing from the saved stop.
  4. Kill a test projection between a durable update and its Kafka commit. A replay should repeat the input and leave the same database total. Repeat with an out-of-order worker completion and verify the checkpoint never skips unfinished work.
  5. In a separate replicated test cluster, remove one of three replicas, wait for the ISR to settle and run the write probe. Remove a second and observe the minimum-ISR failure. Restore replicas, observe catch-up, then reconcile acknowledged IDs.
  6. Compare elapsed replay time with both the fixed-range and live catch-up budgets. Document the earliest guaranteed restart point, source of any missing history and observable evidence required before enabling v2.
