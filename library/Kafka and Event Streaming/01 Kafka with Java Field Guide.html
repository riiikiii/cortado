1. What you will build

An OMS publishes six fills for two orders. A Java service reads them and records its progress. You will restart that service, replay the fills three ways, and check exactly what moved. The application uses the native Kafka client so you can see where your code takes responsibility for delivery. The example project contains every file, including the full source shown below.

Stack: JDK 21, Maven 3.9+, Docker with Compose v2, Apache Kafka 4.4.0 in KRaft mode. Run the shell commands in Bash (macOS, Linux or WSL2) from the extracted project root. Java runs on the host. The Kafka CLI runs inside the broker container. Allow time for Maven and Docker to download dependencies on the first run.

Concept In the fill service
Topic trade.fills.v1 holds an append-only sequence per partition. Reading a fill leaves it available to other readers.
Key ORD-A puts that order’s fills on the same partition under the default keyed partitioner and a stable partition count. Multiple orders can share one partition.
Partition and offset (trade.fills.v1, 2, 41) identifies one log position. Offset 41 in partition 0 is unrelated. Concurrent producers still need a business sequence if causal order matters.
Consumer group Instances with group ID positions-v1 share the partitions. Another group, such as surveillance-v1, can independently read all of them.
Commit A checkpoint per group, topic and partition. It records the next offset to read on resumption. Your database transaction has its own commit.
Retention The broker decides how long records remain available. A slow or stopped consumer cannot hold them indefinitely.

Coming from RabbitMQ, think about what happens when the handler succeeds. A queue acknowledgement normally lets the broker remove that delivery from the queue. Here, success advances one group’s checkpoint. That separation enables both independent subscribers and historical replay.

2. Start Kafka and create the topic

The project’s Compose service publishes port 9092 on loopback. The official image’s default single-node setup supplies a combined broker and KRaft controller. The broker serves data, while the controller manages cluster metadata. You can stop and start this container between exercises. Treat container recreation as a fresh lab.

YAML
services:
  kafka:
    image: apache/kafka:4.4.0
    ports:
      - "127.0.0.1:9092:9092"
BASH
docker compose up -d
# Define once per shell. -T keeps CSV exports free of terminal formatting.
k() { local tool="$1"; shift; docker compose exec -T kafka "/opt/kafka/bin/$tool.sh" --bootstrap-server localhost:9092 "$@"; }
k kafka-topics --list

If Kafka is still starting, inspect docker compose logs --tail=50 kafka and repeat the list command. An empty list on a new cluster is fine.

BASH
k kafka-topics --create --if-not-exists --topic trade.fills.v1 \
  --partitions 3 --replication-factor 1 \
  --config cleanup.policy=delete --config retention.ms=604800000
k kafka-topics --describe --topic trade.fills.v1

Expect three partition rows, each with a leader and one in-sync replica (ISR). Seven days is the lab retention window. Three partitions let at most three group members actively read this topic at once. One broker gives no failover. Re-running topic creation with --if-not-exists does not reconcile an existing topic’s configuration.

Networking: bootstrap.servers is the initial contact point. The broker then advertises addresses the client must be able to reach. A Java container would resolve localhost to itself. For a containerised app and a host app together, configure separate internal and external advertised listeners, such as kafka:29092 and localhost:9092, with corresponding listener bindings and security protocols. The supplied Compose setup is for the host-based client.

3. Build and run the Java application

The ZIP contains pom.xml, compose.yaml, and two files under src/main/java/lab/. Maven compiles for Java 21 and pins org.apache.kafka:kafka-clients:4.4.0. Use a JDK for Maven. Check mvn -version if the compiler rejects release 21.

BASH
mvn -q compile
run() { mvn -q exec:java "-Dexec.args=$*"; }
run produce
run consume positions-v1 20
k kafka-consumer-groups --describe --group positions-v1
run consume positions-v1 10

On an empty topic, the producer prints six broker acknowledgements with partition and offset. The first consumer should print six JSON payloads within its 20-second window. The second should print none if no new fills arrived and the first finished committing. If initial group formation takes longer, rerun the consumer. Order within each partition is stable. Output order across partitions may vary. Run the producer once for the exercise. Running it twice intentionally appends another six records with the same business IDs.

The complete producer and consumer

JAVA
package lab;

import java.time.Duration;
import java.time.Instant;
import java.util.List;
import java.util.Properties;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.serialization.*;

public class Trades {
    static final String TOPIC = "trade.fills.v1";
    static Properties base() {
        var p = new Properties();
        p.put("bootstrap.servers", System.getenv().getOrDefault("KAFKA_BOOTSTRAP", "localhost:9092"));
        return p;
    }

    static void publish() throws Exception {
        var p = base();
        p.put("key.serializer", StringSerializer.class.getName());
        p.put("value.serializer", StringSerializer.class.getName());
        p.put("acks", "all");
        p.put("enable.idempotence", "true");
        try (var producer = new KafkaProducer<String, String>(p)) {
            for (int i = 1; i <= 6; i++) {
                String order = i % 2 == 1 ? "ORD-A" : "ORD-B";
                String fill = "FILL-" + i;
                String body = """
                    {"schemaVersion":1,"fillId":"%s","orderId":"%s","quantity":%d}
                    """.formatted(fill, order, i * 10).strip();
                var ack = producer.send(new ProducerRecord<>(TOPIC, order, body)).get();
                System.out.printf("%s %s -> partition=%d offset=%d%n",
                        fill, order, ack.partition(), ack.offset());
            }
        }
    }

    static Properties reader() {
        var p = base();
        p.put("key.deserializer", StringDeserializer.class.getName());
        p.put("value.deserializer", StringDeserializer.class.getName());
        p.put("enable.auto.commit", "false");
        return p;
    }

    static void consume(String group, int seconds) {
        var p = reader();
        p.put("group.id", group);
        p.put("auto.offset.reset", "earliest");
        p.put("max.poll.records", "100");
        try (var consumer = new KafkaConsumer<String, String>(p)) {
            consumer.subscribe(List.of(TOPIC));
            var deadline = Instant.now().plusSeconds(seconds);
            while (Instant.now().isBefore(deadline)) {
                var batch = consumer.poll(Duration.ofMillis(500));
                for (var r : batch) print(r); // Replace with a durable, idempotent write.
                if (!batch.isEmpty()) consumer.commitSync(batch.nextOffsets());
            }
        }
    }

    static void print(ConsumerRecord<String, String> r) {
        System.out.printf("%s [%d] @%d key=%s %s%n",
                r.topic(), r.partition(), r.offset(), r.key(), r.value());
    }

    public static void main(String[] args) throws Exception {
        if (args.length == 1 && args[0].equals("produce")) publish();
        else if (args.length == 3 && args[0].equals("consume"))
            consume(args[1], Integer.parseInt(args[2]));
        else if (args.length == 1 && args[0].equals("snapshot")) Snapshot.run();
        else throw new IllegalArgumentException("Use produce | consume GROUP SECONDS | snapshot");
    }
}

Producer. The key selects the partition. The value contains the business event. send().get() waits for the acknowledgement and surfaces delivery failures to the caller. It makes the six sends easy to follow. For throughput, reuse one thread-safe producer, send asynchronously, handle failed callbacks and track outstanding sends through shutdown. Batching, compression and linger.ms trade some latency and CPU for throughput. Measure the trade-off with real record sizes.

Idempotence. Kafka can suppress duplicates generated by client retries with producer idempotence enabled. Generating the same fill again is a new application-level send. Keep a stable event ID across retries, corrections and upstream recovery, with distinct IDs for genuinely distinct events. Use a versioned schema and compatibility checks for long-lived topics. Historical bytes must remain decodable during a rebuild. The example uses a fixed JSON template for controlled inputs. Use a JSON serializer or a schema-aware format for arbitrary input.

Consumer. poll() advances the local position as it returns data. The example processes the entire batch, then commits its returned next offsets. If processing throws, the loop exits before committing that batch. On restart it can receive already-processed records again. If you catch and suppress the exception and then commit the whole batch, you can skip a failed fill. In a service, use a long-running poll loop and graceful shutdown. Keep the consumer on one thread; another thread can call wakeup() to interrupt a blocking poll. Let the owner finish or abort the current unit of work and close the client.

Read the offsets yourself

Suppose partition 2 has retained offsets 37 through 45, with a log end of 46. The group has committed 42. A poll returns 42, 43 and 44.

Moment Local next position Committed next offset What a replacement consumer reads first
Before polling 42 42 42
Poll returned, database write running 45 42 42
Database committed, process dies before Kafka commit 45 before crash 42 42, so the write must tolerate duplicates
Kafka commit succeeds after database commit 45 45 45

The CLI would show lag of one offset unit in the last row. Offset differences can include gaps due to transactions or compaction. They are neither exact business-event counts nor elapsed time. For latency, also measure the age of the records your handler completes.

4. Choose a replay strategy

Goal Mechanism Impact on live processing
Rebuild a positions table with new logic Fresh group and fresh output table Live group continues independently. Both readers add load.
Repair the live group’s checkpoint Stop all group members, preview, then reset selected partitions Changes where the production group resumes. Reprocessed side effects require a plan.
Audit a fixed input range Manual assignment, explicit start and exclusive end per partition No group offsets change. The audit terminates while new fills can continue arriving.
Retry a transient downstream failure Retry the failed work without committing past it Preserves order on the affected partition. A prolonged failure can delay later fills.

A. Rebuild using a new consumer group

BASH
run consume positions-rebuild-001 20
k kafka-consumer-groups --describe --group positions-rebuild-001
k kafka-consumer-groups --describe --group positions-v1

The new group receives the six retained fills because its offsets are initially absent and the client chooses earliest. Reusing that new group resumes from its own commits. Changing auto.offset.reset on the original group does nothing to valid checkpoints. The setting is a fallback when a checkpoint is absent or out of range. Use none for a critical processor where an unexpected missing checkpoint should stop the service for investigation.

For a real rebuild, write to a versioned shadow table. Record target end offsets per partition, keep processing new arrivals, and reconcile both projections at the same offsets. For the lab’s six unique fills, expect three fills and 90 units for ORD-A, and three fills and 120 units for ORD-B. Validate event IDs and quantities, then switch readers to the new projection. A fresh group alone does not isolate database writes, notifications or external API calls.

B. Reset an existing group’s committed offsets

The timed consumer exits on its own. For a deployed service, stop every replica and suspend automatic restarts. Verify zero active members and inspect the current offsets first. Use the lab group for the following commands.

BASH
k kafka-consumer-groups --describe --group positions-v1 --state
k kafka-consumer-groups --describe --group positions-v1
k kafka-consumer-groups --reset-offsets --group positions-v1 \
  --topic trade.fills.v1 --to-current --dry-run --export > positions-before.csv
cat positions-before.csv
k kafka-consumer-groups --reset-offsets --group positions-v1 \
  --topic trade.fills.v1 --to-earliest --dry-run

Check the group, topic, partitions and proposed offsets. Preserve the CLI description as well as the CSV. A partition with no prior checkpoint is a distinct state, so an exported numeric offset for it is not an exact backup of that absence. Earliest means the oldest still retained offset for each partition.

BASH
k kafka-consumer-groups --reset-offsets --group positions-v1 \
  --topic trade.fills.v1 --to-earliest --execute
k kafka-consumer-groups --describe --group positions-v1
run consume positions-v1 20
k kafka-consumer-groups --describe --group positions-v1

On the original lab data you should see six records again, followed by zero lag on partitions with committed offsets. A reset changes no broker records. A forward reset can skip unprocessed work; a backward reset can repeat completed effects.

Restore checkpoint positions. Stop the group again. Compare saved offsets against the current earliest and latest offsets. A position that has aged out cannot restore expired history. Inspect the candidate plan before applying it.

Restoring a checkpoint cannot undo database mutations, messages published, emails sent or trades submitted during a replay. Reconcile those separately.

C. Run a bounded, read-only audit in Java

BASH
run snapshot
k kafka-consumer-groups --describe --group positions-v1

This reader discovers partitions, assigns them directly, captures an exclusive end for each, and seeks each partition to its retained start. It prints only records below those ends. It never commits and needs no group ID. Completion uses the consumer position, so a gap or empty partition does not require an invented “last message”. The demo has a 60-second deadline and reports incomplete work if exceeded.

JAVA
package lab;

import java.time.Duration;
import java.time.Instant;
import java.util.HashSet;
import org.apache.kafka.clients.consumer.KafkaConsumer;
import org.apache.kafka.common.TopicPartition;

class Snapshot {
    static void run() {
        var p = Trades.reader();
        p.put("auto.offset.reset", "none");
        p.put("isolation.level", "read_committed");
        try (var c = new KafkaConsumer<String, String>(p)) {
            var partitions = c.partitionsFor(Trades.TOPIC).stream()
                    .map(info -> new TopicPartition(info.topic(), info.partition())).toList();
            c.assign(partitions);
            var starts = c.beginningOffsets(partitions);
            var ends = c.endOffsets(partitions);
            var pending = new HashSet<>(partitions);
            for (var tp : partitions) {
                c.seek(tp, starts.get(tp));
                System.out.printf("%s [%d, %d)%n", tp, starts.get(tp), ends.get(tp));
            }
            var deadline = Instant.now().plusSeconds(60);
            while (!pending.isEmpty()) {
                for (var tp : new HashSet<>(pending)) {
                    if (c.position(tp) >= ends.get(tp)) {
                        c.pause(java.util.Set.of(tp));
                        pending.remove(tp);
                    }
                }
                if (pending.isEmpty()) break;
                if (Instant.now().isAfter(deadline))
                    throw new IllegalStateException("Replay incomplete: " + pending);
                for (var r : c.poll(Duration.ofMillis(500))) {
                    var tp = new TopicPartition(r.topic(), r.partition());
                    if (r.offset() < ends.get(tp)) Trades.print(r);
                }
            }
        }
    }
}

Suppose the captured end for partition 2 is 46. A fetch can return offsets 44, 45, 46 and 47 if new records arrived after capture. Only 44 and 45 belong in the audit. Capturing the ends gives a vector of per-partition boundaries. It does not establish an atomic business-time snapshot across partitions. With read_committed, the end used here is the last stable offset, so an open transaction can hold it back.

For repeatable runs, persist topic identity, per-partition starts and ends, isolation level, decoder version and output destination. The demo captures fresh bounds on each invocation. To audit from a UTC instant, call offsetsForTimes with epoch milliseconds for every partition. An entry can be null when there is no matching record. Use the captured end for that partition, cap returned starts at that end, and validate retained bounds. Plan a backfill source if retention or compaction can remove the evidence during the job.

5. Make replay safe for a database-backed application

Consider a positions service adding a fill quantity to an order’s cumulative filled quantity. Replaying a +50 fill blindly adds another 50. A database unique constraint can make the handler safe even when two attempts overlap. Below is PostgreSQL SQL with JDBC bind placeholders in order: event ID, order ID, quantity. Scope the deduplication table to this projection. Use one connection and transaction, confirm its commit, then let the Java consumer commit the offset.

SQL
CREATE TABLE applied_fill (
    fill_id text PRIMARY KEY
);
CREATE TABLE filled_quantity (
    order_id text PRIMARY KEY,
    quantity bigint NOT NULL
);

-- One statement for each fill in the application transaction.
WITH accepted AS (
    INSERT INTO applied_fill (fill_id) VALUES (?)
    ON CONFLICT (fill_id) DO NOTHING
    RETURNING fill_id
)
INSERT INTO filled_quantity (order_id, quantity)
SELECT CAST(? AS text), CAST(? AS bigint) FROM accepted
ON CONFLICT (order_id) DO UPDATE
SET quantity = filled_quantity.quantity + EXCLUDED.quantity;

If the DB commit succeeds and the Kafka commit fails, retrying sees the event ID and performs no second increment. If the DB rolls back, neither the event ID nor the increment survives. Keep deduplication history for the full supported replay horizon. Rebuild a fresh projection with a matching empty deduplication table. If the source can reuse fill IDs, use a sufficiently scoped key such as venue plus execution ID. Corrections and busts need explicit events and business rules.

Output Suitable boundary
Kafka input → PostgreSQL Database transaction and stable unique event ID, followed by offset commit.
Kafka input → Kafka output Transactional producer: begin transaction, send results, call sendOffsetsToTransaction(batch.nextOffsets(), consumer.groupMetadata()), then commit the transaction. Give each active producer a unique transactional ID stable across its restarts. Configure downstream readers with read_committed. Abort and rewind/recreate the consumer before retrying failed work.
Database change → Kafka Write an outbox record in the same DB transaction as the change. Publish it through CDC or a relay. Downstream readers still need a duplicate policy.
External trading or notification API Use an externally enforced idempotency key or reconcile ambiguous outcomes before retrying. Historical projection rebuilds should have outbound execution disabled.

A poison record needs an explicit policy. For transient errors, use bounded retries, backoff and monitoring. For a permanent schema or validation failure, either halt that partition or durably quarantine the original bytes, key, headers, topic, partition, offset and error. Advance past it only when the chosen policy permits it. Quarantining a fill may make later per-order state wrong until you repair it. Deserialisation errors can occur inside poll() before a record reaches your handler. A byte-array consumer with application decoding is one way to preserve the raw payload.

6. Operate and troubleshoot Kafka

Daily inspection commands

BASH
k kafka-topics --list
k kafka-topics --describe --topic trade.fills.v1
k kafka-configs --entity-type topics --entity-name trade.fills.v1 --describe
k kafka-get-offsets --topic trade.fills.v1 --time earliest
k kafka-get-offsets --topic trade.fills.v1 --time latest
k kafka-consumer-groups --list
k kafka-consumer-groups --describe --group positions-v1
k kafka-consumer-groups --describe --group positions-v1 --members --verbose
k kafka-metadata-quorum describe --status

Run the membership command while a longer consumer is active (run consume positions-v1 120 in a second shell with the same function definition). Start another instance with the same group to watch partition ownership move. A third instance can own the remaining partition, but a partition with no records still contributes no throughput. Different groups have independent assignments.

Change retention in the lab and verify the applied override:

BASH
k kafka-configs --entity-type topics --entity-name trade.fills.v1 \
  --alter --add-config retention.ms=1209600000
k kafka-configs --entity-type topics --entity-name trade.fills.v1 --describe

This sets 14 days for future availability. Increasing retention cannot recover records already deleted. A byte limit can trigger removal sooner and operates per partition. Deletion works on eligible log segments, so expiry time is approximate. A compacted topic eventually retains the latest value per key, subject to tombstones and any delete policy. Keying a compacted fills topic by order ID could erase earlier individual fills. For replayable execution history use a deletion-retained event topic with suitable archival, and use a separate compacted topic for current order state.

Incident triage

Observation Inspect Action to test
Bootstrap connects but produce/fetch times out Advertised listener hostnames, DNS, port reachability from the client, TLS and ACL errors Test the returned broker endpoints from the application network.
Restart reads nothing Correct group, committed positions, topic end and partition assignment Try the read-only audit. A valid checkpoint at the end explains an idle consumer.
Lag grows on one partition Key distribution, oldest unprocessed event, handler latency and downstream locks Resolve the hot key or slow dependency. Another group member cannot split one partition.
Lag grows everywhere Ingress versus processing rate, DB pool saturation, throttling, GC and consumer CPU Reduce the bottleneck. Add consumers up to available partitions when parallelism helps.
Frequent rebalances or commit failures Deployment churn, time between polls, max.poll.interval.ms, batch duration Reduce max.poll.records, bound handler latency and stop cleanly. Avoid committing work after partition ownership is lost.
Missing historical events Earliest offsets, retention, compaction, old schema compatibility Recover from a verified archive. New group IDs cannot recreate deleted history.
Producer reports insufficient replicas ISR size, offline brokers, disk and network health Restore replication health. Lowering minimum ISR trades away durability.
Read-committed consumer stalls despite writes Open transactions, transactional producer failures, last stable offset Resolve the producer or transaction timeout and compare the two isolation levels during diagnosis.

For a backlog of 900,000 offset units with approximately one record per offset, ingress of 2,000/s and sustained processing of 5,000/s, estimated catch-up is 900,000 / (5,000 − 2,000) = 300 seconds. Calculate this per partition too. A single slow partition can determine the finish time, and the estimate assumes stable rates.

7. Move from the laptop to production

Decision Practical starting point and trade-off
Cluster and storage Use a managed service or design separate KRaft controllers and brokers across failure domains. Three voting controllers tolerate one unavailable voter. Configure persistent storage, rack awareness, capacity headroom and an independently tested recovery plan.
Replication and acknowledgement A common three-broker topic configuration is replication factor 3, min.insync.replicas=2, and producer acks=all. With only one in-sync replica left, writes fail. An acknowledgement covers all current in-sync replicas, subject to the configured minimum.
Topic ownership Declare topics, ACLs, retention, partition count and owners in version control. Restrict automatic topic creation. Increasing partitions can remap existing keys for future records, so plan for per-key order during migration.
Security Use TLS with hostname verification and an authentication mechanism supported by your cluster. Give producer, consumer, replay and admin identities the operations they actually need. Restrict topic writes and consumer-group modifications independently. Supply credentials via your runtime secret mechanism.
Retention capacity Estimate compressed ingress bytes/s × retention seconds × replication factor across the cluster. Add space for segments awaiting cleanup, skew, reassignment and failures. Validate the busiest broker and partition.
Monitoring Track offline partitions, under-replicated partitions, under-min-ISR partitions, controller quorum health, broker disk headroom, producer error/latency, consumer lag and event age, rebalance frequency and downstream success. Alert against the time left before retention removes unread data.
Schema and recovery Publish schema evolution rules, sample old records in compatibility tests, preserve archives and rehearse restoring a projection to known partition boundaries. Broker replication alone cannot undo an accidental deletion.

Configuring a secured Java client: merge a mounted Java properties file into base() before creating a producer or consumer. The following snippet goes immediately before return p; and allows the configured cluster to override the local bootstrap address. An operator can reuse the same file with Kafka admin tools using --command-config /path/client.properties where that file is accessible to the CLI process.

JAVA
String file = System.getenv("KAFKA_CLIENT_CONFIG");
if (file != null) {
    try (var in = java.nio.file.Files.newInputStream(java.nio.file.Path.of(file))) {
        p.load(in);
    } catch (java.io.IOException ex) {
        throw new java.io.UncheckedIOException("Cannot read Kafka client configuration", ex);
    }
}
PROPERTIES
# Example shape for a cluster configured for mutual TLS.
bootstrap.servers=broker-a.example:9093,broker-b.example:9093
security.protocol=SSL
ssl.truststore.type=PKCS12
ssl.truststore.location=/run/secrets/kafka-trust.p12

# Supply the store/key passwords in the protected runtime configuration.

For a SASL-authenticated cluster, follow its mechanism-specific settings (for example SASL_SSL with SCRAM or a cloud identity provider). A client-side properties change requires a matching broker listener, certificate trust and identity permissions.

If your service uses Spring Boot

The Kafka semantics above carry across. Spring Boot’s KafkaTemplate wraps the producer and @KafkaListener delegates polling, acknowledgements and rebalances to a listener container. Use the Spring Kafka dependency version managed by your Boot release. A practical mapping for a record listener is spring.kafka.consumer.enable-auto-commit=false and spring.kafka.listener.ack-mode=record. Put the transactional database write inside the handler or a service it calls and let failures propagate to the configured error handler. Review retries and dead-letter recovery explicitly. The container can advance offsets after successful recovery, which matters when rebuilding financial state. A new listener group or an offline CLI reset works on the same broker-side group offsets described above.

8. Check your understanding

  1. You change the live group’s fallback to earliest and restart. Why no replay? Its committed positions are valid, so the fallback is never used.
  2. A fill is written to PostgreSQL and the process dies. What happens? If the Kafka offset commit did not complete, the fill may return. An atomic insert of the fill ID and the corresponding state change makes retry safe.
  3. How do you verify yesterday’s fills without moving today’s consumer? Use a separate reader with explicit partition bounds, filter on business time and disable outbound side effects. Compare both counts and business totals.
  4. Why can a replay report zero lag yet produce the wrong position? Zero lag measures checkpoint progress. It says nothing about skipped records, duplicate effects, rejected schemas or incorrect aggregation.
  5. How do you pause the local lab and keep its data? Run docker compose stop and resume with docker compose start using the same container. Removing the container can discard the lab data.
