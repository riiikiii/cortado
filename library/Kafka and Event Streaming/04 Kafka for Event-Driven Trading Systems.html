Guide 3 of 3 - Streaming architecture

Kafka for Event-Driven Trading Systems

Kafka from first principles, then how to use it in trading: ordering, exactly-once, state, design patterns, latency, resilience, and the limits you must design around.

Written November 2026 against Apache Kafka 4.4 (KRaft only). Config values are starting points, not universal answers: measure on your own workload.

Contents

    Where Kafka fits in a trading stack

    Kafka is a distributed, replicated, append-only log. Producers append records to topics, consumers read them in order at their own pace, and the data stays on disk for as long as you configure. That combination (durable, ordered, replayable, many independent readers) is why it has become the backbone for event-driven systems in finance.

    It is not a low-latency messaging bus. Being clear about that boundary is the most important design decision in this guide.

    ZoneLatency budgetTypical technologyKafka's role

    Order and execution management, pre-trade risk state, smart routing decisions at human or algo-slice speedLow millisecondsIn-memory services with a sequenced journalPossible as the journal if single-digit milliseconds is acceptable. Often a downstream copy.

    Why it earns its place

    • One ordered history of orders and executions that every downstream system reads, instead of point-to-point feeds that each see a slightly different truth.
    • Replay. Rebuild a position service from the day's fills, re-run a risk model on yesterday's flow, reproduce an incident exactly.
    • Decoupling. A slow surveillance consumer cannot back-pressure the order flow. A new consumer can be added without touching producers.
    • Audit. An immutable, timestamped record of what happened and in what order.

    Delete versus compact

    PolicyKeepsUse for
    cleanup.policy=deleteEverything, until it ages out by time or size.Events: orders, fills, ticks.
    cleanup.policy=compactAt least the latest record for every key. A record with a null value (a tombstone) eventually removes the key.Current state: positions, reference data, limits, last quote.
    compact,deleteLatest per key, within a time window.State that should expire, such as intraday keys.

    Compaction runs in the background and never touches the active segment, so a reader of a compacted topic can still see several values for a key. It guarantees the latest value is retained, not that old ones are gone.

    Tiered storage

    Older log segments can be moved to object storage while recent data stays on broker disks. This makes long retention (months or years of order flow for replay) affordable and keeps brokers quick to recover. It does not apply to compacted topics, and reads from the remote tier are slower, so it suits history, not the live path.

    Durability and replication

    Each partition is replicated to several brokers. The leader accepts writes and followers fetch from it. Followers that are caught up form the in-sync replica set (ISR). A record is committed, and visible to consumers, once every in-sync replica has it.

    SettingWhereTrading-grade valueEffect
    replication.factorTopic3 (across three zones or racks)Copies of each partition.
    min.insync.replicasTopic or broker2With acks=all, a write succeeds only if this many replicas have it. Below that, producers get errors instead of silent risk.
    acksProducerallWait for the full ISR before acknowledging.
    unclean.leader.election.enableTopic or brokerfalseNever elect an out-of-date replica as leader. Prefers unavailability to data loss.
    broker.rackBrokerSet to the zoneSpreads replicas across failure domains.

    With RF 3 and min ISR 2 you tolerate one broker (or zone) failure with no loss and no interruption beyond a leader election of a few seconds. A second failure makes the partition read-only until a replica returns. That is the right trade for order and trade data: stop accepting writes before risking divergence.

    What "durable" really means

    By default Kafka acknowledges a write when it is in the page cache of the in-sync replicas, not when it is fsynced. Durability comes from replication across independent machines. A simultaneous power loss of all replicas can lose recent records. That is why replicas must sit in separate failure domains, and why some firms keep a second independent record (a venue drop copy, or a local gateway journal) for the most critical flow.

    Producers

    A producer batches records per partition, optionally compresses the batch, and sends it to the partition leader. The settings below decide your latency, throughput and safety.

    SettingDefaultGuidance for trading flows
    acksallKeep. Never 0 or 1 for orders, fills or positions.
    enable.idempotencetrueKeep. The broker de-duplicates retries using a producer id and sequence number, so retries cannot create duplicates or reorder within a partition.
    max.in.flight.requests.per.connection5Safe up to 5 with idempotence: order is preserved.
    linger.ms5 since Kafka 4.0How long to wait to fill a batch. 0 for lowest latency on thin flows, a few ms for throughput. Under load, batching often lowers tail latency.
    batch.size16 KBRaise (64 to 256 KB) for market data and high-volume topics.
    compression.typenonelz4 or zstd for throughput and storage. Costs a little CPU, saves network and disk.
    delivery.timeout.ms120000Upper bound on send plus retries. Decide deliberately what the application does when it expires.
    transactional.idunsetSet for exactly-once pipelines. Must be stable per logical producer instance.

    The send is asynchronous

    send() returns before the broker has the record. If the process dies, records still in the client buffer are lost. If a business action depends on the event being durable (for example, "do not acknowledge the client until the order event is stored"), wait for the callback or future. If the event describes something that has already happened elsewhere, you need the outbox pattern or a local journal, covered later.

    Consumers and groups

    A consumer polls for batches of records, processes them, and commits the offset it has reached. Committed offsets are stored in Kafka per group, so a restarted or replacement consumer resumes from the last commit.

    The poll loop and commits

    consumer.subscribe(List.of("executions.v1"));
while (running) {
    ConsumerRecords<String, Fill> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, Fill> r : records) {
        handle(r);                         // must be idempotent
    }
    consumer.commitSync();                 // commit AFTER processing: at-least-once
}
    Commit strategyResult
    Auto-commit (the default)Offsets are committed on a timer, regardless of whether processing finished. Can lose or duplicate. Turn it off for anything that matters.
    Commit after processingAt-least-once: a crash between processing and commit replays records. Requires idempotent handling.
    Commit before processingAt-most-once: a crash loses records. Rarely acceptable.
    Offsets stored with the resultEffectively exactly-once: commit the output and the offset atomically, either in a Kafka transaction or in the same database transaction as the state change.

    Rebalancing

    When members join, leave or time out, partitions are reassigned. During reassignment the affected partitions are not being processed, and stateful consumers may need to rebuild state. For a position or risk service this pause is a real latency event.

    • Use the new consumer group protocol (group.protocol=consumer, production-ready since 4.0). Assignment is computed on the broker and applied incrementally, so one member changing no longer stops the whole group. The classic protocol is on its way to deprecation.
    • Static membership (group.instance.id) lets a restarting instance reclaim its partitions without a rebalance, which is what you want for rolling deploys of stateful services.
    • Stay inside max.poll.interval.ms. A handler that blocks too long gets the consumer evicted, its partitions reassigned, and the same slow record handed to the next member. Keep handlers fast, or reduce max.poll.records.
    • Read only committed data when upstream uses transactions: isolation.level=read_committed. The default is read_uncommitted.

    Lag

    Consumer lag (latest offset minus committed offset) is the primary health signal of an event-driven system. Lag measured in time ("this risk view is 4 seconds behind") is more meaningful to the business than lag in records. Alert on it, and decide what each service should do when it is behind: a risk check running on stale positions should know it is stale.

    Share groups (queues)

    Kafka 4.x adds share groups: several consumers read the same partition with per-record acknowledgement, redelivery, a delivery-count limit and, from 4.4, a dead-letter queue. This gives work-queue semantics without sizing partitions to consumer count. The price is no ordering guarantee, so use them for independent tasks (enrichment, notifications, report generation), never for order or fill processing.

    Delivery guarantees and exactly-once

    GuaranteeHowFailure behaviour
    At-most-onceCommit, then process. Or acks=0.Loss.
    At-least-onceIdempotent producer, acks=all, process then commit.Duplicates on retry or rebalance. The normal baseline.
    Exactly-once (within Kafka)Transactions: output records and consumed offsets commit atomically.Neither loss nor duplicates for Kafka-to-Kafka processing.

    How transactions work

    A transactional producer registers a transactional.id with a coordinator and receives an epoch. It writes records to any number of partitions, adds the consumer offsets it has processed, and commits. The coordinator writes commit markers so that read_committed consumers see all of the transaction or none of it. If a second instance starts with the same transactional.id, the epoch is bumped and the old instance is fenced: this is what stops a "zombie" from writing after it has been replaced.

    producer.initTransactions();
while (running) {
    ConsumerRecords<String, Fill> in = consumer.poll(Duration.ofMillis(50));
    if (in.isEmpty()) continue;
    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, Fill> r : in) {
            producer.send(new ProducerRecord<>("positions.deltas.v1", positionKey(r.value()), toDelta(r.value())));
        }
        producer.sendOffsetsToTransaction(nextOffsets(in), consumer.groupMetadata());
        producer.commitTransaction();
    } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException fatal) {
        producer.close();                  // another instance has taken over: stop
        throw fatal;
    } catch (KafkaException retriable) {
        producer.abortTransaction();
        rewindToLastCommitted(consumer);   // reprocess the batch
    }
}

    What exactly-once does not give you

    • It covers Kafka only. A REST call, a FIX message to a venue, an email or a database write inside the loop is not part of the transaction. On retry it happens twice. External effects need their own idempotency key or the outbox pattern.
    • It does not remove upstream duplicates. If a venue resends an execution report, or a producer without idempotence retried, the duplicate is a legitimate record as far as Kafka is concerned. Business-level de-duplication (by execution id, by client order id) is still required.
    • It costs latency. read_committed consumers cannot read past the oldest open transaction, so end-to-end delay includes the transaction's duration. Short, frequent transactions keep this to a few milliseconds. A stalled producer blocks readers of those partitions until it commits or its transaction times out (transaction.timeout.ms).
    • It costs throughput at very small batch sizes because each commit is several round trips.
    Rule of thumb

    Make every consumer idempotent first. Add transactions where a duplicate or a gap in a Kafka-to-Kafka step would be a correctness problem (positions, ledgers, limit usage). Do not rely on transactions as a substitute for idempotency.

    Ordering, keys and partitioning

    Kafka guarantees order within a partition and nothing across partitions. The producer picks the partition by hashing the record key. So the key is your ordering contract: every record that must be seen in sequence relative to another must share a key.

    KeyGuaranteesGood forProblem
    Order idAll events of one order in sequence.Order lifecycle, order state machines.Fills for the same instrument or account arrive unordered relative to each other.
    InstrumentAll activity in one instrument in sequence.Market data, per-instrument books and signals.Heavy skew: a few instruments dominate volume and create hot partitions.
    Account or bookAll activity for one account in sequence.Limits, margin, buying power.Large accounts become hot keys.
    Book + instrumentSequence per position.Position keeping.Account-level aggregates then need another step.

    No single key serves every consumer. The standard answer is to re-key: a small stage reads the stream keyed one way and writes it keyed another way to a new topic, which the next stage consumes. Kafka Streams does this automatically with repartition topics.

    Rules that prevent subtle bugs

    • Changing the partition count breaks the key-to-partition mapping. New records for a key land on a different partition, and ordering relative to old records is lost. Size for growth up front, and if you must change, migrate to a new topic.
    • Do not use null keys where order matters: they spread across partitions.
    • All producers of a topic must use the same partitioner and the same key serialisation. Clients in different languages have had different default hash functions.
    • Global order needs a single partition. That caps throughput at one partition's capacity (still tens of thousands of records per second or more) and one consumer per group. It is a legitimate choice for a low-volume sequenced stream, such as a firm-wide command log.
    • Carry your own sequence. Put a monotonic sequence number from the source (venue sequence, OMS event sequence) in the payload. It lets consumers detect gaps and duplicates, and re-order after a merge.
    • Time is not order. Kafka's timestamp has millisecond resolution and comes from the producer's clock by default. Carry the venue timestamp, the gateway receive timestamp and your own event timestamp in the payload at full precision.

    Sizing partitions

    Partitions set maximum consumer parallelism. More partitions mean more open files, longer leader elections and more end-to-end latency at the margin. Start from the required parallelism at peak (open, close, a volatility event), add headroom, and prefer a moderate number, for example 12 to 48 for busy topics, to hundreds. Test with peak-day replays, not averages.

    Hot keys are handled by design, not by tuning: isolate the hot instrument on its own topic, sub-key where order allows (instrument plus venue), conflate market data before it reaches Kafka, or accept one busy partition and make its consumer fast.

    Topic and event design

    Three kinds of topic

    KindMeaningExamplePolicy
    CommandA request to do something. May be rejected. One logical handler.orders.commands.v1Delete. Short retention is fine once audited elsewhere.
    EventA fact that has happened. Immutable. Many consumers.orders.events.v1, executions.v1Delete, with long retention or tiered storage.

    Name topics by domain and meaning, not by producing application: <domain>.<entity>.<kind>.v<major>. Create them through infrastructure as code with explicit partitions, replication and retention. Disable automatic topic creation.

    • Events are facts in the past tense and carry enough data to be understood alone (event-carried state). Consumers should not have to call back to the producer.
    • Prices and quantities are decimals, as strings or scaled integers. Never binary floating point.
    • Identifiers for idempotency: a unique event id, the business ids (order, execution), and a per-entity sequence.
    • Correlation and causation ids, and trace context in headers, so one order can be followed across services.

    Schemas and evolution

    Use Avro or Protobuf with a schema registry, and enforce compatibility in CI. For long-lived event topics choose FULL or at least BACKWARD compatibility: new fields are optional with defaults, fields are never renamed or re-typed, enum values are only added with a safe default. A breaking change means a new topic version (.v2) and a migration, with both published for a period.

    Replay makes this stricter than in a request-response system: a consumer deployed next year must still read events written today. Upcasting old events on read is a normal part of an event-sourced codebase.

    The central design choice: is Kafka in front of, or behind, the decision?

    Log first (Kafka as the sequencer)Act first (Kafka as the record)
    FlowThe command is written to Kafka. The OMS consumes it in order, decides, and emits events.The OMS decides in memory, sends to the venue, and publishes events afterwards.
    StrengthDeterministic: state is a pure function of the log. Replay and failover are straightforward. Nothing is acted on that is not recorded.Lowest latency. The hot path does not wait on a broker.
    WeaknessAdds a durable Kafka write (milliseconds, with tail risk) to every order.A crash between acting and publishing leaves the log missing a fact. Needs a local journal or outbox and reconciliation.

    Many firms use both: a purpose-built sequenced journal (Aeron Cluster, a replicated in-memory log) for the hot path, bridged into Kafka in order, so that everything after the trade is event-driven on a complete and ordered stream.

    Order state and idempotency

    • Model the order as an explicit state machine (New, PendingNew, Working, PartiallyFilled, Filled, PendingCancel, Cancelled, Rejected, Expired). Reject events that are invalid for the current state, and log them: they indicate reordering or loss.
    • Commands are idempotent by client order id. A retried NewOrder with the same id must not create a second order.
    • Fills are idempotent by venue execution id. Venues resend on reconnect, so de-duplicate at the gateway and again where money is counted.
    • Corrections are new events. A trade bust or price correction is a compensating event that references the original execution. Never edit or delete history.
    • Pre-trade risk is checked in process against in-memory limits and positions built from Kafka, not by a synchronous call through Kafka. Kafka keeps that in-memory state current.

    Handling state

    Events are easy. State (positions, open orders, limit usage, P&L) is where event-driven systems become difficult. The questions to answer for every stateful service are: where does the state live, how is it rebuilt, how long does that take, and how do you know it is right.

    Kafka Streams: a position keeper

    StreamsBuilder b = new StreamsBuilder();

KTable<String, Position> positions = b
    .stream("executions.v1", Consumed.with(Serdes.String(), fillSerde))
    .selectKey((orderId, fill) -> fill.book() + "|" + fill.instrumentId())   // re-key

    .aggregate(
        Position::flat,

            .withValueSerde(positionSerde));

positions.toStream().to("positions.v1", Produced.with(Serdes.String(), positionSerde));

Properties cfg = new Properties();
cfg.put(StreamsConfig.APPLICATION_ID_CONFIG, "position-keeper");
cfg.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);

    Things to know before relying on it:

    • Joins need co-partitioning: both sides keyed the same way with the same partition count.
    • Standby replicas are what make failover fast. Without them a new owner replays the changelog before it can serve.
    • Under exactly-once, a crash used to force a full store rebuild. Kafka 4.4 introduces opt-in transactional state stores that replay only writes since the last commit, which shortens recovery considerably. It is new: test it before production.
    • Changelog and repartition topics are real topics with real cost. Monitor them, and set their replication to 3.
    • Interactive queries expose the local store over your own API, but an instance only holds its own partitions, so you need routing, and reads are eventually consistent.

    Exactly-once into a database

    BEGIN;
  -- skip if already applied (idempotency on the business key)
  INSERT INTO applied_executions (exec_id) VALUES (:execId)
    ON CONFLICT DO NOTHING;
  -- only if the row above was inserted:
  UPDATE positions SET qty = qty + :signedQty, cost = cost + :signedNotional
    WHERE book = :book AND instrument_id = :instrumentId;
  -- progress marker stored with the data
  INSERT INTO consumer_offsets (topic, part, next_offset) VALUES (:t, :p, :o)
    ON CONFLICT (topic, part) DO UPDATE SET next_offset = EXCLUDED.next_offset;
COMMIT;

    On start-up the consumer reads consumer_offsets and seeks to it, ignoring Kafka's committed offsets. State and progress can never disagree.

    Practices that make state trustworthy

    • Deterministic handlers. State must depend only on the events and their embedded timestamps. No wall-clock reads, no random numbers, no lookups to mutable external services inside the fold. Then replay gives the same answer, and two replicas agree.
    • Snapshots. Periodically persist state with the offset it corresponds to. Recovery is load snapshot, then replay the tail. Start-of-day positions plus intraday fills is the same pattern expressed in business terms.
    • A catch-up gate. On start, record the end offsets, consume up to them, and only then declare ready. A risk engine answering from half-loaded positions is worse than one that is down.
    • Staleness is part of the state. Expose "as of" offsets and timestamps with every view. Downstream checks can then refuse, widen limits conservatively or alert when inputs are behind.
    • Reconcile continuously. Compare derived positions with an independent source: the venue or prime broker drop copy, the books and records system. Event-driven state can drift through a bug or a missed correction, and reconciliation is how you find out the same day.
    • Out-of-order and late events. Across partitions and sources there is no order. Use source sequence numbers, buffer briefly where needed, and design aggregates so that a late fill or correction is applied as an adjustment instead of being dropped.
    • Version the logic. If the calculation changes, replaying old events through new code gives different history. Record which version produced each output, and decide explicitly whether to restate.
    • Bound the state. Expire closed orders, roll day-scoped keys with tombstones, and watch store size. Unbounded key growth is the slow failure of stateful stream processors.

    Design patterns

    Event sourcing

    The event log is the source of truth and state is derived. Natural for orders and positions: full audit and replay for free. Costs: schema evolution forever, and eventual consistency for readers.

    CQRS

    One model handles commands and emits events. Separate read models (a blotter, a risk cube, a search index) are built from those events, each shaped for its queries.

    Transactional outbox

    A service writes its state change and an outbox row in one database transaction. A relay (often Debezium CDC) publishes outbox rows to Kafka. Solves "update the database and publish" without distributed transactions.

    Idempotent consumer

    Every handler tolerates seeing a record twice: de-duplicate on a business key, use upserts, or store offsets with results. The foundation everything else rests on.

    Single writer

    Exactly one service instance owns and writes each entity or key. Removes concurrent-update conflicts. Kafka's partition assignment plus fencing enforces it.

    Saga

    A multi-step business process (order, allocate, confirm, settle) as a chain of local steps with compensating actions. Choreographed through events, or orchestrated by a coordinator that owns the state machine.

    Snapshot plus delta

    Publish a full state periodically and changes in between, with sequence numbers linking them. The standard market-data and position-feed shape. A compacted topic plus an event topic is the Kafka form.

    Claim check

    Store a large payload (a risk report, a document) in object storage and send a reference through Kafka. Keeps records small and brokers fast.

    Errors, retries and dead letters

    A record that cannot be processed (a "poison pill") blocks its partition if you retry forever, and breaks ordering if you skip it. Decide per topic:

    StrategyOrderingUse when
    Retry in place with backoff, then halt and alertPreservedOrder matters and gaps are unacceptable: fills into positions. A stopped partition is the correct outcome, with a human decision.
    Dead-letter topic: park the record and continueBroken for that keyRecords are independent, or the bad record can be repaired and re-applied as an adjustment.
    Retry topics with delaysBrokenFailures are transient and order is irrelevant: notifications, enrichment.
    Park the key: divert all later records for a failed key until it is fixedPreserved per keyYou need both progress and per-key order. More machinery.

    Distinguish deserialisation and validation failures (permanent: dead-letter with full context) from dependency failures (transient: retry, do not dead-letter a healthy record because a database was down).

    Patterns to avoid

    • Request-reply over Kafka for synchronous needs. Use gRPC or an in-process call, and let Kafka carry the resulting facts.
    • Dual writes: writing to a database and to Kafka separately and hoping both succeed.
    • A shared "everything" topic with mixed event types, keys and schemas.
    • Using Kafka as a queryable database. There is no lookup by key. Materialise a view.

    Market data on Kafka

    Kafka is a good distribution layer for market data to everything that does not need it in microseconds: risk, P&L, analytics, surveillance, research capture. It is the wrong transport between a feed handler and a strategy.

    • Normalise at the edge. Feed handlers decode venue formats and publish a common schema, keyed by instrument, with venue sequence numbers and timestamps preserved.
    • Separate topics by purpose and rate: trades, top-of-book quotes, depth, and a conflated stream (for example, latest quote per instrument at a fixed interval). Most consumers want the conflated one.
    • Last value cache: a compacted topic keyed by instrument gives any late joiner the current quote for every instrument by reading it from the start.
    • Throughput settings: larger batches, a few milliseconds of linger, lz4 or zstd, compact binary encoding. Per-record overhead dominates with small ticks.
    • Slow consumers fall behind instead of slowing the producer. For pricing, old ticks are worthless: a lagging consumer should skip to the latest offset or switch to the conflated stream, and say so.
    • Skew is extreme. Opening and closing auctions, index rebalances and news produce bursts many times the average, concentrated in few instruments. Capacity-test with recorded peak days.
    • Joins against trades ("what was the mid when this fill happened") need event-time semantics and a bounded wait for late quotes. Versioned state stores or Flink temporal joins exist for this.

    Latency and tuning

    With acks=all and three replicas in one region, a well-run cluster typically delivers produce-to-consume latency in the low single-digit milliseconds at the median and tens of milliseconds at the 99th percentile, with occasional excursions into hundreds of milliseconds during leader elections, rebalances or garbage collection. Treat those as orders of magnitude and measure your own. The tail, not the median, is what decides where Kafka can sit.

    Multi-site and disaster recovery

    ModelHowData loss on site failureCost
    Stretch clusterOne cluster across three zones or nearby data centres, synchronous replication.None for committed records.Needs low, stable latency between sites. A third site for quorum. Every write pays the inter-site round trip.
    Active-passive mirroringA second cluster fed asynchronously (MirrorMaker 2 or a vendor's cluster linking).The replication lag: usually well under a second, never zero.Failover is a procedure. Offsets differ between clusters and must be translated. Consumers may see duplicates or a small gap.
    Active-active mirroringBoth sites take writes and mirror to each other, with topic naming that prevents loops.The lag, per site.Consumers must merge two streams with no order between them. Conflicts are an application problem.

    For order and trade data the usual combination is a stretch cluster across zones within a metro area for zero-loss resilience, plus asynchronous mirroring to a distant region for disaster recovery, accepting a small recovery point that is closed by reconciliation against venue and broker records.

    Failover is an application concern too

    • After an asynchronous failover, the surviving log may be missing the last moments of flow. Request resends from venues (FIX sequence reset and resend, drop copies) and reconcile open orders and positions before resuming.
    • Stateful consumers must rebuild from the surviving cluster's data, not carry over state that reflects records the new cluster never received.
    • Rehearse it. An untested failover is a hypothesis. Run it on a schedule, including failing back.
    • Kafka is not a backup. Mirroring replicates mistakes instantly. Keep an independent archive of critical topics in immutable object storage.

    Security, audit and compliance

    • Authentication: mutual TLS or SASL (OAuth bearer tokens, SCRAM). One identity per service, never shared.
    • Authorisation: ACLs per topic and consumer group, least privilege. Only the owning service may write to an event topic. Transactional ids and group ids are protected resources too.
    • Encryption: TLS in transit. Disk encryption at rest. Field-level encryption for client identifiers or personal data, which also gives you a route to erasure by deleting keys.
    • Quotas per client so a replay or runaway producer cannot affect order flow.
    • Segregation: separate clusters, or strictly separated topics and principals, across information barriers.
    • Record keeping: regimes such as MiFID II require order and transaction records to be retained for years, in a form that cannot be altered. Kafka's log supports the audit trail but should not be the only copy: archive critical topics to write-once storage with integrity checks, and make sure the archive can be replayed and queried.
    • Clock discipline: regulators expect business timestamps traceable to UTC at fine granularity. Synchronise hosts (PTP where needed) and stamp events at source.
    • Lineage: correlation and causation ids let you reconstruct, for any order, every decision and every system that touched it.

    Testing

    • Unit: test stream topologies with TopologyTestDriver, and handlers as pure functions of events.
    • Integration: real brokers through Testcontainers, including the schema registry.
    • Replay tests: feed a recorded production day through a new build and compare outputs with the previous build. This is the highest-value test an event-driven trading system can have, and determinism is what makes it possible.
    • Failure injection: kill brokers, consumers and producers mid-transaction. Partition the network. Verify no loss and no duplicates in the business outputs, not just in Kafka.
    • Peak load: replay the busiest open and close on record at a multiple of real speed. Watch tail latency and lag.
    • Contract tests: schema compatibility as a build gate.
    • Operational drills: rolling upgrade, partition reassignment, full state rebuild, site failover, each timed.

    Running it

    Options range from self-managed (on machines, or on Kubernetes with the Strimzi operator) to managed services such as Amazon MSK and Confluent Cloud. Self-managing buys control over latency, placement and versions at the price of expertise. Either way: dedicate clusters to critical flow, automate topic and ACL management, keep client libraries current, and upgrade regularly.

    Best practices and anti-patterns

    • Kafka sits behind the hot path, or in front only where milliseconds are acceptable.
    • Critical topics: RF 3, min ISR 2, acks=all, idempotent producers, unclean election off, replicas in separate failure domains.
    • The key of every topic is a documented ordering contract. Partition counts are sized for peak and not changed in place.
    • Commands, events and state live in separate topics. Events are immutable, past-tense and self-describing.
    • Schemas are registered, compatibility is enforced, money is decimal.
    • Every consumer is idempotent on a business key. Transactions are added where gaps or duplicates between Kafka topics would be incorrect.
    • External side effects use idempotency keys or an outbox. No dual writes.
    • Every stateful service has a defined rebuild path, a measured recovery time, snapshots, a catch-up gate and an "as of" marker.
    • Handlers are deterministic. Recorded days can be replayed through new builds.
    • Derived state is reconciled against an independent source every day.
    • Each topic has an explicit poison-record policy. Dead letters are monitored and owned.
    • Lag is alerted on in time units. Stale consumers know they are stale.
    • Source timestamps and sequence numbers are carried in the payload at full precision.
    • Critical and bulk traffic are isolated by cluster or quota.
    • Failover and full rebuild are rehearsed, timed and documented.
    • Critical topics are archived to immutable storage independent of the cluster.

    Anti-patterns

    • Kafka between market data and order placement in a latency-sensitive strategy.
    • Auto-commit on a consumer that books trades.
    • Assuming exactly-once covers the database or the venue.
    • Null or random keys on ordered flows.
    • Increasing partitions on a keyed topic in production.
    • Retry topics on order-dependent flows.
    • Skipping a bad fill to keep the pipeline moving, with no adjustment path.

    More anti-patterns

    • One giant topic for all event types.
    • Synchronous request-reply tunnelled through topics.
    • State that can only be rebuilt by replaying years of history.
    • Floating-point prices.
    • Wall-clock time inside aggregation logic.
    • Treating mirroring as backup.
    • Monitoring broker health but not consumer lag or reconciliation.

    Version notes for the 4.x line

    ChangeWhat it means for you
    ZooKeeper removed (4.0)KRaft is the only metadata mode. Clusters still on ZooKeeper must migrate on 3.9 before upgrading. Old tooling flags that pointed at ZooKeeper are gone.
    New consumer group protocol (4.0)Broker-driven, incremental rebalances. Opt in with group.protocol=consumer. The classic protocol is being steered towards deprecation.
    Java baseline raised (4.0)Brokers and tools need Java 17, clients and Streams Java 11. Very old clients and message formats are no longer supported.
    Stronger transaction protocol (4.0)Server-side defences against hanging and zombie transactions. Upgrade clients to benefit fully.
    linger.ms default is 5 (4.0)Producers batch slightly by default. Set it explicitly on latency-critical producers.
    Share groups / queues (4.x)Queue semantics with per-record acknowledgement. 4.4 adds dead-letter queues for them.
    Streams rebalance protocol (4.x)Kafka Streams gains the same broker-side assignment as consumers, with broker-side custom assignors arriving in 4.4.
    Transactional state stores (4.4, opt-in)Under exactly-once, recovery replays only uncommitted writes instead of rebuilding the store.
    Tiered storage refinements (4.3, 4.4)Followers can bootstrap from the tiered offset, and uploads can be delayed to cut redundant storage.
    Deprecations heading for 5.0The streams-scala module, old MirrorMaker metric names and the broker.id config are deprecated. Plan to move off them.

    Release cadence is roughly three feature releases a year. Read the upgrade notes for every version you cross, upgrade brokers before clients, and keep clients within a few versions of the brokers so that new protocol features and fixes actually apply to you.
