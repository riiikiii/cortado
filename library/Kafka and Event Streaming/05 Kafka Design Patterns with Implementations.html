Kafka Design Patterns, Explained and Implemented

Eighteen patterns for event-driven trading systems. Each one with the problem it solves, how it works, a worked Java implementation, the pitfalls, and when to use it.

    Idempotent consumer

    Problem

    Kafka's normal guarantee is at-least-once. A consumer that crashes after processing but before committing sees the record again. Rebalances, producer-side resends from upstream systems and operator replays all cause redelivery. If applying a fill twice doubles a position, the system is wrong.

    How it works

    Make the effect of processing a record the same whether it happens once or several times. There are three techniques, in order of preference:

    1. Naturally idempotent operations: set a value instead of adding to it, upsert by key.
    2. De-duplicate on a business identifier: remember which execution ids have been applied, in the same transaction as the effect.
    3. Sequence high-water mark: if each key carries a monotonic sequence, remember the last one applied and ignore anything at or below it.

    Implementation: de-duplication table in the same transaction

    CREATE TABLE applied_executions (
  exec_id     text PRIMARY KEY,
  applied_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE positions (
  book text, instrument_id text, qty bigint NOT NULL, cost numeric NOT NULL,
  PRIMARY KEY (book, instrument_id)
);
    void apply(Connection db, Fill f) throws SQLException {
    db.setAutoCommit(false);
    try (var dedupe = db.prepareStatement(
             "INSERT INTO applied_executions (exec_id) VALUES (?) ON CONFLICT DO NOTHING");
         var upsert = db.prepareStatement("""
             INSERT INTO positions (book, instrument_id, qty, cost) VALUES (?, ?, ?, ?)
             ON CONFLICT (book, instrument_id)
             DO UPDATE SET qty = positions.qty + EXCLUDED.qty, cost = positions.cost + EXCLUDED.cost""")) {

        dedupe.setString(1, f.execId());
        boolean firstTime = dedupe.executeUpdate() == 1;
        if (firstTime) {                               // duplicate: skip the effect, still commit
            upsert.setString(1, f.book());
            upsert.setString(2, f.instrumentId());
            upsert.setLong(3, f.signedQty());
            upsert.setBigDecimal(4, f.px().multiply(BigDecimal.valueOf(f.signedQty())));
            upsert.executeUpdate();
        }
        db.commit();
    } catch (SQLException e) {
        db.rollback();
        throw e;
    }
}

    Implementation: sequence high-water mark

    When the source assigns a gap-free sequence per key, no table of ids is needed. This also detects loss.

    final Map<String, Long> lastSeq = new HashMap<>();     // rebuilt with the state it guards

void onDelta(String key, PositionDelta d) {
    long last = lastSeq.getOrDefault(key, 0L);
    if (d.seq() <= last) return;                        // duplicate or replay: ignore
    if (d.seq() != last + 1) throw new GapDetected(key, last, d.seq());   // loss: resync
    applyDelta(key, d);
    lastSeq.put(key, d.seq());
}

    Pitfalls

    • The de-duplication record and the effect must commit atomically. A separate "have I seen this" lookup followed by a write is a race.
    • Choose the identifier carefully. Kafka offsets identify a delivery, not a business fact: the same fill resent by a venue has a new offset. Use the execution id.
    • The de-duplication store grows forever unless pruned. Keep ids for longer than any possible replay window (often a trading day plus margin) and delete older ones.
    • Side effects outside the transaction (an email, a FIX message) are not covered. Give them their own idempotency key, or route them through an outbox.

    Use when

    Always. Every other pattern in this guide assumes consumers are idempotent.

    Transactional outbox

    Problem

    A service must change its own database and publish an event about it. Writing to both separately (a dual write) fails in the gap: the database commits and the publish fails, or the reverse. There is no transaction spanning a database and Kafka.

    How it works

    Write the event into an outbox table in the same local transaction as the state change. A separate relay reads the outbox and publishes to Kafka. The event is published if and only if the state change committed. Delivery is at-least-once, so consumers de-duplicate on the event id.

        db.rollback();
        throw e;
    }
}

    Implementation: polling relay

    Simpler to run where CDC is not available. Run exactly one active instance so that order is preserved.

    void relayOnce(Connection db, KafkaProducer<String, String> producer) throws Exception {
    db.setAutoCommit(false);
    List<Future<RecordMetadata>> acks = new ArrayList<>();
    List<UUID> sent = new ArrayList<>();
    try (var q = db.prepareStatement(
            "SELECT id, aggregateid, type, payload FROM outbox ORDER BY created_at, id LIMIT 500 FOR UPDATE");
         var rs = q.executeQuery()) {
        while (rs.next()) {
            var rec = new ProducerRecord<>("orders.events.v1", rs.getString("aggregateid"), rs.getString("payload"));
            rec.headers().add("eventId", rs.getString("id").getBytes(UTF_8));
            rec.headers().add("eventType", rs.getString("type").getBytes(UTF_8));
            acks.add(producer.send(rec));
            sent.add((UUID) rs.getObject("id"));
        }
    }
    for (var ack : acks) ack.get(10, TimeUnit.SECONDS);    // all durable before deleting
    try (var del = db.prepareStatement("DELETE FROM outbox WHERE id = ANY (?)")) {
        del.setArray(1, db.createArrayOf("uuid", sent.toArray()));
        del.executeUpdate();
    }
    db.commit();        // a crash before this re-sends the batch: duplicates, never loss
}

    Pitfalls

    • Delivery is at-least-once. Carry the outbox id as the event id and de-duplicate downstream.
    • Ordering with a poller depends on a single relay and a stable sort. Rows committed out of timestamp order by concurrent transactions can be published out of order across aggregates. Per-aggregate order holds if each aggregate has a single writer. CDC avoids the issue by following commit order.
    • The outbox must be emptied or pruned. With CDC, delete rows immediately after insert (the log still contains them) or prune on a schedule.
    • Latency is the relay's lag: milliseconds with CDC, the polling interval otherwise.
    • CDC needs care: a replication slot that is not consumed retains WAL and can fill the database disk. Monitor it.

    Use when

    The service's source of truth is a database and other services need to hear about changes. The mirror image, for consuming, is the inbox: the idempotent consumer table from the previous section.

    Transactional consume-transform-produce

    Problem

    A stage reads records from one topic, computes results and writes them to another. A crash between writing output and committing the input offset produces duplicates. A crash the other way round loses output.

    How it works

    A Kafka transaction makes the output records and the consumed offsets commit together. Downstream consumers using read_committed see the output only if the offsets moved too. A replacement instance with the same group is protected from a lingering predecessor by fencing.

    Implementation

    final class FillToDeltaStage implements Runnable, ConsumerRebalanceListener {
    private final KafkaConsumer<String, Fill> consumer;       // read_committed, auto-commit off
    private final KafkaProducer<String, PositionDelta> producer;   // transactional.id set, unique per instance
    private volatile boolean running = true;

    public void run() {
        producer.initTransactions();                           // fences any previous holder of this id
        consumer.subscribe(List.of("executions.v1"), this);
        while (running) {
            ConsumerRecords<String, Fill> batch = consumer.poll(Duration.ofMillis(50));
            if (batch.isEmpty()) continue;

            producer.beginTransaction();
            try {
                Map<TopicPartition, OffsetAndMetadata> next = new HashMap<>();
                for (ConsumerRecord<String, Fill> r : batch) {
                    Fill f = r.value();
                    producer.send(new ProducerRecord<>("positions.deltas.v1", f.positionKey(), PositionDelta.of(f)));
                    next.put(new TopicPartition(r.topic(), r.partition()), new OffsetAndMetadata(r.offset() + 1));
                }
                producer.sendOffsetsToTransaction(next, consumer.groupMetadata());
                producer.commitTransaction();
            } catch (ProducerFencedException | OutOfOrderSequenceException | AuthorizationException fatal) {
                running = false;                               // we have been replaced: stop, do not abort
                throw fatal;
            } catch (KafkaException e) {
                producer.abortTransaction();
                rewind();                                      // reprocess from the last committed offsets
            }
        }
    }

    private void rewind() {
        Map<TopicPartition, OffsetAndMetadata> committed = consumer.committed(consumer.assignment());
        for (TopicPartition tp : consumer.assignment()) {
            OffsetAndMetadata o = committed.get(tp);
            if (o != null) consumer.seek(tp, o.offset()); else consumer.seekToBeginning(List.of(tp));
        }
    }

    public void onPartitionsRevoked(Collection<TopicPartition> parts) { }   // nothing is buffered between polls
    public void onPartitionsAssigned(Collection<TopicPartition> parts) { }
}

    In Kafka Streams the whole pattern is one setting, processing.guarantee=exactly_once_v2, which also covers state stores.

    Pitfalls

    • The transformation must be free of external side effects. Anything outside Kafka runs again on retry.
    • Output is invisible to read_committed readers until commit, so transaction duration is added to end-to-end latency. Commit per poll, with small polls, for latency-sensitive flows.
    • One transaction per record is expensive. One transaction per batch is the normal unit.
    • A poison record aborts the whole batch repeatedly. Combine with an error-handling pattern from later sections.
    • Downstream consumers left on the default read_uncommitted will see aborted output.

    Use when

    A Kafka-to-Kafka step where a duplicate or a gap would be a correctness error: deriving position deltas, ledger postings, limit utilisation.

    Offsets stored with state

    Problem

    The consumer's output is a database, not a Kafka topic. Kafka transactions cannot include the database, so committing offsets to Kafka and committing data to the database are again two separate writes.

    How it works

    Stop using Kafka's committed offsets as the record of progress. Store the next offset to read in the database, in the same transaction as the data. On start or reassignment, seek to the stored offset. Data and progress can never disagree, which gives exactly-once into the database.

    Implementation

    CREATE TABLE consumer_progress (
  consumer text, topic text, part int, next_offset bigint NOT NULL,
  PRIMARY KEY (consumer, topic, part)
);
    final class PositionSink implements ConsumerRebalanceListener {
    private static final String NAME = "position-sink";
    private final KafkaConsumer<String, Fill> consumer;
    private final DataSource ds;

    void run() throws SQLException {
        consumer.subscribe(List.of("executions.v1"), this);
        while (true) {
            ConsumerRecords<String, Fill> batch = consumer.poll(Duration.ofMillis(100));
            if (batch.isEmpty()) continue;
            try (Connection db = ds.getConnection()) {
                db.setAutoCommit(false);
                try {
                    for (TopicPartition tp : batch.partitions()) {
                        List<ConsumerRecord<String, Fill>> recs = batch.records(tp);
                        for (ConsumerRecord<String, Fill> r : recs) upsertPosition(db, r.value());
                        saveProgress(db, tp, recs.get(recs.size() - 1).offset() + 1);
                    }
                    db.commit();                                // data and offsets together
                } catch (SQLException e) {
                    db.rollback();
                    seekToStored(consumer.assignment());        // re-read the batch
                }
            }
        }
    }

    public void onPartitionsAssigned(Collection<TopicPartition> parts) {
        seekToStored(parts);                                    // the database decides where to start
    }
    public void onPartitionsRevoked(Collection<TopicPartition> parts) { }

    private void seekToStored(Collection<TopicPartition> parts) {
        try (Connection db = ds.getConnection();
             var q = db.prepareStatement(
                 "SELECT next_offset FROM consumer_progress WHERE consumer = ? AND topic = ? AND part = ?")) {
            for (TopicPartition tp : parts) {
                q.setString(1, NAME); q.setString(2, tp.topic()); q.setInt(3, tp.partition());
                try (var rs = q.executeQuery()) {
                    if (rs.next()) consumer.seek(tp, rs.getLong(1));
                    else consumer.seekToBeginning(List.of(tp));
                }
            }
        } catch (SQLException e) { throw new IllegalStateException(e); }
    }

    private void saveProgress(Connection db, TopicPartition tp, long next) throws SQLException {
        try (var up = db.prepareStatement("""
                INSERT INTO consumer_progress (consumer, topic, part, next_offset) VALUES (?, ?, ?, ?)
                ON CONFLICT (consumer, topic, part) DO UPDATE SET next_offset = EXCLUDED.next_offset
                WHERE consumer_progress.next_offset < EXCLUDED.next_offset""")) {
            up.setString(1, NAME); up.setString(2, tp.topic()); up.setInt(3, tp.partition()); up.setLong(4, next);
            up.executeUpdate();
        }
    }
}

    Pitfalls

    • Lag tooling that reads Kafka's committed offsets shows nothing useful. Either also commit to Kafka after the database commit, purely for monitoring, or export lag from the table.
    • During a rebalance the previous owner may still be mid-transaction. The guarded update on next_offset stops a stale owner moving progress backwards, but for strict safety add fencing (the single-writer pattern below).
    • Batch size sets the trade-off between throughput and how much is redone after a failure.
    • Resetting a consumer now means editing a table, so build a small admin command for it.

    Use when

    Kafka into a transactional store: positions in Postgres, a ledger, a read model that must be exact. If the sink cannot hold offsets transactionally, fall back to the idempotent consumer.

    Event sourcing

    Problem

    Storing only current state throws away how it got there. For orders you need the full history for audit, for debugging and for rebuilding downstream views, and you need state to be reproducible.

    How it works

    The ordered list of events for an entity is its state. Two pure functions define the entity:

    • decide(state, command) returns the new events, or a rejection. It contains the business rules.
    • evolve(state, event) returns the next state. It contains no rules and never fails.

    Current state is the fold of evolve over the events. Handling a command means: load state, decide, append events. On Kafka, commands and events are keyed by order id and co-partitioned, so the instance that owns a command partition is the only writer of the matching event partition.

    Implementation: the aggregate

    sealed interface OrderCommand { String orderId(); }
record NewOrder(String orderId, String clOrdId, String instrumentId, Side side, long qty) implements OrderCommand { }
record CancelOrder(String orderId) implements OrderCommand { }
record ReportFill(String orderId, String execId, long qty, BigDecimal px) implements OrderCommand { }

sealed interface OrderEvent { String orderId(); long seq(); }
record OrderAccepted(String orderId, String clOrdId, long qty, long seq) implements OrderEvent { }
record OrderRejected(String orderId, String reason, long seq) implements OrderEvent { }
record OrderFilled(String orderId, String execId, long lastQty, BigDecimal lastPx, long cumQty, long seq) implements OrderEvent { }
record OrderCancelled(String orderId, long leavesQty, long seq) implements OrderEvent { }

enum Status { NONE, WORKING, FILLED, CANCELLED, REJECTED }

record OrderState(Status status, long qty, long cumQty, long seq, Set<String> execIds) {
    static final OrderState EMPTY = new OrderState(Status.NONE, 0, 0, 0, Set.of());

    OrderState evolve(OrderEvent e) {                   // no rules, no failures
        return switch (e) {
            case OrderAccepted a  -> new OrderState(Status.WORKING, a.qty(), 0, a.seq(), Set.of());
            case OrderRejected r  -> new OrderState(Status.REJECTED, qty, cumQty, r.seq(), execIds);
            case OrderFilled f    -> new OrderState(f.cumQty() == qty ? Status.FILLED : Status.WORKING,
                                         qty, f.cumQty(), f.seq(), plus(execIds, f.execId()));
            case OrderCancelled c -> new OrderState(Status.CANCELLED, qty, cumQty, c.seq(), execIds);
        };
    }

    List<OrderEvent> decide(OrderCommand c) {           // all the rules
        long next = seq + 1;
        return switch (c) {
            case NewOrder n when status != Status.NONE -> List.of();            // duplicate command
            case NewOrder n when n.qty() <= 0 -> List.of(new OrderRejected(n.orderId(), "bad quantity", next));
            case NewOrder n -> List.of(new OrderAccepted(n.orderId(), n.clOrdId(), n.qty(), next));
            case ReportFill f when execIds.contains(f.execId()) -> List.of();   // duplicate fill
            case ReportFill f when status != Status.WORKING || cumQty + f.qty() > qty ->
                throw new PermanentException();                                  // impossible: investigate
            case ReportFill f -> List.of(new OrderFilled(f.orderId(), f.execId(), f.qty(), f.px(), cumQty + f.qty(), next));
            case CancelOrder x when status != Status.WORKING -> List.of();      // nothing to cancel
            case CancelOrder x -> List.of(new OrderCancelled(x.orderId(), qty - cumQty, next));
        };
    }
    private static Set<String> plus(Set<String> s, String v) { var n = new HashSet<>(s); n.add(v); return Set.copyOf(n); }
}

    Implementation: the command handler

    final class OrderCommandHandler implements ConsumerRebalanceListener {
    private final KafkaConsumer<String, OrderCommand> commands;        // orders.commands.v1
    private final KafkaProducer<String, OrderEvent> producer;          // transactional
    private final Supplier<KafkaConsumer<String, OrderEvent>> eventReader;
    private final Map<Integer, Map<String, OrderState>> stateByPartition = new HashMap<>();

    public void onPartitionsAssigned(Collection<TopicPartition> parts) {
        for (TopicPartition tp : parts)                               // rehydrate from the event log
            stateByPartition.put(tp.partition(), rebuild(new TopicPartition("orders.events.v1", tp.partition())));
    }
    public void onPartitionsRevoked(Collection<TopicPartition> parts) {
        parts.forEach(tp -> stateByPartition.remove(tp.partition()));
    }

    private Map<String, OrderState> rebuild(TopicPartition events) {
        Map<String, OrderState> state = new HashMap<>();
        try (KafkaConsumer<String, OrderEvent> reader = eventReader.get()) {   // read_committed
            reader.assign(List.of(events));
            reader.seekToBeginning(List.of(events));                  // or seek to a snapshot offset
            long end = reader.endOffsets(List.of(events)).get(events);
            while (reader.position(events) < end)
                for (ConsumerRecord<String, OrderEvent> r : reader.poll(Duration.ofMillis(200)))
                    state.merge(r.key(), OrderState.EMPTY.evolve(r.value()), (old, x) -> old.evolve(r.value()));
        }
        return state;
    }

    void run() {
        producer.initTransactions();
        commands.subscribe(List.of("orders.commands.v1"), this);
        while (true) {
            ConsumerRecords<String, OrderCommand> batch = commands.poll(Duration.ofMillis(20));
            if (batch.isEmpty()) continue;
            Map<Integer, Map<String, OrderState>> pending = new HashMap<>();   // applied only on commit
            Map<TopicPartition, OffsetAndMetadata> next = new HashMap<>();
            producer.beginTransaction();
            try {
                for (ConsumerRecord<String, OrderCommand> r : batch) {
                    var live = stateByPartition.get(r.partition());
                    var staged = pending.computeIfAbsent(r.partition(), p -> new HashMap<>());
                    OrderState s = staged.getOrDefault(r.key(), live.getOrDefault(r.key(), OrderState.EMPTY));
                    for (OrderEvent e : s.decide(r.value())) {
                        // same partition number as the command: keeps the two topics co-partitioned
                        producer.send(new ProducerRecord<>("orders.events.v1", r.partition(), r.key(), e));
                        s = s.evolve(e);
                    }
                    staged.put(r.key(), s);
                    next.put(new TopicPartition(r.topic(), r.partition()), new OffsetAndMetadata(r.offset() + 1));
                }
                producer.sendOffsetsToTransaction(next, commands.groupMetadata());
                producer.commitTransaction();
                pending.forEach((p, m) -> stateByPartition.get(p).putAll(m));
            } catch (ProducerFencedException fenced) {
                throw fenced;
            } catch (KafkaException e) {
                producer.abortTransaction();                          // in-memory state untouched
                rewindToCommitted(commands);
            }
        }
    }
}

    Pitfalls

    • Events are forever. Old events must remain readable by new code. Add fields with defaults, never repurpose one, and upcast old versions on read.
    • Rehydration time grows. Take snapshots (state plus the offset it reflects) and replay only the tail. Remove terminal orders from memory.
    • Never put rules in evolve. If replaying history can throw, the entity can become unloadable.
    • Fixing mistakes means new events (a correction, a bust), not edits.
    • Readers are eventually consistent. A query straight after a command may not see it yet. Return the event sequence to the caller so it can wait for its read model to reach it.
    • Commands and events topics must have the same partition count, permanently.

    Use when

    Entities with a meaningful lifecycle and audit needs: orders, allocations, positions, limits. Avoid it for simple reference data where current state is all anyone wants.

    CQRS read models

    Problem

    The event log is ideal for writing and useless for querying. A blotter wants orders by trader and status, risk wants exposure by book, compliance wants search by client. No single model serves all of them.

    How it works

    Separate the write model (the event-sourced aggregate, or any service that emits events) from any number of read models. Each read model is a projection: a consumer that folds events into a store shaped for one set of queries. Read models are disposable. To change one, build a new version from the start of the log and switch over.

    Rebuilding a read model

    1. Create the new table (_v3) and deploy the new projector with a new group id and auto.offset.reset=earliest.
    2. Let it catch up while the old version keeps serving.
    3. Switch the query API to the new table once lag is near zero, then retire the old projector and table.

    Pitfalls

    • Staleness is inherent. Expose the last applied event time or sequence with query results, and alert on projector lag.
    • Projections must be idempotent (the last_seq guard above), because rebuilds and retries replay events.
    • Rebuild cost depends on retention. If the event topic does not keep full history, the read model needs a snapshot source.
    • Do not let read models write back to the entity. Commands go to the write model.
    • One projector per read model. Sharing one consumer for several stores couples their failure and rebuild.

    Use when

    More than one query shape over the same facts, or read load that should not touch the write path. It pairs naturally with event sourcing but does not require it.

    Single writer with fencing

    Problem

    If two instances act for the same order or position at once, they interleave updates and corrupt state. The dangerous case is the "zombie": an instance that paused (long GC, network stall), was replaced, then resumed without knowing.

    How it works

    Assign every entity to exactly one writer, and make it impossible for a stale writer to have any effect. Kafka provides the assignment: a key maps to one partition, and a partition is owned by one member of a consumer group. Fencing provides the enforcement: each new owner obtains a higher fencing token, and every write is rejected unless it carries the current token.

    • Writes to Kafka are fenced for you when using transactions: a stale producer gets ProducerFencedException, and a commit from a stale group generation is refused.
    • Writes elsewhere (a database, a venue session) need an explicit token check.

    Implementation: fencing external writes

    final class VenueSender implements ConsumerRebalanceListener {
    private final Map<TopicPartition, Long> myEpoch = new ConcurrentHashMap<>();
    private final String instanceId = UUID.randomUUID().toString();
    private final DataSource ds;

    public void onPartitionsAssigned(Collection<TopicPartition> parts) {
        for (TopicPartition tp : parts) myEpoch.put(tp, claim(tp));   // take ownership, bump the token
    }
    public void onPartitionsRevoked(Collection<TopicPartition> parts) { parts.forEach(myEpoch::remove); }
    public void onPartitionsLost(Collection<TopicPartition> parts)    { parts.forEach(myEpoch::remove); }

    private long claim(TopicPartition tp) {
        try (Connection db = ds.getConnection(); var q = db.prepareStatement("""
                INSERT INTO partition_owner (topic, part, epoch, owner) VALUES (?, ?, 1, ?)
                ON CONFLICT (topic, part) DO UPDATE SET epoch = partition_owner.epoch + 1, owner = EXCLUDED.owner
                RETURNING epoch""")) {
            q.setString(1, tp.topic()); q.setInt(2, tp.partition()); q.setString(3, instanceId);
            try (var rs = q.executeQuery()) { rs.next(); return rs.getLong(1); }
        } catch (SQLException e) { throw new IllegalStateException(e); }
    }

    /** Records the intent to send. Fails if this instance is no longer the owner. */
    void enqueueOutbound(TopicPartition tp, String clOrdId, String fixMessage) throws SQLException {
        try (Connection db = ds.getConnection(); var ins = db.prepareStatement("""
                INSERT INTO venue_outbound (cl_ord_id, fix_message, owner_epoch)
                SELECT ?, ?, ?
                 WHERE EXISTS (SELECT 1 FROM partition_owner WHERE topic = ? AND part = ? AND epoch = ?)
                ON CONFLICT (cl_ord_id) DO NOTHING""")) {
            long epoch = myEpoch.get(tp);
            ins.setString(1, clOrdId); ins.setString(2, fixMessage); ins.setLong(3, epoch);
            ins.setString(4, tp.topic()); ins.setInt(5, tp.partition()); ins.setLong(6, epoch);
            if (ins.executeUpdate() == 0 && !alreadyQueued(db, clOrdId))
                throw new FencedException(tp, epoch);                  // a newer owner exists: stop
        }
    }
}

    The token check and the write are one statement, so there is no window between "am I still the owner" and "write". The unique cl_ord_id adds idempotency on top.

    Pitfalls

    • A check followed by a separate write is not fencing. The pause can happen between them. The resource being written must enforce the token.
    • Leases and timeouts alone are unsafe: a paused process cannot know its lease expired.
    • Systems that cannot check a token (many external venues) need a different guard: a single connection per session id, enforced by the counterparty, plus idempotent client order ids.
    • Hot keys cannot be scaled out under single writer. That is the price of the guarantee.

    Use when

    Any stateful entity with invariants: order state, limit usage, sequence generation, a venue session.

    Re-keying

    Problem

    Fills are keyed by order id so that an order's events stay in sequence. The position keeper needs every fill for a book and instrument in sequence, and on the same instance. One topic cannot be ordered both ways.

    How it works

    Insert a stage that reads the stream under its original key and writes it to a new topic under the key the next consumer needs. Order is preserved per new key only in the sense that each source partition's records keep their relative order. Records for one new key arriving from different source partitions interleave in an unspecified way, so carry a sequence or timestamp if cross-order ordering matters.

    Pitfalls

    • Every re-key adds a topic, a hop of latency and storage. Do it once and let several consumers share the result.
    • Use transactions (or exactly_once_v2) on the stage, otherwise a retry duplicates records into the re-keyed topic.
    • Check the new key for skew before choosing it. Position keys in a firm with one dominant book will be lopsided.
    • The re-keyed topic's partition count is as fixed as any other keyed topic's.

    Use when

    A consumer's unit of state does not match the producer's unit of ordering, and whenever two streams must be joined (both sides need the same key and partition count).

    Saga

    Problem

    A business process crosses services that each own their data. Example: after a block order completes, allocate it to client accounts, check settlement limits, then book to the ledger. There is no distributed transaction, yet the process must end either fully done or cleanly undone.

    How it works

    Break the process into local steps. Each step has a compensating action that semantically undoes it. If a later step fails, run the compensations for the completed steps in reverse order. Two styles:

    ChoreographyOrchestration
    ControlEach service reacts to the previous service's event.A coordinator sends commands and waits for replies.
    StrengthNo central component. Loose coupling.The process is explicit, visible and testable in one place. Timeouts are easy.
    WeaknessThe flow exists only implicitly across services. Hard to follow beyond three steps.One more service to run. Risk of logic leaking into it.

    Implementation: an orchestrated allocation saga

    The orchestrator is a state machine per saga id, held in a Kafka Streams state store. Commands go to each service's command topic. Replies come back on one topic keyed by saga id, so each saga's replies are processed in order by one instance.

    enum Step { ALLOCATING, CHECKING_LIMITS, BOOKING, RELEASING, DONE, FAILED }

record SagaState(String sagaId, String orderId, Step step, Instant deadline, String failure) {
    SagaState at(Step s, Instant now) { return new SagaState(sagaId, orderId, s, now.plusSeconds(30), failure); }
    SagaState failing(String why, Instant now) { return new SagaState(sagaId, orderId, Step.RELEASING, now.plusSeconds(30), why); }
}
record SagaReply(String sagaId, String from, boolean ok, String detail) { }   // from: allocation | risk | ledger
record SagaCommand(String sagaId, String commandId, String type, String orderId) { }

final class AllocationSaga implements Processor<String, SagaReply, String, SagaCommand> {
    private ProcessorContext<String, SagaCommand> ctx;
    private KeyValueStore<String, SagaState> store;

    public void init(ProcessorContext<String, SagaCommand> ctx) {
        this.ctx = ctx;
        this.store = ctx.getStateStore("allocation-sagas");
        ctx.schedule(Duration.ofSeconds(1), PunctuationType.WALL_CLOCK_TIME, this::checkTimeouts);
    }

    public void process(Record<String, SagaReply> rec) {
        SagaReply r = rec.value();
        Instant now = Instant.ofEpochMilli(rec.timestamp());
        SagaState s = store.get(r.sagaId());

        if (s == null) {                                             // "start" reply from the trigger stage
            s = new SagaState(r.sagaId(), r.detail(), Step.ALLOCATING, now.plusSeconds(30), null);
            send("allocation.commands.v1", s, "AllocateBlock");
        } else switch (s.step()) {
            case ALLOCATING -> {
                if (!r.from().equals("allocation")) return;          // stale or duplicate reply: ignore
                if (r.ok()) { s = s.at(Step.CHECKING_LIMITS, now); send("risk.commands.v1", s, "CheckSettlementLimits"); }
                else        { s = new SagaState(s.sagaId(), s.orderId(), Step.FAILED, now, r.detail()); }
            }
            case CHECKING_LIMITS -> {
                if (!r.from().equals("risk")) return;
                if (r.ok()) { s = s.at(Step.BOOKING, now); send("ledger.commands.v1", s, "BookAllocations"); }
                else        { s = s.failing(r.detail(), now); send("allocation.commands.v1", s, "ReleaseAllocation"); }
            }
            case BOOKING -> {
                if (!r.from().equals("ledger")) return;
                if (r.ok()) { s = s.at(Step.DONE, now); }
                else        { s = s.failing(r.detail(), now); send("allocation.commands.v1", s, "ReleaseAllocation"); }
            }
            case RELEASING -> {
                if (!r.from().equals("allocation")) return;
                s = new SagaState(s.sagaId(), s.orderId(), Step.FAILED, now, s.failure());
            }
            case DONE, FAILED -> { return; }                         // terminal: late replies are ignored
        }
        store.put(s.sagaId(), s);
    }

    private void send(String topic, SagaState s, String type) {
        // commandId is deterministic, so a retried step is recognised as a duplicate by the receiver
        SagaCommand cmd = new SagaCommand(s.sagaId(), s.sagaId() + ":" + type, type, s.orderId());
        ctx.forward(new Record<>(s.orderId(), cmd, ctx.currentSystemTimeMs()), topic);   // child sink name = topic
    }

    private void checkTimeouts(long nowMs) {
        Instant now = Instant.ofEpochMilli(nowMs);
        try (KeyValueIterator<String, SagaState> it = store.all()) {
            while (it.hasNext()) {
                SagaState s = it.next().value;
                if (s.step() == Step.DONE || s.step() == Step.FAILED || s.deadline().isAfter(now)) continue;
                switch (s.step()) {
                    case ALLOCATING      -> send("allocation.commands.v1", s, "AllocateBlock");        // safe to repeat
                    case CHECKING_LIMITS -> send("risk.commands.v1", s, "CheckSettlementLimits");
                    case BOOKING         -> send("ledger.commands.v1", s, "BookAllocations");
                    case RELEASING       -> send("allocation.commands.v1", s, "ReleaseAllocation");
                    default -> { }
                }
                store.put(s.sagaId(), s.at(s.step(), now));           // re-arm the deadline; alert after N attempts
            }
        }
    }
}

    Run the topology with exactly_once_v2, so that the state transition, the outgoing command and the consumed reply commit together. Each participating service handles its command idempotently by commandId and always replies, including for a duplicate.

    Pitfalls

    • Compensation is not rollback. Other parties may have seen the intermediate state. A released allocation is a new fact, not an erased one.
    • Some steps cannot be compensated (a confirmation sent to a client, a trade reported to a regulator). Order the saga so those come last, after everything that can fail.
    • Every command and compensation must be idempotent, because timeouts cause re-sends.
    • No isolation. Two sagas can interleave on the same data. Use semantic locks (a "pending allocation" status) where that matters.
    • Timeouts need a decision: retry, compensate, or escalate to a human. An unbounded retry is an invisible stuck process.
    • Purge terminal sagas from the store after a retention period, and publish saga outcomes so operations can see them.

    Use when

    A process spans services and each step can be undone or retried. Prefer orchestration beyond two or three steps or when timeouts matter. Do not use a saga where a hard real-time invariant is required, such as a pre-trade limit: that needs a single owner making a synchronous decision.

    Snapshot plus delta

    Problem

    A consumer that joins late, or restarts, needs the current value of every key. Replaying all history is too slow, and a stream of changes alone never tells it where to start.

    How it works

    The owner publishes two things for each key: the full current state to a compacted snapshot topic, and each change to a delta topic. Both carry a per-key sequence number. A consumer loads the snapshot, then applies only deltas with a higher sequence. A gap in the sequence means something was missed, and the consumer resynchronises from the snapshot.

    Implementation: publisher

    record PositionDelta(String key, long seq, long qtyChange, BigDecimal costChange, String execId) { }
record PositionSnapshot(String key, long seq, long qty, BigDecimal cost, int deltaPartition, long deltaOffsetHint) { }

// inside the position keeper's transaction, for each applied fill
void publish(KafkaProducer<String, Object> producer, Position before, Position after, Fill f, long deltaOffsetHint) {
    String key = f.positionKey();
    producer.send(new ProducerRecord<>("positions.deltas.v1", key,
        new PositionDelta(key, after.seq(), after.qty() - before.qty(), after.cost().subtract(before.cost()), f.execId())));
    producer.send(new ProducerRecord<>("positions.snapshot.v1", key,
        new PositionSnapshot(key, after.seq(), after.qty(), after.cost(),
                             partitionOf(key), deltaOffsetHint)));     // where a reader may safely start deltas
}

    Because both sends are in one transaction, a snapshot at sequence n exists if and only if delta n does. The offset hint is any delta-topic offset at or before this delta, for example the position's offset at the previous commit.

    Implementation: consumer

    final class PositionView {
    private final Map<String, PositionSnapshot> state = new HashMap<>();
    private final Set<String> stale = new HashSet<>();

    void start(KafkaConsumer<String, PositionSnapshot> snap, KafkaConsumer<String, PositionDelta> deltas) {
        // 1. load the compacted snapshot topic to its current end
        List<TopicPartition> sp = partitions(snap, "positions.snapshot.v1");
        snap.assign(sp); snap.seekToBeginning(sp);
        Map<TopicPartition, Long> end = snap.endOffsets(sp);
        Map<Integer, Long> startFrom = new HashMap<>();
        while (sp.stream().anyMatch(tp -> snap.position(tp) < end.get(tp)))
            for (ConsumerRecord<String, PositionSnapshot> r : snap.poll(Duration.ofMillis(200))) {
                if (r.value() == null) { state.remove(r.key()); continue; }     // tombstone
                state.put(r.key(), r.value());
                startFrom.merge(r.value().deltaPartition(), r.value().deltaOffsetHint(), Math::min);
            }

        // 2. start deltas from the earliest point any loaded snapshot might need
        List<TopicPartition> dp = partitions(deltas, "positions.deltas.v1");
        deltas.assign(dp);
        for (TopicPartition tp : dp) {
            Long from = startFrom.get(tp.partition());
            if (from != null) deltas.seek(tp, from); else deltas.seekToEnd(List.of(tp));
        }
    }

    void onDelta(PositionDelta d) {
        PositionSnapshot cur = state.get(d.key());
        long last = cur == null ? 0 : cur.seq();
        if (d.seq() <= last) return;                                   // already reflected in the snapshot
        if (d.seq() != last + 1) { stale.add(d.key()); return; }       // gap: mark and resync this key
        state.put(d.key(), new PositionSnapshot(d.key(), d.seq(),
            (cur == null ? 0 : cur.qty()) + d.qtyChange(),
            (cur == null ? BigDecimal.ZERO : cur.cost()).add(d.costChange()),
            0, 0));
        stale.remove(d.key());
    }

    Optional<PositionSnapshot> get(String key) {
        return stale.contains(key) ? Optional.empty() : Optional.ofNullable(state.get(key));   // never serve a known-bad value
    }
}

    Pitfalls

    • Deltas need a sequence. Without one the consumer cannot align the two streams or detect loss.
    • Snapshot every change or periodically? Every change is simplest and keeps recovery instant, at the cost of write volume. Periodic snapshots (every N changes or seconds) need the consumer to replay more deltas.
    • Compaction lag means the snapshot topic holds several versions per key. Always keep the highest sequence.
    • Resync on a gap must be implemented and tested, not assumed. The simple form is re-reading that key's snapshot partition.
    • Start-of-day is the same pattern in business terms: yesterday's closing positions are the snapshot, today's fills are the deltas.

    Use when

    Many consumers need current state plus live changes: positions, limits, order books, risk aggregates.

    Catch-up gate

    Problem

    A service that derives state from Kafka starts with empty state. If it begins answering queries or making decisions before it has consumed the backlog, it acts on wrong data: a risk check against positions that are still loading.

    How it works

    At start-up, record the current end offset of every input partition. Consume without serving until the consumer's position reaches those offsets. Then mark the service ready. Afterwards, track staleness continuously and drop back to not-ready if lag exceeds a bound.

    Implementation

    final class CatchUpGate {
    private final AtomicBoolean ready = new AtomicBoolean(false);
    private volatile Instant lastEventTs = Instant.EPOCH;

    void consume(KafkaConsumer<String, Fill> consumer, String topic, Consumer<Fill> apply) {
        List<TopicPartition> parts = consumer.partitionsFor(topic).stream()
            .map(p -> new TopicPartition(topic, p.partition())).toList();
        consumer.assign(parts);
        seekToSnapshotOrBeginning(consumer, parts);

        Map<TopicPartition, Long> target = consumer.endOffsets(parts);   // the line to reach
        while (true) {
            for (ConsumerRecord<String, Fill> r : consumer.poll(Duration.ofMillis(100))) {
                apply.accept(r.value());
                lastEventTs = Instant.ofEpochMilli(r.timestamp());
            }
            if (!ready.get() && parts.stream().allMatch(tp -> consumer.position(tp) >= target.get(tp)))
                ready.set(true);                                         // caught up to where the log was at start
        }
    }

    /** Wire this to the readiness probe and to every decision that depends on the state. */
    boolean isFresh(KafkaConsumer<?, ?> consumer, Duration maxStaleness) {
        if (!ready.get()) return false;
        boolean lagging = consumer.assignment().stream()
            .anyMatch(tp -> consumer.currentLag(tp).orElse(0) > 0);
        return !lagging || Duration.between(lastEventTs, Instant.now()).compareTo(maxStaleness) < 0;
    }
}

    Pitfalls

    • With read_committed, endOffsets returns the last stable offset, which is the right target.
    • Readiness must gate inbound traffic and decisions, not just a log line. Connect it to the Kubernetes readiness probe and to the code path that uses the state.
    • A quiet topic is not a lagging topic. Distinguish "no new records" from "behind" using lag, not just the age of the last record.
    • Catch-up time is your recovery time. Measure it, and shorten it with snapshots or standby replicas.
    • Decide what "not fresh" means for the business: reject, apply conservative limits, or alert and continue.

    Use when

    Every service that makes decisions from state it rebuilt from Kafka.

    • The table is eventually consistent with the owner. For limits that must be exact at decision time, the owner must make the decision.

    Read-mostly data needed on a hot processing path: reference data, configuration, entitlements, latest prices for valuation.

    Claim check

    Problem

    Some payloads are large: a risk report, a full order book snapshot, a document. Kafka's default limit is about 1 MB per record, and large records hurt everyone through memory pressure, replication delay and latency spikes.

    How it works

    Store the payload in object storage and send a small reference through Kafka: location, size and a checksum. The consumer fetches the object only if it needs it. Kafka keeps the ordering and delivery semantics, object storage carries the bytes.

    Implementation

    record ClaimCheck(String bucket, String objectKey, long sizeBytes, String sha256, String contentType) { }

                     .contentType("application/vnd.apache.parquet").build(),
                 RequestBody.fromBytes(report));

        new ClaimCheck("acme-risk-payloads", objectKey, report.length, sha, "application/vnd.apache.parquet"));

}

    Pitfalls

    • Upload before publishing. The reverse order lets consumers receive a reference to something that does not exist yet.
    • Orphans. An upload followed by a failed publish leaves an unreferenced object. Content-addressed keys make retries harmless, and a lifecycle rule cleans up.
    • Retention must match. If the object expires before the Kafka record, replay breaks. Set object lifetime at least as long as topic retention.
    • Access control now lives in two places. A consumer needs permission on the bucket as well as the topic.
    • Objects must be immutable. Never overwrite a referenced key.
    • Put what consumers filter on in the event itself (book, as-of time, type), so most never need to fetch.

    Use when

    Payloads above roughly a few hundred kilobytes, or anything binary and bulky. Keep ordinary events inline.

    Stop and retry in place

    Problem

    A record fails to process and order matters. Skipping it would apply later records for the same key on top of missing state: a position missing one fill is simply wrong.

    How it works

    Do not move past the failing record. For a transient failure, pause that partition, wait with backoff, and retry the same record. For a permanent failure, stop consuming that partition and raise an alert: a human decides. Other partitions keep flowing. The consumer keeps calling poll throughout so it stays in the group.

    Implementation

    final class OrderedConsumer {
    private final Map<TopicPartition, Integer> attempts = new HashMap<>();
    private final Map<TopicPartition, Instant> resumeAt = new HashMap<>();
    private final Set<TopicPartition> halted = new HashSet<>();

    void run(KafkaConsumer<String, byte[]> consumer, Deserializer<Fill> serde, Consumer<Fill> handler) {
        while (true) {
            resumeDue(consumer);
            ConsumerRecords<String, byte[]> batch = consumer.poll(Duration.ofMillis(100));
            for (TopicPartition tp : batch.partitions()) {
                long done = -1;
                for (ConsumerRecord<String, byte[]> r : batch.records(tp)) {
                    try {
                        handler.accept(serde.deserialize(r.topic(), r.value()));   // deserialise here, so failures are catchable
                        done = r.offset();
                        attempts.remove(tp);
                    } catch (TransientException e) {
                        int n = attempts.merge(tp, 1, Integer::sum);
                        long delayMs = Math.min(30_000, 100L << Math.min(n, 8));   // exponential backoff, capped
                        consumer.seek(tp, r.offset());                             // re-read this record next time
                        consumer.pause(List.of(tp));
                        resumeAt.put(tp, Instant.now().plusMillis(delayMs));
                        if (n == 10) alert("partition retrying", tp, r.offset(), e);
                        break;                                                     // nothing after it on this partition
                    } catch (RuntimeException permanent) {
                        consumer.seek(tp, r.offset());
                        consumer.pause(List.of(tp));
                        halted.add(tp);                                            // stays paused until an operator acts
                        alert("partition halted on poison record", tp, r.offset(), permanent);
                        break;
                    }
                }
                if (done >= 0) consumer.commitSync(Map.of(tp, new OffsetAndMetadata(done + 1)));
            }
        }
    }

    private void resumeDue(KafkaConsumer<?, ?> consumer) {
        Instant now = Instant.now();
        resumeAt.entrySet().removeIf(e -> {
            if (e.getValue().isAfter(now)) return false;
            consumer.resume(List.of(e.getKey()));
            return true;
        });
    }
}

    Pitfalls

    • Paused state is lost on rebalance. A new owner starts unpaused and hits the same record. That is fine, but a halted partition needs its alert to keep firing.
    • A halt needs a runbook: inspect the record, fix the code or data, or publish a correcting event and skip with an explicit, audited offset reset.
    • One bad record blocks every key on the partition. If that is too coarse, use the park-the-key pattern.
    • Consume as bytes and deserialise inside the handler. Otherwise a malformed record throws from poll itself, which is harder to handle per record.
    • Classify failures correctly. Treating a dependency outage as permanent halts everything. Treating a bad record as transient retries forever.

    Use when

    Per-key order is a correctness requirement and a stalled partition is preferable to a wrong answer: fills into positions, ledger postings.

    Dead-letter topic

    Problem

    A record can never be processed (malformed, fails validation, references something that does not exist) and the records behind it are independent. Blocking the partition for it helps nobody.

    How it works

    Publish the failing record, unchanged, to a dead-letter topic together with enough context to diagnose and replay it. Only after that write is durable, commit past the record and continue. Someone owns the dead-letter topic: it is monitored, triaged, and records are repaired and redriven or explicitly discarded.

    Implementation

    final class DeadLetters {
    private final KafkaProducer<byte[], byte[]> producer;      // acks=all, idempotent
    private final String consumerName;

    void send(ConsumerRecord<byte[], byte[]> failed, Exception cause) throws Exception {
        var out = new ProducerRecord<>(failed.topic() + ".dlq", null, failed.key(), failed.value(), failed.headers());
        out.headers()
           .add("dlq.source.topic", failed.topic().getBytes(UTF_8))
           .add("dlq.source.partition", Integer.toString(failed.partition()).getBytes(UTF_8))
           .add("dlq.source.offset", Long.toString(failed.offset()).getBytes(UTF_8))
           .add("dlq.source.timestamp", Long.toString(failed.timestamp()).getBytes(UTF_8))
           .add("dlq.consumer", consumerName.getBytes(UTF_8))
           .add("dlq.error.class", cause.getClass().getName().getBytes(UTF_8))
           .add("dlq.error.message", String.valueOf(cause.getMessage()).getBytes(UTF_8))
           .add("dlq.failed.at", Instant.now().toString().getBytes(UTF_8));
        producer.send(out).get(10, TimeUnit.SECONDS);          // must be durable before the offset moves on
    }
}

// in the consumer loop
for (ConsumerRecord<byte[], byte[]> r : batch) {
    try {
        handle(deserialise(r));
    } catch (TransientException e) {
        throw e;                                 // not a dead letter: let the retry policy deal with it
    } catch (Exception permanent) {
        deadLetters.send(r, permanent);          // if this throws, do not commit: the record is retried
        metrics.counter("dlq.sent", "topic", r.topic()).increment();
    }
}
consumer.commitSync();

    Redriving

    A redrive tool consumes the dead-letter topic, optionally filters by error class or time, and republishes each record to its dlq.source.topic with the original key, adding a dlq.redriven header so that a second failure can be recognised. Because consumers are idempotent, redriving a record that had in fact been processed is harmless.

    Pitfalls

    • Order is broken for that key. Later records for the same key have already been processed when the dead letter is redriven. Only use it where that is acceptable, or redrive as an explicit adjustment.
    • Never dead-letter transient failures. A database outage would otherwise empty the main topic into the DLQ in seconds.
    • An unmonitored DLQ is silent data loss. Alert on any arrival for critical flows, and on rate for others.
    • Keep the original bytes. A re-serialised copy may lose exactly the detail that explains the failure.
    • One DLQ per source topic and consumer, with retention long enough for triage.
    • For share groups, Kafka 4.4 can route records that exceed their delivery count to a dead-letter queue on the broker side.

    Use when

    Records are independent of each other, or the bad record can be repaired and applied later without harm: enrichment, notifications, reporting feeds, inbound data from external parties.

    Delayed retry topics

    Problem

    A failure is transient but may last a while (a downstream system is restarting, a counterparty is rate limiting). Retrying in place blocks the partition, and the records behind the failed one are independent and could proceed.

    How it works

    Move the failing record to a retry topic and carry on. A separate consumer reads the retry topic and waits until the record's delay has elapsed before trying again. A chain of topics gives increasing delays. After the last tier the record goes to the dead-letter topic.

    main topic→ .retry.5s→ .retry.1m→ .retry.10m→ .dlq

    Implementation

    final class RetryTiers {
    private static final List<Duration> DELAYS = List.of(Duration.ofSeconds(5), Duration.ofMinutes(1), Duration.ofMinutes(10));
    private final KafkaProducer<byte[], byte[]> producer;
    private final DeadLetters deadLetters;

    /** Called by the main consumer, or by a retry consumer, when handling fails transiently. */
    void defer(ConsumerRecord<byte[], byte[]> r, String baseTopic, Exception cause) throws Exception {
        int attempt = header(r, "retry.attempt").map(Integer::parseInt).orElse(0);
        if (attempt >= DELAYS.size()) { deadLetters.send(r, cause); return; }

        Duration delay = DELAYS.get(attempt);
        var out = new ProducerRecord<>(baseTopic + ".retry." + delay.toSeconds() + "s", null, r.key(), r.value(), r.headers());
        out.headers().remove("retry.attempt").remove("retry.due.at")
           .add("retry.attempt", Integer.toString(attempt + 1).getBytes(UTF_8))
           .add("retry.due.at", Long.toString(System.currentTimeMillis() + delay.toMillis()).getBytes(UTF_8));
        producer.send(out).get(10, TimeUnit.SECONDS);
    }
}

/** One of these per retry topic. Records in a tier share a delay, so they become due in offset order. */
void runRetryConsumer(KafkaConsumer<byte[], byte[]> consumer, String baseTopic, RetryTiers tiers) throws Exception {
    Map<TopicPartition, Long> wakeAt = new HashMap<>();
    while (true) {
        long now = System.currentTimeMillis();
        wakeAt.entrySet().removeIf(e -> { if (e.getValue() > now) return false; consumer.resume(List.of(e.getKey())); return true; });

        ConsumerRecords<byte[], byte[]> batch = consumer.poll(Duration.ofMillis(200));
        for (TopicPartition tp : batch.partitions()) {
            long done = -1;
            for (ConsumerRecord<byte[], byte[]> r : batch.records(tp)) {
                long due = header(r, "retry.due.at").map(Long::parseLong).orElse(0L);
                if (due > System.currentTimeMillis()) {            // not yet: wait without blocking the poll loop
                    consumer.seek(tp, r.offset());
                    consumer.pause(List.of(tp));
                    wakeAt.put(tp, due);
                    break;
                }
                try { handle(r); }
                catch (TransientException e) { tiers.defer(r, baseTopic, e); }     // on to the next tier
                catch (Exception permanent)  { deadLetters.send(r, permanent); }
                done = r.offset();
            }
            if (done >= 0) consumer.commitSync(Map.of(tp, new OffsetAndMetadata(done + 1)));
        }
    }
}

    Pitfalls

    • Ordering is gone. A retried record is processed after later records for the same key. Never use this for order-dependent flows.
    • Do not sleep in the poll loop. Sleeping past max.poll.interval.ms gets the consumer evicted. Pause the partition and keep polling, as above.
    • A fixed delay per topic is what keeps it simple. Mixed delays in one topic would block short delays behind long ones.
    • During a full outage everything flows into the retry tiers, then returns in a burst. Size the tiers and rate-limit the retry consumers.
    • More topics and consumers to operate. Frameworks such as Spring Kafka provide this pattern ready-made.

    Use when

    Independent records with failures that resolve themselves over seconds to minutes: outbound notifications, calls to rate-limited external APIs, non-critical enrichment.

    Park the key

    Problem

    You need both properties at once: per-key order must hold, and one bad record must not block every other key on the partition. Stop-and-retry gives the first, a dead-letter topic gives the second, and neither gives both.

    How it works

    When a record fails, mark its key as parked and divert the record to a parking topic. While a key is parked, every later record for that key is diverted too, without being processed, so order within the key is kept. All other keys continue. Once the cause is fixed, the parked records are replayed in order and the key is released.

    fillskeyed by position→ Processoris this key parked?→ appliednormal path Processor→ fills.parkedfailed + later records for the key→ Redrive tool→ fills.replayrecords, then a RELEASE marker→ Processor

    Implementation

    The set of parked keys is state that must move with the partition, so a Kafka Streams state store is the natural home. The store holds, per parked key, how many records have been diverted.

    record Envelope(Fill fill, boolean release, long replayedCount) {        // value type on the replay topic
    static Envelope of(Fill f) { return new Envelope(f, false, 0); }
}

final class ParkingProcessor implements Processor<String, Envelope, String, Fill> {
    private ProcessorContext<String, Fill> ctx;
    private KeyValueStore<String, Long> parked;                          // key -> number of records diverted
    private final Consumer<Fill> apply;

    public void init(ProcessorContext<String, Fill> ctx) {
        this.ctx = ctx;
        this.parked = ctx.getStateStore("parked-keys");
    }

    public void process(Record<String, Envelope> rec) {
        String key = rec.key();
        Envelope in = rec.value();
        boolean replay = rec.headers().lastHeader("replay") != null;
        Long count = parked.get(key);

        if (in.release()) {                                              // marker written after the replayed records
            if (count != null && count == in.replayedCount()) parked.delete(key);   // everything diverted was replayed
            else ctx.forward(rec.withValue((Fill) null), "release-incomplete");     // more arrived meanwhile: tool repeats
            return;
        }
        if (count != null && !replay) {                                  // key is parked: divert, preserving order
            parked.put(key, count + 1);
            ctx.forward(rec.withValue(in.fill()), "parked-sink");
            return;
        }
        try {
            apply.accept(in.fill());                                     // idempotent: replays are safe
            ctx.forward(rec.withValue(in.fill()), "applied-sink");
        } catch (TransientException e) {
            throw e;                                                     // let the stream thread retry
        } catch (RuntimeException permanent) {
            if (replay) throw permanent;                                 // still failing after the fix: stop and alert
            parked.put(key, 1L);
            rec.headers().add("park.error", String.valueOf(permanent.getMessage()).getBytes(UTF_8));
            ctx.forward(rec.withValue(in.fill()), "parked-sink");
        }
    }
}

    Topology: the processor reads the live topic and the replay topic (same key, same partition count, merged), writes to fills.applied and fills.parked, and runs with exactly_once_v2 so the store, the diversion and the input offset move together.

    The redrive tool

    1. Read fills.parked for the chosen key, from the first parked record to the current end, counting records.
    2. Publish each to fills.replay in the same order with a replay header.
    3. Publish a release marker for the key carrying the total count replayed so far.
    4. If the processor reports release-incomplete (new records were parked in the meantime), repeat from the last replayed position. The key is released only when the counts match, so nothing is skipped and nothing overtakes.

    Pitfalls

    • Complexity. This is the most machinery of the four error patterns. Use it only where both requirements are real.
    • A parked key is stale. Downstream must be able to see that: publish parked keys so that position views can flag the affected book and instrument.
    • Parking must be bounded. Alert on any parked key, and on the count of diverted records growing.
    • Cross-key dependencies break it. If key B's correctness depends on key A's records, parking A silently corrupts B.
    • The handler must be idempotent, since replay may reapply records that partly succeeded.

    Use when

    Many independent keys share partitions, per-key order matters, and one key's problem must not stop the rest: per-account or per-position processing with occasional bad data.

    Priority lanes

    Problem

    Kafka has no message priority. Within a partition, records are consumed strictly in order, so a cancel request can sit behind thousands of queued new orders, and a kill-switch behind a backlog.

    How it works

    Give each priority class its own topic. One consumer subscribes to all of them and, whenever the urgent lane has anything waiting, pauses the others. Urgent work is always drained first. The lanes are independent logs, so there is no ordering between them: this only suits operations that are safe to reorder relative to the other lane.

    Implementation

    final class PriorityConsumer {
    private static final String URGENT = "orders.commands.urgent.v1";    // cancels, kill-switch, limit cuts
    private static final String NORMAL = "orders.commands.v1";

    void run(KafkaConsumer<String, OrderCommand> consumer, Consumer<OrderCommand> handler) {
        consumer.subscribe(List.of(URGENT, NORMAL));
        while (true) {
            ConsumerRecords<String, OrderCommand> batch = consumer.poll(Duration.ofMillis(20));

            // urgent first, always
            for (ConsumerRecord<String, OrderCommand> r : batch.records(URGENT)) handler.accept(r.value());

            Set<TopicPartition> normal = consumer.assignment().stream()
                .filter(tp -> tp.topic().equals(NORMAL)).collect(Collectors.toSet());
            boolean urgentWaiting = consumer.assignment().stream()
                .filter(tp -> tp.topic().equals(URGENT))
                .anyMatch(tp -> consumer.currentLag(tp).orElse(0) > 0);

            if (urgentWaiting) {
                // put back what we fetched but have not processed, then hold the normal lane
                for (TopicPartition tp : normal) {
                    List<ConsumerRecord<String, OrderCommand>> recs = batch.records(tp);
                    if (!recs.isEmpty()) consumer.seek(tp, recs.get(0).offset());
                }
                consumer.pause(normal);
            } else {
                for (ConsumerRecord<String, OrderCommand> r : batch.records(NORMAL)) handler.accept(r.value());
                consumer.resume(normal);
            }
            consumer.commitSync();
        }
    }
}

    Keep max.poll.records small on this consumer so that the check for urgent work happens often.

    Pitfalls

    • No ordering across lanes. A cancel can now arrive before the new order it refers to. The handler must cope: remember the cancel and apply it when the order appears, or reject it and let the sender retry.
    • Starvation. A flood of urgent records stops normal work entirely. Decide whether that is intended (for a kill-switch it is) or add a ratio.
    • Priority is only as fast as the poll loop. A slow handler on a normal record still delays the next urgent one.
    • For true low-latency preemption, Kafka is the wrong layer: handle cancels and kill-switches in the gateway's own in-memory path, and use Kafka to record them.
    • Dedicated consumers per lane are an alternative when lanes can be processed fully independently.

    Use when

    A small class of control messages must not wait behind bulk flow, and can safely be processed out of order relative to it: cancels, limit reductions, halts, configuration changes.

    Testing each pattern

    • Deliver every record twice and assert identical results (idempotency).
    • Kill the process between every pair of steps: after the write and before the commit, mid-transaction, mid-rebalance.
    • Start a second instance with the same identity and assert the first is fenced.
    • Inject a permanent failure on one key and assert other keys keep flowing, or the partition halts, according to the chosen policy.
    • Inject a dependency outage and assert nothing is dead-lettered.
    • Drop a delta and assert the gap is detected and the key resynchronised.
    • Restart with a large backlog and assert nothing is served before the catch-up gate opens.
    • Rebuild a read model from the start of the log and compare it with the live one.
    • Time out each saga step and assert retries are idempotent and compensations run in reverse order.
    • Replay a recorded production day through the whole pipeline and compare outputs with the previous build.
