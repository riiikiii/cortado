What does “received” mean?

A fills service records a purchase of 100 units. A position service reads the fill, updates its database, then loses its connection to Kafka. On restart, should it add another 100? To answer you need three pieces of evidence held by different components. You can inspect all three in the lab. Familiarity with SQL transactions and a consumer loop is sufficient.

EvidenceWho owns it?What it can establish
Input recordKafka topic, partition and offsetA record existed at that address. Reading it leaves it available to other readers while retention permits.
Recovery checkpointKafka consumer group, per topic-partitionThe next offset the group has chosen for restart. Kafka accepts the application’s bookkeeping. It has no visibility into a SQL commit.
Business receipt and positionProjection databaseA particular logical fill has already contributed to this version of the position, even if it appears again at another Kafka offset.

A projection is a queryable view derived from events. Here it is the signed sum of fills for a book trading one instrument. The matching engine owns the facts. The position service owns the derived table. An independent surveillance service can read those same facts with its own group and its own checkpoint. Replicas of the position service share one group to divide work.

Suppose partition 0 contains E7 at offset 0 and E8 at offset 1. The broker’s end offset is 2. After fetching both, a consumer’s in-memory position can already be 2 while the committed group offset is 0. Both records remain eligible for redelivery on restart. Commit 1 after E7 and a replacement starts at E8. Commit 2 before E8 is durable and the replacement can pass over unfinished work. Kafka’s definitions of position and committed position.

Design an event you can read twice

Use one topic called fills. The key is the book, the event ID identifies one immutable booking, and the schema version describes how to interpret its fields. Each event carries a signed change in whole units of the same instrument. A multi-instrument position would normally group by book and instrument and specify units explicitly. Pick an ordering key that covers the business invariant you actually enforce.

An offset identifies a physical record within one partition of one topic. If a relay publishes E7 twice at offsets 0 and 2, both offsets are genuine. The two records still describe one fill. Assign the event ID when the source accepts the booking and preserve it through retries, archive restores and republishing. Generating a UUID inside the consumer would make every delivery look new.

In a production envelope include event type, source namespace if IDs are only locally unique, event time, recording time and trace or causation ID. A correction needs its own identity and a reference to the original. For example, correcting E7 from 100 to 90 by publishing a signed adjustment of −10 gives 60 after E8. Publishing another fill of +90 gives 160. For a full replacement event, retain the previous contribution and apply the difference in one transaction. Document which convention the publisher uses.

Events express facts that have occurred. Commands such as “place an order” request work and can become dangerous when repeated. Keep projections that recompute history separate from handlers authorised to cause new external actions. An event-driven integration also need not make Kafka the system of record. Decide whether authoritative recovery comes from an event archive, the booking database or a retained Kafka log before setting retention.

Make the database update repeatable

The smallest working consumer can be demonstrated without a broker. Save the next two listings alongside each other. Run python drill.py with Python 3.12 and SQLite 3.35 or later. A temporary database holds both the receipt and the position. The fresh connection in the drill models a process reopening its durable state.

The unique constraint arbitrates who owns the first application of E7. A preliminary SELECT followed by an unconditional update has a race when two workers see an absent receipt. Here the insert claims E7, and only its winner adds the quantity. Leaving the transaction commits both writes. An exception in the update rolls both back. The conflict path compares the fields that determine this projection, so a publisher accidentally changing E7 from +100 to +101 raises a visible fault.

This SQLite file belongs to a single-worker lab. In a replicated deployment use a shared transactional database such as PostgreSQL, with a unique key on (projection_version, source, event_id) when several projections share a receipt table. Keep each writer’s transaction short and use an atomic increment or row lock to prevent lost updates. Retry a rolled-back transaction as a whole. Scale workers without skipping unfinished events

With four partitions and two members of one ordinary consumer group, each partition has one assigned reader at a time. A third member can take some partitions during reassignment. Increasing the group beyond the partition count leaves extra members idle. Use a stable key and partitioner for events whose relative order matters. Across partitions there is no comparable offset and no global delivery order. Increasing the partition count can remap a key, so plan a cutover for order-sensitive streams.

Consider a worker that fetched offsets 40, 41 and 42 in one partition and dispatches them to a thread pool. Tasks 40 and 42 finish. A commit of 43 skips the unfinished 41 if the worker dies. The highest safe next offset here is 41. After 41 succeeds, the safe boundary advances to 43. Track the completed prefix of the delivered sequence per partition. Compaction and transactional reads can leave gaps in numeric offsets.

The easiest production starting point is serial processing within each partition, parallelism across partitions, and batched checkpoint commits after durable writes. This reduces coordinator traffic but widens the duplicate window by the uncommitted batch. A worker pool also needs per-partition completion tracking, bounded queues and usually key-level ordering. A correct checkpoint prevents skipped work but cannot undo an amendment that ran before the original.

On partition revocation, stop dispatching that partition, finish or cancel in-flight work within the client’s ownership deadline, and commit only completed progress while ownership permits. A lost assignment or rejected commit means the successor may read those records. The old worker can still finish an external write after ownership changes. Unique receipts protect additive fills. Mutable snapshots also need a condition such as “apply only if incoming version exceeds stored version”; strict deltas may require an exact predecessor. Bound database timeouts and batch sizes against max.poll.interval.ms. Test by terminating a worker during peak processing and checking balances after takeover.

Close the two dual-write gaps

At the publisher. A booking service commits the trade and crashes before publishing the fill. Every consumer can show zero lag while that trade is missing. Insert an outbox row containing the immutable event in the same database transaction as the booking. A relay or change-data-capture connector publishes committed outbox rows. If the relay dies after Kafka accepts E7 but before its own progress is durable, it may publish E7 again. The stored event ID lets every projection recognise that repeat. Monitor the age of the oldest unpublished row and reconcile source bookings to published events.

At the consumer. Suppose reaching a limit should send an alert. In the projection transaction, insert a uniquely keyed notification intent, for example (limit_id, crossing_event_id, action_type). A separate dispatcher delivers that intent with the same idempotency key on every attempt. If the provider accepts the alert but times out on the response, query its status or retry under its documented idempotency contract. Without durable provider deduplication or a status lookup, a local sent flag cannot distinguish “accepted, reply lost” from “never arrived”. Route ambiguous outcomes for reconciliation before triggering another external action.

A producer’s idempotence handles eligible transport retries within Kafka’s producer protocol. It cannot infer that a new API command, a restarted relay’s fresh send, or a repeated payment request represents the same business operation. Record client command IDs at the source when double submission itself is possible. A shadow replay of a read model should use credentials and destinations that cannot send live alerts or orders.

Rebuild a live projection while trades keep arriving

An offset boundary for a topic with several partitions is a vector. Suppose the build starts with exclusive end offsets {p0: 3, p1: 5}. V2 must include visible input below 3 in p0 and below 5 in p1. Comparing its totals with a live V1 that has already consumed p1 offset 5 can manufacture a discrepancy. An offset vector is reproducible for a retained log, but does not by itself establish a common business-time close across books.

A timestamp search finds candidate starting offsets based on Kafka record timestamps. Those may represent producer creation time or broker append time. A backdated trade can carry a business date weeks earlier. For an “as known at Tuesday close” reconstruction, use the recording history, as-of reference data and explicit late-arrival rules. Store replay manifests with topic identity, partition bounds, code revision, schema readers, reference snapshot and reconciliation results. A current FX-rate lookup or a call to the clock can make the same offsets produce different valuations tomorrow.

Retention bounds what can be rebuilt. With delete retention the oldest available record may already be mid-history. Compaction by book retains the latest value for a key eventually. If the values were +100 and −30 deltas, keeping only −30 cannot recreate 70. A compacted snapshot topic keyed by book with absolute balance 70 has different semantics. Handle deletion tombstones and their retention horizon during restores. For an immutable fill ledger, retain or archive the required events and periodically verify a snapshot-plus-tail restore. Use a fail-closed reset policy for established critical groups if an expired checkpoint should raise an incident instead of silently starting mid-history.

Retries, poison records and production evidence

SymptomDistinguishing observationResponse
Lag rises on every partitionDatabase latency and poll processing time rise togetherBound transaction size and in-flight work, back off transient failures with jitter and a budget. Adding consumers to a saturated database can worsen lag.
One partition stalls on the same offsetDecoder or validation error repeats with stable inputPreserve original bytes, headers, source coordinates, event ID if readable, schema and error. Repair the reader or quarantine according to the ordering contract.
Current group lag is zero, ledger differsMissing source outbox event, early offset commit, incompatible units or stale restored stateTrace individual booking IDs from source to outbox, Kafka and receipt. Compare book-level totals at matching boundaries.
Lag spikes after rolling deploysRebalances, commit errors or slow state restores coincideCheck poll deadlines, shutdown drain, restore throughput and ownership changes. Time a controlled failover.
Shadow replay cannot catch upLive arrival rate approaches replay throughputMeasure net drain rate. With 900,000 records behind, 2,000 processed/s and 500 arriving/s, catch-up is roughly 600 seconds if rates hold.

A dead-letter topic is a durable exception queue that needs an owner and a redrive process. If publishing the failed record there and advancing its input offset are separate writes, a crash can duplicate the exception or lose it. Use a Kafka transaction for that Kafka-to-Kafka handoff or record a uniquely keyed quarantine in the same database transaction as durable progress where applicable. A redrive preserves the original business ID and provenance. Restrict access to raw payloads and track the oldest unresolved exception.

Skipping a poison record is a business decision. If event 41 creates a trade and 42 cancels it, moving 41 to a retry topic while applying 42 can break the state machine. Pause that partition or park that key with its successors durably until the predecessor succeeds. For independent commutative increments, delayed retry can be acceptable if readers tolerate incomplete interim totals and reconciliation tracks the gap. Set a named recovery owner and an age threshold in either case.

Observe business freshness alongside offset lag. Record event age, oldest unprocessed source booking, time since last successful durable write, duplicate and conflicting-ID rates, commit failures, partition skew and dead-letter age. A metric labelled with every event ID will overwhelm most metrics stores. Put individual IDs and coordinates in structured logs and sampled traces. Alert on the loss of an expected source heartbeat even when the topic is empty.

A handover note for the on-call engineer

Before deploying a consumer, write down its group, ordering key, source of truth, state store, business deduplication key, transaction boundary and policy for side effects. Record exactly how to find the next safe offset for each partition after a database restore. Exercise one duplicate, one conflicting event, one crash after SQL commit, and one shadow rebuild before relying on the design.

When an incident arrives, start with one disputed fill. Locate its source booking and Kafka coordinates. Check which projection version owned the write, whether its receipt exists and what contribution it made. Then decide among resuming, correcting a fact, redriving a quarantined record or rebuilding an isolated projection. This sequence gives the operator evidence for the smallest intervention that can actually repair the fault.
