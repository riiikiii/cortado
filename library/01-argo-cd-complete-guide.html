Guide 1 of 3 - GitOps delivery

Argo CD: The Complete Guide

Concepts, architecture, day-to-day usage, patterns for many teams and clusters, and the practices that keep GitOps boring in production.

Written November 2026 against Argo CD 3.6. Commands and manifests are examples: pin versions and adapt names to your environment.

Contents

    What Argo CD is, and the idea behind it

    Argo CD is a Kubernetes controller that keeps a cluster matching what is declared in a source of truth, almost always Git. You describe the desired state (plain YAML, Helm, Kustomize, Jsonnet or OCI artifacts), and Argo CD continuously compares it with what is actually running, shows you the difference, and applies it on request or automatically.

    That loop is GitOps. The four principles (from the OpenGitOps project) are worth memorising because most Argo CD design questions reduce to them:

    Declarative

    The system is described as desired state, not as a script of steps.

    Versioned and immutable

    That state lives in a store with history: Git commits, signed tags, OCI digests.

    Pulled automatically

    An agent inside the platform pulls the state. CI never needs cluster credentials.

    Continuously reconciled

    Drift is detected and corrected all the time, not only at deploy time.

    Developeropens PR→ Config repomerge = intent→ Argo CDrender, diff→ Kubernetes APIapply→ Live statewatched, compared

    What you gain, and what it costs

    BenefitCost or caveat
    Every change is a reviewed, auditable commit. Rollback is git revert.Git becomes a production dependency and its permissions become your deployment permissions.
    CI pipelines stop holding cluster-admin credentials.Argo CD itself now holds them. It is a high-value target and must be secured as such.
    Drift is visible within minutes and can self-heal.Controllers and humans that mutate resources fight with it until you teach it what to ignore.
    One UI shows what is deployed where, at which revision.It deploys manifests. It does not build images, run tests, or decide when to promote.
    Scope

    Argo CD is the CD half only. A typical flow is: CI builds and pushes an image, then CI (or a bot) commits the new image tag to the config repo, and Argo CD takes it from there.

    Architecture

    Argo CD is a set of deployments in one namespace (normally argocd). Knowing which component does what tells you where to look when something is slow or broken.

    ComponentRoleWhen it hurts
    argocd-serverAPI (gRPC and REST) and web UI. Authenticates users, enforces RBAC. Stateless.UI or CLI slow, login problems.
    repo-serverClones repos and renders manifests (helm template, kustomize build, plugins). Caches results.Slow refreshes, ComparisonError, high CPU on big monorepos.
    application-controllerThe reconciler. Watches live resources in every managed cluster, diffs against rendered manifests, runs syncs. A StatefulSet that can be sharded by cluster.Memory growth with cluster count and object count, sync queues backing up.
    applicationset-controllerGenerates Application objects from templates and generators.Apps not being created or being deleted unexpectedly.
    redisCache only (rendered manifests, live state trees). Safe to lose, but a cold cache is slow.Everything slow after a restart.
    dex (optional)Bridges SSO providers that are not plain OIDC (SAML, LDAP, GitHub).Login failures.
    notifications-controllerSends events to Slack, Teams, email, webhooks, GitHub statuses.Missing alerts.
    commit-server (optional)Pushes rendered manifests back to Git for the Source Hydrator.Hydration not committing.

    All state that matters is in Kubernetes objects: Application, ApplicationSet and AppProject custom resources, plus ConfigMaps and Secrets for settings, repositories and clusters. There is no database to back up. If you manage those objects declaratively, you can rebuild an Argo CD instance from Git.

    The main settings objects

    ObjectHolds
    argocd-cmGeneral settings: SSO, resource customisations (health, actions, ignore rules), tracking method, reconciliation timing.
    argocd-rbac-cmRBAC policy and default role.
    argocd-cmd-params-cmStart-up flags for each component (replicas, timeouts, feature switches).

    Core concepts

    Application

    The unit of deployment: one or more sources (where manifests come from) mapped to one destination (a cluster and namespace), owned by a project.

    apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: pricing-api-prod
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io   # delete workloads when the app is deleted
spec:
  project: pricing
  source:
    repoURL: https://github.com/acme/platform-config.git
    targetRevision: main
    path: apps/pricing-api/overlays/prod
  destination:
    server: https://kubernetes.default.svc     # or: name: prod-eu-west-1
    namespace: pricing
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
      - ServerSideApply=true
    retry:
      limit: 5
      backoff: { duration: 10s, factor: 2, maxDuration: 3m }

    The two statuses

    Every application carries two independent statuses. Reading them separately is the single most useful habit.

    StatusQuestion it answersValues
    Sync statusDoes live state match Git?Synced, OutOfSync, Unknown
    Health statusIs what is running actually working?Healthy, Progressing, Degraded, Suspended, Missing, Unknown

    Synced plus Degraded means Git was applied faithfully and the result is broken (bad image, failing probe). OutOfSync plus Healthy means it works but someone or something changed it, or a new commit is waiting.

    Vocabulary

    TermMeaning
    Target stateRendered manifests from the source at targetRevision.
    Live stateWhat the cluster API returns right now.
    RefreshRe-fetch Git and recompute the diff. Changes nothing in the cluster. A hard refresh also discards the manifest cache.
    SyncApply the target state to the cluster.
    PruneDelete live resources that are no longer in Git.
    Self-healRe-sync when live state drifts, even with no new commit.
    Resource trackingHow Argo CD knows a resource belongs to an app. Since 3.0 the default is an annotation (argocd.argoproj.io/tracking-id) instead of the app.kubernetes.io/instance label.
    AppProjectA guard rail: which repos, clusters, namespaces and resource kinds a group of apps may use.
    How often does it check?

    Argo CD polls Git on a timer (a few minutes by default, set with timeout.reconciliation plus jitter in argocd-cm) and reacts immediately to changes in live resources because it watches them. Configure a Git webhook to /api/webhook so commits are picked up in seconds without lowering the poll interval.

    Installing and deploying a first application

    Install

    Two supported routes: the upstream manifests, or the community Helm chart (argo/argo-cd). Pin a version in both cases. Use the HA manifests for anything shared.

    kubectl create namespace argocd
kubectl apply -n argocd --server-side --force-conflicts \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.6.0/manifests/install.yaml
# HA variant: .../manifests/ha/install.yaml  (needs 3+ nodes)

# or with Helm
helm repo add argo https://argoproj.github.io/argo-helm
helm install argocd argo/argo-cd -n argocd --create-namespace -f values.yaml

    Log in

    argocd admin initial-password -n argocd          # one-time admin password
kubectl -n argocd port-forward svc/argocd-server 8080:443 &
argocd login localhost:8080 --username admin --insecure
argocd account update-password

    For real use, expose argocd-server through an Ingress or Gateway with TLS, configure SSO, then disable the admin account.

    Create an app three ways

    # 1. CLI
argocd app create guestbook \
  --repo https://github.com/argoproj/argocd-example-apps.git \
  --path guestbook --revision HEAD \
  --dest-server https://kubernetes.default.svc --dest-namespace guestbook \
  --sync-option CreateNamespace=true

argocd app diff guestbook        # what would change
argocd app sync guestbook        # apply
argocd app wait guestbook --health --timeout 180

    2. The UI: New App, fill in the same fields. Good for exploring, poor as a habit because nothing records the change.

    3. Declaratively: commit an Application manifest (as in the previous section) and let Argo CD manage it. This is the route to standardise on.

    Bootstrap rule

    Install Argo CD once by hand or with Terraform, then point it at a repo that contains its own configuration and every other Application. From then on, changes to Argo CD are pull requests too.

    Sources and config tools

    ToolHow Argo CD uses itWatch for
    Plain YAML or JSON directoryApplies every manifest in path (optionally recursive).No templating: copies multiply across environments.
    KustomizeRuns kustomize build if a kustomization.yaml exists.The bundled Kustomize version changes with Argo CD upgrades.
    HelmRuns helm template and applies the output. It does not run helm install, so there is no Helm release object and helm ls shows nothing.Helm hooks are mapped to Argo CD hooks. lookup returns nothing. Random values regenerate on every render and cause permanent drift.
    JsonnetEvaluated natively.Niche: fewer people can review it.
    OCI artifactsHelm charts and manifest bundles pulled from a registry by tag or digest.Use digests for immutability.
    Config Management PluginA sidecar on repo-server that runs any command which prints YAML.Arbitrary code inside Argo CD: treat as privileged.

    Helm chart from a registry with values from Git (multi-source)

    The common real-world shape: a vendor or platform chart, and your values file kept in your config repo.

    spec:
  sources:
    - repoURL: https://charts.example.com
      chart: pricing-api
      targetRevision: 4.2.1
      helm:
        releaseName: pricing-api
        valueFiles:
          - $values/apps/pricing-api/values-prod.yaml
    - repoURL: https://github.com/acme/platform-config.git
      targetRevision: main
      ref: values          # exposes this repo as $values

    Helm or Kustomize?

    Use Helm when you are packaging something for others to configure, or consuming a third-party chart. Use Kustomize for your own services, where a shared base plus small per-environment patches is easier to review than a templated chart. Combining them (Kustomize inflating a Helm chart) works but makes diffs hard to reason about, so do it only when you need to patch a chart you do not own.

    Syncing in depth

    Sync policy

    SettingEffectGuidance
    Manual (no automated)Argo CD shows drift, a human or pipeline presses sync.Reasonable for production gates, but drift accumulates silently if nobody looks.
    automatedSync whenever Git changes.Default for lower environments, and for production once promotion is controlled in Git.
    automated.pruneAlso delete resources removed from Git.Turn on. Without it, deleted manifests leave orphans running.
    automated.selfHealRevert manual changes to live state.Turn on once teams are used to it. It is what makes Git authoritative.
    retryRetry failed syncs with backoff.Always set: CRDs and webhooks frequently fail on the first attempt.

    Phases, hooks and waves

    A sync runs in phases. Within each phase resources are ordered by wave (lowest first), then by kind (namespaces and CRDs before workloads), then by name. Argo CD waits for each wave to be healthy before starting the next.

    PreSyncmigrations, checks→ Syncwaves -N .. +N→ PostSyncsmoke tests, notify SyncFailruns if sync fails PreDelete / PostDeletearound app deletion 
    apiVersion: batch/v1
kind: Job
metadata:
  generateName: db-migrate-
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation   # or HookSucceeded, HookFailed
    argocd.argoproj.io/sync-wave: "-1"
spec:
  backoffLimit: 0
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: registry.example.com/pricing-api:1.42.0
          args: ["migrate", "up"]
    Hooks are not transactions

    If a PreSync migration succeeds and the Sync phase then fails, nothing rolls the migration back. Make migrations backward compatible (expand, deploy, contract) so a failed or reverted rollout still runs against the new schema.

    Sync options you will actually use

    OptionUse it when
    CreateNamespace=trueThe destination namespace is not managed elsewhere.
    ServerSideApply=trueLarge resources (CRDs that exceed the client-side annotation limit), or when other controllers own some fields. Increasingly the sensible default.
    ApplyOutOfSyncOnly=trueApps with hundreds of resources: only touch what changed.
    PruneLast=trueDeletions should happen after everything new is healthy.
    PrunePropagationPolicy=foregroundYou need dependents gone before the sync is reported complete.
    RespectIgnoreDifferences=trueFields you ignore in the diff must also be left alone during sync.
    FailOnSharedResource=trueYou want an error if two apps claim the same resource.
    Replace=trueLast resort for immutable-field changes. It deletes and recreates, so expect downtime.
    SkipDryRunOnMissingResource=trueA custom resource is applied in the same sync as its CRD.

    Most can also be set per resource with the annotation argocd.argoproj.io/sync-options. Two protective ones are worth knowing: Prune=false and Delete=false on resources that must never be removed automatically, such as PersistentVolumeClaims.

    Sync windows

    Defined on a project, sync windows allow or deny syncs on a cron schedule. Typical use: block automated production syncs during trading hours or a change freeze, while leaving manual sync available for emergencies.

    spec:
  syncWindows:
    - kind: deny
      schedule: "0 7 * * 1-5"     # 07:00 Mon-Fri
      duration: 10h
      timeZone: Europe/London
      applications: ["*-prod"]
      manualSync: true            # humans can still override

    Diffing and drift

    An app that never reaches Synced is the most common Argo CD complaint. The cause is nearly always a field that something else writes after apply: an autoscaler setting replicas, a mutating webhook injecting sidecars or defaults, a controller filling in caBundle.

    Fixes, in order of preference

    1. Remove the field from Git. If an HPA owns replicas, do not declare replicas in the Deployment at all.
    2. Use server-side apply and server-side diff. The API server computes the result, including defaulting and admission webhooks, which removes whole classes of false diffs. Recent releases move further in this direction: 3.6 pairs server-side diff with server-side apply by default, so read the upgrade notes when you move to it.
    3. Ignore the difference explicitly, per app or globally.
    spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers: ["/spec/replicas"]
    - group: admissionregistration.k8s.io
      kind: MutatingWebhookConfiguration
      jqPathExpressions: [".webhooks[].clientConfig.caBundle"]
    - group: "*"
      kind: "*"
      managedFieldsManagers: ["kube-controller-manager"]
  syncPolicy:
    syncOptions: ["RespectIgnoreDifferences=true"]

    System-wide rules go in argocd-cm under resource.customizations.ignoreDifferences.<group>_<kind>. Keep the list short and commented: every ignore rule is a place where Git is no longer the truth.

    Resources Argo CD ignores entirely

    Since 3.0, high-churn resources such as Endpoints, EndpointSlices and Leases are excluded by default so they do not flood the controller. Adjust with resource.exclusions and resource.inclusions if you need them tracked.

    Health checks and resource actions

    Argo CD has built-in health logic for core kinds (Deployment rollout complete, Service load balancer assigned, PVC bound, Ingress has an address) and for many popular CRDs. An application is as healthy as its least healthy resource.

    For your own CRDs, add a Lua health check so waves and argocd app wait --health behave correctly:

    # argocd-cm
data:
  resource.customizations.health.streaming.acme.io_KafkaTopicClaim: |
    hs = { status = "Progressing", message = "Waiting for reconciliation" }
    if obj.status ~= nil and obj.status.conditions ~= nil then
      for _, c in ipairs(obj.status.conditions) do
        if c.type == "Ready" and c.status == "True" then
          hs.status = "Healthy"; hs.message = c.message
        elseif c.type == "Ready" and c.status == "False" then
          hs.status = "Degraded"; hs.message = c.message
        end
      end
    end
    return hs

    Resource actions are Lua snippets exposed as buttons and CLI commands, for example restart a Deployment, or promote or abort an Argo Rollout. They mutate live state deliberately, so control them through RBAC (applications, action/...).

    Projects, RBAC and SSO

    AppProject: the tenancy boundary

    Never let teams use the built-in default project: it permits everything. Give each team or domain a project that states exactly what it can deploy and where.

    apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: pricing
  namespace: argocd
spec:
  description: Pricing team workloads
  sourceRepos:
    - https://github.com/acme/platform-config.git
  destinations:
    - { name: "prod-*", namespace: "pricing*" }
    - { name: "dev-*",  namespace: "pricing*" }
  clusterResourceWhitelist: []            # no cluster-scoped resources at all
  namespaceResourceBlacklist:
    - { group: "", kind: ResourceQuota }
    - { group: "", kind: LimitRange }
    - { group: networking.k8s.io, kind: NetworkPolicy }
  roles:
    - name: deployer
      groups: ["acme:pricing-devs"]
      policies:
        - p, proj:pricing:deployer, applications, get,  pricing/*, allow
        - p, proj:pricing:deployer, applications, sync, pricing/*, allow

    RBAC

    Policies live in argocd-rbac-cm in Casbin CSV form: p, subject, resource, action, object, effect. Groups come from your identity provider's claims.

    data:
  policy.default: role:readonly
  scopes: "[groups]"
  policy.csv: |
    p, role:platform-admin, *, *, */*, allow
    p, role:release-manager, applications, sync,     */*-prod, allow
    p, role:release-manager, applications, action/*, */*-prod, allow
    g, acme:platform,         role:platform-admin
    g, acme:release-managers, role:release-manager
    3.x behaviour changes that surprise people

    Since 3.0, update and delete on an application no longer imply the same rights on its child resources, and viewing pod logs needs an explicit logs, get permission. If roles were written for 2.x, re-test them.

    Hardening the identity side

    • Use SSO (OIDC directly, or Dex for SAML and others). Map IdP groups to roles, never individual users.
    • Disable the local admin user after setup (admin.enabled: "false"). Keep a break-glass path documented.
    • For automation, use project roles with short-lived JWT tokens, scoped to specific apps.
    • Sync impersonation: by default the controller applies everything with its own, very powerful, service account. With impersonation enabled, each project names a destination service account and syncs run with only that account's Kubernetes RBAC. This is the strongest tenancy control available on a shared instance.
    • Apps in any namespace: lets teams keep their Application objects in their own namespace instead of argocd, constrained by the project's sourceNamespaces. Useful for self-service, but it widens the trust boundary, so pair it with strict projects.

    Managing many applications

    App of Apps

    A parent Application whose source directory contains child Application manifests. Simple, explicit, and good for bootstrapping a cluster (platform add-ons first, using sync waves). It does not scale well when the children differ only by cluster or environment, because you end up copying files.

    ApplicationSet

    A template plus one or more generators that produce parameters. One ApplicationSet can create an app per cluster, per directory, per pull request, or the product of several of those.

    GeneratorProduces an app for eachTypical use
    ListHard-coded elementSmall, fixed set of environments.
    ClusterRegistered cluster matching a label selectorPlatform add-ons on every cluster.
    Git directories / filesFolder or config file in a repoOnboard a service by adding a folder.
    Matrix / MergeCombination of two generatorsEvery service on every matching cluster.
    Pull RequestOpen PREphemeral preview environments.
    SCM ProviderRepository in an organisationAuto-discover services.
    OCI (3.6)Artifact in a registryConfig shipped as OCI bundles instead of Git.
    Plugin / Cluster Decision ResourceResult of an external callCustom placement logic.
    apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: services
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
    - matrix:
        generators:
          - clusters:
              selector:
                matchLabels: { argocd.acme.io/tenant-workloads: "true" }
          - git:
              repoURL: https://github.com/acme/platform-config.git
              revision: main
              directories:
                - path: "apps/*/overlays/{{ index .metadata.labels \"env\" }}"
  template:
    metadata:
      name: "{{ index .path.segments 1 }}-{{ .name }}"
    spec:
      project: "{{ index .path.segments 1 }}"
      source:
        repoURL: https://github.com/acme/platform-config.git
        targetRevision: main
        path: "{{ .path.path }}"
      destination:
        name: "{{ .name }}"
        namespace: "{{ index .path.segments 1 }}"
      syncPolicy:
        automated: { prune: true, selfHeal: true }
  syncPolicy:
    preserveResourcesOnDeletion: true
    ApplicationSets can delete a lot, quickly

    If a generator suddenly returns nothing (a renamed label, a broken path glob, an SCM API outage), the controller removes the generated Applications, and with the resources finalizer, their workloads. Protect yourself: set preserveResourcesOnDeletion: true, consider the create-update applications sync policy so the controller never deletes apps, and review ApplicationSet changes as carefully as production code.

    Progressive syncs let an ApplicationSet roll a change through groups of apps in order (for example dev clusters, then one production region, then the rest) using a RollingSync strategy with label-matched steps. Version 3.6 added metrics and clearer failure conditions for these rollouts. Check the feature's maturity level for your version before depending on it.

    Repository structure and promotion

    Rules that hold up

    • Separate config from application source. A commit that only bumps an image tag should not trigger a CI build, and developers who can change code should not automatically be able to change production config.
    • Environments are directories, not branches. Long-lived environment branches drift, and merges between them carry unintended changes. Use base/ plus overlays/dev, overlays/staging, overlays/prod.
    • Pin everything that reaches production. Image digests or immutable tags, chart versions, remote Kustomize bases by commit SHA. latest and floating HEAD make rollbacks meaningless.
    • Promotion is a pull request that copies a known-good version from one environment's directory to the next.
    platform-config/
  apps/
    pricing-api/
      base/                 deployment, service, hpa, kustomization.yaml
      overlays/
        dev/                kustomization.yaml  (image tag, replicas, config)
        staging/
        prod/
  platform/                 ingress, cert-manager, external-secrets, monitoring
  clusters/                 per-cluster values and cluster registration
  argocd/                   projects, applicationsets, argocd config itself

    The rendered manifests pattern and the Source Hydrator

    With Helm or Kustomize, the pull request shows a change to inputs (a values file), not to what will actually be applied. A chart upgrade can alter hundreds of lines that no reviewer sees. The rendered manifests pattern fixes this: render to plain YAML, commit the output to an environment-specific branch or path, and have Argo CD deploy only that.

    The Source Hydrator builds this into Argo CD. An application declares a dry source (the templates) and a sync source (where hydrated YAML is committed), and the commit-server pushes the rendered result. Recent releases have kept extending it, including hydrating to a separate repository and signing hydrated commits, which is marked alpha in 3.6. Treat it as a maturing feature: check the status for your version and trial it on non-critical apps first.

    Automating the version bump

    ApproachHowTrade-off
    CI writes to GitAfter pushing the image, the pipeline opens a PR or commits the new tag.Simple and explicit. CI needs write access to the config repo.
    Argo CD Image UpdaterWatches registries and updates the app or writes back to Git.Less pipeline code, but adds a second source of change. Use Git write-back so history stays complete.
    Promotion tooling (GitOps Promoter, Kargo)Models stages, checks and approvals, and moves versions between environments through Git.More moving parts, real structure for multi-stage promotion.

    Secrets

    Plain secrets must not be in Git, and Argo CD has no secret store of its own. The project's own guidance is to prefer solutions where the secret is fetched in the destination cluster, over plugins that inject secret values while manifests are rendered.

    ApproachWhat is in GitNotes
    External Secrets OperatorAn ExternalSecret that references a path in AWS Secrets Manager, Vault, and so on.The usual choice. Rotation works without a commit. Argo CD never sees the value.
    Secrets Store CSI DriverA SecretProviderClass.Mounts secrets as files, optionally syncing to a Secret.
    Sealed SecretsCiphertext only the cluster's controller can decrypt.No external store needed. Key backup and rotation are on you.
    SOPS (via plugin or KSOPS)Encrypted files.Decryption happens in repo-server, so plaintext ends up in the manifest cache.
    Render-time injection pluginsPlaceholders.Discouraged: values land in Redis, and rotating a secret needs a re-render that Argo CD cannot detect.

    Multi-cluster topologies

    ModelShapeGood forRisk
    Hub and spokeOne Argo CD manages many clusters.Single pane of glass, one place to upgrade.The hub holds credentials to everything and is a single point of failure. Controller memory grows with fleet size.
    Instance per clusterEvery cluster runs its own Argo CD.Strong isolation, no cross-cluster credentials, works in disconnected networks.Many instances to upgrade and observe.
    Instance per environment or domainFor example one for non-production, one for production.A pragmatic middle: blast radius limited by environment.Two sets of config to keep aligned.
    Agent basedA central control plane with lightweight agents in each cluster that connect outbound.Large or network-restricted fleets: no inbound access to workload clusters.Newer model with its own operational learning curve.

    Clusters are registered as labelled Secrets (or with argocd cluster add). Put meaningful labels on them (environment, region, tier) because ApplicationSet cluster generators select on those labels.

    On Amazon EKS

    Avoid long-lived bearer tokens for spoke clusters. Give the application-controller and server an IAM role (EKS Pod Identity or IRSA) and grant that role access on each target cluster with EKS access entries. AWS also offers Argo CD as a managed EKS Capability, which runs the control plane for you and integrates sign-in with IAM Identity Center. It trades some configurability for not operating Argo CD yourself.

    Progressive delivery with Argo Rollouts

    Argo CD applies a Deployment and Kubernetes does a rolling update: it does not judge whether the new version is any good. Argo Rollouts is a separate controller that replaces Deployment with a Rollout resource supporting canary and blue-green strategies, traffic shifting through an ingress or mesh, and automated analysis against metrics.

    apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: pricing-api
spec:
  replicas: 6
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - analysis:
            templates: [{ templateName: error-rate-below-1pct }]
        - setWeight: 50
        - pause: { duration: 10m }
  selector: { matchLabels: { app: pricing-api } }
  template: { }   # the usual pod template goes here

    Argo CD understands Rollout health: a paused canary shows as Suspended, and promote or abort are available as resource actions. Rollback remains a Git operation. If you abort a canary but leave the bad version in Git, the app is Degraded until you revert the commit.

    Notifications and observability

    Notifications

    Triggers (conditions such as on-sync-failed, on-health-degraded, on-deployed) and templates are defined in argocd-notifications-cm. Apps or projects subscribe by annotation:

    metadata:
  annotations:
    notifications.argoproj.io/subscribe.on-sync-failed.slack: pricing-alerts
    notifications.argoproj.io/subscribe.on-health-degraded.slack: pricing-alerts

    Useful beyond chat: post a commit status back to GitHub or GitLab, or call a webhook that records a deployment marker in your monitoring system.

    Metrics worth alerting on

    MetricTells you
    argocd_app_info (labels sync_status, health_status)Apps OutOfSync or Degraded for too long. The core alert.
    argocd_app_sync_total (label phase)Failed syncs and deployment frequency.
    argocd_app_reconcileReconciliation duration: controller saturation.
    workqueue_depthController falling behind.
    argocd_git_request_total, argocd_git_request_duration_secondsGit provider slowness or rate limiting.
    argocd_cluster_api_resource_objectsHow much each cluster costs the controller in cached objects.

    All components can also emit OpenTelemetry traces, which is the fastest way to see whether a slow sync is spent in Git, in manifest rendering, or in the Kubernetes API.

    Scaling and high availability

    • Run the HA manifests: multiple argocd-server and repo-server replicas, and Redis with HA. The server and repo-server scale horizontally without ceremony.
    • Shard the application-controller across clusters by raising its replica count (and the matching ARGOCD_CONTROLLER_REPLICAS). Each shard owns a subset of clusters. One very large cluster still lands on a single shard, so size memory for your largest cluster.
    • Cut the watch load: exclude resource kinds you never deploy, and restrict managed namespaces on clusters where Argo CD only owns a few. Version 3.6 added server-side label filtering and cheaper cache serialisation, with the release notes reporting large controller memory reductions in their tests.
    • Help the repo-server with monorepos: a single commit otherwise invalidates the cache for every app in the repo. Set argocd.argoproj.io/manifest-generate-paths on each app so only changes under its paths trigger re-rendering, and use webhooks.
    • Prefer more, smaller apps over one giant app. Thousands of resources in one Application make every diff and sync slow and every failure wide.
    • Mind Git provider rate limits. Many apps polling the same repo share one cached clone, but many repos with short polling intervals can exhaust API quotas.

    Upgrading Argo CD itself

    Minor versions ship roughly every three months and the three newest minors receive fixes. Upgrade one minor at a time, read the per-version upgrade notes (defaults do change, as with tracking and RBAC in 3.0), and try it on a non-production instance that manages real apps before production.

    Security checklist

    • SSO only, admin disabled, groups mapped to least-privilege roles.
    • No team uses the default project. It is locked down to nothing.
    • Projects restrict source repos, destinations and cluster-scoped kinds. Tenants cannot create Namespaces, ClusterRoles, CRDs or webhooks.
    • Sync impersonation enabled on shared instances, or separate instances per trust zone.
    • The config repo has branch protection, required reviews and CODEOWNERS on production paths. Whoever can merge can deploy.
    • Repository credentials are read-only and scoped (deploy keys or a GitHub App), with credential templates instead of per-repo secrets.
    • API and UI are not on the public internet, or sit behind an identity-aware proxy. Webhook endpoints have secrets configured.
    • Config Management Plugins are reviewed like privileged code and are not installable by tenants.
    • Argo CD is patched promptly. Subscribe to its security advisories.
    • Where provenance matters, require signed commits or verified sources at project level.

    Best practices and anti-patterns

    Do

    • Manage Applications, Projects and Argo CD config declaratively.
    • Enable auto-sync with prune and self-heal as the normal state.
    • Promote by pull request between environment directories.
    • Pin images, charts and remote bases.
    • Keep apps small and cohesive: one service, one environment.
    • Alert on OutOfSync and Degraded duration, not just events.
    • Practise the full rollback path: revert, sync, verify.

    Avoid

    • Clicking changes in the UI, or kubectl edit in production.
    • One branch per environment.
    • CI running argocd app sync with a cluster-wide token as the deployment mechanism.
    • Secrets, or tools that render secrets, in the manifest path.
    • A growing pile of unexplained ignoreDifferences.
    • Helm charts with random or time-based values.
    • Treating argocd app rollback as a real rollback: Git still says otherwise.

    A sensible adoption path

    1. Install on a non-production cluster. Put one service under manual sync and get used to the diff.
    2. Create the config repo layout, a project per team, and SSO with groups.
    3. Turn on auto-sync, prune and self-heal in dev. Fix every false diff properly.
    4. Move platform add-ons under Argo CD with an app-of-apps and sync waves.
    5. Introduce ApplicationSets once the copy-paste becomes visible.
    6. Add notifications, metrics and alerts. Then production, with sync windows and PR-based promotion.
    7. Later, as needed: Rollouts for canaries, the hydrator for reviewable rendered output, impersonation for hard tenancy.
