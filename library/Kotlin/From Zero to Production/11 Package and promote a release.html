Build a deployable artefact

The service process owns transient request state. PostgreSQL owns the observation history. An image bundles application code and its runtime. A container is one running instance of that image. Replacing the instance should have no effect on stored quotes.

The first stage has Maven and a JDK and runs the test suite while assembling the executable jar. The second starts with a JRE and receives only that jar. Its process runs under a numeric non-root identity. The exec-form ENTRYPOINT lets the JVM receive process termination signals directly. Spring enables graceful shutdown with a phase timeout in the properties file. A container scheduler still needs a termination grace period that accommodates the actual shutdown sequence.

The inspect output should be 10001:10001. The application listens on port 8080 in the container. EXPOSE describes the port and Compose publishes it to the host. The loopback binding is deliberate. This is a local lab with development credentials. The JDBC host is db because Compose resolves service names on the project network. Inside the API container, localhost points back to that API container.

From the HTTP guide’s terminal, send a PUT using the known UUID. Run docker compose restart api, wait for readiness, then send the identical request. Expect 204 and the same JSON on GET. Stop and start the Compose stack without deleting its volume to repeat the experiment with a fresh PostgreSQL container. Removing volumes destroys the lab data, including the record required for the replay test.

Understand startup failures before shipping

Boot creates its datasource from the environment, runs Flyway migrations during startup and then accepts application traffic. An incorrect password may keep the application from starting at all. A database outage after successful startup can leave the process alive while readiness fails. Those cases call for different actions. Inspect the first meaningful exception and the state of the process before assuming an HTTP or Kubernetes routing problem.

Hikari's maximum pool size of eight applies to each JVM. Three pods can hold up to 24 connections before accounting for migration jobs and other applications. Its connection-timeout bounds the wait to borrow a connection. It does not bound the time a query can run or a network read can block. For production, derive connection, socket, statement and lock timeouts from an end-to-end request budget and verify how the driver behaves under failure.

Promote exactly what you built

Run this in the application's source repository after committing the version being released. Select the architecture of your target nodes or build a multi-platform image. Use a registry account or workload identity authorised for this repository. Record the returned digest and deploy the digest-qualified reference in the next lesson. A tag is useful to people and can point to a different image later. The digest identifies the content the registry actually accepted.

For a release pipeline, pin the builder and runtime base images by reviewed digest, retain the build provenance and scan the resulting image. Update base digests deliberately, rebuild and rerun the same tests. The lab's floating Java 21 tags are convenient for experimentation and intentionally leave the patch selection to the day of the build.
