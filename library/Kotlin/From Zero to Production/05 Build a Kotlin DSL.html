Read a Kotlin builder as ordinary function calls

Kotlin libraries often look like miniature languages. If you have seen a Gradle build script or Ktor routing block, the absence of explicit receiver names can hide what the code is doing. Build a small price policy and uncover every call. The policy allows GILT within a configured band. It runs after the Quote constructor checks its universal invariants. A valid quote can therefore still be unacceptable to a particular desk.

Run quotes.PolicyDemo using the exec command from the first guide after compiling. Expect true and false. Read the first result backwards. A Quote at 10125 is the first matching instance in the mixed list. Let passes it to a predicate. That predicate looks up GILT in a private snapshot and checks a closed range. The second quote is valid to construct, yet 9999 is below the desk's configured floor.

Expand the receiver manually

A function type with a receiver still has an input object. In the lambda that object is available as this. Apply runs the function with the new builder as receiver and returns that builder. Build then captures a map. The DSL creates no new parser, keywords or execution engine. You can set breakpoints in allow and build and observe the same call sequence as in the expanded version.

The annotation class is marked with DslMarker. When several implicit receivers marked with the same DSL marker are nested, Kotlin limits accidental access to outer receivers. This one-level example does not need the restriction yet. A nested instrument or venue block would. A DSL marker controls name resolution, not state ownership. The private snapshot is what stops subsequent changes to the builder from changing an existing policy.

For a distinguishing experiment, call build, add a rule for a second instrument, then call build again. The earlier predicate should reject that second instrument while the later one can accept it. If build captured the mutable limits map directly, both predicates would change. An immutable configuration snapshot lets a process replace a complete policy while existing requests finish using their previous copy. Publication across threads still requires safe coordination.

What inline and reified actually enable

The mixed collection exists here to demonstrate an interoperability boundary, such as an untyped event bus. In ordinary Kotlin code a sealed event hierarchy is easier to validate exhaustively. On the JVM generic arguments are usually erased. A normal generic function cannot ask it is T for arbitrary T at runtime. In an inline function, a reified parameter lets the compiler supply the type check at a call site where T is known. The safe cast as? yields null when the cast fails.

Reification does not attach runtime metadata for the element types inside every existing JVM list. A check for List can at most identify the outer List for an erased value in this context. Validate the elements explicitly or use a decoder that receives the full target type. Also consider binary compatibility: changing an inline library function's body can require rebuilding callers to get the new inlined behaviour.

Recognise the hidden branch in a lambda

The first return exits the enclosing function because forEach is inline and its lambda allows a non-local return. The labelled return in the second example ends only that lambda invocation. The loop proceeds to the next element. With an ordinary non-inline callback the compiler rejects an unlabelled non-local return. A plain for loop with continue or return often communicates the choice more clearly.

Try declaring a second GILT rule. The builder rejects it. Replacing the check with a simple map assignment would make the last rule silently win. That is a design choice in the configuration language, even though the implementation is only a few lines of ordinary Kotlin.
