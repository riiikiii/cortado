Prove which state a coroutine protects

Eight workers each accept 1,000 records. How many increments should an in-process counter show? The arithmetic says 8,000. Kotlin's coroutine machinery only makes that result reliable when the update itself has an appropriate ownership or synchronisation rule.

Run quotes.SharedState after compiling. Each launch inherits its parent Job but explicitly uses Dispatchers.Default, which can execute tasks on multiple threads. The enclosing coroutineScope suspends until its children finish. The subsequent read therefore happens after all increments. The mutex ensures that each read-modify-write of accepted completes while its caller has exclusive access. The final observable result is 8000.

Make a lost update visible without relying on timing

Read Reads 4 Reads 4 4
Compute Computes 5 Computes 5 4
Write Stores 5 — 5
Write — Stores 5 5

Both jobs completed one increment. Only one increment survived. Waiting for both workers to complete fixes the timing of the final observation, not the overlapping writes. Marking a field volatile improves visibility on the JVM but does not make a compound increment atomic. A test can happen to print the correct answer for an unsafe counter, particularly on one thread. The interleaving above establishes the bug even when a local stress test misses it.

A coroutine Mutex suspends waiting coroutines. A JVM monitor or a contended blocking lock occupies a thread while waiting. Keep the useful critical section short regardless of mechanism. Holding the lock across a network round trip serialises all callers behind an unreliable dependency. The mutex is also non-reentrant: a helper that tries to acquire the same mutex again from within a locked section can wait indefinitely.

Match the mechanism to the state

For a single JVM integer a Java AtomicInteger with incrementAndGet is simpler. For several fields that must agree, a lock around all related updates and reads can give readers one coherent snapshot. Another design is to assign one coroutine ownership of state and communicate through a Channel. A bounded channel then makes queue capacity a visible choice. Decide what the sender should do after the queue fills or its owner fails. All three approaches lose that state on process termination.

An atomic integer does not solve a two-field invariant such as “accepted plus rejected equals seen” for a reader that samples the three fields independently. If you need coherent snapshots, store an immutable snapshot behind a lock or atomically replace one state object. If you only need approximate process metrics, use a metrics registry with clearly documented aggregation. And if the state decides whether a price has been durably recorded, move ownership to the database.

Test virtual time separately from actual contention

A coroutine test with runTest and a TestDispatcher can advance virtual time past delay calls without sleeping. It is a good fit for retry schedules and deadlines, provided the dispatcher and scheduler are supplied to the code under test. A hard-coded Dispatchers.IO or real JDBC call does not run on that virtual clock. Add kotlinx-coroutines-test with the same version as the core library if introducing this style of test. The companion's concurrency demos use real dispatchers.

A deterministic schedule test and a parallel stress test answer different questions. The former can show exactly when the third retry is scheduled and whether cancellation prevents it. The latter can exercise shared objects under actual simultaneous access. Even a successful stress test cannot cover every interleaving. Make the guarantee explicit in the implementation and use tests to catch regressions to that design.

Change the exercise to create a separate GateCounter for each worker. Each local total becomes 1000 and the original shared counter remains zero. That is what happens when this design is moved unchanged into eight pods. Summing metrics can reconstruct a fleet-level observation rate. Enforcing one durable record per event key needs a single authority visible to all pods, which the HTTP and persistence lessons build next.
