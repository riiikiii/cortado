Where I would use each language on a desk

Suppose you own three things: an internal quote-booking API, a pricing SDK distributed to multiple desks, and the market-data decoder feeding a latency-sensitive strategy. I would use Kotlin for the first if its maintainers are comfortable reviewing it, preserve the Java-facing contract of the second, and leave the decoder in its measured implementation until a benchmark justifies changing it. Those are three different decisions inside the same firm.

Spring Boot runs either language. The quote API in this series still uses Spring MVC, Jackson, JDBC, PostgreSQL and the same JVM tooling when its controller is written in Java. Transaction isolation, message ordering, database durability and authentication remain properties of the system you design. The language choice changes which mistakes the compiler catches, how easily callers consume your API, and what your build and on-call team must understand. Spring Boot 3.5 Kotlin support

Financial workload My starting choice What would change the decision
Internal booking, reconciliation or reference-data API Kotlin for new domain and service code. A sealed decision can distinguish booked, duplicate and conflict; an exhaustive when forces each caller to handle a new case. A Java-only support rotation or imminent handover favours Java until there are two competent maintainers and an exercised runbook.
Java vendor SDK integration or widely distributed risk library Keep the public Java interface. Implement individual adapters or calculations in Kotlin behind it. If every consumer is rebuilt together and owned by the same Kotlin team, Kotlin-specific signatures become much cheaper to evolve.
Pricing and scenario batch Either. Keep the algorithm, decimal conventions and reference results fixed. Kotlin makes distinct units and optional values easy to express. Existing validated Java with no identified defect gives a rewrite little return. A new pricing model with many invalid state combinations is a stronger candidate.
Low-latency feed handler or execution path Keep the measured baseline. Compare an isolated Kotlin candidate against the existing implementation before moving traffic. Promote it if tail latency, allocation, GC behaviour and supportability meet the same budget under realistic bursts. Java can allocate heavily too.
ORM- or annotation-processor-heavy back office Start with Java entities and generated bindings, then add Kotlin above that boundary. A small integration test that proves generation, mapping, lazy loading and rollback can justify moving the boundary later.

Java 21 already has records, sealed hierarchies, pattern matching and virtual threads. Compare a well-written modern Java implementation with idiomatic Kotlin. Kotlin's advantage in a domain model often comes from the combination of null-aware expressions, exhaustive decisions and concise transformations across many small functions. Its cost becomes visible when those conveniences enter a long-lived API consumed by independently released Java applications.

What you cannot express directly in Kotlin

Java capability or expectation Kotlin/JVM boundary Practical response
Require every caller to catch or declare a checked exception Kotlin does not enforce Java checked exceptions at Kotlin call sites. A Java method can throw IOException through a Kotlin function with no compiler prompt. Keep @Throws on exported methods when Java callers rely on it. Model expected business outcomes explicitly; test transport failures separately.
Declare a package-private Kotlin member or type Kotlin has no package-private visibility modifier. Internal means the compilation module. JVM exposure and name mangling make it unsuitable as a Java access barrier. Keep a small Java declaration when exact package access is contractual, or redesign the module's public interface.
Use Java named arguments or inherit Kotlin defaults at arbitrary Java call sites Kotlin source generally cannot use named arguments on Java methods. Java callers of Kotlin normally provide all parameters. Offer explicit overloads or use @JvmOverloads where its generated overloads suit the contract. Preserve pre-existing JVM signatures.
Call a suspending Kotlin method as an ordinary Java method returning its eventual value Its JVM signature includes a Continuation and uses a compiler protocol. Java can see that machinery, but it is a poor public SDK contract. Expose a blocking interface for a blocking vendor, or a CompletionStage facade with documented executor, cancellation and timeout behaviour.
Assume a public Kotlin property is a Java field, or that a data class is a Java record A typical property exposes accessors. A regular data class and a JVM record have different class and accessor shapes. Keep an established record, use an eligible @JvmRecord data class, or deliberately expose a field with @JvmField where appropriate. Verify reflection-based consumers.
Pass every Kotlin value class around as an unboxed primitive with a stable Java name Generic, nullable and interface uses can box values; signatures involving value classes can be mangled. Use a conventional DTO or primitive plus an explicit unit at the SDK boundary. Keep strong types inside; inspect bytecode and benchmark critical paths.

None of these prevents Kotlin from calling a Java FIX engine, using JDBC, running on virtual threads, or using the JVM monitoring and deployment stack. A vendor's support agreement, sample code and certified versions are separate questions from bytecode compatibility. Ask whether the supplier will reproduce a fault through its documented Java API. A slim Java adapter can give support exactly that reproduction path. Java calling Kotlin · Kotlin calling Java · Visibility · JVM records

Lab: replace a mark service underneath a compiled Java client

A vendor supplies a decimal price as text, returns null for an unknown instrument, and throws IOException when its transport fails. The desk's outward contract uses Optional for missing data. We want to change the implementation language while keeping an already shipped caller working. The toy mark uses a fixed scale of two and ties-to-even rounding. A real contract would obtain scale, units, currency and rounding stage from the instrument and valuation policy. The supplied inputs and dependencies are non-null except for the vendor's documented missing value.

Save the four files below in an empty directory. They deliberately share package desk. The separate output directories allow the two implementations to have the same fully qualified class name. Only one goes on each runtime classpath.

Compile the caller once against the Java implementation. Then remove that implementation from the runtime classpath and substitute the Kotlin one. Prerequisites are a JDK 21 and Kotlin/JVM compiler 2.2.21. These commands use a POSIX shell. The kotlin launcher supplies the Kotlin runtime for the second execution; a Java-launched deployed application must package the Kotlin standard library.

Both runs produced GILT=101.24, UNKNOWN=missing and TIMEOUT=unavailable on separate lines. The unchanged Java caller constructs desk.MarkService with a desk.VendorFeed and invokes mark(String) returning Optional. Keeping the package, owner, method name and erased descriptor allows that invocation to link. Assigning the unannotated Java return value to String? makes its platform nullability explicit before business logic touches it. The exception is allowed to propagate so an upstream outage cannot appear as a legitimate missing price.

Now remove @Throws, recompile the Kotlin class and run the old Java client again. It still prints all three results. Recompile the Java client against that new class and javac rejects its catch block: the try body no longer declares IOException. Both observations were reproduced. The throws declaration is relevant to Java source checking and reflection, while the JVM method descriptor used for linking is unchanged. A test that always rebuilds everything misses some binary breaks; a test that only runs an old binary misses this source break.

The lab establishes compatibility for three cases. Kotlin also generates null checks for non-null parameters. The old Java constructor could accept a null feed and fail later; the Kotlin constructor rejects it immediately. Inventory actual caller behaviour before tightening nullability on a maintained SDK. Add malformed decimal input, stale marks, unsupported currencies and late corrections to a real fixture.

Financial correctness: same BigDecimal, surprising Kotlin

Kotlin's equality operator calls BigDecimal.equals, which includes scale. Java code using compareTo for a numerical comparison would change behaviour if mechanically converted to Kotlin ==. In the quote service this could turn a valid replay into a conflict if you replaced integer ticks with unnormalised decimals in a data class. Pick a canonical scale and rounding rule at the correct boundary, or define economic equivalence explicitly. Preserve raw source precision separately if reconciliation needs it. Use decimal text or integer ticks at ingestion; constructing a financial decimal from a binary floating-point approximation can change the starting value. JDK BigDecimal

Null safety is valuable for prices, optional settlement dates and missing vendor values, but it cannot distinguish a stale price from a current one by itself. A nullable decimal only has two states. A sealed result can carry Available(value, timestamp), Missing and Stale(lastValue, timestamp). After introducing Stale, an exhaustive when expression makes each Kotlin valuation path decide whether to fail, fall back or defer. Persist the decision and input timestamp if a later price challenge must be explained. Neither language supplies that audit trail automatically.

Spring and tooling failure modes worth testing

Boundary Likely migration failure A test with diagnostic value
Spring AOP and transactions Kotlin classes and methods are final by default. Subclass proxies need overridable methods. Self-invocation can bypass proxy advice in either language. Call the real injected service through the container, write a row, then force an unchecked failure. Verify with a separate transaction that the row rolled back. Use kotlin-spring/all-open or the appropriate interface proxy design.
JPA and Hibernate No-argument construction, proxyability and entity equality need explicit design. A generated data-class toString or hashCode can traverse lazy relations or change with mutable fields. Load an entity, use a lazy association inside the intended boundary, persist and reload it. Configure no-arg and openness as needed for the provider and compiler version. JDBC avoids these entity-specific requirements.
Jackson and validation Constructor defaults, absent properties, explicit nulls, and field versus getter annotation placement can change accepted input. Run the same JSON fixtures through the real endpoint. Include omitted, explicit null, zero and fractional amounts. Register Jackson's Kotlin module and specify annotation targets such as @field: where required.
Generated Java code Lombok and Java annotation processors may emit methods after the Kotlin compiler needs to see them. IDE completion can mask build-order issues. Build from an empty checkout. Compile generated models in a Java module first, or verify the specific Kotlin plugin and processor integration. Compile a downstream Java consumer in CI.
Concurrency and observability Wrapping JDBC in a suspend function leaves the blocking call in place. Thread-local context, MDC and transactions need the right integration when execution moves. Carry one correlation ID through a request and an exception under load. Check trace continuity, transaction ownership, pool wait and timeout behaviour.

Spring's default transaction rollback rules also distinguish unchecked from checked exceptions. Kotlin's lack of compiler enforcement does not reclassify an IOException on the JVM. If a write must roll back on a checked failure under that configuration, specify the rollback rule and test that exact path. Migrate in slices that can be reversed

  1. Choose a seam. Start with a pure mark normaliser or vendor adapter behind an existing Java interface. Inventory consumers, ABI, exception declarations, nullable values, wire schemas and ownership of persisted data. Avoid coupling the first language change to a database or pricing model change.
  2. Make the build bilingual. Pin the Kotlin compiler and match its JVM target to the Java release. For Maven, configure Kotlin and Java source roots, compile Kotlin with Java sources visible, then run javac against Kotlin output. Apply the corresponding order for test compilation. The course companion POM is set up for Kotlin source roots; simply dropping Java files beside it is insufficient. For a large legacy build, a separately compiled Java API module and a Kotlin implementation module are easier to reason about. Mixed-source Maven configuration
  3. Freeze observable behaviour. Run historical or synthetic valuation fixtures covering ties, missing inputs, stale inputs, time zones, business-date cut-offs, retries and outages. Record output, scale, exceptions and side effects. For a client SDK, compile a new Java consumer and run a previously compiled one. Preserve overloads used by existing clients; adding a defaulted parameter can still remove the original JVM method.
  4. Compare safely. Run the Kotlin function in shadow on the same immutable inputs and reference-data snapshot. Capture mismatches keyed by business identifier and valuation time. Shadow a pure calculation or suppress all external side effects: two implementations must never both book, publish or route the same live order. Define acceptable numerical tolerances per calculation before seeing results. Use exact equality for contractual tick amounts.
  5. Measure the real path. Keep CPU, JDK, heap, GC, input distribution and warm-up comparable. Use JMH for a narrow decoder or calculation, then load-test the whole service. Compare throughput, allocation per operation, p99/p99.9 latency, GC pauses and recovery after bursts. A boxed List, a sequence chain or a dispatcher hop is a hypothesis to measure; relative performance cannot be inferred from the file extension.
  6. Cut over one writer. Route an agreed cohort or one service instance to the new implementation. Preserve identifiers, schema and event formats. Monitor pricing discrepancies, replay conflicts and dependency errors as well as latency. Keep the previous image or implementation selectable. Roll back on the pre-agreed thresholds and replay a known observation to confirm recovery.

For a finance team already operating Java Spring Boot, my default is Kotlin for new internal business logic, stable Java-shaped contracts for shared libraries, and selective migration of existing code when there is a measurable benefit. A successful pilot leaves a maintainer able to explain the price, debug the failure from a JVM stack trace, rebuild both consumers and restore the previous implementation within the desk's recovery budget.
