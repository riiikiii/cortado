Decide whether the service is meeting its contract

Imagine the desk reports “recording a quote takes two seconds”. A live process can still be unusably slow. Separate the client timeline into admission, waiting for a connection, executing SQL and sending the reply. Begin with one affected interval and one known request. Confirm the endpoint, response status and whether the client retried with the same identifier.

Make a few HTTP requests first so the relevant meter series exist. Micrometer records HTTP timings and pool metrics. Endpoint labels should identify a route template such as /quotes/{id}. Raw UUIDs as metric labels create a time series for each observation and can overwhelm the monitoring system. Use request or trace IDs in structured logs for individual investigations, subject to retention and access policy.

Separate a slow dependency from a saturated JVM

Evidence over the same interval Plausible mechanism Distinguishing observation
Borrowers waiting and active connections near maximum Database work is slow or requests exceed available pool capacity Compare query and lock wait times with pool wait times.
CPU high, little database time Parsing, allocation or application compute dominates Sample stacks or collect a bounded Java Flight Recorder recording on a representative instance.
Many 409s, normal latency Reused keys carry different payloads Compare the sender's immutable request identity and payload history.
Readiness fails on all pods, liveness stays UP A dependency shared across replicas is unavailable Check the database and network from the service network, then verify recovery.

A pool can become saturated while database CPU stays low. Return to the persistence guide and leave the winning insert uncommitted. Conflicting writers can occupy connections waiting on that one transaction while making almost no CPU progress. Raising the pool limit permits more waiters. Inspect lock holders and transaction age first.

For a controlled staging diagnosis, use a database role with the required monitoring visibility and inspect aggregate waits. An empty wait category alone does not establish that there is no lock contention. Sample over the actual incident interval.

Build an operational budget

Assume the service receives 200 requests per second and each borrows one connection for a mean of 20 ms. In a stable system the mean number occupied by these requests is about 200 × 0.020 = 4. If the database time rises to 100 ms, the same arrival rate needs about 20 concurrent connections before allowing for variability. Two pools of eight cannot sustain that steady state. Work queues, timeouts or client backoff must absorb the mismatch. The calculation uses means, not p99 latency, and ignores retries, pool acquisition and other workloads. Measure those separately.

Derive an availability indicator from valid requests. Decide deliberately whether an expected replay or an intentional conflict counts as success for the client journey. A raw percentage of non-2xx responses can page the wrong team when one sender reuses UUIDs. Track latency by route and outcome. If you need fleet-wide percentiles, configure appropriate histogram buckets before querying them; a count and sum alone give a mean. Establish a baseline at realistic payload sizes and connection counts before promising an SLO.

Graduation exercise: recover an observation across a release

Use a disposable staging namespace and a database whose backup policy and restoration process are understood. Choose a fresh ID and commit GILT at 10125. Save the request and expected response outside the pod. Send the same payload concurrently and confirm that only the original create exists. Attempt 10130 for the same ID and verify that the stored price is still 10125.

Roll a compatible second image using the previous lesson. Follow availability and the HTTP and pool metrics. Retry the original request after both new pods become ready. A replay should return 204. Introduce an invalid database configuration only in an isolated test deployment. Observe whether startup fails or established readiness drops, identify the responsible layer and recover the previous working configuration. Finally perform a binary rollback and exercise the same known key once more.

For real client traffic, close the remaining environment decisions explicitly. Identify the owner of the ingress and service identity, configure verified TLS, limit database permissions, protect management endpoints, set request and dependency deadlines, define retention and backups, and agree who acts on alerts. The sample gives you executable evidence for application behaviour. Those environment decisions supply the operating guarantees for a particular deployment.

What was exercised for this edition

The supplied Kotlin source was compiled with Kotlin 2.2.21 targeting JVM 21. All five language entry points ran, including both deadline paths and the 8,000-increment check. The three JUnit tests passed. The compiled Spring application started against a fresh PostgreSQL 17.12 database, applied V1, served the eight-request concurrency test and exposed Prometheus metrics. An identical PUT returned 204 after restarting the JVM against the same database. Container publishing, hosted CI and the Kubernetes rollout are hands-on deployment labs for your own environment.
