Make the tests fail at the right boundary

A normal unit test should run with a database outage, a broken Docker daemon and no open ports. It checks the transformations that Kotlin owns. A database race needs a real unique index and simultaneous requests. These tests have different costs and catch different defects.

The rejection test contains an out-of-range integer literal as text. It exercises parsing before the Kotlin constructor can run. The copy test checks the second path into a data class. Remove the init requirement and that test fails even if parseLine still rejects zero. This is an example of testing an invariant through all supported ways to create the value.

On Windows use the Python launcher if appropriate. The shell examples elsewhere use POSIX syntax and also work in WSL. Maven's test reports go into target/surefire-reports. The Python script needs an ordinary Python 3 installation and an available HTTP endpoint. It generates a new UUID and intentionally leaves one observation in the target. Use a disposable or designated test database.

Follow an assertion across all layers

Eight requests use identical JSON and one shared UUID. The thread pool overlaps requests; scheduling does not guarantee a particular order. Sorting statuses removes an irrelevant ordering dependency. The assertion demands exactly one creator and seven replays. The next call changes the economic value and should conflict. The following requests are invalid even though their identifier already exists. Finally the GET proves that the winning payload survived all those attempts.

An implementation that unconditionally returned 204 for all duplicates would pass the eight-request check yet fail the altered-payload check. An implementation that overwrote then returned 409 would pass the status check and fail the final GET. The fractional input tests the JSON boundary. A Java or Kotlin-only test constructing a Long cannot express that failure mode.

The HTTP run increases confidence in end-to-end wiring. Eight requests can still be scheduled serially, so this test alone cannot prove the implementation handles a real lock wait. The explicit two-session experiment in the preceding chapter controls that ordering. Add a deterministic blocked-transaction fixture in CI when changing concurrency semantics.

Structure a release build

The included workflow runs on a GitHub project containing the companion application at its root. Extract the application into its own repository before enabling it. The guide collection only distributes the archive. The workflow uses an ephemeral PostgreSQL service, builds the jar, launches it, polls readiness and runs the public smoke contract. A fresh runner removes reliance on a developer's local Maven cache or IDE.

The readiness loop has a deadline and prints the application log on failure. Without a deadline a misconfigured database can consume the entire job timeout. Without an actual readiness check the smoke test can race server startup and obscure the underlying failure. Build once for a release, publish an identifiable immutable image from the verified source and promote that image to later environments. Rebuilding from mutable base tags later can produce a different binary environment.

Failure Narrow it down
Pure tests pass, every valid HTTP call returns 400 Inspect content type, DTO shape and JSON numeric conversion.
HTTP starts but readiness stays DOWN Inspect the database connection, account, migration history and health group.
Race returns two creates Check that both requests used one key and reached a database with the unique constraint.
Replay returns 409 after unchanged payload Inspect persisted units, equality fields, normalisation and which database served the read.

Add a recovery case after a deployment change. Record a fresh UUID, restart the application while preserving its database, then retry that exact pair and expect 204. A second invocation of smoke.py uses a fresh ID and therefore cannot demonstrate persistence across restart.
