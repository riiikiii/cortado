Give one component authority over the invariant

Two healthy pods receive the same UUID at the same instant. Each JVM has its own memory, so synchronising a method or protecting a map with a mutex cannot decide the winner across both pods. PostgreSQL owns the unique index on the key and sees both writes. Put the decision there.

The UUID identifies a client's observation. The symbol identifies an instrument. Many independent observations can refer to GILT, so a unique index on symbol would reject valid events. A database constraint also protects against scripts and future services that bypass the Kotlin constructor. The price bound and symbol syntax must therefore match the application rules.

JdbcTemplate manages connection checkout, cleanup and parameter binding. The question marks stand for data values bound by the driver. A successful insert affects one row. A conflicting insert whose action is DO NOTHING affects zero. The explicit conflict target matters. It limits the replay interpretation to a collision on id. A separate constraint failure must remain distinguishable.

Trace an overlapping write

Moment Session A Session B What a third reader sees
1 INSERT K, GILT, 10125 in an open transaction Idle No committed K
2 Transaction still open Attempts INSERT with K; waits on the conflicting transaction No committed K
3 COMMIT Resolves conflict; zero inserted A's row
4 Done New SELECT reads GILT, 10125 Same row

If A rolls back at moment 3, B can insert and becomes the creator. This is the case a read-then-insert implementation misses. Both sessions can first read “absent”. Unique enforcement still stops a duplicate, but you must handle the losing write. ON CONFLICT makes the expected alternative explicit.

Our adapter uses JDBC autocommit, an immutable table through the API and primary-database reads. The comparison runs in a fresh statement after the insert finishes. The winner can commit after B's insert statement took its initial snapshot. Under PostgreSQL Read Committed a later statement can see the winner. Folding the fallback SELECT into the same statement with a CTE can yield an unexpectedly empty result under contention because the statement uses one snapshot. A read replica introduces a different problem: replication lag can briefly hide the committed row. Keep the conflict read on the primary.

From the project root use docker compose exec db psql -U quotes -d quotes in two terminals. Use an unused identifier for each experiment. First execute the following in A and leave the transaction open.

Then execute the following in B. In A issue COMMIT. B should finish with INSERT 0 0. Now run a SELECT on that identifier in B. Repeat with a fresh ID and ROLLBACK in A to observe INSERT 0 1 instead.

Know when the design stops working

The table must remain append-only for the service's advertised replay window. If another writer deletes K between the conflict and the comparison, find returns null and the adapter classifies it as a conflict. If a retention job deletes K tomorrow, tomorrow's retry can be created anew. Set the retention and retry contract together. Grant limited runtime privileges on an established schema. Run DDL with a separately controlled migration identity when moving beyond the local lab.

One SQL insertion makes the quote durable. Adding a Kafka publication immediately afterwards creates two independent commits. A crash between them would persist the quote and omit the notification. If that notification becomes a requirement, introduce an outbox row in the same database transaction and a relay with replay-aware consumers. Suspended code, a retry loop or a method named saveAndPublish cannot confer atomicity across those systems.

For a lost HTTP response after commit, retry the original ID and payload. For a 409 stop and reconcile the payload. Retrying with a fresh identifier defeats the mechanism. A unique index establishes at most one persisted row per key. It does not prove that every client ever saw a successful response.
