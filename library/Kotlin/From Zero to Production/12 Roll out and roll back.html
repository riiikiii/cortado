Deploy two interchangeable instances

Start with a registry digest from the preceding build, a Kubernetes test namespace, kubectl pointing at that cluster and a reachable PostgreSQL 17 database. An AKS or EKS cluster works with the same application manifest. Provisioning networks, identities and the managed database belongs to the target environment. The exercise begins once those exist. Configure image-pull permissions for the registry. Confirm the cluster context and namespace before applying any change.

Create a secret named quotes-db in the target namespace through your normal secret delivery mechanism. It must expose SPRING_DATASOURCE_URL, SPRING_DATASOURCE_USERNAME and SPRING_DATASOURCE_PASSWORD. For the lab the account needs migration rights on its own schema. For managed PostgreSQL use TLS with hostname and CA verification and supply the trust material your driver configuration references. The secret creation command is for first installation. An existing managed secret should already be in place. A Kubernetes Secret requires cluster access controls and appropriate protection at rest. The supplied manifest creates a ClusterIP service. Use an isolated namespace and restrict access at the network boundary until client authentication and authorisation are integrated.

Read the three probe decisions

Probe What it decides Consequence in this project
Startup Has startup finished far enough to evaluate regular probes? Repeated failure past the budget restarts the container.
Readiness Can this instance currently serve a quote? A failed DB check removes the pod from ready Service endpoints after the configured failure threshold.
Liveness Is this application process healthy enough to keep? Repeated failure restarts the container; the DB is deliberately excluded.

Putting the shared database in liveness would cause healthy processes to restart together during a database outage. Here readiness includes the database because every quote operation needs it. That choice can take every pod out of traffic during a shared outage. If the service later offers cached reads, separate capabilities or revisit this decision. Probes should be cheap and timed so a slow dependency does not itself create excessive load.

Forward the Service for an authenticated operator's local check. Keep this terminal open. In a second terminal run the smoke script. A port-forward to a Service selects a backing pod and can end when that pod is replaced. Restart the forward if necessary during later experiments.

Work through a rolling update

With two ready replicas, maxUnavailable zero and maxSurge one, the controller can start a third pod. A new pod must become available before an old one is removed. Three pools with a maximum of eight connections can temporarily require 24 database connections. Terminating pods may overlap, so leave additional headroom. If there is no capacity to schedule the surge pod, the old release can continue serving while the update stalls. Observe scheduling events before increasing probe timeouts.

Observation Next inspection
ImagePullBackOff Registry name, immutable reference, pull credentials and node architecture
Pending CPU or memory requests, node capacity, scheduling rules
Running, zero ready Readiness endpoint, database reachability, secrets and migration result
CrashLoopBackOff Previous container logs, exit code, OOMKilled reason and startup probe failures

Release a second compatible image by regenerating the manifest with its digest. Record a known key before release and read it back afterwards. Retry the same payload and check 204. In a shared staging environment also send repeated traffic through the real service route while rolling. A single port-forward cannot prove load-balanced availability.

Roll back the binary, preserve the data

A deployment progress deadline reports a stalled update. It does not automatically undo it. If a previous compatible revision exists, use the commands below and verify the known quote again. Reconcile any declarative source of truth so it retains the intended digest.

A rollback selects an earlier pod specification. Flyway history and previously committed quotes stay in PostgreSQL. Dropping the old price column in the same release that introduces a new one makes binary rollback unsafe. Expand first, run code that can coexist with both versions, backfill and validate, switch readers, then contract only after the old release and rollback window have passed. For large migrations, make lock duration and backfill progress observable independently of pod startup.
