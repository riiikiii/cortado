GUIDE 01 ⏱ 15 min read Architecture & Infra

Architecture, Domain Modeling & Local Infrastructure

Welcome to the definitive production engineering series for building a fault-tolerant, distributed Order Management System (OMS). Across 8 deep-dive guides, we will architect, code, and harden a multi-module microservices platform using Java 25 LTS, Spring Boot 4.1.3, Gradle 9.9.3, Hazelcast 5.7, and Apache Kafka 4.4 (KRaft).

1.1 Microservices Topology & Bounded Contexts

An enterprise OMS cannot rely on synchronous REST chains for order fulfillment. If inventory-service or payment-service experiences a 4-second GC pause or transient network partition, synchronous calls cascade into thread-pool exhaustion and dropped revenue. Instead, we decompose the system into four cohesive modules communicating asynchronously via Kafka 4.4 and accelerated at the read/idempotency edge by Hazelcast 5.7:

  • order-service (API + Saga Orchestrator): Owns the Order aggregate, enforces edge idempotency via Hazelcast, persists orders + outbox events atomically in PostgreSQL, and drives the Order Fulfillment Saga.
  • inventory-service (Stock Reservation + Locking): Manages SKU stock levels with pessimistic/optimistic concurrency control, executes atomic reservations, and supports commutative compensating releases.
  • payment-service (Ledger Settlement): Processes customer charges against an append-only ledger with strict idempotency guarantees and emits settlement outcomes.
  • common-events (Shared Sealed Contracts): Pure Java 25 library containing sealed interface OmsEvent, versioned EventEnvelope records, and zero Spring dependencies.

GUIDE 03 ⏱ 20 min read JPA, Lombok & Flyway

Domain Layer, Lombok Mastery & Database Persistence

Lombok and Hibernate 7 are a powerful pair—or a production outage waiting to happen. Misusing @Data on JPA entities causes LazyInitializationException in logs, triggers N+1 queries inside toString(), and corrupts HashSet collections when database-generated IDs mutate.

3.1 Lombok + JPA: Anti-Patterns vs. Production

Why this breaks in production: @Data generates equals/hashCode over all fields (including lazy @OneToMany collections and mutable @Id) and a toString() that forces lazy loading outside a transaction. 

@Data // ❌ NEVER use @Data on @Entity!
@Entity
public class BadOrderEntity {
    @Id @GeneratedValue
    private UUID id; // ❌ hashCode() changes after persist() -> lost in HashSet!

    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    private List<OrderLineItemEntity> items; // ❌ toString() triggers LazyInitializationException!
}

Production Pattern: Use @Getter, @NoArgsConstructor(access = AccessLevel.PROTECTED), explicit @ToString(onlyExplicitlyIncluded = true), and Hibernate-proxy-safe equals/hashCode using a constant class hashCode. 

@Entity
@Table(name = "orders")
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@ToString(onlyExplicitlyIncluded = true)
public class OrderEntity {
    @Id
    @ToString.Include
    private UUID id; // Assigned in Java (UUIDv7/v4) before persist -> stable identity!

    @Version
    private Long version;

    @Override
    public final boolean equals(Object o) {
        if (this == o) return true;
        if (o == null) return false;
        Class<?> oEffective = o instanceof HibernateProxy p ? p.getHibernateLazyInitializer().getPersistentClass() : o.getClass();
        Class<?> thisEffective = this instanceof HibernateProxy p ? p.getHibernateLazyInitializer().getPersistentClass() : this.getClass();
        if (thisEffective != oEffective) return false;
        OrderEntity that = (OrderEntity) o;
        return getId() != null && Objects.equals(getId(), that.getId());
    }

    @Override
    public final int hashCode() {
        return this instanceof HibernateProxy p
            ? p.getHibernateLazyInitializer().getPersistentClass().hashCode()
            : getClass().hashCode();
    }
}

            case CANCELLING     -> next == CANCELLED;
            case COMPLETED, CANCELLED -> false;
        };
    }
}

GUIDE 04 ⏱ 15 min read Concurrency & ACID

Transactions, Concurrency & Locking Deep Dive

During a flash sale, 500 concurrent requests may attempt to reserve the last 3 units of a SKU. Without disciplined transaction boundaries and row-level locking, your OMS will oversell inventory or exhaust its HikariCP connection pool in seconds.

4.1 Spring @Transactional Proxy Mechanics

  • The Self-Invocation Trap: Spring creates a CGLIB proxy around your bean. Calling this.innerTransactionalMethod() from another method in the same class bypasses the proxy completely—no transaction is started! Always extract to a separate collaborator bean.
  • Rollback Rules: By default, Spring rolls back on RuntimeException and Error, but commits on checked exceptions. Use @Transactional(rollbackFor = Exception.class) when checked exceptions represent business failures.
  • @Transactional(readOnly = true): Sets Hibernate's flush mode to MANUAL, skips dirty-checking snapshots (saving significant heap/CPU), and hints JDBC drivers to route to read replicas.

4.3 Preventing Overselling: Optimistic vs. Pessimistic Locking

In inventory-service, we implement Optimistic Locking (@Version) for normal traffic (zero lock contention) and Pessimistic Locking (SELECT ... FOR UPDATE with a 2-second timeout) for hot-SKU flash sales where optimistic retries would thrash the CPU. 

package com.oms.inventory;

import jakarta.persistence.LockModeType;
import jakarta.persistence.QueryHint;
import lombok.RequiredArgsConstructor;
import org.springframework.data.jpa.repository.*;
import org.springframework.orm.ObjectOptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.Optional;

public interface InventoryRepository extends JpaRepository<InventoryItemEntity, String> {

    // Pessimistic row-level exclusive lock with 2s timeout to prevent deadlock stalls
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "2000"))
    @Query("SELECT i FROM InventoryItemEntity i WHERE i.sku = :sku")
    Optional<InventoryItemEntity> findBySkuForUpdate(String sku);
}

@Service
@RequiredArgsConstructor
public class InventoryReservationService {

    private final InventoryRepository inventoryRepository;

    // Strategy A: Pessimistic Lock (Best for high-contention flash-sale SKUs)
    @Transactional
    public void reserveStockPessimistic(String sku, int quantity) {
        InventoryItemEntity item = inventoryRepository.findBySkuForUpdate(sku)
            .orElseThrow(() -> new IllegalArgumentException("Unknown SKU: " + sku));

        if (item.getAvailableQty() < quantity) {
            throw new InsufficientStockException(sku, item.getAvailableQty(), quantity);
        }
        item.reserve(quantity); // Mutates managed entity -> flushed on commit
    }

    // Strategy B: Optimistic Lock with bounded retry (Best for low-contention catalog)
    public void reserveStockOptimistic(String sku, int quantity) {
        int maxAttempts = 3;
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            try {
                attemptOptimisticReserve(sku, quantity);
                return;
            } catch (ObjectOptimisticLockingFailureException ex) {
                if (attempt == maxAttempts) throw ex;
            }
        }
    }

    @Transactional
    protected void attemptOptimisticReserve(String sku, int quantity) {
        InventoryItemEntity item = inventoryRepository.findById(sku)
            .orElseThrow(() -> new IllegalArgumentException("Unknown SKU: " + sku));
        item.reserve(quantity); // Hibernate checks: UPDATE ... WHERE sku=? AND version=?
    }
}
🔥 Concurrency Warning: Never Perform Network I/O Inside @Transactional

Suppose your HikariCP pool has 15 connections. If a @Transactional method calls a payment gateway HTTP API taking 300ms, your maximum theoretical throughput collapses to 15 / 0.3s = 50 req/sec—even if your CPU is 95% idle!

Rule: Keep database transactions under 15ms. Perform all Kafka publishing and external HTTP calls outside the transaction (or via the Transactional Outbox in Guide 07).

GUIDE 05 ⏱ 20 min read Hazelcast 5.7

Hazelcast 5.7 Distributed Caching, Near Cache & Idempotency

In production microservices, we run Hazelcast 5.7 in Client-Server topology—never Embedded. Why? When Kubernetes autoscales order-service pods up or down, an embedded Hazelcast cluster would trigger constant partition migrations and GC pauses. Decoupling the Hazelcast data grid lets microservices scale elastically in seconds.

5.1 Hazelcast 271-Partition Distribution & L1 Near Cache

5.2 Smart Client Config & Zero-Reflection Compact Serialization

Standard Java Serializable is slow, bloated, and brittle across deployments. Hazelcast's Compact Serialization is zero-reflection, schema-evolved, and ~5x faster and smaller on the wire. 

package com.oms.order.cache;

import com.hazelcast.nio.serialization.compact.*;
import java.math.BigDecimal;
import java.util.UUID;

public record OrderSnapshot(UUID orderId, UUID customerId, String status, BigDecimal totalAmount) {}

public class OrderSnapshotCompactSerializer implements CompactSerializer<OrderSnapshot> {
    @Override
    public OrderSnapshot read(CompactReader reader) {
        return new OrderSnapshot(
            UUID.fromString(reader.readString("orderId")),
            UUID.fromString(reader.readString("customerId")),
            reader.readString("status"),
            reader.readDecimal("totalAmount")
        );
    }

    @Override
    public void write(CompactWriter writer, OrderSnapshot snapshot) {
        writer.writeString("orderId", snapshot.orderId().toString());
        writer.writeString("customerId", snapshot.customerId().toString());
        writer.writeString("status", snapshot.status());
        writer.writeDecimal("totalAmount", snapshot.totalAmount());
    }

    @Override
    public String getTypeName() { return "oms.OrderSnapshot"; }

    @Override
    public Class<OrderSnapshot> getCompactClass() { return OrderSnapshot.class; }
}

    }

6.3 Resilient Consumer with @RetryableTopic & Two-Tier Idempotency

Kafka guarantees at-least-once delivery. Network blips or consumer crashes before offset commit will redeliver the same message. We defend with Two-Tier Idempotency: a sub-millisecond Hazelcast check to drop obvious duplicates, backed by a PostgreSQL processed_events primary-key constraint inside the exact same business transaction. 

package com.oms.inventory.kafka;

import com.oms.events.EventEnvelope;
import com.oms.events.OmsEvent;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.kafka.annotation.*;
import org.springframework.kafka.retrytopic.TopicSuffixingStrategy;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.retry.annotation.Backoff;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Slf4j
@Component
@RequiredArgsConstructor
public class InventoryCommandConsumer {

    private final ProcessedEventRepository processedEventRepo;
    private final InventoryReservationService reservationService;

    @RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 1000, multiplier = 2.0, maxDelay = 10000),
        topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_INDEX_VALUE,
        dltTopicSuffix = ".dlt"
    )
    @KafkaListener(topics = "oms.inventory.commands", groupId = "inventory-service")
    @Transactional
    public void onCommand(EventEnvelope<OmsEvent> envelope, Acknowledgment ack) {
        // Tier-2 Durable Idempotency: INSERT ... ON CONFLICT DO NOTHING
        int inserted = processedEventRepo.insertIfAbsent(envelope.eventId(), "inventory-service");
        if (inserted == 0) {
            log.info("Duplicate eventId={} skipped idempotently", envelope.eventId());
            ack.acknowledge();
            return;
        }

        // Java 25 Exhaustive Pattern Matching over Sealed Interface
        switch (envelope.payload()) {
            case OmsEvent.ReserveStockCommand cmd -> reservationService.handleReserve(cmd);
            case OmsEvent.ReleaseStockCommand cmd -> reservationService.handleRelease(cmd);
            default -> log.warn("Ignoring unrelated event type: {}", envelope.payload().getClass());
        }

        ack.acknowledge(); // Manual commit only after DB transaction succeeds
    }

    @DltHandler
    public void handleDlt(EventEnvelope<OmsEvent> envelope) {
        log.error("CRITICAL: Message routed to DLT! eventId={}, orderId={}",
            envelope.eventId(), envelope.payload().orderId());
    }
}

7.1 Atomic Order + Outbox Persistence

package com.oms.order.application;

import com.oms.events.OmsEvent;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import tools.jackson.databind.json.JsonMapper;
import java.util.UUID;

@Service
@RequiredArgsConstructor
public class OrderApplicationService {

    private final OrderRepository orderRepository;
    private final OutboxRepository outboxRepository;
    private final JsonMapper jsonMapper; // Spring Boot 4 / Jackson 3

    @Transactional
    public OrderEntity createOrder(CreateOrderRequest req) {
        // 1. Persist Order Aggregate
        OrderEntity order = OrderEntity.createPending(req);
        orderRepository.save(order);

        // 2. Append Outbox Event inside the EXACT SAME PostgreSQL transaction
        var command = new OmsEvent.ReserveStockCommand(order.getId(), order.toEventLineItems());
        OutboxEventEntity outbox = OutboxEventEntity.pending(
            "Order",
            order.getId().toString(),
            "ReserveStockCommand",
            "oms.inventory.commands",
            jsonMapper.writeValueAsString(command)
        );
        outboxRepository.save(outbox);

        // Both commit atomically or both roll back. Zero dual-writes!
        return order;
    }
}

7.2 Relay Implementation: Polling vs. Debezium CDC

Zero extra infrastructure. Uses PostgreSQL's FOR UPDATE SKIP LOCKED so multiple order-service pods can poll concurrently without ever claiming the same outbox row. 

@Component
@RequiredArgsConstructor
public class OutboxPollingRelay {

    private final OutboxRepository outboxRepository;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelay = 250)
    @Transactional
    public void relayPendingEvents() {
        // SELECT * FROM outbox_events WHERE status = 'PENDING'
        // ORDER BY created_at ASC LIMIT 100 FOR UPDATE SKIP LOCKED
        List<OutboxEventEntity> batch = outboxRepository.claimNextBatch(100);

        for (OutboxEventEntity event : batch) {
            kafkaTemplate.send(event.getTopic(), event.getAggregateId(), event.getPayload())
                         .join(); // Wait for broker ack before marking PUBLISHED
            event.markPublished();
        }
    }
}

8.1 Saga Orchestrator & Out-of-Order Tombstone Compensation

package com.oms.order.saga;

import com.oms.events.OmsEvent;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
public class OrderSagaOrchestrator {

    private final OrderRepository orderRepository;
    private final OutboxService outboxService;

    @Transactional
    public void onStockReserved(OmsEvent.StockReservedEvent event) {
        OrderEntity order = orderRepository.findByIdOrThrow(event.orderId());
        order.transitionTo(OrderStatus.STOCK_RESERVED);

        // Forward Step 2: Charge Payment via Transactional Outbox
        outboxService.enqueue("oms.payment.commands", order.getId().toString(),
            new OmsEvent.ProcessPaymentCommand(
                order.getId(), order.getCustomerId(), order.getTotalAmount(), order.getCurrency()
            ));
    }

    @Transactional
    public void onPaymentFailed(OmsEvent.PaymentFailedEvent event) {
        OrderEntity order = orderRepository.findByIdOrThrow(event.orderId());
        order.transitionTo(OrderStatus.CANCELLING);
        order.setFailureReason(event.reason());

        // Backward Compensation: Release reserved inventory
        outboxService.enqueue("oms.inventory.commands", order.getId().toString(),
            new OmsEvent.ReleaseStockCommand(
                order.getId(), order.toEventLineItems(), "Payment failed: " + event.reason()
            ));
    }

    @Transactional
    public void onPaymentCompleted(OmsEvent.PaymentCompletedEvent event) {
        OrderEntity order = orderRepository.findByIdOrThrow(event.orderId());
        order.transitionTo(OrderStatus.COMPLETED);
    }
}
