1Why ORMs exist

Java thinks in objects that point at each other. A relational database thinks in sets of rows that refer to each other by value. Every Java application that talks to a database has to translate between those two worlds, and an object-relational mapper (ORM) is a library that does the translation for you.

That translation is harder than it looks, and the difficulties have a name: the object-relational impedance mismatch. It shows up in five places.

  • Identity. Java has two notions of sameness, a == b and a.equals(b). The database has a third: same primary key. An ORM has to keep all three in step.
  • Granularity. You might model an Address as its own small object, but store it as three columns in the venue table. Objects are often finer-grained than tables.
  • Inheritance. Java classes extend each other. SQL tables don't, so a class hierarchy has to be flattened, split or duplicated.
  • Associations. An object reference points one way: a concert knows its venue. A foreign key can be joined from either side, and a many-to-many relationship needs a third table that has no class of its own.
  • Navigation. In Java you walk a graph one reference at a time. In SQL you ask for everything you need in one go, with a join. This mismatch causes more performance problems than the other four put together.

What an ORM actually gives you

Martin Fowler named the moving parts in Patterns of Enterprise Application Architecture (2002), and every serious Java ORM implements them:

  • Data mapper: annotations describe how classes map to tables, so domain classes contain no SQL.
  • Unit of work: it tracks what you created, changed or deleted, and writes the SQL at the end.
  • Identity map: one row, one Java object, per unit of work.
  • Lazy load: related objects load when you first touch them.
  • Dialects and a query language: correct SQL for each database from one mapping, and queries written in classes and fields.

The price is that SQL is now generated rather than written, and generated SQL can surprise you. The thesis of this guide is simple: use the ORM for what it does well, and always know what SQL it is sending. People who get into trouble with ORMs almost always broke the second half of that rule.

2Your first entity

We'll use one small domain all the way through: a concert-ticketing system. Venues host concerts, concerts have tickets, and fans buy them. It is just big enough to show every interesting problem, including two fans trying to buy the last seat at the same moment.

Add Hibernate and a JDBC driver. If you're using Spring Boot, skip this: the spring-boot-starter-data-jpa starter brings Hibernate 7 with it.

Now the entity. Read every annotation: each one is a decision.

  • @Entity makes the class persistent, mapped by default to a table of the same name.
  • @Id marks the primary key. Its position also sets the access type: on a field, Hibernate reads fields directly; on a getter, it uses getters and setters. Field access is usual, because it keeps setters out of your API.
  • @GeneratedValue asks the database to supply the key (strategies below).
  • @Column is optional: every non-transient field is persisted anyway. Add it for constraints, lengths or a different name.
  • @Enumerated(EnumType.STRING) stores ON_SALE rather than 0. The default is ORDINAL, which silently corrupts your data the day someone reorders the enum constants.
  • The two association annotations are the subject of the next chapter.

JPA has a few rules for entity classes. They need a no-argument constructor (it can be protected), they must not be final (Hibernate creates subclasses at runtime as lazy-loading proxies), and their persistent fields must not be final either. That's why a Java record can't be an entity. Records are still welcome, though: since JPA 3.2 they can be embeddables, and they make excellent read-only query results.

Guru note: names

That's why startsAt has an explicit column name. Left alone, plain Hibernate maps it to a column called startsAt (which PostgreSQL folds to startsat), while Spring Boot configures a naming strategy that produces starts_at. If you move code between the two, or share a schema with another team, set the naming strategy explicitly rather than relying on defaults.

3Associations

Associations are where an ORM earns its keep, and where most mapping bugs live. The key idea is the owning side.

In the database, the relationship between a concert and its tickets is one foreign key column: ticket.concert_id. In Java you can have two references, ticket.concert and concert.tickets. Two references, one column: Hibernate needs to know which reference to read when it writes that column. The answer is the side that has the foreign key, and you mark the other side with mappedBy.

In Concert, @OneToMany(mappedBy = "concert") says "this collection is the mirror image of Ticket.concert; don't write anything for it". Because two Java references now describe one fact, keep them in step with small methods on the parent:

Pitfall: changing only the inverse side

If you add a ticket to concert.getTickets() but never set ticket.concert, nothing is written: the collection is the inverse side and Hibernate ignores it when deciding the foreign key. Changes are only persisted from the owning side. Helper methods make this mistake impossible.

Fetch types: make everything lazy

Every association has a fetch type. LAZY means "load it when I touch it"; EAGER means "always load it with the owner". The JPA defaults are historical and inconsistent:

AnnotationDefault fetchWhat to use
@ManyToOneEAGERLAZY
@OneToOneEAGERLAZY
@OneToManyLAZYLAZY
@ManyToManyLAZYLAZY

The rule is to map every association as LAZY and decide what to fetch per query (chapter 6). An eager mapping applies everywhere, forever, even to the screen that only needed the concert title. Worse, a JPQL query ignores eager joins in the mapping and fetches eager associations with extra selects afterwards. Lazy mappings plus explicit fetching give you control; eager mappings take it away. Jakarta Persistence 4.0 is adding a persistence-unit setting that makes to-one associations lazy by default, which tells you where the experts landed.

Cascades and orphans

A cascade passes an operation from parent to child: with cascade = CascadeType.ALL on Concert.tickets, persisting a concert persists its new tickets and removing it removes them. orphanRemoval = true goes further: a ticket removed from the collection is deleted from the database.

Cascade from aggregate roots to the things they own, and nowhere else. A ticket doesn't own its concert, so Ticket.concert has no cascade. A fan doesn't own the tickets they hold. And never put CascadeType.REMOVE on a @ManyToMany: deleting one student would try to delete every course they were enrolled in, along with everyone else's enrolment.

Lists, sets and bags

A List without an @OrderColumn is what Hibernate calls a bag: an unordered collection that allows duplicates. Bags are fine on their own, but you can't join-fetch two bags in one query, because the result would be a Cartesian product. Hibernate refuses with a MultipleBagFetchException. If an entity has several collections you'll fetch together, use Set for them, or fetch them in separate queries.

Many-to-many: usually a missing entity

@ManyToMany works, but real relationships grow attributes. "Fan follows artist" soon needs a followedAt date, which a bare join table can't hold. Model the link as its own entity (Follow, with two @ManyToOnes) from the start.

Guru note: the lazy one-to-one that isn't

On the inverse (mappedBy) side of a @OneToOne, Hibernate can't use a proxy, because it doesn't know whether the related row exists until it looks. So that side is effectively eager unless you enable bytecode enhancement. The fix most experts use is to share the primary key with @MapsId and map only the owning side.

Inheritance

If you have Event with subclasses Concert and Comedy, JPA offers three ways to store the hierarchy:

StrategyTablesTrade-off
SINGLE_TABLEOne table with a discriminator columnFastest queries and simplest SQL, but subclass columns must be nullable.
JOINEDOne table per class, joined on the keyNormalised, allows constraints. Polymorphic queries need joins.
TABLE_PER_CLASSOne full table per concrete classPolymorphic queries need UNIONs. Rarely the right answer.

Start with SINGLE_TABLE. To share fields like createdAt without polymorphic queries, use @MappedSuperclass: no hierarchy in the database at all.

equals and hashCode

Entities go into sets and get compared, so they need equals and hashCode that survive a lifecycle in which the ID starts as null and is assigned later. This version is safe:

Use other.getId() rather than other.id: on an uninitialised proxy the field is empty, but the getter works. If your entity has a natural key that never changes, such as a fan's email, comparing on that is even better.

Pitfall: Lombok's @Data on entities

@Data generates equals, hashCode and toString over every field, including lazy collections. Logging an entity can then trigger a cascade of queries, or a LazyInitializationException, or a stack overflow on a bidirectional pair. Use @Getter and write the other three by hand.

4The persistence context

If you understand one thing deeply, make it this. The persistence context is the unit of work and identity map from chapter 1, living inside every EntityManager (Hibernate calls it the Session). Almost every ORM behaviour that surprises people is the persistence context doing exactly what it was designed to do.

Think of it as a map from (entity type, ID) to a Java object, plus a snapshot of the values loaded from the database. Watch what happens in this method:

There is no save() call, and there doesn't need to be. The objects are managed: at flush time Hibernate compares each one with its snapshot (this is dirty checking) and generates an UPDATE for each that changed. That's also why the second find costs nothing and returns the identical object: one row, one object, per persistence context.

Flush means "send the pending SQL"; commit means "make it permanent". Hibernate flushes automatically at commit, before running a query whose results might be affected by pending changes, and whenever you call flush(). Until then, changes live only in memory. This write-behind is what makes batching possible: twenty updates to the same table can go in one JDBC round trip.

The four states of an entity

persist versus merge

persist(x) makes x itself managed. merge(x) does something quite different: it finds or loads the managed instance with the same ID, copies x's state onto it, and returns that managed instance. The object you passed in stays detached. This trips up nearly everyone once:

In Spring Data

repository.save(entity) calls persist if the entity looks new and merge otherwise. "New" means a null @Version if the entity has a wrapper-typed one (Long, not long), and otherwise a null ID. So always use the return value of save(). And if you assign IDs yourself, say a UUID in the constructor, every save of a brand-new entity looks like a merge and costs an extra SELECT. Add a Long @Version field or implement Persistable to fix it. Inside a transaction you rarely need save() for updates at all: dirty checking does it.

find versus getReference

find() returns the real object, querying if needed. getReference() returns a proxy holding only the ID, with no query until you call one of its other methods. That's perfect for setting a foreign key:

Scope, and the famous exception

A persistence context is cheap to create and not thread-safe. Use one per unit of work, which in Spring means one per transaction. It also holds a reference to everything it has loaded, so a batch job that streams a million rows through one context will run out of memory unless it calls flush() and clear() every few hundred rows.

When the context closes, its entities become detached, and an uninitialised lazy proxy can no longer reach the database. Touching it throws LazyInitializationException. The exception is a symptom, not the disease: it means some code needed data that the query didn't fetch. The fix is to fetch what the use case needs while the transaction is open (chapter 6), not to make the association eager or keep the session open longer.

5Querying

Choose your query by what you'll do with the result. If you're going to change it, load entities, so dirty checking can write the changes back. If you're only going to show it, load exactly the columns you need into a DTO. Most screens are read-only, so most queries should return DTOs.

JPQL and HQL

JPQL is SQL-shaped but speaks in entities and fields. HQL is Hibernate's superset of it, and in Hibernate 6 and later the two are almost the same language. Paths like c.venue.address.city become joins for you.

Always bind values as parameters, never by concatenating strings. Parameters prevent SQL injection and let the database reuse execution plans. JPA 3.2 standardised several things Hibernate users had long enjoyed: queries without a select clause (from Concert where status = :s), union, intersect and except, and functions such as cast(), left(), right(), replace(), id() and version().

DTO projections with records

One query, four columns, no entities, nothing for the persistence context to track. Note the fully qualified class name in select new, which JPA requires.

Criteria API and the metamodel

For queries assembled at runtime, such as a search form with optional filters, use the Criteria API. Add the hibernate-processor annotation processor to your build and it generates a static metamodel: a class Concert_ whose fields describe Concert's attributes. Typos then fail at compile time instead of in production.

And when you need something the query language can't express cleanly, such as a recursive CTE or a vendor-specific function, write native SQL with createNativeQuery. Using an ORM doesn't mean giving up SQL.

Spring Data repositories

Spring Data JPA derives queries from method names, takes explicit JPQL in @Query, and can shape results into interfaces or records:

Jakarta Data: the standard repository

Jakarta Data takes the repository idea and standardises it. With Hibernate's implementation, the annotation processor generates the repository and type-checks your queries at compile time. A misspelt field in a query is a build error.

Hibernate's repositories run on a StatelessSession by default: no persistence context, no lazy loading, no dirty checking. You call @Update when you want an update. It's more explicit and harder to misuse, and it's where the standard is heading (chapter 10).

Paging: offset versus keyset

setFirstResult and setMaxResults (or Spring's Pageable) produce OFFSET pagination. It's simple, but page 5,000 makes the database read and throw away 100,000 rows. For deep or infinite scrolling, use keyset pagination: remember the last row you showed and seek past it.

Spring Data supports keyset scrolling through ScrollPosition.keyset() and the Window result type, and Hibernate has KeyedPage. Always order by something unique, such as adding the ID as a tie-breaker.

Bulk updates skip the persistence context

This is one SQL statement and far faster than loading every ticket. But it goes straight to the database: tickets already loaded in this persistence context still hold the old price, and their @Version values don't change. Run bulk statements at the start of a transaction, or call em.clear() afterwards. (HQL's update versioned also bumps the version.)

6Performance

ORM performance problems are almost never Hibernate being slow at Java. They're Hibernate sending more SQL than you expected, because the code asked for it without realising.

The N+1 problem

The loop looks innocent. But getVenue() returns a lazy proxy, and getName() makes it load, so each venue costs its own query. Try the four standard fixes on the same task: 100 concerts spread across 40 venues.

Pick a fetch strategy and see what reaches the database.

41SQL statements
select c1_0.id, ..., c1_0.venue_id from concert c1_0
select v1_0.id, v1_0.capacity, ... from venue v1_0 where v1_0.id=?   -- venue 1
select v1_0.id, v1_0.capacity, ... from venue v1_0 where v1_0.id=?   -- venue 2
-- ... 37 more ...
select v1_0.id, v1_0.capacity, ... from venue v1_0 where v1_0.id=?   -- venue 40

Why 41 and not 101? The persistence context loads each venue once; concerts at the same venue share one object. It's still 40 network round trips that a single join would have avoided. Mapping venue as EAGER wouldn't help: a JPQL query fetches eager associations with these same extra selects, just earlier.

1SQL statement
select c1_0.id, ..., v1_0.id, v1_0.name, ...
from concert c1_0 join venue v1_0 on v1_0.id=c1_0.venue_id

select c from Concert c join fetch c.venue loads the concerts and their venues in one statement. In Spring Data, @EntityGraph(attributePaths = "venue") does the same without writing JPQL. Best when you know the use case needs the association. Be careful join-fetching collections with paging; see below.

4SQL statements
select c1_0.id, ... from concert c1_0
select v1_0.id, ... from venue v1_0 where v1_0.id = any (?)   -- 16 ids
select v1_0.id, ... from venue v1_0 where v1_0.id = any (?)   -- 16 ids
select v1_0.id, ... from venue v1_0 where v1_0.id = any (?)   -- 8 ids

With hibernate.default_batch_fetch_size=16 (or @BatchSize on the association), touching one uninitialised venue loads up to 16 of them at once. On PostgreSQL, Hibernate passes the IDs as a single array parameter; on other databases it uses an IN list. It's a safety net that fixes N+1 everywhere without changing any queries. Many teams set it globally on day one.

1SQL statement
select c1_0.title, v1_0.name
from concert c1_0 join venue v1_0 on v1_0.id=c1_0.venue_id

select new com.example.ConcertLine(c.title, c.venue.name) from Concert c fetches exactly two columns. No entities are created, nothing is dirty-checked, and the result can't trigger lazy loading later. For a read-only list this is the fastest option and usually the right one.

Collections behave the same way, but worse, because they don't share. Calling c.getTickets().size() in that loop costs one query per concert: 1 + 100. The same four fixes apply.

The pagination trap

Combine a collection join fetch with setMaxResults(20) and Hibernate can't put LIMIT in the SQL, because the database would be limiting joined rows, not concerts. So it fetches everything and pages in memory, logging warning HHH90003004. Fine in tests, a disaster on a real table. Turn the warning into an error with hibernate.query.fail_on_pagination_over_collection_fetch=true, and page in two steps:

You don't need distinct here: since Hibernate 6, entity results of a join fetch are de-duplicated automatically.

Writing fast: batching

By default every INSERT and UPDATE is its own round trip. Turn on JDBC batching and Hibernate groups them:

This is where SEQUENCE keys pay off. With IDENTITY, Hibernate must execute each insert immediately to learn its key, so insert batching quietly switches off. For large imports, skip the persistence context entirely with a StatelessSession: no snapshots, no first-level cache, just insert(), update() and delete() that go straight to JDBC.

Caching: know the three levels

  • First-level cache: the persistence context itself. Always on, scoped to one transaction. It's why repeated find()s are free.
  • Second-level cache: opt-in, shared across transactions, provided by a JCache implementation. Excellent for read-mostly reference data, such as venues. Wrong for frequently updated data, such as tickets, where cache invalidation costs more than the query it saves. Mark entities with @Cacheable.
  • Query cache: stores query results and is invalidated whenever any table in the query changes. Rarely worth it.
Pitfall: Open Session in View

Spring Boot enables spring.jpa.open-in-view by default, and logs a warning saying so. It keeps the persistence context open until the HTTP response is rendered, so lazy loading "just works" in controllers and views. The cost: a database connection is held for the whole request, and queries fire from places nobody reviews, often as N+1s. Set it to false and fetch what each endpoint needs in the service layer.

Make the SQL visible

You can't fix what you can't see. In development, log every statement and its bind values; in production, log the slow ones.

Then make it a test: assert the number of statements a use case sends (chapter 8). Once that number is pinned in CI, nobody can introduce an N+1 by accident.

7Transactions and concurrency

The persistence context lives inside a transaction, so where you draw transaction boundaries decides what you can lazily load, when changes are written, and how long you hold database connections and locks.

Put @Transactional on service methods that represent one business operation. Keep them short, and never make remote calls (HTTP, messaging, email) inside one: you'd be holding a connection, and maybe row locks, while waiting on someone else's network.

  • @Transactional(readOnly = true) on queries. Spring tells Hibernate not to flush, and Hibernate can skip keeping snapshots for dirty checking.
  • The default propagation, REQUIRED, joins an existing transaction. REQUIRES_NEW suspends it and starts a separate one, for an audit record that must survive a rollback, for example.
  • By default Spring rolls back on unchecked exceptions only. A checked exception commits unless you set rollbackFor.
Pitfall: self-invocation

Spring applies @Transactional through a proxy. If placeOrder() calls this.reserveSeats() in the same class, the call doesn't go through the proxy, and reserveSeats()'s annotation is ignored. Move the method to another bean, or put the transaction on the outer method.

The last ticket

Two fans open the same concert page. One seat is left. Both click "buy" within a millisecond:

Both transactions read the ticket, both see no holder, both set themselves as holder, both commit. The second update silently overwrites the first. This is a lost update, and the database's default isolation level (read committed on PostgreSQL, Oracle and SQL Server) does not prevent it.

Fix 1: optimistic locking

The @Version field on Ticket changes the update Hibernate sends:

The first commit matches the row and moves it to version 4. The second finds no row with version 3, updates nothing, and Hibernate throws an OptimisticLockException (Spring wraps it as ObjectOptimisticLockingFailureException). Nothing is overwritten. You then tell the fan the seat is gone, or retry the whole transaction from a fresh read. Optimistic locking takes no locks at all, so it suits the common case where conflicts are rare. Put @Version on every entity that users edit concurrently.

Fix 2: an atomic conditional update

One statement; the database guarantees only one caller can match the row. A return value of 1 means you got the seat, 0 means someone beat you. Often the simplest correct answer is a well-aimed piece of SQL.

Fix 3: pessimistic locking

@Lock(LockModeType.PESSIMISTIC_WRITE) on a repository method (or em.find(Ticket.class, id, LockModeType.PESSIMISTIC_WRITE)) emits SELECT ... FOR UPDATE: the second buyer waits until the first commits, then sees the holder. Use it when conflicts are frequent, and keep the transaction tiny. For work queues, where several workers grab jobs, add SKIP LOCKED so each worker takes rows nobody else holds; Hibernate treats a lock timeout of -2 as SKIP LOCKED on databases that support it.

8Schema and testing

Hibernate can create your schema from the mappings, and that's lovely for a tutorial. It's not how you run production.

spring.jpa.hibernate.ddl-auto (plain Hibernate: hibernate.hbm2ddl.auto) accepts none, validate, update, create and create-drop. Use create-drop for throwaway experiments only. In every real environment, manage the schema with versioned migration scripts in Flyway or Liquibase, reviewed like any other code, and set Hibernate to validate so the application refuses to start if mappings and schema disagree. update never drops or renames anything and can't migrate data, so it drifts.

Test against the real database

An in-memory H2 database is not PostgreSQL. It differs in SQL syntax, types, locking and the query plans that drive performance. Testcontainers starts the real thing in Docker for each test run, and Spring Boot wires it in with one annotation:

9Beyond JPA

JPA is the default in Java, not the only option. The real question is which side owns the truth. If your domain model is the centre and the database is how you store it, a full ORM fits. If the SQL is the centre, because of complex reporting, a schema owned by DBAs, or performance-critical queries, a SQL-first tool fits better. Many good systems use both.

jOOQ: SQL as Java

jOOQ reads your schema and generates a class per table. You then write SQL in Java, and the compiler checks every table, column and type:

If someone renames a column, the build breaks rather than a query in production. jOOQ's MULTISET operator can even nest collections, such as concerts with their tickets, inside one SQL statement, with no N+1. The open-source edition supports open-source databases and needs Java 21 from version 3.20; commercial editions add Oracle, SQL Server and others.

MyBatis: you write the SQL, it maps the results

There's no query language to learn and no generated SQL to second-guess: what you write is what runs. #{city} binds a parameter safely (avoid ${...}, which pastes text into the SQL). Turn on mapUnderscoreToCamelCase so starts_at fills startsAt. The trade-off is that you also write every insert and update yourself.

Mixing them

A pattern that ages well: use JPA for the write side, where loading an aggregate, changing it and letting dirty checking and optimistic locking do the rest is exactly right, and use jOOQ or native SQL for read-heavy screens and reports, where you want precise SQL returning DTOs. Both can share one transaction and one DataSource. Nobody gives out prizes for using a single tool.

Java persistence is in its busiest period in a decade. Here's the state of play in November 2026.

  • Hibernate 7.4 is the current stable series, and Spring Boot 4.1 ships with it. Hibernate 7 implements Jakarta Persistence 3.2 and Jakarta Data 1.0, needs Java 17, and is the first fully Apache-licensed release. Its StatelessSession has grown to near feature parity with Session.
  • Jakarta Persistence 4.0 is under active development for Jakarta EE 12, with the release targeted for late 2026 and milestone builds available now.
  • Hibernate 8.0 released its first candidate on 12 November 2026. It implements the JPA 4.0 drafts and Jakarta Data 1.1.
  • Spring: Spring Boot 4 sits on Jakarta EE 11, so JPA 3.2 and Hibernate 7. Spring Boot 4.2 was scheduled for November 2026, and Spring Data can now generate repository implementations ahead of time (AOT) for faster startup.

The headline JPA 4 changes

Based on the milestone drafts, so details may still change:

  • EntityAgent standardises Hibernate's StatelessSession: explicit insert, update, delete and upsert that act directly on the database, with no persistence context. The standard is formally acknowledging that the stateful model isn't always the right one.
  • Static queries declared with annotations and type-checked at compile time by an annotation processor, referenced through the generated metamodel.
  • A Statement interface separates updates and deletes from queries, and TypedQuery.ofType() returns records without select new.
  • A persistence-unit default that makes @ManyToOne and @OneToOne lazy, plus findMultiple() for loading batches by ID and a get() that throws instead of returning null.

Hibernate 8 also changes how flushing works internally: it plans inserts, updates and deletes as a graph using the mapped foreign-key constraints, which removes a whole class of constraint-ordering surprises.

The direction is clear: more compile-time checking, more explicit operations, less hidden magic. Chapters 4 to 7 don't go out of date; they're what lets you choose between the stateful and stateless models with your eyes open.

11Guru check

Ten rules that cover most of what separates a calm ORM codebase from a haunted one.

  1. Map every association LAZY, and decide what to fetch in each query.
  2. Turn off Open Session in View, and load what each endpoint needs in the service layer.
  3. Use SEQUENCE (or time-ordered UUID) keys, turn on JDBC batching, and set a default batch fetch size.
  4. Read with DTO projections; load entities only when you're going to change them.
  5. Put @Version on every entity users can edit at the same time.
  6. Keep transactions short, in the service layer, with no remote calls inside.
  7. Write associations from the owning side, through helper methods that keep both sides in step.
  8. Manage the schema with migrations, and run Hibernate in validate mode.
  9. Test against the real database, and assert the number of statements per use case.
  10. Know when to drop to SQL, with jOOQ, MyBatis or a native query, and do it without guilt.

Test yourself

Answer each in your head before opening it.

You load 100 concerts held at 40 venues, with venue mapped LAZY, and print each venue's name in a loop. How many SELECTs run?

41: one for the concerts and one per distinct venue. The persistence context loads each venue only once, so concerts at the same venue share an object. A join fetch, an entity graph or a DTO projection brings it to 1; batch fetching with size 16 brings it to 4.

You call repository.save(fan) on a detached fan, then call fan.setName("Ada") before the transaction commits. Is the new name saved?

No. For a detached entity, save() calls merge(), which returns a different, managed instance. Your fan variable still points at the untracked object. Always use the return value: fan = repository.save(fan);

Why does GenerationType.IDENTITY hurt bulk inserts in Hibernate?

The key only exists after the database runs the INSERT, and Hibernate needs the key straight away to put the entity in the persistence context. So it executes each insert immediately instead of delaying and batching them. Sequences let Hibernate assign keys in memory.

You add a ticket to concert.getTickets() but never call ticket.setConcert(concert). What does the database contain after commit?

Nothing links the two. Concert.tickets is the inverse side (mappedBy), so Hibernate ignores it when writing the foreign key. With the cascade, the ticket is inserted, but with a null concert_id, or the insert fails if the column is NOT NULL. Write from the owning side, through a helper method.

A query join-fetches c.tickets and calls setMaxResults(20). What happens?

Hibernate can't apply LIMIT to joined rows without cutting a concert's tickets in half, so it fetches every row and paginates in memory, logging HHH90003004. Page the IDs first, then fetch the graph for those IDs.

Inside one transaction you load a ticket, then run a bulk JPQL update that changes its price, then read ticket.getPrice(). Which price do you see?

The old one. Bulk statements go straight to the database and don't touch the persistence context. Call em.clear() after the bulk update (or run it first) and reload.

A @Transactional method is called from another method in the same class that isn't transactional. Does it run in a transaction?

No. Spring's transaction proxy only sees calls that come from outside the bean, so a call through this skips it. Move the method to another bean or make the calling method transactional.

Two fans buy the last ticket at the same moment, and Ticket has a @Version field. What happens?

Both read version 3. The first commit runs update ... where id = ? and version = 3 and succeeds. The second matches no rows, and Hibernate throws OptimisticLockException. Nothing is overwritten; the application tells the second fan the seat has gone, or retries from a fresh read.

What exactly does dirty checking compare, and when?

At flush time, it compares each managed entity's current field values with the snapshot taken when the entity was loaded, and generates an UPDATE for each that differs. Read-only transactions and stateless sessions skip it, which is part of why they're cheaper.
