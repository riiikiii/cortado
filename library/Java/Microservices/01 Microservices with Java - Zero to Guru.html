Level 1 · Zero

What microservices are, and when they're worth it

Before any code: the shape of the idea, the price you pay, and how to cut a system into pieces that won't fight each other.

  • Explain microservices in one sentence
  • Weigh them against a modular monolith
  • Draw service boundaries

1.1What a microservice really is

Here's a definition worth memorising: a microservice is an independently deployable unit of software that owns one business capability and its data, and talks to other services only through published contracts over the network.

Three phrases carry the weight. Independently deployable means the Orders team can ship on a Tuesday afternoon without asking anyone. Owns its data means nobody else reads Orders' tables. Published contracts means the only way in is an API or an event stream that Orders promises to keep stable.

Notice what's missing: size. A service isn't "micro" because it has few lines of code, but because one team can understand it end to end and could rewrite it in weeks rather than years.

◎Mental model: the restaurant kitchen

A monolith is one brilliant chef cooking everything: quick to set up, but every dish queues behind them. Microservices are a kitchen brigade. Grill, pastry and sauces each have their own station and their own fridge (database), and tickets flow through the pass (APIs and brokers). You can hire a second pastry chef without retraining the grill, but now you need a ticket system and someone who notices when the fish station is on fire. That's observability, in Level 4.

1.2The trade: what you buy, what you pay

Microservices are a trade, not an upgrade. You buy team autonomy, independent scaling (40 copies of Catalog during a sale, 2 of Shipping), fault isolation (a recommendations bug shouldn't stop checkout) and smaller codebases.

You pay with every method call that becomes a network call. A method call takes nanoseconds and works or throws. A network call takes milliseconds and can succeed, fail, time out, or succeed on the server while the client thinks it failed. That last case double-charges customers.

Engineers at Sun Microsystems listed the classic fallacies of distributed computing in the 1990s: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, and so on. In a microservice system, each one eventually becomes a real bug.

1.3When not to, and what to do instead

Here's the uncomfortable truth: microservices mostly solve an organisational problem, not a technical one. They let many teams work in parallel without stepping on each other. If you have one team of six people, you don't have that problem, and you'll pay the distributed-systems tax for nothing.

This is Conway's Law: systems mirror the communication structure of the organisation that builds them. If your service map doesn't match your team map, one of them will eventually bend to fit the other.

The sensible default for most new products is a modular monolith: one deployable with strict internal boundaries. Spring Modulith lets you declare modules, verify in a test that none reaches into another's internals, and publish events between them. If a module later needs to become a service, the seam is already clean.

1.4Finding service boundaries

Cutting a system into services is the most important decision you'll make, and the hardest to reverse. The best tool comes from Domain-Driven Design (DDD): the bounded context, a boundary inside which a model and its vocabulary mean one thing consistently.

Take the word "product" in Teal Teas. To Catalog, a product is a name, tasting notes and photos. To Inventory, it's a SKU, a bin location and a quantity. To Shipping, it's a weight and box size. Same word, three different models. That's a strong hint you've found three bounded contexts, and that sharing one giant Product class between them would be a mistake.

Heuristics that work

  • Split by business capability, not technical layer. "Payments" is a good service; "validation service" is not.
  • Things that change together stay together. If every feature touches A and B, they want to be one service.
  • Avoid entity services. A CustomerService that everyone calls for every field becomes a bottleneck and a single point of failure.
  • Database per service, always. Others ask through the API or listen to events. A shared database couples everyone's releases through the schema.
!Gotcha: the distributed monolith

If two services must always be deployed together, they're one service wearing two hats, with a network in the middle. You get all the cost of microservices and none of the benefit. The usual causes: a shared database, a shared "domain model" library, or synchronous call chains where every request touches four services.

2.1The 2026 Java toolkit

Java is in a very strong position for services right now. JDK 25 (September 2025) is the current long-term-support release, and JDK 27 (15 September 2026) is the newest feature release. For a fleet of services, standardise on 25 unless you specifically need something newer.

Four platform features make modern Java a natural fit:

  • Virtual threads (final since JDK 21): simple blocking code that scales like asynchronous code.
  • Records, sealed types and pattern matching: concise, immutable API types and events.
  • Project Leyden's AOT cache (JDK 24 and 25): faster startup by reusing work from a training run.
  • GraalVM native images: millisecond startup and a small memory footprint, when you need them.

2.2Build the Orders service

Generate a project at start.spring.io: Java 25, Spring Boot 4.2, with Spring Web, Validation, Spring Data JPA, PostgreSQL Driver, Actuator, OpenTelemetry and Testcontainers. Spring Boot 4 split its auto-configuration into small focused modules, so each starter now pulls in only what it needs.

Start with the contract: what callers send and what they get back. Records are perfect for this.

OrderApi.java
// The public contract: immutable, validated, and NOT the JPA entity.
public record PlaceOrder(
        @NotBlank String customerId,
        @NotEmpty List<@Valid Line> lines) {

    public record Line(@NotBlank String sku, @Positive int quantity) {}
}

public record OrderView(UUID id, String status, BigDecimal total) {}

Then the controller. Keep it thin: translate HTTP into a call on a service class, and the result back into HTTP.

OrderController.java
@RestController
@RequestMapping("/orders")
class OrderController {

    private final OrderService orders;

    OrderController(OrderService orders) {
        this.orders = orders;
    }

    @PostMapping
    ResponseEntity<OrderView> place(@Valid @RequestBody PlaceOrder cmd) {
        OrderView created = orders.place(cmd);
        return ResponseEntity
                .created(URI.create("/orders/" + created.id())) // 201
                .body(created);
    }

    @GetMapping("/{id}")
    OrderView byId(@PathVariable UUID id) {
        return orders.find(id).orElseThrow(() -> new OrderNotFound(id));
    }
}

// Errors as RFC 9457 "problem details": one JSON shape for every failure.
class OrderNotFound extends ErrorResponseException {
    OrderNotFound(UUID id) {
        super(HttpStatus.NOT_FOUND,
              ProblemDetail.forStatusAndDetail(
                      HttpStatus.NOT_FOUND, "No order " + id),
              null);
    }
}

Three habits are hiding in that code. API types are not entities: return your JPA class and your database schema becomes a public API you can never change. Validation happens at the edge, so bad input never reaches business logic. And errors have one shape: ProblemDetail follows RFC 9457, so every service fails the same way and clients need only one error parser.

2.3Virtual threads: one line, big effect

Most service code waits: on the database, on another service, on a queue. With classic platform threads, each waiting request ties up an expensive operating-system thread, so the thread pool runs dry at a few hundred concurrent requests. Reactive programming avoided that, at the cost of much harder code.

Virtual threads are managed by the JVM. When one blocks on I/O, the JVM parks it cheaply and runs another on the same carrier thread, so you can have hundreds of thousands. You keep plain blocking code, and the thread pool stops being your limit.

application.yml
spring:
  application:
    name: orders
  threads:
    virtual:
      enabled: true     # web server, @Async, schedulers, listeners
  mvc:
    problemdetails:
      enabled: true          # Spring's own errors use RFC 9457 too
management:
  endpoints:
    web:
      exposure:
        include: health,info
  endpoint:
    health:
      probes:
        enabled: true        # /actuator/health/liveness and /readiness
!Gotcha: the bottleneck moves

Virtual threads don't make CPU-heavy work faster, and they remove a throttle you were relying on without knowing it. With 10,000 concurrent requests and a database pool of 20 connections, the requests now queue on the pool instead of the thread pool. Level 5 shows how to put explicit limits around scarce resources.

2.4Configuration the twelve-factor way

The Twelve-Factor App, a short manifesto from Heroku engineers, still describes good service hygiene. Its key rule: configuration lives in the environment, not in the code or the image. One image runs in dev, staging and production; only the environment changes.

In Spring Boot, any property can be overridden by an environment variable (SPRING_DATASOURCE_URL overrides spring.datasource.url). On Kubernetes, settings come from ConfigMaps and credentials from a secret manager such as Vault. Bind your own settings to a typed record so a typo fails at startup rather than at 3 a.m.:

OrdersProperties.java
@ConfigurationProperties("orders")
public record OrdersProperties(Duration reservationTtl,
                               int maxLinesPerOrder) {}

// Register once, e.g. @ConfigurationPropertiesScan on the main class.
// orders.reservation-ttl=15m  orders.max-lines-per-order=50

2.5Health checks that don't hurt you

Kubernetes asks every container two different questions, and Spring Boot's Actuator answers both:

  • Liveness (/actuator/health/liveness): "Are you broken beyond repair?" If this fails, Kubernetes restarts the container.
  • Readiness (/actuator/health/readiness): "Can you take traffic right now?" If this fails, Kubernetes stops sending requests but leaves the container alone.
!Gotcha: the self-inflicted outage

Never put a downstream dependency, like the database, in the liveness check. When the database has a 30-second blip, every Orders pod fails liveness, Kubernetes restarts them all at once, and they come back to a cold cache and a stampede of reconnections. A dependency problem belongs in readiness at most; liveness is only about the process itself.

Level 3 · Practitioner

Services talking, data staying consistent

One service is just an app. The interesting problems start when services need each other and the data is spread across many databases.

  • Choose sync or async per interaction
  • Write declarative HTTP clients
  • Publish events reliably
  • Run a saga

3.1Sync or async? Choose per interaction

Services communicate in two basic styles. Request/response (REST or gRPC) is a question that needs an answer now: "What's the price of SKU-1?" Events (Kafka, RabbitMQ and friends) are announcements of facts that others may care about: "Order 42 was placed."

The key difference is temporal coupling. With request/response, both services must be up at the same moment. With events, Orders can announce something while Shipping is mid-deploy, and Shipping catches up later. Rule of thumb: query synchronously, react asynchronously.

3.2REST done well: HTTP service clients

For years Java teams called other services with RestTemplate or Feign. Both are now legacy: Spring Boot 4.2 deprecates RestTemplate in favour of RestClient, and Spring Cloud OpenFeign is feature-complete. The modern way is a declarative HTTP service client: write an interface, and Spring Framework 7 implements it.

InventoryClient.java
@HttpExchange("/stock")
public interface InventoryClient {

    @GetExchange("/{sku}")
    StockLevel stock(@PathVariable String sku);

    @PostExchange("/reservations")
    Reservation reserve(@RequestBody ReserveStock request);
}

// Registers the client in a named group that shares HTTP settings.
@Configuration
@ImportHttpServices(group = "inventory", types = InventoryClient.class)
class ClientConfig {}
application.yml
spring:
  http:
    clients:
      connect-timeout: 1s
      read-timeout: 2s             # never rely on defaults for timeouts
    serviceclient:
      inventory:
        base-url: http://inventory:8080

Now InventoryClient is just a bean you inject. If you add Spring Cloud LoadBalancer and leave out the base URL, the group name is used as a service ID and requests are load-balanced across instances.

API habits that save you later

  • Evolve, don't break. Add fields freely; never rename or remove one in use. Clients should be tolerant readers that ignore unknown fields.
  • Make money-moving POSTs idempotent. Accept an Idempotency-Key header so a retry after a timeout can't create a second payment.

When you do need a breaking change, Spring Framework 7 has built-in API versioning. Tell Spring where the version lives, then tag handler methods:

Versioning
// application.properties:  spring.mvc.apiversion.use.header=API-Version
@GetMapping(path = "/{id}", version = "1")
OrderView v1(@PathVariable UUID id) { ... }

@GetMapping(path = "/{id}", version = "2")
OrderViewV2 v2(@PathVariable UUID id) { ... }

gRPC is the other common option for internal calls: typed Protobuf contracts, HTTP/2 and streaming. It's faster and stricter than JSON, but less friendly to humans and browsers. Spring Boot 4.1 added Spring gRPC auto-configuration.

3.3Events and messaging

An event is a fact in the past tense: OrderPlaced, PaymentCaptured. The publisher doesn't know who listens. That's the superpower: tomorrow a new Loyalty service can award points by subscribing to OrderPlaced, and Orders doesn't change at all.

Apache Kafka is the usual backbone: a durable, partitioned log. Consumers in a group share the partitions, and ordering is guaranteed only within a partition, so key events by the entity they're about (the order ID).

PaymentsListener.java
public record OrderPlaced(UUID orderId, String customerId,
                          BigDecimal total, Instant at) {}

@Component
class PaymentsListener {

    private final ProcessedMessages processed; // unique key on message id
    private final PaymentService payments;

    PaymentsListener(ProcessedMessages processed, PaymentService payments) {
        this.processed = processed;
        this.payments = payments;
    }

    @KafkaListener(topics = "orders", groupId = "payments")
    @Transactional
    void on(OrderPlaced event) {
        if (!processed.markIfNew(event.orderId())) {
            return;                   // duplicate delivery: already handled
        }
        payments.charge(event.orderId(), event.total());
    }
}
◎Mental model: at-least-once is the real world

Brokers redeliver after crashes, rebalances and timeouts, so assume every message can arrive more than once. Kafka's "exactly-once" covers reads and writes within Kafka, not the charge you make in your own database. The robust answer is an idempotent consumer: record what you've processed in the same transaction as the side effect, and skip repeats.

3.4Consistency without distributed transactions

Placing an order at Teal Teas touches three databases: create the order, charge the card, reserve the tea. In a monolith that's one ACID transaction. Across services, two-phase commit (XA) is slow, fragile, holds locks across the network, and isn't supported by most brokers and cloud databases. So we don't use it.

The saga pattern

A saga is a sequence of local transactions. Each step commits in its own service and triggers the next. If a step fails, earlier steps are undone by compensating actions: refund the payment, release the stock, cancel the order.

Sagas come in two flavours. In choreography, services react to each other's events with no central brain, as in the diagram. It's loosely coupled and fine for three or four steps, but the overall flow lives in nobody's code. In orchestration, a coordinator (a saga class, or a workflow engine such as Temporal or Camunda) tells each service what to do next and tracks state. It's easier to understand and monitor once flows get long or branchy.

!Gotcha: compensation isn't rollback

You can't un-send an email or un-ship a parcel. Compensations are new business actions ("refund", "send an apology") and must be designed with the business. They also need to be idempotent, because they'll be retried too.

The dual-write trap and the transactional outbox

Orders must save the order and publish OrderPlaced. Save then crash before publishing, and the event is lost. Publish first and then fail the save, and Payments charges for an order that doesn't exist. The transactional outbox fixes this: write the event into an outbox table in the same local transaction as the order, and let a separate relay publish it to Kafka, retrying until it succeeds.

OrderService.java
@Transactional
public OrderView place(PlaceOrder cmd) {
    Order order = orders.save(Order.from(cmd));
    outbox.save(OutboxEvent.of("orders", order.id(),
            new OrderPlaced(order.id(), cmd.customerId(),
                            order.total(), Instant.now())));
    return order.view();   // both rows commit together, or neither does
}

// Simplest relay: poll. At scale, prefer change data capture (e.g. Debezium).
@Scheduled(fixedDelay = 500)
@Transactional
void relay() {
    for (OutboxEvent e : outbox.findTop100ByPublishedFalseOrderByIdAsc()) {
        kafka.send(e.topic(), e.key(), e.payload()).join();
        e.markPublished();
    }
}

If you're on a modular monolith, Spring Modulith's event publication registry gives you the same guarantee out of the box, and can externalise events to Kafka when a module becomes a service.

Read models (CQRS)

The "My orders" page needs data from Orders, Payments and Shipping. Calling all three on every view is slow and fragile. Instead, build a read model: a table that listens to all three event streams and keeps a view shaped exactly for that page. Separating writes from reads like this is CQRS (command query responsibility segregation). The view is eventually consistent, usually a fraction of a second behind, so let the UI say "processing" rather than pretend.

3.5Discovery and the API gateway

On Kubernetes, discovery is built in: a Service gets a stable DNS name (http://inventory) and load-balances across healthy pods. Outside Kubernetes, use a registry such as Eureka or Consul with Spring Cloud LoadBalancer.

An API gateway is the single front door: routing, token validation, rate limits, CORS, and hiding your internal topology. Spring Cloud Gateway 5 comes as Server Web MVC (servlet-based, a great match for virtual threads) or Server WebFlux (reactive).

gateway application.yml
spring:
  cloud:
    gateway:
      server:
        webmvc:                     # note the new prefix in Gateway 5
          routes:
            - id: orders
              uri: http://orders:8080
              predicates:
                - Path=/api/orders/**
              filters:
                - StripPrefix=1
!Gotcha: the upgrade that silently drops your routes

Gateway 5 renamed its starters (spring-cloud-starter-gateway-server-webmvc or -webflux) and moved properties under spring.cloud.gateway.server.webmvc or .webflux. Old-style properties are simply ignored, so an upgrade can leave you with a gateway that starts fine and routes nothing.

A common refinement is the backend for frontend (BFF): one gateway per client type, shaping responses for mobile or web. Either way, keep business logic out of the gateway. Once it makes pricing decisions, it's a monolith in disguise.

4.1Resilience: assume everything fails

Here's how one slow service takes down a site. Inventory starts answering in 5 seconds instead of 50 milliseconds. Every Orders request now waits, holding a database connection. The pool drains, so even requests that don't need Inventory fail. Users retry, load doubles, and checkout is down. This is a cascading failure, and the defences are layered:

  1. Timeouts on every remote call. No timeout means "wait forever".
  2. Retries for transient errors on idempotent calls only, with exponential backoff and jitter, capped.
  3. Circuit breakers that stop calling a failing dependency and test when it has recovered.
  4. Bulkheads and concurrency limits, so one dependency can only use a bounded share of resources.
  5. Fallbacks: a cached price, a default, or "delivery estimate unavailable".
  6. Rate limiting and load shedding when demand exceeds capacity.

▶Try it: the retry storm

Each layer in a call chain retries a failed call. How many requests hit the bottom service for one user click?

That exponential blow-up is why the rule is: retry at one layer only, usually the one closest to the failure, and add jitter so thousands of clients don't retry in lockstep.

Built-in resilience in Spring Framework 7

Spring Framework 7 brought retry and concurrency throttling into the core, so simple cases need no extra library:

PricingClient.java
@Configuration
@EnableResilientMethods   // switches on @Retryable and @ConcurrencyLimit
class ResilienceConfig {}

@Service
class PricingClient {

    @Retryable(includes = TransientPricingException.class,
               maxRetries = 3, delay = 200, multiplier = 2, jitter = 50)
    @ConcurrencyLimit(20)   // max 20 in flight, even with virtual threads
    Price quote(String sku) {
        return pricing.quote(sku);
    }
}

Circuit breakers with Resilience4j

For circuit breakers, the standard library is Resilience4j, via Spring Cloud Circuit Breaker. A breaker watches a sliding window of recent calls. Past a failure threshold it opens and rejects calls instantly; after a wait it goes half-open and lets a few trial calls through; if they succeed it closes.

StockChecker.java
@Service
class StockChecker {

    private final InventoryClient inventory;
    private final CircuitBreaker breaker;

    StockChecker(InventoryClient inventory,
                 CircuitBreakerFactory<?, ?> factory) {
        this.inventory = inventory;
        this.breaker = factory.create("inventory");
    }

    StockLevel check(String sku) {
        return breaker.run(
                () -> inventory.stock(sku),
                failure -> StockLevel.unknown(sku));  // fallback: verify later
    }
}
application.yml
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        sliding-window-size: 20
        minimum-number-of-calls: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 3
  timelimiter:
    instances:
      inventory:
        timeout-duration: 2s
!Gotcha: the hidden one-second timeout

Spring Cloud Circuit Breaker wraps Resilience4j calls in a time limiter whose default is one second, so a legitimate 1.5-second call "fails" and trips your breaker. Set it explicitly, as above, in line with your HTTP read timeout.

4.2Observability: one story from three signals

In a monolith you debug with a stack trace. In a fleet, one click might touch eight services. Observability is the ability to answer new questions about the system from the outside, using three signals:

  • Logs: what happened, in detail. Make them structured JSON so they can be queried.
  • Metrics: how many, how fast, how often. Cheap to store, perfect for dashboards and alerts.
  • Traces: where the time went. A trace follows one request across every service; each hop is a span.

OpenTelemetry (OTel) is the vendor-neutral standard for all three. Trace context travels in the W3C traceparent header, so a trace started at the gateway continues through Orders, Kafka and Payments. Spring Boot 4 ships spring-boot-starter-opentelemetry, built on Micrometer, which exports over OTLP to a collector and on to your backend (Grafana's stack, Jaeger, or a vendor). The OTel Java agent is the zero-code alternative.

application.yml
management:
  tracing:
    sampling:
      probability: 0.1       # keep 10% of traces; more in test envs
  opentelemetry:
    tracing:
      export:
        otlp:
          endpoint: http://otel-collector:4318/v1/traces
  otlp:
    metrics:
      export:
        url: http://otel-collector:4318/v1/metrics
logging:
  structured:
    format:
      console: ecs           # JSON logs, with trace and span IDs

What to measure

For every endpoint, track RED: Rate, Errors and Duration (percentiles, not averages). For every resource (pools, queues, CPU), track USE: Utilisation, Saturation and Errors.

Then define SLOs (service level objectives) for what users feel: "99.9% of POST /orders succeed within 300 ms over 28 days." The remaining 0.1% is your error budget. Alert when you burn it too fast, not when CPU hits 80%. Users don't feel CPU; they feel slow checkouts.

4.3Security at every hop

Microservices need zero trust: every service verifies every request, because "it came from inside the network" proves nothing.

  • Users sign in through an OAuth 2 / OpenID Connect provider (Keycloak, Okta, Entra ID, Cognito); the gateway passes on their JWT access token.
  • Each service validates the token itself as a resource server and checks scopes.
  • Service-to-service calls use their own identity: client-credentials tokens, or mutual TLS from a service mesh such as Istio or Linkerd.
SecurityConfig.java
// application.yml:
//   spring.security.oauth2.resourceserver.jwt.issuer-uri=https://auth.example
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/actuator/health/**").permitAll()
            .requestMatchers(HttpMethod.POST, "/orders")
                .hasAuthority("SCOPE_orders:write")
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(Customizer.withDefaults()))
        .build();
}
★Guru tip

Don't forward the user's full-power token everywhere; use token exchange to get a narrower one for each hop. And treat the supply chain as security: scan dependencies, publish an SBOM (add the CycloneDX build plugin and Spring Boot serves it from /actuator/sbom), and keep images minimal.

4.4Testing a fleet

In microservices, most bugs live at the edges: SQL, serialisation, HTTP mapping, configuration. So many teams swap the classic test pyramid for a testing honeycomb: a thick middle of integration tests that run one service against real infrastructure, and very few slow end-to-end tests across the fleet.

End-to-end (a handful)
Contract tests between services
Integration tests: one service + real DB, broker
Unit tests for real logic

Testcontainers starts real PostgreSQL, Kafka or Redis in Docker for your tests, and Spring Boot's @ServiceConnection wires the connection details in automatically. Spring Boot 4 also adds RestTestClient, a fluent client for testing your endpoints.

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
@AutoConfigureRestTestClient
@Testcontainers
class PlaceOrderIT {

    @Container
    @ServiceConnection   // Testcontainers 2: org.testcontainers.postgresql.*
    static PostgreSQLContainer postgres =
            new PostgreSQLContainer("postgres:18");

    @Autowired RestTestClient client;

    @Test
    void placesAnOrder() {
        var cmd = new PlaceOrder("c-42",
                List.of(new PlaceOrder.Line("SENCHA-100G", 2)));
        client.post().uri("/orders").body(cmd)
              .exchange()
              .expectStatus().isCreated()
              .expectHeader().exists("Location");
    }
}

Integration tests prove a service works; contract tests prove services still fit together. With consumer-driven contracts (Pact or Spring Cloud Contract), Orders records what it expects from Inventory's API, and Inventory's build fails if a change would break it.

4.5Ship it: containers, Kubernetes, startup

You don't need a hand-written Dockerfile. ./mvnw spring-boot:build-image uses Cloud Native Buildpacks to produce a layered, non-root image (on Ubuntu 26.04 by default in Spring Boot 4.2); Jib is a popular alternative. Layering means a code change rebuilds only the thin top layer.

deployment.yaml (excerpt)
containers:
  - name: orders
    image: registry.example.com/orders:1.4.2
    env:
      - name: JAVA_TOOL_OPTIONS
        value: "-XX:MaxRAMPercentage=75"   # heap as % of limit
    resources:
      requests: { cpu: "500m", memory: "768Mi" }
      limits:   { memory: "768Mi" }
    startupProbe:
      httpGet: { path: /actuator/health/liveness, port: 8080 }
      periodSeconds: 2
      failureThreshold: 30            # up to 60 s to start
    livenessProbe:
      httpGet: { path: /actuator/health/liveness, port: 8080 }
    readinessProbe:
      httpGet: { path: /actuator/health/readiness, port: 8080 }
terminationGracePeriodSeconds: 45     # > Spring's 30 s shutdown

Three details matter more than they look. The JVM is container-aware, so size the heap as a percentage of the limit rather than hard-coding -Xmx. Many teams set a CPU request but no CPU limit, because throttling can stall garbage collection. And Spring Boot shuts down gracefully by default, finishing in-flight requests on SIGTERM, provided Kubernetes gives it time.

5.1Tail latency and the fan-out tax

Averages lie. What users feel is the tail: the one request in a hundred that's slow because of a GC pause, a cold cache or a noisy neighbour. In a fleet, the tail compounds.

Suppose the Teal Teas home page calls 20 backends in parallel and waits for all of them. Each is slow just 1% of the time. The page is fast only if all 20 are fast: 0.9920 ≈ 82%. So about 18% of page views are slow, even though every individual service looks excellent on its own dashboard. Google's Jeff Dean and Luiz André Barroso described this effect in their 2013 paper "The Tail at Scale".

▶Try it: the fan-out calculator

The chance that a request waiting on every backend hits at least one slow response.

18.2%

To pay less tax: call fewer services per request (Level 3's read models are the big win), cache, return partial results when a non-essential backend is slow, and use hedged requests for idempotent reads: if no answer arrives by the usual 95th-percentile time, ask another replica and take the first reply.

Availability compounds the same way in sequential chains: four services at 99.9% each give about 99.6% together, almost four times the downtime of any one.

5.2Concurrency mastery on modern Java

Virtual threads changed the rules, so update your instincts:

  • Don't pool virtual threads. Pools ration expensive things; virtual threads are cheap, so create one per task.
  • Ration the scarce things instead with @ConcurrencyLimit or a semaphore: database access, rate-limited partner APIs, memory-hungry work.
  • Pinning is mostly solved. Virtual threads used to stick to their carrier inside synchronized; JDK 24 fixed that (JEP 491). Native calls can still pin.

Structured concurrency

The Orders dashboard needs a customer and their recent orders from two services. Run both at once; if either fails, cancel the other, with no leaked threads. That's structured concurrency. It's still a preview API (seventh preview in JDK 27), so it needs --enable-preview and may change slightly, but the shape is settled:

DashboardService.java (preview API)
Dashboard load(String customerId) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {  // all must succeed
        Subtask<Customer> customer =
                scope.fork(() -> customers.find(customerId));
        Subtask<List<OrderView>> recent =
                scope.fork(() -> orders.recent(customerId));
        scope.join();   // waits for both; one fails, the other is cancelled
        return new Dashboard(customer.get(), recent.get());
    }
}

Scoped values

Request context (tenant, user, correlation ID) used to live in ThreadLocal: mutable, leak-prone and costly with millions of virtual threads. Scoped values, final since JDK 25, are immutable, bound to a block of code, and inherited by child tasks in a structured scope.

TenantContext.java
static final ScopedValue<String> TENANT = ScopedValue.newInstance();

void handle(Request request) {
    ScopedValue.where(TENANT, request.tenantId())
               .run(() -> process(request));  // TENANT.get() works inside
}

5.3Evolving contracts without drama

In a fleet you can't upgrade everyone at once, so every change must work with old and new versions side by side:

  • Expand, then contract, for APIs as well as schemas: add the new field, migrate consumers, remove the old one only when nobody reads it.
  • A schema registry for events (Avro, Protobuf or JSON Schema) that enforces compatibility on publish: backward (new consumers read old events), forward (old consumers read new events) or full.
  • Treat events as public APIs. Once another team consumes OrderPlaced, its shape is a promise; breaking changes get a new event type.
  • Announce deprecation in-band with the standard Deprecation and Sunset HTTP headers, and use metrics to see who still calls the old version.

◎Mental model

A little duplication is cheaper than the wrong coupling. Two services each having their own small Address record is fine. Two services sharing one Address class that neither can change without the other is not.

5.5Migrating a monolith: the strangler fig

Most teams migrate to microservices rather than start with them. Never attempt a big-bang rewrite. Use the strangler fig pattern, named by Martin Fowler after a vine that grows around a tree until it stands on its own:

  1. Put a facade in front of the monolith (the API gateway works well) to redirect traffic route by route.
  2. Pick a first capability that's valuable, self-contained and low-risk: notifications, not payments.
  3. Build the new service behind an anti-corruption layer that translates the old model so it doesn't leak in.
  4. Sync the data with events or change data capture, then switch the route.
  5. Delete the old code. Skip this and you end up maintaining two systems.

Track delivery metrics such as DORA's (deployment frequency, lead time, change failure rate, time to restore). If they aren't improving, the migration isn't paying for itself.

5.6Platform thinking: the guru's real job

With five services, heroics work. With fifty, only consistency scales. The highest-leverage thing a senior engineer can build is a golden path: a service template where the build, image, pipeline, probes, tracing, logging, security defaults, dashboards, SLO alerts and runbook come pre-wired. Service number 37 is then as production-ready as number 1.

  • A service catalogue (Backstage is the common choice): who owns this, and where are its docs, dashboards and on-call?
  • A short list of standards: one framework, one logging format, one tracing setup, one API style guide.
  • Clear ownership: every service has a team, an SLO and an on-call rotation. A service nobody owns is a future incident.
  • Cost awareness: compute, telemetry and people all cost money. Retire services that don't earn their keep.
★Guru tip

The best microservice architectures look boring from the inside. Every service is built the same way, fails the same way, and is debugged the same way. Save your creativity for the business problem.
