A trader books 100 units of GILT10 into the ALPHA book. The booking screen receives a success response. A position query still returns zero. Both services can be correct. Follow one immutable booking through two Spring Boot applications, two PostgreSQL databases and one Kafka topic. Service design

Choose the boundary from the business rule

Start with two promises. Booking remembers the terms accepted under a client-supplied trade ID. Positions answers how many units of an instrument a book holds across all accepted trades it has processed. The first promise is about one immutable instruction. The second is an aggregate across instructions. They have different write patterns, different failure costs and different definitions of “up to date”.

Decision Booking Positions
Authority Accepted terms for a trade ID Materialised net units for a book and instrument
Write path Validated HTTP command Committed booking events
Identity Trade ID for the command, event ID for publication Event ID for deduplication, book and instrument for the balance
If Kafka is down Accept while database and backlog capacity permit Serve the last applied value with an appropriate freshness policy
Recovery evidence Trade row and pending publication Applied-event record, balance and group progress

A bounded context gives a word a precise meaning within an area of the business. Here “position” means signed booked units. A settled holding would also depend on settlement events, and risk exposure might depend on multipliers, market data and currency conversion. Naming all three “position” and passing a shared ORM entity disguises material differences. Specify the unit, sign, lifecycle stage and effective time before publishing a shared contract.

Decide what belongs in one transaction

Write down the condition that must hold at commit. For booking it is “exactly one set of accepted terms per trade ID, accompanied by a durable intention to publish”. PostgreSQL can enforce that within one database. For positions it is “every accepted event ID contributes its units once”. Another local transaction can enforce that. The business has agreed that the balance may lag. That agreement is what makes this split viable.

Suppose the same team owns both capabilities, runs one release train and needs the balance to be current on every booking response. Two Java packages in one deployable with a local transaction may serve those constraints better. Separate processes earn their cost when an independent release, scaling decision, ownership boundary or failure boundary matters. You can start with modules, private tables and explicit Java interfaces, then extract the consumer when its query load or availability requirements diverge.

Choose a communication mechanism for each interaction

Interaction Mechanism What success establishes
Accept these trade terms HTTP PUT with a stable identity Booking committed locally. A timeout leaves the caller uncertain.
Announce an accepted booking Kafka event retained under a topic contract Independent groups can consume or replay within retention.
Display net units HTTP GET to the positions read model Value observed at query time. Freshness requires additional evidence.
Reserve limited capacity Command to the owner of the limit Decision and reservation committed against authoritative capacity.

If you know RabbitMQ, think of a Kafka consumer group as a group of workers sharing work. The analogy breaks at acknowledgement. Kafka retains a log independently of a group's progress. Recording an offset moves one group's restart point. Another group can read the same records, and resetting a group can deliberately revisit retained records. This is why adding an audit consumer needs a distinct group ID, while adding a second positions replica generally needs the same one. Kafka design

Give each service a practical shape

Keep HTTP and Kafka adapters thin. A controller validates the wire request and maps the result to a status. An application service owns the transaction and decides whether this command is new, repeated or conflicting. A listener decodes an event and calls a transactional projection bean. In the sample JDBC sits directly in these small classes so you can inspect the exact writes. Introduce a repository interface when a domain operation gains reusable persistence behaviour. An interface per table would add little here.

Deploy the services from separate Maven projects. Give each its own Flyway migration history and database credentials. They may eventually share a managed PostgreSQL cluster while retaining distinct databases and roles. Sharing a cluster couples capacity, failover and maintenance windows. Letting one service join another's private tables adds a second coupling: a column rename now requires a coordinated deployment. A published event or query API gives the owning team a contract it can version.

Command handling

Make a booking safe to repeat

A lost HTTP response is a normal distributed-systems outcome. The client knows it sent a request and has no evidence of the outcome. Give it a stable trade ID before its first attempt. The API accepts a PUT to that resource. In this particular API the resource is immutable after creation: identical terms succeed on retry and changed terms produce a conflict. A correction needs a separately identifiable domain operation.

trade=http://localhost:8080/trades/11111111-1111-4111-8111-111111111111

}

On a fresh database the expected sequence is 201, 200, 409. The first request creates the trade, the second confirms the original terms, and the last tries to reuse the identity for a different quantity. Generating a fresh UUID on each retry would turn one human action into two valid trades. Scope client-provided IDs to an authorised tenant or upstream system in a multi-client API. An idempotency key is evidence of identity, never authority to read or write the underlying book.

Let the database arbitrate simultaneous requests

Booking.accept · transactional method
public boolean accept(UUID id, Terms t) {
        if (t.units() == 0) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST);
        }
        int inserted = db.update("""
            INSERT INTO trade(id, book, instrument, units)
            VALUES (?, ?, ?, ?) ON CONFLICT (id) DO NOTHING
            """, id, t.book(), t.instrument(), t.units());
        if (inserted == 0) {
            Terms stored = db.queryForObject("""
                SELECT book, instrument, units FROM trade WHERE id = ?
                """, (r, i) -> new Terms(r.getString(1),
                     r.getString(2), r.getLong(3)), id);
            if (!t.equals(stored)) {
                throw new ResponseStatusException(HttpStatus.CONFLICT);
            }
            return false;
        }
        UUID eventId = UUID.randomUUID();
        db.update("""
            INSERT INTO outbox(id, trade_id, payload)
            SELECT ?, id, jsonb_build_object(
              'eventId', CAST(? AS uuid), 'tradeId', id,
              'type', 'TradeBooked', 'schemaVersion', 1,
              'book', book, 'instrument', instrument, 'units', units)
            FROM trade WHERE id = ?
            """, eventId, eventId, id);
        return true;
    }

Two simultaneous requests can both observe that a row is absent. A preliminary SELECT therefore cannot enforce uniqueness. The primary key makes concurrent inserts contend on the same identity. Under PostgreSQL's default Read Committed isolation, the losing insert can wait for the winner. Its subsequent SELECT obtains a fresh statement snapshot and sees the committed terms. If the winner rolls back, the competing insert can succeed. This reasoning assumes immutable rows and the shown isolation level. At stronger isolation levels be prepared to retry the whole transaction on a serialization failure. PostgreSQL transaction isolation

The outbox stores the exact integration payload alongside its immutable event ID. If the insert into the outbox fails, the transaction rolls back the trade as well. If the commit succeeds but the network drops the HTTP response, the client's repeat sees the accepted terms. The unique outbox trade ID is specific to this single-event lifecycle. A service that emits amendments needs an event identity per change and a uniqueness constraint such as (trade ID, aggregate revision).

What Spring contributes

The controller receives a Spring-managed Booking bean through its constructor. The transaction interceptor surrounds the external call to its public accept method. JdbcTemplate participates using the transaction-bound connection. On successful return the interceptor attempts to commit before control returns to the controller. A failed commit must propagate as a failure. In the default proxy model, calling an annotated helper through this inside the same object bypasses the interceptor. Also check rollback rules for checked exceptions. The relay below explicitly requests rollback for them. Spring transaction annotations

JdbcTemplate makes the uniqueness and update semantics visible here. JPA is a good fit for a richer aggregate with relationships and optimistic locking. With JPA, managed entities can be flushed before commit, and a successful save call alone cannot establish that the transaction committed. Avoid serialising a managed entity as an event: lazy relationships, persistence-only fields and column changes would become accidental public API. Map explicitly from the accepted state to a small event.

Design the wire contract

Illustrative TradeBooked payload
{
  "type": "TradeBooked", "schemaVersion": 1,
  "eventId": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
  "tradeId": "11111111-1111-4111-8111-111111111111",
  "book": "ALPHA", "instrument": "GILT10", "units": 100
}

The ID in the Kafka key is the trade ID. The UUID in eventId identifies this occurrence across every delivery. schemaVersion identifies the data shape. None of these is a Kafka offset. Topic, partition and offset identify one stored record; publishing the same event again creates a new record with the original event ID. Add correlation and causation IDs when a workflow crosses several services. They help explain a chain of events but have different uniqueness requirements.

Use immutable past-tense facts for self-contained integration events. Including book, instrument and signed units lets positions process a booking while the booking API is unavailable. An ID-only notification reduces copied data, but a GET during processing can retrieve a later state or fail during an outage. Where event-time reconstruction matters, publish the facts required at that point in the lifecycle. For this example quantity is a signed integer number of instrument units. For fractional quantities specify decimal precision, scale, rounding and canonical wire representation explicitly.

A schema change can compile cleanly in the producer and still corrupt a consumer. Adding an optional execution venue works when older readers tolerate unknown fields and newer readers handle historical records without it. Changing units from individual bonds to lots under the same field name would silently multiply exposures. Introduce a new field with explicit units or a versioned event, run old and new consumers against common fixtures, and retire the old contract after its replay horizon. A schema registry with compatibility checks can catch structural breaks. A fixture saying “two lots of 100 must become 200 units” catches the semantic one.

Publication and consumption

Cross the database–Kafka boundary

Consider the two obvious implementations. Send to Kafka first, then commit the trade: a database rollback leaves a booking event about a trade that never existed. Commit first, then send: a process crash between the statements leaves a real trade invisible to positions. An after-commit callback moves the timing but still relies on the process surviving. The outbox turns that volatile piece of work into a queryable database row. Transactional outbox pattern

Relay.java · scheduled publication
@Scheduled(fixedDelay = 100)
    @Transactional(rollbackFor = Exception.class)
    public void publishOne() throws Exception {
        var batch = db.query("""
            SELECT id, trade_id, payload::text FROM outbox
            WHERE sent_at IS NULL ORDER BY created_at, id
            LIMIT 1 FOR UPDATE SKIP LOCKED
            """, (r, i) -> new Pending(r.getObject(1, UUID.class),
                 r.getString(2), r.getString(3)));
        if (batch.isEmpty()) return;
        var e = batch.getFirst();
        kafka.send("trade.booked.v1", e.key(), e.payload())
             .get(20, TimeUnit.SECONDS);
        db.update("UPDATE outbox SET sent_at=now() WHERE id=?", e.id());
    }

Each scheduled invocation takes one pending row, holds its lock while waiting for the Kafka acknowledgement, and marks the row sent within the same database transaction. A timeout has an ambiguous outcome. Leave the row pending so a later attempt can send the same event again. SKIP LOCKED allows another worker to select a different row. That can change publication order across concurrent workers, even if Kafka later appends their messages to the same partition. The lab has one booking per trade and sums integer deltas, so the final result tolerates this.

The design buys simplicity at a cost. A broker delay ties up a database connection and a row lock. With a 100 ms fixed delay after each invocation, even instant sends cannot sustain more than about ten records per second per worker. Acknowledgement time adds to the interval. For higher rates, batch deliberately or use change data capture (CDC) to relay committed outbox inserts from PostgreSQL's write-ahead log. CDC shifts the load from polling to a connector with its own offsets, replication slot and operational recovery procedure. Monitor retained WAL during an outage, and verify how event IDs and keys emerge on the wire before switching relays.

Decide what Kafka promises to the producer

The sample sets acks=all and enables producer idempotence. The acknowledgement concerns the partition's current in-sync replicas, subject to the topic's minimum in-sync replica setting. In the single-broker lab only one replica exists. A production example uses replication factor three, minimum in-sync replicas two and acks=all. With two in-sync replicas the write can proceed; with only one it must fail or retry. This availability cost protects the chosen durability threshold. Replication across suitable failure domains matters as much as the count. Producer configuration

Producer idempotence handles certain transport retries by the producer. A restarted relay that deliberately sends an outbox row again makes a new application send. Both copies can be present and valid. Kafka transactions address a different boundary: a Kafka processor can atomically publish output records and advance input offsets, with downstream consumers configured for read_committed. An independent PostgreSQL transaction still needs its own recovery design. Spring's coordination of successive Kafka and database commits leaves a failure interval between them. Spring Kafka transactions

Choose the partition key from the ordering requirement

Kafka orders records by offset within a partition. With the same key bytes, stable partition count and consistent key-based partitioning, events for one trade reach one partition. Different trades contributing to ALPHA/GILT10 may be processed on different threads. The SQL update adds to the current stored balance atomically, so those increments compose even under concurrency. A Java read-modify-write sequence that reads 100 twice and then writes 110 and 120 loses one increment. The correct result after +10 and +20 is 130. PostgreSQL INSERT and ON CONFLICT

A book/instrument key puts related position changes together, useful for a stateful computation such as running weighted-average cost. It can concentrate a busy book on one partition. A trade key spreads the work and preserves an individual trade's history, but a portfolio algorithm that depends on a prescribed ordering must establish that ordering separately. More partitions change the mapping of keys under typical hashing schemes. For an order-sensitive stream, plan a versioned topic migration, a cutover boundary and a reconciliation step before changing the partition count.

Apply each event once in the read model

Projection.apply · transactional method
public void apply(Booked e) {
        int first = db.update("""
            INSERT INTO consumed(event_id) VALUES (?)
            ON CONFLICT (event_id) DO NOTHING
            """, e.eventId());
        if (first == 0) return;
        db.update("""
            INSERT INTO position(book, instrument, units) VALUES (?, ?, ?)
            ON CONFLICT (book, instrument) DO UPDATE
            SET units = position.units + EXCLUDED.units
            """, e.book(), e.instrument(), e.units());
    }

The consumer inserts the event ID under a unique constraint. Only the transaction that inserts it can add the quantity. Both writes commit or roll back together. A process crash between the two SQL statements rolls back the first as well. If the same event arrives in parallel, one insert can wait for the other transaction's outcome. This costs an indexed insert per new event and storage proportional to event count. Pruning consumed IDs while older duplicate events can still enter the live projection reopens the double-counting window.

Spring calls a synchronous record listener. It decodes the schema, verifies the key matches the payload, and invokes the separate transactional projection bean. The listener returns only after the database method has committed. The container then commits the next offset under RECORD acknowledgement with auto-commit disabled. BATCH, the usual container default, amortises offset commits across records returned by a poll and can repeat more work after failure. Both need deduplication. Dispatching to an executor and immediately returning would acknowledge progress while the write was still pending. Spring Kafka listener containers

At the hardest boundary there are three different witnesses. PostgreSQL knows the event has affected the balance. Kafka knows where the group last committed. The consumer process briefly knows both operations are in progress, then loses that knowledge when it exits. The database uniqueness constraint supplies durable evidence on restart. A delivery counter might now read two even though the business balance increased exactly once. This claim is scoped to the local projection. Adding email or a broker instruction inside the listener introduces a new external side effect with its own identity and recovery requirements.

Make failures explicit in Spring

The supplied project configures CommonContainerStoppingErrorHandler. On an exception the listener container stops; a JVM and its HTTP endpoint can remain alive. The record remains available for recovery under the chosen record acknowledgement mode. A stale read endpoint could still answer requests, so expose consumer-running state and data freshness to your readiness or serving policy. After correcting a transient cause, restart the listener or application. For an incompatible record, deploy a compatible reader or apply an audited recovery procedure before resuming. Spring Kafka error handling

Recovery option Consequence for progress Best fit
Stop the container Assigned work stalls until repair or reassignment Missing or misordered financial facts make a projection unsafe
Bounded blocking retry Delays work on the affected listener thread Short transient database or network errors
Retry topic with backoff Other records can overtake the failed one Independent operations with tolerant ordering

With a dead-letter topic, capture the original key, value, topic, partition, offset, event ID when decodable and failure category. Verify recovery publication succeeds before advancing the source offset. Define who can authorise a corrected payload, how the original is preserved and how the repair is reconciled. For an ordered sequence, parking revision 2 and applying revision 3 can make the resulting state invalid. A per-aggregate quarantine or a stopped partition may be the right cost. Retrying a schema error a hundred times spends capacity without changing the result.

Operating the design

Scale, replay and change the system safely

Size for recovery as well as traffic

Suppose bookings arrive at 120 records/s and a fifteen-minute consumer outage accumulates 108,000 records. Recovering at 300 records/s while 120/s continue arriving drains the backlog at 180/s, or ten minutes. That is a capacity scenario, not a benchmark for the one-row relay. If a hot partition receives 80/s while its single worker sustains 70/s, aggregate headroom elsewhere cannot drain it. Track rates and lag by partition alongside end-to-end age, database contention and outbox age.

With one topic, three partitions and an ordinary consumer group, at most three group members can actively own a partition at once. Two replicas each configured with listener concurrency two create four consumers; at least one has no partition for this topic. Increasing concurrency also increases competing database connections and row locks. A sudden rebalance can revisit work that finished just before ownership changed. Idempotency therefore matters during routine rollouts as much as during crashes.

Set poll size and timeouts using observed tail latency. For sequential processing, 100 records at 250 ms each already occupy 25 seconds before retries, commits or pauses. max.poll.interval.ms bounds the time between polls in normal group operation. A slow batch can lose its assignment and amplify duplicates. Lower max.poll.records, shorten the blocking operation or add capacity along the slow path. Raising the interval alone also lengthens the time before the group detects some stuck consumers. Consumer configuration

Rebuild a projection while the live one serves

Imagine a defect that inverted the sign of a sell. The consumed table proves the event ran, so replaying it against the same database correctly does nothing. Build a shadow positions database with empty balances and empty consumed IDs. Start a new consumer group from earliest with the fixed code. A new group supplies an independent cursor; an empty target supplies an independent result. Reusing the old consumed table produces empty balances. Reusing old balances with a new consumed table doubles the totals.

Capture a per-partition reference end offset at the start of verification. Consume to that boundary and reconcile against an equivalent source cut, or quiesce writes for a small exercise. The sum of signed units per book and instrument is an independent oracle for immutable bookings when taken at a matching cut. Comparing two live databases at unrelated instants can flag legitimate in-flight trades. Continue tailing, validate the catch-up and switch the read endpoint. Preserve the former projection briefly as a fallback, with a clear plan for its ongoing freshness.

Earliest means the earliest retained record. If the first year has expired, a replay can catch up perfectly while reconstructing the wrong balance. Restore a trusted snapshot containing balances and corresponding per-partition next offsets, then replay the suffix under a deduplication policy that covers any overlap. If old duplicate logical events might be emitted anew, that snapshot also needs the relevant dedupe state or an equivalent revision guard. A compacted latest-value topic keyed by book does not preserve a full sequence of trade deltas. Decide which history is reconstructible before setting retention.

Use real PostgreSQL and Kafka in containerised integration tests. An in-memory database or mocked KafkaTemplate cannot demonstrate unique-index contention, broker acknowledgement or group recovery. Poll for observable outcomes with a deadline instead of sleeping a fixed number of milliseconds. Give each test its own topic/group and database state. Deploy database and event changes in stages

Ship one independently versioned image per service. Run one migration owner per database deployment or use Flyway's coordinated startup with tested lock behaviour. For a renamed column, first add the replacement as nullable, deploy writers that maintain both, backfill in bounded batches, verify parity, move reads and only later remove the old column. During a rolling deployment old and new code overlap. Exercise rollback against the expanded database. Destructive cleanup belongs after the rollback window.

For Kafka, deploy tolerant consumers before a producer emits a new optional field. When a semantic break requires a new topic, identify which stream each projection reads during the transition. Subscribing to both while generating new IDs for the same economic booking defeats deduplication. Preserve logical event identity where it represents the same fact and reconcile counts and amounts by business key. Define an explicit cutover revision or source watermark.

Use separate workload identities for the two services. Booking needs to produce to the booking topic; positions needs to read it and use its consumer group. Restrict database roles to the owned database, distinguish migration from runtime privileges and protect application and broker traffic in the deployed environment. Keep business authorisation at the command boundary, for example whether the authenticated user can book into ALPHA. Avoid publishing unnecessary counterparty or trader details on a broadly consumed topic. The lab's loopback setup has no application authentication.

Diagnose stale positions from the first missing fact

Start from the trade ID on the caller's receipt. Confirm the accepted terms in booking, obtain the event ID from its outbox, then find the corresponding record and the consumer group's partition progress. Finally inspect the consumed identity and the position row. In a high-volume environment use structured correlation logs and a bounded diagnostic lookup rather than scanning the whole topic. Avoid logging entire payloads or using trade IDs as metric labels; the latter creates an unbounded set of time series.

Set separate objectives for booking availability and projection freshness, for example a target fraction of accepted trades visible within five seconds under agreed load. Monitor the age of the oldest pending outbox entry, the time from acceptance to application, per-partition lag, consumer-running status and database lock waits. A median delay of 30 ms can hide one partition stalled for hours. An HTTP health endpoint can remain green while its Kafka listener has stopped. Spring Boot Actuator endpoints

Transfer case: enforce a 1,000-unit limit

Change one requirement. ALPHA may hold at most 1,000 units of GILT10, and every new buy must pass the limit before acceptance. The projection shows 900. Two clients concurrently request +80. Both read 900, each computes 980, and both accept. The committed total becomes 1,060. Faster consumption or a book-based Kafka key reduces some timing gaps but leaves the pre-acceptance race intact. The design needs a single authority that can decide and record the reservation atomically.

Design excerpt · reserve capacity in the owning database
-- Parameters: requested units, book, instrument, requested units.
-- Called inside the transaction that claims the unique command ID.
UPDATE limit_usage
SET used_units = used_units + ?
WHERE book = ? AND instrument = ?
  AND used_units + ? <= max_units
RETURNING used_units;

Under the simple assumptions of one positive buy, one book and one instrument, the first transaction locks and updates the limit row from 900 to 980. Under Read Committed, the competing update waits, then PostgreSQL rechecks the predicate against 980. Adding another 80 would exceed 1,000, so zero rows update. Treat that result as a rejection. Persist the booking or reservation identity and its outcome in the same transaction so that a lost success response cannot reserve twice. A rejection policy must specify whether a retried identical command retains its first decision or may be re-evaluated after capacity changes.

If another service owns capacity, use a saga: record the booking as pending, request a reservation under a durable operation ID, and transition to accepted on confirmation. A rejection moves it to rejected. If a later business step fails, request an idempotent release. A timeout after requesting a reservation is ambiguous; query or retry with the same operation ID before deciding to release or rebook. Persist workflow state and deadlines so a restarted coordinator resumes the same operation. Expose pending explicitly to the caller. Positions should consume the accepted fact only after the business rule has been satisfied.

The reusable decision is to locate the write that makes the promise true. An asynchronous projection suits “show me the latest processed holdings”. A conditional reservation suits “never accept a buy that exceeds available capacity”. The same services and broker can support both, provided the API says which decision has actually committed.
