Chapter 1 · Topics 001–020

Model a reservation in Java

A customer requests the last unit of SKU TEA. A Java value crosses the HTTP, persistence and event boundaries. Its identity must survive all three.

Spot where a generated constructor, a changing hash or a shared object can change the meaning of a command.

Java 21 · JShell excerpt
record TaxRule(String band, int percent) {}
record Line(String sku, int units, TaxRule rule) {}
var reduced = new TaxRule("R1", 5);
var a = new Line("TEA", 1, reduced);
var b = new Line("RICE", 3, reduced);
System.out.println(a.rule() == b.rule());
System.out.println(a.equals(b));
Expected observation

true, then false. Both lines point to the same immutable rule. Each line owns its SKU and quantity. Looking up a second equal TaxRule can preserve value equality even if reference equality changes.

Lombok builder generation · Lombok equality generation · Java records

001 Record identity

Represent a reservation command as a record when equality means the same component values. Two deliveries with equal payloads can still be separate purchases. Carry a client-issued command ID so deduplication answers a business question that object equality cannot.

Java · excerpt
record Command(String key, String sku, int units) {}
var x = new Command("K9", "TEA", 1);
var y = new Command("K9", "TEA", 1);
System.out.println(x.equals(y));

A record declares a fixed set of components. Java supplies accessors, a canonical constructor and component-based equality. Here the output is true even though x and y are separate allocations. In the service, persist K9 under a unique tenant-scoped constraint. That lets another JVM recognize the same command after the original object has disappeared.

002 Compact constructors

An HTTP adapter and a Kafka listener both construct Quantity. Put the positive-count check in its compact constructor so replay follows the same rule. Normalize the constructor parameter before the implicit field assignment. Assigning a normalized local copy leaves the original parameter untouched.

Java · excerpt
record Sku(String value) {
  Sku {
    value = value.strip();
    if (value.isEmpty()) throw new IllegalArgumentException();
  }
}

Constructing Sku with " TEA " stores "TEA". The compact constructor runs before Java copies the parameters into the fields. Decide whether stripping is part of the public contract, then use the normalized value for routing and lookup. Check for null explicitly if callers need a domain-specific error instead of a NullPointerException. Record constructors.

003 Shallow immutability

A record holding List<Line> can change if its caller keeps the original mutable list. Take List.copyOf at construction and make Line immutable too. Otherwise a command can pass validation at ingress and contain different quantities when serialized later.

Java · excerpt
record Basket(List<Line> lines) {
  Basket { lines = List.copyOf(lines); }
}

Clearing the caller’s original ArrayList after construction leaves the basket’s membership intact. An unmodifiable view over the caller’s list would still reflect its structural changes. If Line contains a mutable byte array, copy that array at its own boundary. Repeat the mutation check at each level whose contents participate in equality or serialization.

004 Sealed outcomes

Model a stock decision with a sealed interface and Reserved and SoldOut implementations. An exhaustive switch in the HTTP adapter forces a deliberate mapping when Backordered joins the hierarchy. Keep a separate wire discriminator so renaming a Java class preserves stored events.

Java · excerpt
sealed interface Decision permits Held, Empty {}
record Held(String reservationId) implements Decision {}
record Empty() implements Decision {}

A sealed type restricts which classes directly implement the contract. In Java 21, switch on Decision with a case for Held and another for Empty, omitting a catch-all branch when every case needs explicit business handling. Adding Backordered and recompiling then points to each incomplete mapping. Keep null out of the contract or handle it deliberately.

005 Decimal identity

BigDecimal values 2.0 and 2.00 compare numerically equal but differ under equals. A HashMap can therefore hold two price keys. Canonicalize using the agreed currency scale and explicit rounding policy before the price enters a key or an event fingerprint.

Java · excerpt
var a = new BigDecimal("2.0");
var b = new BigDecimal("2.00");
System.out.println(a.compareTo(b));
System.out.println(a.equals(b));

The outputs are 0 and false. BigDecimal retains scale, so sorting and hash-based identity can disagree. For GBP prices, one possible acceptance rule is setScale(2, RoundingMode.UNNECESSARY), which accepts 2.0 and rejects 2.001. Put currency alongside the normalized amount. Two decimal places would be the wrong rule for some other currencies.

006 Time as a domain value

Persist the reservation deadline as an Instant. A warehouse promise of “by 17:00 in London” starts as a local date, time and zone and needs a daylight-saving policy. Inject Clock so an expiry decision can be reproduced at the exact boundary.

Java · excerpt
Instant now = clock.instant();
boolean expired = !now.isBefore(reservation.expiresAt());

This policy makes equality with the deadline count as expired. Use Clock.fixed in a test and evaluate one instant before, exactly at, and just after the boundary. An Instant records a point on the timeline. When customers choose a local wall time, resolve ambiguous or nonexistent local times before persisting that point.

007 Typed identifiers

Wrap OrderId and ReservationId in separate records even if both contain UUIDs. A reversed pair now fails at compilation. At Kafka ingress parse the string once and report the offending field with its schema version when conversion fails.

Java · excerpt
record OrderId(UUID value) {}
record ReservationId(UUID value) {}
interface Holds { void release(ReservationId id); }

The compiler rejects release(orderId) even if both IDs serialize to the same UUID format. Implement conversions at the repository and transport edges, keeping the application API typed. Validate presence when constructing the wrapper. A generated record constructor accepts null unless you supply the check yourself.

008 Flyweight state

Ten thousand lines can share one immutable description of a tax category. Store category rules in the flyweight and quantity on each line. Include the rule version in the lookup key or a historical reconstruction can silently use today’s tax treatment.

Java · excerpt
record TaxKey(String band, int version) {}
var rules = Map.of(new TaxKey("R1", 2), reduced);
var line = new Line("TEA", 1, rules.get(new TaxKey("R1", 2)));

A flyweight separates shared intrinsic state, here a tax rule, from extrinsic state supplied by each line, here its SKU and quantity. Use the registry when constructing each line, so one rule serves many lines. Reject an unknown key before construction. Compare retained memory with realistic data because a registry of mostly unique rules adds overhead.

009 Canonicalization lifetime

A map from customer-supplied labels to shared objects grows with distinct inputs. Fifty shared categories are a good fit for an immutable registry. Ten million distinct coupon strings need a bounded cache or ordinary allocation. Measure retained bytes after collection.

Canonicalization means choosing one representative for equivalent values. For a finite tax catalogue, build the registry from a validated configuration snapshot and publish it once. On refresh, replace the whole registry and allow old snapshots to become collectible when readers finish. For an open-ended key space, track distinct keys and eviction rates to establish whether sharing saves any memory.

010 Identity-sensitive operations

A flyweight registry rebuilt on refresh can return a different Java instance for the same category. Reference equality then changes a pricing branch after refresh. Compare stable category values and reserve reference equality for identities whose lifetime the API explicitly controls.

Java · excerpt
var first = new TaxKey("R1", 2);
var second = new TaxKey("R1", 2);
System.out.println(first == second);
System.out.println(first.equals(second));

The first line prints false and the second prints true. A cache hit can make an accidental reference comparison pass every test until eviction. Add a test that decodes the same key twice from wire data. Use the domain key as a map key wherever independently reconstructed values must address the same entry.

011 @RequiredArgsConstructor

Lombok includes uninitialized final fields and qualifying @NonNull fields in the generated constructor. A new mutable repository field can quietly miss constructor injection. Mark required collaborators final and inspect the constructor signature whenever dependency wiring behaves unexpectedly.

Java · excerpt
@Service
@RequiredArgsConstructor
class ReserveService {
  private final StockRepository stock;
}

With Lombok annotation processing enabled, this class gets a constructor taking StockRepository. Spring can use its single constructor without an injection annotation. In a unit test, instantiate it with a fake repository. Adding a final collaborator will change that call at compile time, making the newly required dependency visible.

012 @Value and mutable members

@Value gives fields final references by default. A byte array containing a payload hash can still be modified through an accessor. Copy on input and output or store an immutable encoded digest when equality and audit checks depend on it.

Think of @Value as generating an immutable-looking API around the fields you supply. If the field is byte[], clone the incoming array in an explicit constructor and return a clone from its accessor. Clone on just one side and either the caller or a reader can still change stored data. For short digests, a validated hex string avoids both array aliases.

013 @Builder.Default

A field initializer alone does not supply a class-level builder default. An omitted retry count can become zero. @Builder.Default supplies the initializer when the caller omits the setter. Calling the setter with zero is an explicit override and deserves a separate test.

Java · excerpt
@Builder
class DeliveryPolicy {
  @Builder.Default private int attempts = 3;
}

DeliveryPolicy.builder().build() gets three attempts. Calling attempts(0) records that the setter ran, so build() keeps zero. Lombok tracks whether a value was supplied separately from the value itself. Validate the resulting policy at the construction boundary if zero is invalid. A default only covers omission. Lombok builder defaults.

014 @Singular

A generated collection builder supports accumulating items and builds an immutable collection snapshot. Building command A and then adding line B to the builder leaves A’s collection unchanged. Its elements can still share mutable state, so inspect the element type as well.

Java · excerpt
@Builder
class Shipment {
  @Singular private List<String> labels;
}

The builder gets label("fragile") for one item and labels(collection) for many. Build a shipment, add another label to the builder, and build again. Only the second shipment includes the addition. For patch APIs that must distinguish “absent” from “replace with empty”, model that intent explicitly instead of inferring it from the built collection.

015 @EqualsAndHashCode

Including a generated database ID in an entity hash can move its logical bucket after insertion. A HashSet lookup may fail after persistence assigns the ID. Prefer immutable value keys for sets and design entity equality around the full persistence lifecycle.

Java · excerpt
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
class SkuKey {
  @EqualsAndHashCode.Include private final String code;
  SkuKey(String code) { this.code = code; }
}

Here equality follows a stable business key from construction onwards. Test insertion and lookup with two independently constructed keys. For persistence entities, check transient, managed and detached instances as separate cases. Including a parent or child collection in equality can also trigger queries or recurse around a bidirectional relationship. Lombok field selection.

016 @ToString

An association included in generated output can trigger lazy loading while formatting a diagnostic log. Under load the apparent logging slowdown becomes extra SQL. Explicitly include safe scalar fields such as order ID and status and keep payloads out of the representation.

Java · excerpt
@ToString(onlyExplicitlyIncluded = true)
class OrderSummary {
  @ToString.Include private String orderId;
  private String customerEmail;
}

Only the explicitly selected order identifier appears in the generated representation. Start with an allowlist on objects that may gain sensitive fields or associations. Test the formatted string with an entity whose associations are unloaded and observe the SQL count. An unexpected select during formatting is evidence the diagnostic path touches persistent state.

017 @Data on entities

Generated setters let callers skip a reserve operation that checks stock and records a domain event. Generate selected accessors and expose reserve(quantity) as the state transition. A persistence model and a transport DTO often need different mutation contracts.

@Data bundles several generated methods, including getters, setters for eligible fields, equality, hashing and a string representation. Review what each one means for the entity. For Stock, give quantity a getter, use a protected no-argument constructor if the persistence provider needs it, and expose a reserve method that checks and changes quantity together. Enforce the corresponding race-sensitive invariant in PostgreSQL too.

018 @With

A wither returns a value with one field changed and may reuse the current instance when appropriate. Ignoring its return leaves the old state in place. Reassign the returned snapshot and perform the database version check separately when saving it.

Java · excerpt
@Value @With
class Quote { String currency; int cents; }
// Given an existing quote in GBP
Quote inEur = quote.withCurrency("EUR");

The generated wither uses the other existing field values to construct the result. The original quote keeps GBP and the result carries EUR with the same numerical cents. That is a structural copy, so use a domain operation for real currency conversion where changing currency also requires recalculating the amount. Generated withers.

019 @NonNull boundaries

Lombok’s generated null check rejects a missing reference when an annotated parameter reaches that method. A non-null empty SKU still passes. Validate transport shape at the adapter and enforce business invariants in the type used by every entry point.

Place @NonNull on an explicit constructor parameter when every caller needs the generated entry check. Put constraints such as a positive count or a recognized currency beside it using domain validation. For an HTTP DTO, use Jakarta validation to collect field errors for the response. A generated exception alone carries neither an HTTP status nor a consumer recovery policy.

020 Delombok as a review tool

When a builder or generated equality method surprises you, inspect the expanded Java with delombok using the project’s Lombok version. Follow which constructor build() invokes. A validation check in a different overload never sees that creation path.

Command · excerpt
java -jar lombok.jar delombok src/main/java -d expanded

With the project’s Lombok JAR and the relevant classpath, inspect the generated class under expanded. Trace build() to its constructor and locate the default-value branch. Keep this output in a temporary inspection directory. Adding it as a normal source root alongside the annotated classes would define the same classes twice.

Change one constraint

A tax change arrives at noon. Replacing the shared rule in the registry leaves existing lines pointing to the old immutable value. Persist the rule version on the reservation too. On a replay tomorrow, resolve that historical version so the tax decision survives the JVM’s lifetime.

Budget concurrency with virtual threads

The HTTP tier accepts 600 simultaneous requests. PostgreSQL can spare only 20 connections. Where the other 580 spend their time determines the customer’s experience.

Calculate the resource that caps throughput and distinguish pool waiting from a pinned carrier.

Spring Boot 3.5 · application.properties excerpt
spring.threads.virtual.enabled=true
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.connection-timeout=500
Expected observation

On a supported Java 21+ setup with Boot-managed request execution and HikariCP, virtual-thread support changes execution capacity. At saturation 20 connections may be checked out and acquisition can time out after the configured 500 ms. The property does not convert arbitrary custom executors.

Java 21 scheduling and diagnostics · Java 24 pinning behavior · Boot task execution

021 Virtual thread per task

A blocked reservation request can release its carrier platform thread while waiting on supported I/O. A second request can then run on the carrier. CPU-heavy pricing still occupies a core while it executes. Compare wall time with CPU time before changing the executor.

Java · excerpt
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
  var reply = executor.submit(() -> prices.lookup("TEA"));
  return reply.get();
}

Each submitted task gets its own virtual thread. While lookup waits on supported socket I/O, the scheduler can run another virtual thread on its carrier. Use this shape for independent blocking tasks, handle execution failures and interruption at the caller, and keep a separate concurrency limit on the pricing service. Java 21 virtual threads.

022 Admission control

A virtual-thread executor accepts many simultaneous tasks. Set a concurrency budget around the scarce dependency. For 12 pricing permits, the thirteenth caller must wait within its remaining deadline or receive an overload response before it spends a connection.

Java · excerpt
if (!slots.tryAcquire(50, TimeUnit.MILLISECONDS))
  throw new BusyException();
try { return prices.lookup(sku); }
finally { slots.release(); }

Create one Semaphore per intended budget and share it across requests to that dependency. A completed lookup returns its permit even when it throws. A semaphore inside the method body would give each request its own budget. Four replicas with twelve permits each can still send 48 concurrent calls.

023 JDBC pool arithmetic

A pool of 20 connections held for an average of 50 ms supports an ideal ceiling of 400 acquisitions per second in steady state. Include lock waits and commit time in the hold interval. Lower throughput with all connections active often points to longer holds.

Measure hold time from successful checkout through release, including result-set consumption. At 250 reservations per second and 50 ms average hold, the mean demand is 12.5 connections if each reservation checks out once. A target of 13 leaves little margin for variance. Increase load gradually while plotting both acquisition delay and database wait events.

024 Queue residence time

At a steady 600 requests per second, 0.2 seconds of average residence implies 120 requests in the system by Little’s law. Counting active SQL queries alone misses callers waiting to acquire a connection. Time acquisition and execution independently.

Instrument arrival, admission and completion timestamps for the same population. At the stated 600/s and 200 ms residence, if 20 requests are executing, about 100 are waiting on average. A timer starting only when a worker begins misses that queue. Use a steady interval and a consistent system boundary when comparing measured counts with the calculation.

025 Carrier pinning by JDK version

On JDK 21, blocking while holding a Java monitor can pin the carrier. Use a flight recording to find frequent long pins before rewriting critical sections. JDK 24’s monitor changes remove this common cause. Native calls can still constrain scheduling.

On JDK 21, record jdk.VirtualThreadPinned events while exercising the actual slow dependency. Inspect the stack for a monitor held across blocking I/O. Move the call outside the critical section if correctness permits, or use an appropriate explicit lock. On a later JDK, verify the pinning mechanism for that release before interpreting a change in event count.

026 Lock scope

Moving remote pricing outside a stock lock frees contenders but allows stock to change before pricing returns. Read a version first, calculate outside the lock, then conditionally update that version. A zero-row update signals the decision needs fresh inputs.

PostgreSQL · excerpt
UPDATE stock SET units = units - 1, version = version + 1
WHERE sku = 'TEA' AND version = 8 AND units >= 1;

Suppose the initial read returned version 8. While pricing runs another writer advances it to 9. This update then affects zero rows. Reload the inputs and decide whether a quote is still valid before retrying. Keep the version check and mutation in the same statement to close the gap between validation and use.

027 Interruption discipline

An interrupted sleep throws InterruptedException and clears the flag. Propagate the exception or restore interruption when translating it at a boundary. Swallowing it in a retry loop can keep a terminating pod issuing writes beyond its shutdown deadline.

Java · excerpt
catch (InterruptedException e) {
  Thread.currentThread().interrupt();
  throw new ReservationCancelledException(e);
}

Use this catch block when the method’s interface cannot propagate the checked exception. Restoring the flag lets outer code detect cancellation, and leaving the operation stops its retry loop. An interrupt is cooperative. Downstream I/O may require its own timeout, and a write already committed still needs normal outcome reconciliation.

028 Deadline propagation

An ingress budget of 800 ms with 300 ms already spent leaves 500 ms for pool acquisition, SQL and response. Pass remaining time downstream and reserve cleanup time. Reassigning the original 800 ms at each hop permits work after the caller has abandoned it.

Use a monotonic clock such as System.nanoTime for elapsed durations inside one JVM. Subtract elapsed time before acquiring a permit, and again before calling the dependency. If the budget is exhausted, stop before issuing more work. Propagate a supported timeout or deadline across service boundaries because a nanoTime value has meaning only within its local timing context.

029 Cancellation and commit

A caller can time out after COMMIT reached PostgreSQL but before the acknowledgement arrived. Cancelling the Java future cannot determine the outcome. Reuse the command key and consult the durable receipt before attempting the same business transition.

Implement an “outcome unknown” branch for a lost connection during commit. On a fresh authoritative connection look up the receipt, verifying its tenant and request fingerprint. If it is missing, run the same keyed transaction again. The unique key arbitrates even if the original transaction is still resolving. Generating a new key would bypass that protection.

030 Thread-local footprint

A large per-thread formatter cache that worked for 40 workers becomes expensive across thousands of live virtual threads. Share immutable formatters and keep request context small. A heap histogram under realistic concurrency reveals retained objects a single-request benchmark misses.

Inspect what each ThreadLocal actually retains. A 64 KiB buffer held by 10,000 simultaneously live threads represents about 625 MiB before object overhead. Replace it with a bounded shared pool only if borrowing and return are simpler than allocation. Thread-local request metadata can still be reasonable when small and cleaned up at the task boundary.

031 Context propagation

A task submitted to another executor needs an explicit path for the trace and tenant context it consumes. Capture immutable values at submission and install and clear them around the task. Derive authorization from trusted ingress data before creating that context.

Java · excerpt
var tenantId = requestContext.tenantId();
executor.submit(() -> rebuildFor(tenantId));

Here the task captures the validated tenant value while the request is active. Passing it as an argument makes its origin reviewable and keeps the task usable outside a request thread. When a framework requires thread-local tracing context, use its context wrapper so previous worker state is restored even if the task fails.

032 Transaction thread affinity

Imperative Spring transactions bind resources to the executing thread. A virtual thread moving between carriers keeps its logical identity. Starting a second virtual thread inside the method creates another execution context. Its JDBC call requires its own transaction decision.

Place the transactional write on an injected service and invoke that service inside the worker when independent transactions are intended. If two writes must commit together, execute them in one transaction on the calling thread. Passing a live EntityManager or JDBC Connection into parallel tasks introduces concurrent access and does not extend Spring’s transaction boundary.

033 Safe publication

An immutable routing table built on a refresh thread still needs publication to readers. Replace one volatile reference to a fully constructed map. Mutating a shared HashMap in place allows requests to observe intermediate routing decisions during a configuration refresh.

Java · excerpt
private volatile Map<String, Route> routes = Map.of();
void reload(Map<String, Route> next) {
  routes = Map.copyOf(next);
}

The volatile write publishes a fully constructed snapshot. Capture routes into a local variable before performing several related lookups so they all use one generation. Treat Route values as immutable too. Publishing the map safely cannot protect concurrent mutations inside the values it references.

  int n = units.get();
  if (n == 0) return false;
  if (units.compareAndSet(n, n - 1)) return true;
}

037 Fan-out latency

If five independent calls each have a 99% chance of finishing by a deadline, all five finish by it about 95.1% of the time. Shared dependencies make independence doubtful. Budget for the slowest required branch and remove optional calls from the critical path.

List which responses the reservation actually needs before it can commit. If tax and stock are mandatory but recommendations are optional, remove recommendations from the join. For five mandatory independent calls the calculation is 0.99 raised to the fifth power. Measure the joint result in production because a shared network stall can affect all branches together.

038 Bounded buffering

A worker consuming 80 items per second behind an arrival rate of 100 accumulates 20 per second. A 1,000-slot buffer fills in about 50 seconds from empty. Choose an explicit rejection or upstream pause policy before that threshold.

Prove the PostgreSQL transaction

Two buyers see one unit. Follow the moment the second writer wakes after the first commits and discover which predicate PostgreSQL evaluates.

-- Once, outside a transaction
CREATE TABLE stock (
  sku text PRIMARY KEY,
  units integer NOT NULL CHECK (units >= 0)
);
INSERT INTO stock VALUES ('TEA', 1);
-- A: begin and update; leave the transaction open
BEGIN;
UPDATE stock SET units = units - 1
WHERE sku = 'TEA' AND units >= 1 RETURNING units;
-- B: run the same BEGIN and UPDATE, then wait
-- A: COMMIT; B: observe the result, then COMMIT
Expected observation

A gets one row containing 0. B waits on the conflicting write. After A commits, B rechecks the predicate against the updated row, finds units=0 and returns zero rows. Zero rows and one returned row containing zero mean different business outcomes. If A rolls back instead, B can reserve the unit.

061 Statement snapshots

At PostgreSQL READ COMMITTED, successive SELECTs in one transaction can see different committed data. A stock check followed by an unconditional decrement races with another buyer. Put the available-count predicate directly in the UPDATE and inspect RETURNING.

PostgreSQL · excerpt
UPDATE stock SET units = units - 1
WHERE sku = 'TEA' AND units >= 1
RETURNING units;

With one unit available, a successful buyer gets a returned row containing zero. A waiting buyer re-evaluates the condition against the committed update and gets no row. Map those outcomes separately in the repository. Reading a count into Java and later saving count minus one loses the predicate that made the original decision valid.

062 MVCC visibility

An UPDATE produces a new row version. A reader whose snapshot predates the commit may still see the old quantity while a new reader sees the new one. A stale result on the primary can therefore originate from an old snapshot as well as a cache.

Multi-version concurrency control gives each row change a version whose visibility depends on transaction status and snapshot. Open a repeatable-read transaction, read quantity one, then commit a decrement on another connection. Reading again on the first connection still yields one. Commit and read on a new transaction to distinguish snapshot behavior from a stale cache.

063 Repeatable read

PostgreSQL REPEATABLE READ gives a stable transaction snapshot after its first snapshot-taking statement. A report can read orders and lines consistently. An attempted update conflicting with a later committed change can fail and require a fresh transaction.

PostgreSQL · excerpt
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM orders;
SELECT sum(amount) FROM orders;
COMMIT;

Both report queries see a consistent committed population even if checkouts finish between them. Keep this reporting transaction short. If it later tries to update a row modified after its snapshot, the database can reject the attempt. Restart the complete use case with a new snapshot when retrying a write.

064 Write skew

Two warehouse operators each see two staff on call and each removes a different person. Distinct-row writes can both succeed under snapshot isolation. Encode the minimum staffing decision on a shared guard row or use SERIALIZABLE with whole-transaction retry.

Reproduce the staffing race with rows A and B both on call. Each transaction counts two, then updates only its own row to off call. With disjoint writes, a stable snapshot alone can permit a final count of zero. 065 Serializable dependencies

PostgreSQL tracks read/write dependencies and can abort a transaction whose interleaving threatens serial equivalence. SQLSTATE 40001 requests a retry. Re-read inputs and recompute the decision inside a new transaction. Retrying only the failed statement preserves a stale decision.

Implement retries around the transaction callback or proxied service invocation so each loop creates a fresh physical transaction. Examine the underlying SQLSTATE and bound retries with backoff and a request deadline. A serialization failure can surface on commit after the method body ran. Keep emails and other irreversible calls out of the retried region. PostgreSQL isolation.

066 Pessimistic row locks

069 Deadlock order

081 Composite B-tree order

For tenant-specific orders sorted by creation time and ID, index (tenant_id, created_at, id). Equality on tenant narrows the search and the remaining keys provide a deterministic traversal. A global newest-orders feed has a different access path.

PostgreSQL · excerpt
CREATE INDEX order_feed ON orders (tenant_id, created_at, id);

With tenant fixed, successive index entries are already sorted by timestamp and then ID. Request the first fifty rows in that order and inspect EXPLAIN for a bounded index scan without a separate sort. For newest-first, a backward scan can reverse all ordered keys together. Mixed directions may require a different index definition.

082 Covering indexes

INCLUDE(status) can let an index carry everything a status page reads. An index-only scan still consults the heap for pages whose visibility map bits are unset. Compare heap fetches on freshly updated orders and old archived rows.

Add display-only fields with INCLUDE when their presence can avoid a heap visit. They occupy index space but do not supply search ordering. Run EXPLAIN (ANALYZE, BUFFERS) and inspect Heap Fetches under the index-only scan. Frequent updates clear all-visible status on affected pages, so results from an idle archive can overstate the benefit for active stock. PostgreSQL covering indexes.

083 Partial indexes

Index pending outbox rows with WHERE sent_at IS NULL. Once most events are sent, the active index can remain small. The planner must be able to prove the query implies the predicate. Check the actual prepared query plan.

PostgreSQL · excerpt
CREATE INDEX outbox_ready ON outbox (created_at, id)
WHERE sent_at IS NULL;

Use the same pending condition in the relay query and order by the indexed columns before LIMIT. An index entry exists only while its row satisfies the predicate. A parameterized query asking for an arbitrary status may not let a generic plan prove it can use a status-specific partial index. Inspect the plan used by the actual application.

084 Expression indexes

A lookup on lower(external_ref) can use an index built on that expression. Agree on normalization and collation before treating two references as equivalent. A case-sensitive unique index elsewhere would enforce a different contract.

PostgreSQL · excerpt
CREATE UNIQUE INDEX order_ref_ci
ON orders (tenant_id, lower(external_ref));

Two references with the same normalized value now conflict within a tenant. Use lower(external_ref) in the lookup so its expression matches the index, and decide whether null references are permitted. If the Java application uses a different locale or normalization algorithm, let the database’s uniqueness decision govern the final result.

085 GIN for JSONB

Choose a GIN operator class that supports the JSON operators your query uses. A containment-heavy search and a key-existence search may need different choices. Promote frequently joined tenant or order identifiers to typed columns with explicit constraints.

PostgreSQL · excerpt
CREATE INDEX event_payload_gin
ON events USING gin (payload jsonb_path_ops);
SELECT id FROM events WHERE payload @> '{"sku":"TEA"}';

GIN indexes keys derived from the document so a containment query can find candidate records. jsonb_path_ops suits supported containment and path predicates. For the top-level key-existence operator ?, evaluate the default jsonb_ops class. Measure index size, read time and insertion cost using the distribution of real event payloads.

086 BRIN locality

A BRIN summarizes page ranges. On an append-oriented event history, a timestamp predicate can discard large ranges cheaply. Late backfills scatter old timestamps among newer pages and increase rechecks. Measure blocks visited after realistic backfill traffic.

PostgreSQL · excerpt
CREATE INDEX event_time_ranges
ON events USING brin (occurred_at);

A BRIN range records summaries such as minimum and maximum time for groups of adjacent heap pages. A narrow time filter skips groups whose summaries rule them out, then checks candidate rows. Use EXPLAIN with buffers to compare pages visited on ordered ingestion against the same dataset after out-of-order backfills.

087 Planner estimates

A plan expecting ten matching rows but returning fifty thousand can choose an expensive nested loop. Inspect estimated versus actual counts at the first diverging node. Refresh statistics and investigate correlation before forcing a join method.

Read a plan from its input nodes upward and find the first material row-count error. If an inner index scan returns 100 rows per loop across 500 loops, it emitted about 50,000 rows. Compare its filter selectivity against actual data for this tenant. Refresh ANALYZE statistics before attributing the problem to a missing index.

088 Extended statistics

Tenant and order status may be correlated if one tenant owns most pending work. Single-column estimates can misprice their conjunction. CREATE STATISTICS over the relevant columns and ANALYZE, then compare estimates for the same parameter values.

PostgreSQL · excerpt
CREATE STATISTICS tenant_status_stats (mcv, dependencies)
ON tenant_id, status FROM orders;
ANALYZE orders;

Multicolumn statistics give the planner evidence about common value combinations and dependencies within a table. Compare a query for a large tenant’s pending orders before and after ANALYZE, looking at estimated rows. These statistics guide planning. They do not enforce a dependency between values or create a new access path.

089 EXPLAIN with buffers

EXPLAIN (ANALYZE, BUFFERS) executes the query and reports work at plan nodes. A shared-buffer read may still hit the OS cache. Capture representative inputs and inspect loops as well as per-loop rows before blaming storage.

PostgreSQL · excerpt
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM orders WHERE tenant_id = 7 LIMIT 50;

Compare shared hits, reads, actual rows and loops. Buffer counts on a parent can include work in its children, so summing every node double-counts work. EXPLAIN ANALYZE on a mutation actually performs it. Use a controlled dataset for write-path experiments, particularly when triggers or sequences have effects beyond a simple row rollback.

090 Keyset scans

Read the next page using (created_at,id) greater than the last returned tuple with matching ascending order. Require non-null stable sort keys. Large OFFSET still walks discarded rows, while a mutable sort key can move a row behind a cursor.

Build the cursor from the last row actually returned. If the last tuple was (12:00, 41), the strict tuple comparison includes (12:00, 42) and excludes the already seen row. Reverse the comparison for descending traversal. For a fixed export, use a defined snapshot or immutable cutoff because independent page requests can see different committed populations.

091 HOT updates

PostgreSQL can avoid ordinary index churn for eligible updates when changed columns allow it and the new tuple fits on the same heap page. Indexing a frequently updated status can remove that opportunity. Compare HOT update counts before and after the new index.

PostgreSQL · excerpt
SELECT n_tup_upd, n_tup_hot_upd
FROM pg_stat_user_tables WHERE relname = 'stock';

Compare counter deltas over the same workload window to estimate how often updates qualified for heap-only tuples. Updating an indexed quantity typically prevents a HOT update, even with free space on the page. A lower fillfactor can help a space shortage but cannot remove the need to maintain an affected ordinary index.

092 Vacuum horizons

Vacuum cannot remove row versions still needed by old snapshots. A long reporting transaction can hold that horizon while the order table grows. Compare old transaction ages, dead tuple estimates and vacuum progress before increasing vacuum frequency.

PostgreSQL · excerpt
SELECT pid, xact_start, backend_xmin, state
FROM pg_stat_activity WHERE backend_xmin IS NOT NULL
ORDER BY xact_start;

Look for old snapshots that overlap sustained update churn and compare them with vacuum activity. A long read can hold versions needed by its transaction even after all current requests see newer values. Inspect replication slots and other horizon holders as well. Killing the most visible query without identifying the horizon can leave the underlying cause intact.

093 Table fillfactor

Leaving free space on each heap page gives updated rows room to stay nearby. This costs scan density on read-mostly history. Apply a lower fillfactor selectively to hot mutable tables and account for the time needed for existing pages to change.

PostgreSQL · excerpt
ALTER TABLE stock SET (fillfactor = 80);

This target leaves room for future updates as pages are populated. A table already packed with rows does not immediately become 20% empty everywhere. Compare update performance and relation size over time, using a controlled rewrite only when its locking and space costs are acceptable. Avoid applying the same setting indiscriminately to append-only history.

094 Connection multiplication

Eight service replicas with a maximum pool of 20 can demand 160 connections before workers and migrations. Budget across all deployments, including rollout overlap. Compare pool acquisition latency to database CPU before increasing each replica’s maximum.

Start with the database’s usable connection budget after reserving capacity for operations, replication and migrations. Ten live application pods during rollout sharing 120 available sessions allow at most twelve each if no other users share that allocation. Configure pool maxima from the peak replica count and check how often callers actually wait under load.

095 N+1 query detection

One order-page query followed by one line query per order costs 51 round trips for 50 orders. Inspect statement counts per request. Batch-fetch the lines or issue a purpose-built projection and verify cardinality when joining multiple child collections.

PostgreSQL · excerpt
SELECT order_id, sku, units FROM order_lines
WHERE order_id = ANY (:order_ids);

Bind an array of IDs from the current page and assemble child lines by order ID. The page query plus this child query turn 51 round trips into two for 50 orders. Preserve parent order in the response and bound the page size. Fetch-joining multiple independent collections may multiply result rows even when it reduces statement count.

096 JDBC batching

Grouping homogeneous inserts reduces round trips. Flush and clear the persistence context at controlled intervals on large imports so managed objects do not accumulate. Transaction boundaries determine rollback scope independently of the JDBC batch size.

Configuration · excerpt
spring.jpa.properties.hibernate.jdbc.batch_size=50

Hibernate can group compatible statements when identifier strategy and statement shape permit. Verify driver or ORM batch behavior on the actual insert path. On a long import, flush and then clear at intervals to release managed entities. Clearing before flushing can discard pending changes, and flushing batches still leaves rollback scope determined by the encompassing transaction.

097 Partition pruning

Monthly partitions make a bounded time query and history retirement easier. Supply a predicate on the partition key and examine scanned partitions in the plan. PostgreSQL partitioned-table unique constraints must include all partition key columns, affecting event ID uniqueness design.

For monthly history, define range bounds with an inclusive lower and exclusive upper timestamp. Query with the same half-open interval so midnight on the first of the next month appears once. Check EXPLAIN for pruned partitions. A query that wraps the key in an unrelated expression can make it harder for the planner to exclude partitions.

098 Concurrent index builds

CREATE INDEX CONCURRENTLY permits ordinary writes during construction but needs multiple phases and cannot run inside a transaction block. A failure may leave an invalid index. Inspect validity before declaring a rollout complete or retrying the migration.

PostgreSQL · excerpt
CREATE INDEX CONCURRENTLY order_status_idx ON orders (status);

Put the build in a migration configured to run outside a transaction and monitor pg_stat_progress_create_index. After completion inspect pg_index.indisvalid. An interrupted build can leave the name occupied by an invalid index. A later CREATE INDEX IF NOT EXISTS could then appear successful without delivering the intended usable index.

099 Online constraint validation

Add an eligible CHECK or foreign key as NOT VALID, then validate existing rows separately. New changes are checked while historical rows await verification. Observe locks and validation progress and repair offending historical data before relying on universal coverage.

PostgreSQL · excerpt
ALTER TABLE stock ADD CONSTRAINT stock_nonnegative
CHECK (units >= 0) NOT VALID;
ALTER TABLE stock VALIDATE CONSTRAINT stock_nonnegative;

Run the two operations as separate deployment steps if historical validation needs its own window. Between them new inserts and updates must satisfy the check, but untouched historical rows may violate it. For nullable quantities, CHECK alone accepts an unknown result. Use an explicit non-null constraint when null also violates the domain.

100 Replica freshness

A standby can serve yesterday’s status for a receipt just written to the primary. Route read-after-write confirmation to the primary or require a replica to reach a known replay position. Define a timeout and fallback for replicas that cannot catch up.

For a read-your-write flow, capture a suitable authoritative WAL position after commit. Route the read to a standby only after its replay position reaches that token on the correct replication history. If the deadline expires, use the primary or return the agreed pending state. Elapsed seconds since write give weaker evidence than an actual replay position.

Change one constraint

Suppose a customer can edit created_at. Moving row 42 to 11:59 after page one hides it from the next page. A faster index cannot restore that pagination guarantee. Page by an immutable key or serve a defined snapshot for exports that require exact membership.

105 Replication and ISR

Avoid assigning the whole batch to the first order’s parent, which misattributes the remaining work.

186 Lag versus age

Ten records of lag at one record per minute can be worse than ten thousand at high throughput. Track event age and the oldest pending outbox age alongside offset distance. Empty partitions require explicit handling when interpreting age gauges.

Combine the group’s next committed position with the broker end position, then inspect age for the oldest unprocessed visible work. Also record the last successful processing time per active partition. When a partition is idle, an old last-event timestamp alone should not trigger a backlog alert. Include publication age so a stalled outbox is visible even with zero Kafka lag.

187 Pool saturation signatures

High acquisition latency, active connections at the limit and low database CPU suggest connections are held or blocked. Inspect transaction ages and wait events. If PostgreSQL is already CPU-bound, adding connections can increase contention and worsen tail latency.

Compare acquisition time, connection usage time and transaction age on the same timeline. If acquisition jumps while a few connections spend seconds waiting on HTTP inside transactions, shorten that transaction boundary. If PostgreSQL reports high I/O waits on the actual reservation query instead, inspect its plan. The pool metric pinpoints the queue but cannot identify the root holder.

190 Circuit breaker recovery

Opening a breaker after repeated pricing failures preserves resources. Half-open probes test recovery with bounded concurrency. Make the fallback explicit in the order contract, especially if an estimated price can change the amount the customer authorizes.

Configure a bounded sliding window, a minimum sample count, a failure threshold and a half-open probe budget for the pricing dependency. 191 Retry amplification

Three layers each making three total attempts can produce 27 downstream attempts for one command. Give the layer with outcome knowledge the retry budget and use jitter. Count attempts separately from logical commands to expose multiplication.

List every layer that retries a reservation, including SDK, gateway and consumer error handler. With three total attempts at each of three layers, the deepest dependency can see 3 × 3 × 3 calls even though the client sees one failure. Set an end-to-end deadline and use randomized backoff to spread simultaneous retries while stable command keys protect state.

192 Bulkhead partitioning

Reserve separate capacity for interactive reservations and bulk reconciliation when their latency budgets differ. If both share a database, their combined limits must still fit its capacity. Measure intentionally rejected batch work alongside interactive tail latency.

Implement separate semaphores or connection allocations for the interactive path and repair workers. For a pool of 20, admitting at most four concurrent repair operations leaves room for interactive work if each operation uses at most one connection and other users are budgeted. Apply limits across replicas and handle queue overflow explicitly to preserve the intended isolation.

193 Load-test arrival models

A closed-loop client waits for a response before sending again, reducing offered load when the server stalls. Use a controlled arrival schedule to assess an external request stream. Record scheduled arrival time so queueing delay remains visible.

If the target arrival rate is 100/s, schedule one arrival every 10 ms regardless of the preceding response. Record delay from the planned arrival to completion and report dropped or delayed submissions when the generator saturates. A closed-loop run remains useful for a fixed population of interactive clients, but represents a different workload during a stall.

194 GC allocation pressure

A high allocation rate and short-lived DTOs can trigger frequent collections even with stable live memory. Compare allocation profiles with post-GC occupancy. Reusing mutable objects across requests can introduce data races, so first remove measured redundant materialization.

Use JFR allocation samples to identify call sites responsible for frequent temporary objects. Compare before-and-after allocation rates and latency with identical payloads, concurrency and warm-up. A rising live set after comparable collections suggests retention rather than merely high churn. Inspect references to retained objects before increasing the heap or introducing a shared object pool.

195 Capacity under failover

Three equally loaded replicas at 60% each imply roughly 90% per survivor after one loss at the same arrival rate. That leaves little room for recovery traffic. Model connection, CPU and partition reassignment limits independently.

For N balanced replicas at utilization u, ideal surviving utilization after one loss is N × u ÷ (N − 1), assuming the work redistributes evenly. Run a controlled removal with steady arrivals and observe per-partition lag and database waits. Sticky keys and reconnection bursts can make the busiest survivor saturate before the fleet average reaches that prediction.

196 Recovery point and time

A recovery point objective limits acceptable data loss while a recovery time objective limits outage duration. A frequent base backup alone cannot guarantee either. Include WAL coverage, restore throughput and verification before declaring the service recovered.

Translate recovery objectives into a timed restore exercise. For a five-minute recovery point and a thirty-minute recovery time, record the last recoverable committed event, data restoration duration, replay duration and verification duration. WAL archiving delay affects the former and slow reconciliation affects the latter. Measure both on production-sized data before promising the targets.

197 Point-in-time recovery

Restore a base backup and replay archived WAL to the chosen target on an isolated instance. Check a known committed reservation on each side of the target. Database rollback in time may leave Kafka and payment providers ahead of the restored state.

Choose a specific recovery target, restore the base backup and configure matching WAL retrieval and recovery target settings on an isolated server. Verify the recovered timeline using known business receipts immediately before and after the target. Keep readers and writers disconnected from production until Kafka offsets, downstream projections and external payment records have been reconciled.

198 Projection catch-up capacity

A backlog of 120,000 events with 800 events/s processing and 500 events/s ongoing arrivals drains at 300/s, about 400 seconds. Add headroom for skew and retries. An average rate above ingress can still conceal one partition that never catches up.

Use net throughput, computed as successful processing rate minus new arrival rate, for each bottleneck partition. If a hot partition processes 90/s while receiving 100/s, its backlog grows by 10/s even when fleet totals suggest recovery. Compare planned catch-up time with remaining retention. Records lost to retention require a snapshot or archive recovery path.
