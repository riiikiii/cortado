Choose the boundary from the failure

A dealer submits 100 lots under reference T-17. The order sits exactly on the desk limit. The client times out and resubmits the reference, this time with seven lots. What evidence would convince you the first booking survived? A green controller test, a successful SQL insert and an HTTP 201 each answer a different part of that question.

Our contract is deliberately small. The first valid booking returns 201 with its reference. Any later use of an existing reference returns 409 and preserves the original quantity. An empty reference produces 400. An out-of-range quantity produces 422. A booking is a single SQL statement in this lab. A real desk might distinguish an identical retry from a conflicting amendment. That would require storing and comparing the request as well as changing the HTTP contract.

A slice loads selected infrastructure from the application context, Spring's registry of configured objects. A container runs an external process such as PostgreSQL. The two choices are independent. Here the JDBC slice uses a real database while the MVC slice substitutes the store. Reserve the widest test for a crossing where the collaboration itself can break.

Run the booking lab

The lab targets Java 21, Spring Boot 3.5.16, JUnit Jupiter, Maven 3.9 and PostgreSQL 16. It assumes you can read a controller and SQL. You can run the policy and web tests with a JDK and Maven. Test an invariant with plain Java

The highest-value pair here is 100 and 101. Replacing the upper comparison with a strict inequality breaks the 100 case while leaving a conventional example such as ten lots green. The zero and one pair exercises the lower boundary independently. A test that computes its expected boolean from the same inequalities could reproduce the production bug. Literal examples give it an independent oracle.

JUnit Jupiter discovers the method and invokes it once per CSV row. AssertJ builds the assertion and reports the failing input via the display name. Spring has no work to do. Use a fresh object per test when mutable state enters the design. By default Jupiter creates a fresh test instance for each method invocation. Static collections and resources held by Spring beans can still outlive it. Use a method source when a case contains a currency pair, a timestamp and an expected allocation. Give the case a business name so a CI failure identifies the violated rule. JUnit Jupiter user guide

Time, decimals and generated data

Suppose the desk adds a 16:30 London cut-off. Pass a Clock into the policy and derive the local time in an explicit Europe/London zone. Choose instants immediately before and at the cut-off, once in winter and once in summer. At 15:30 UTC in July the London clock already reads 16:30. A test built from the machine's default zone can stay green on a developer laptop and fail in CI. For quantities represented by BigDecimal, decide whether the contract includes scale. AssertJ's isEqualByComparingTo expresses numeric equality across 1.0 and 1.00. For a wire contract requiring two decimals, inspect the encoded representation as well.

Example tests anchor known boundaries. Property-based tests can add breadth when you know an invariant independent of the implementation. For an allocation algorithm, generate positive lot sizes and eligible account weights, then assert that integer allocations sum to the original size and no allocation is negative. Preserve the smallest failing input and seed. For broad algorithmic coverage this can find rounding combinations the handful of hand-written examples miss.

Mocks, fakes and a real collaborator

A stub supplies an answer. A mock can also record calls. A fake implements a small working substitute, for example an in-memory trade store. Use real value objects and the real booking rule in the controller test. Substitute the store because the question there concerns request mapping and JSON. The JDBC test later makes the substitute answer for its assumptions.

Mockito's plain @Mock creates a test-side object when initialised with MockitoExtension. Construct the subject explicitly so you can see which collaborators it receives. @MockitoBean instead supplies a Mockito object in the Spring test context. In an MVC slice the real store is outside the component selection, so Spring needs a bean for the controller constructor. A plain field annotated with @Mock does not satisfy that dependency. In a full-context test where you expect the original bean to exist, @MockitoBean(enforceOverride = true) can catch a missing registration.

A boolean method on an unstubbed Mockito mock normally returns false. In our controller that means 409. A duplicate test that omits the stub might pass even if the controller asks the store about the wrong reference. Explicitly arrange the duplicate and verify the relevant arguments when the interaction is the only observable record of which trade was attempted. In the repository test inspect the real row instead.

A fake backed by a HashMap is convenient for service-level scenario tests. It cannot reproduce PostgreSQL locking or SQL type conversion. Give real and fake adapters a shared contract test when multiple services depend on their equivalence. Include the duplicate-with-changed-quantity case. Keep database-specific race tests against PostgreSQL itself.

Exercise HTTP mapping and security

MockMvc sends a simulated servlet request through the Spring MVC dispatcher. Jackson reads the actual JSON, Bean Validation checks the reference, the controller applies the desk rule and the selected message converter writes the response. No port is opened. Constructing the request as literal JSON gives the client an independent vocabulary. Serialising a Java request object shared with the server can silently update both sides of a field rename.

Add a controller advice when the external contract requires a stable error code or ProblemDetail shape. Assert the content type, machine-readable code and affected field. A status-only test would miss a change that breaks downstream error handling. A standalone MockMvc builder is useful for a tiny controller harness, but custom filters, converters and advice must be installed deliberately. Use the Boot slice when those registrations matter.

Add an authentication boundary

The downloadable lab has no authentication dependency. For a session-authenticated desk application, add Spring Security and the test-scoped spring-security-test dependency. Import the production SecurityFilterChain configuration into the slice when its configuration class falls outside slice scanning. Test the endpoint with an authorised trader, a signed-in reader, and an anonymous caller. For the example below assume the chain requires ROLE_TRADER and CSRF is enabled.

Providing a valid CSRF token isolates the role check. Repeat as TRADER with a missing token to isolate CSRF. Run TRADER with a valid token and expect 201 after stubbing storage. Without that positive control a chain that rejects every request could pass both denial tests. Anonymous behaviour depends on the configured entry point, for example 401 for HTTP Basic or a redirect for form login. In a bearer-token API, a mock JWT lets you test claims and authority decisions. Separately exercise real token decoding and your issuer, audience and signature configuration where those are part of the deployment contract. Spring Security MockMvc CSRF testing

Give persistence tests the production dialect

This path is small enough to reason about statement by statement. Flyway creates the unique reference key. The first insert affects one row. A second insert on the same key affects zero rows. The final query retrieves 100. Checking only the boolean pair would miss a store that changed the quantity as a side effect. If the migration loses its unique index, PostgreSQL can no longer match the specified conflict target. A mock would still return whichever booleans the test arranged.

The JDBC slice creates JDBC infrastructure and a test transaction. Import the adapter explicitly because a slice narrows component scanning. The database fixture starts PostgreSQL and supplies connection details through ServiceConnection. Replace.NONE keeps the configured database. Flyway sees the application's real migrations on the test classpath. Keep schema creation under the same owner as production. A separate hand-maintained test schema can preserve columns that production has removed. Boot service connections and container lifecycle

JDBC, JPA and migrations answer different questions

For Spring Data JPA, use DataJpaTest with the same database fixture and replacement setting. Save an entity, call flush(), then clear() on the EntityManager before loading again by ID. Flush sends pending SQL, exposing many mapping and constraint mistakes. Clear detaches the first-level cache, so reading the entity exercises its database representation. To verify a column default or computed value precisely, read it through JDBC. A deferred constraint or an AFTER_COMMIT listener needs a real commit. Flush alone cannot demonstrate either.

For a migration that makes a column mandatory, a fresh empty database exercises only one path. Start a disposable database at the previous migration, insert a representative legacy row, apply the pending migrations and query the backfilled value. Then attempt an invalid new write. This distinguishes a script that creates the right final schema from one that also upgrades real data. For an expected database error, isolate it in its own transaction. PostgreSQL typically rejects subsequent statements in a failed transaction until rollback.

See exactly who owns the transaction

The JDBC slice and the HTTP test can run identical SQL against identical PostgreSQL images and leave different state after the method returns. The difference is the transaction that owns the insert.

Consider adding a test-level transaction to the random-port test and inserting reference data in @BeforeEach. The client-side setup can see that data immediately. The server's separate connection may see no fixture at all until setup commits. A timeout, missing reference or surprising 404 can be a transaction visibility problem. Seed committed setup, call HTTP, inspect data from a fresh transaction and clean up by the run's unique reference. A stronger variation with concurrent submissions

Two clients can both read âreference absentâ before either writes. A select-then-insert implementation therefore needs a database constraint and deliberate collision handling. For the lab's single INSERT with ON CONFLICT, use two independent JDBC connections. Let connection A begin a transaction and insert T-17 for 100 lots. Leave it open. On a separate executor let B attempt the same reference for seven. Commit A, obtain B's result with a bounded timeout, then inspect the row using a third connection. Expect one insert by A, zero by B and 100 lots. Change one decision: roll back A. B can now insert seven lots.

To prove actual contention, coordinate the start with a latch and observe B waiting on a database lock before releasing A. A latch raised just before JDBC execution proves only that B's thread ran. Give each wait a deadline, set a database statement timeout and release connections in finally blocks so a failed assertion cannot strand the test. Keep a simpler simultaneous-request test when the required property is only one winner. In that test the winning quantity depends on ordering. PostgreSQL transaction isolation

Prove the application works over a socket

This test starts the embedded server on an available port. TestRestTemplate resolves the relative URL against that server. The generated reference lets independent runs coexist. Use fixed T-17 in the rolled-back slice and a per-test key wherever state can escape. The final query doubles as an independent witness. A controller that returned a hard-coded 201 before persisting could satisfy a superficial smoke test.

Choose full-context MOCK plus AutoConfigureMockMvc when the question is application wiring through MVC. Choose RANDOM_PORT to exercise a real HTTP exchange, server routing and cross-thread persistence. Choose NONE when testing a scheduled processor or headless command that requires the full bean graph. A bare contextLoads method proves the selected graph starts. Give it a business assertion if the question concerns behaviour. To verify reverse-proxy headers, gateway routing or TLS termination, send a small smoke request through that deployed boundary using an isolated test identity.

A useful mutation is to change the store's conflict action to update the existing quantity. A web slice with the store stubbed remains green. The store integration test should now fail on its return value or row assertion, and the HTTP integration test should detect the violated duplicate contract. Restore the statement and rerun mvn verify. If both integration tests stayed green during the mutation, inspect discovery and reports before inspecting the business logic.

Prove asynchronous effects and Kafka replay

A booking event introduces three clocks. The publisher receives a broker acknowledgement, the consumer handles the record, and a database transaction commits the projection. Only the final observation answers âcan the desk see the position?â Awaiting the Kafka producer future removes one uncertainty but still leaves two. Use a real broker for partition assignment, serialisation, listener wiring and offset tests. An embedded broker from spring-kafka-test works for focused integration tests. A broker container is useful when testing the deployed broker distribution or configuration. A plain unit test can cover the handler's mapping in milliseconds.

An executable test shape for an existing listener

This extension assumes an application with a listener consuming string event IDs from an isolated single-partition topic, a KafkaTemplate<String,String>, a position projection in PostgreSQL and a marker event the listener records. The fixture interprets E-17 as +100 lots and END-17 as a zero-quantity barrier for the same desk. Each test gets an empty topic, a fresh consumer group configured to read from the beginning, and an empty projection. The lab download stops at HTTP and JDBC. The snippet shows the test body to adapt to your listener, with bounded waits on both sending and observing.

The marker matters. A poll for âposition equals 100â can succeed after the first record even when the second will increase it to 200. With one partition, synchronous ordered processing, no retry-topic reordering and a marker committed after earlier effects, seeing END-17 tells you both copies passed the handler. If handlers dispatch work to a pool or failures go to a retry topic, the marker loses that meaning. In that design collect completion evidence for both input offsets and assert the final position after the pending work drains. Awaitility's untilAsserted retries a read-only assertion. Putting a publish operation inside the polling block would manufacture extra inputs.

Keep the suite fast, isolated and observable

JUnit test objects, Spring contexts, Docker processes and committed rows have different lifetimes. A new test instance may receive the same cached Spring singleton as the previous class. Reuse is valuable for large suites, provided the bean holds no per-test residue. A Spring-managed container bean follows the cached context's lifetime. A JUnit-managed static container can stop at the end of its test class while another class reuses a context pointed at its old mapped port. Give the dependency and its clients compatible lifetimes. With a manually managed external service, use DynamicPropertySource to register its runtime URL before bean creation.

Spring's context cache is keyed by configuration, profiles, property overrides and context customisers, including bean overrides. Tiny per-class variations can force expensive rebuilds. Turn on DEBUG for org.springframework.test.context.cache and compare hits and misses over an entire JVM run. Consolidate genuinely equivalent fixtures. Use DirtiesContext for a test that corrupts context-level state. For one leftover database row, remove that row. Separate JVM forks do not share the in-memory context cache. Spring TestContext caching

Parallelise independent pure tests first. For integration tests choose per-run references, schemas, topics, group IDs and stub-server state to match the resource being isolated. A fresh group on a shared topic can consume another test's history. A unique reference cannot protect against another class truncating the table. Where isolation is intrinsically expensive, serialise just the tests that own that resource. A JUnit resource lock coordinates participating tests within a Jupiter execution. Separate CI workers require separate resources or an external coordination mechanism.

CI execution and diagnosis

Run mvn test for feedback during edits and mvn verify on the change that would ship. Failsafe's verify goal makes the integration-test results affect build success. Calling only integration-test can skip that final verdict. Collect target/surefire-reports and target/failsafe-reports even on failure. For a container failure retain the image name, startup log and the first underlying exception. For asynchronous failures record topic, partition, offset and event ID as well as thread and time. This lets a developer reconstruct the order of observable events. Maven Failsafe lifecycle

Use code coverage to find untouched paths. A covered line says it executed. A mutation such as changing <= to < asks whether the assertions distinguish two behaviours. Spend the strongest checks where a false green costs most: money amounts, duplicate execution, permissions and transaction boundaries. For the booking service, the release evidence is concrete: 100 lots are accepted, 101 are rejected, a second request cannot replace the first, and an independent database read still finds the original quantity.
