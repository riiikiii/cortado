Guide 2 of 3 - Building on EKS

AWS and EKS for Developers

What an engineer shipping services onto Amazon EKS needs to understand: access, IAM, networking, compute, delivery, data, observability, security, upgrades and cost.

Written November 2026. EKS moves quickly: check versions and pricing against AWS documentation before relying on a specific number.

Contents

    The mental model

    Amazon EKS gives you a managed Kubernetes control plane. Everything else (the nodes your pods run on, the network they sit in, the IAM permissions they use, the load balancers in front of them) is ordinary AWS infrastructure that Kubernetes controllers create and manage on your behalf. Most confusing EKS problems are really AWS problems wearing a Kubernetes error message, so a developer needs a working model of both layers.

    Your codecontainer image in ECR→ Kubernetes objectsDeployment, Service, Ingress→ ControllersCNI, LB controller, CSI, Karpenter→ AWS resourcesENIs, ALB/NLB, EBS, EC2

    Getting access to a cluster

    Human access to AWS

    Use short-lived credentials from IAM Identity Center (SSO). Long-lived access keys on a laptop are the classic way credentials leak.

    aws configure sso                       # once: creates a named profile
aws sso login --profile dev
export AWS_PROFILE=dev
aws sts get-caller-identity             # always check who you are first

    From AWS identity to Kubernetes permissions

    EKS authenticates you with IAM, then maps your IAM principal to Kubernetes permissions. The current mechanism is access entries, managed through the EKS API. The older aws-auth ConfigMap is deprecated, so do not build new workflows on it.

    aws eks update-kubeconfig --name dev-euw1 --region eu-west-1 --alias dev
kubectl config get-contexts
kubectl auth whoami
kubectl auth can-i --list -n pricing

# platform side: grant a role edit rights in one namespace
aws eks create-access-entry --cluster-name dev-euw1 \
  --principal-arn arn:aws:iam::111122223333:role/pricing-devs
aws eks associate-access-policy --cluster-name dev-euw1 \
  --principal-arn arn:aws:iam::111122223333:role/pricing-devs \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy \
  --access-scope type=namespace,namespaces=pricing
    Access policyRoughly equals
    AmazonEKSClusterAdminPolicycluster-admin
    AmazonEKSAdminPolicyadmin in the scoped namespaces
    AmazonEKSEditPolicyedit: workloads yes, RBAC no
    AmazonEKSViewPolicyview: read-only, no Secrets

    For finer control, an access entry can instead place you in a Kubernetes group that is bound with normal Role and RoleBinding objects.

    Daily tooling

    kubectx and kubens for switching context and namespace, k9s for a terminal dashboard, stern for tailing logs across pods. Show the current context in your shell prompt: running a command against production by mistake is the most common self-inflicted incident.

    IAM essentials

    IAM answers one question: may this principal perform this action on this resource under these conditions?

    PieceMeaning
    RoleAn identity with no permanent credentials. Something assumes it and receives temporary ones from STS.
    Trust policyAttached to a role: who may assume it.
    Permissions policyAttached to a role: what it may do.
    Resource policyAttached to a resource (S3 bucket, KMS key, SQS queue): who may touch it. Needed for cross-account access.
    Permission boundary, SCPCeilings set by your organisation. They never grant, they only limit.

    Evaluation, simplified: an explicit Deny anywhere wins. Otherwise the action must be allowed by an identity or resource policy and fall inside every boundary and SCP. No matching allow means denied.

    {
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::acme-pricing-snapshots/prod/*" },
    { "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::acme-pricing-snapshots",
      "Condition": { "StringLike": { "s3:prefix": "prod/*" } } }
  ]
}
    Reading AccessDenied

    The error message names the principal, the action and usually the resource. Check all three against what you expected before changing a policy: very often the pod is simply not running as the role you think it is.

    Giving pods AWS permissions

    A pod that calls S3, SQS, DynamoDB or Secrets Manager needs AWS credentials. Never bake keys into images or Secrets, and never rely on the node's instance role, which would give every pod on the node the same rights. Bind an IAM role to a Kubernetes service account instead. There are two mechanisms.

    EKS Pod IdentityIRSA (IAM Roles for Service Accounts)
    How it is wiredAn association in the EKS API: cluster + namespace + service account → role.An annotation on the ServiceAccount, plus a role trust policy that names the cluster's OIDC provider.
    Trust policyOne generic principal, pods.eks.amazonaws.com. The same role is reusable across clusters.References a specific cluster's OIDC issuer and the exact service account.
    NeedsThe Pod Identity Agent add-on (built into Auto Mode).An IAM OIDC provider per cluster.
    ExtrasSession tags (cluster, namespace, service account) usable in policies. Can chain to a role in another account.Works on Fargate and on non-EKS clusters.
    Choose itBy default for new work on EC2-backed nodes.On Fargate, or where it is already established.

    In both cases your code changes nothing. The AWS SDK's default credential chain finds the injected credentials and refreshes them. Do not construct clients with explicit keys, and do use a reasonably recent SDK.

    # debugging: which role is this pod really using?

    Common mistakes

    The Deployment does not set serviceAccountName, so the pod runs as default. The association or annotation was added after the pod started: restart it. The role's trust policy names a different namespace or service account. One role is shared by many services, so every service has every permission.

    Networking

    Pod networking with the VPC CNI

    On EKS each pod receives an IP address from the VPC subnets, so pods are directly routable inside the VPC with no overlay. Consequences:

    • IP addresses are a finite resource. Small subnets run out, and pods then stick in ContainerCreating with IP allocation errors. Platform teams address this with larger or secondary CIDR ranges, prefix delegation, or IPv6 clusters.
    • Pod density per node is bounded by how many network interfaces and addresses the instance type supports, unless prefix delegation is on.
    • Security groups apply at node level by default. Security groups for pods exist for the cases where a specific workload needs its own.
    • Network policies are enforced by the VPC CNI when enabled. Without that, NetworkPolicy objects are accepted and silently do nothing.

    Exposing a service

    NeedKubernetes objectAWS result
    Internal calls between servicesService type ClusterIPNothing in AWS. Cluster DNS name svc.namespace.svc.cluster.local.
    HTTP(S) from outside the clusterIngress or Gateway API HTTPRouteApplication Load Balancer (layer 7: host and path routing, TLS with ACM, WAF, OIDC auth).
    TCP, UDP, gRPC pass-through, static IPs, lowest latencyService type LoadBalancerNetwork Load Balancer (layer 4).
    Private access from another VPC or accountNLB plus a VPC endpoint servicePrivateLink.

    The AWS Load Balancer Controller (built into Auto Mode) turns these objects into load balancers. Use IP target mode so the balancer sends traffic straight to pod IPs, skipping an extra node hop.

    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: pricing-api
  namespace: pricing
  annotations:
    alb.ingress.kubernetes.io/scheme: internal
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/healthcheck-path: /healthz
    alb.ingress.kubernetes.io/group.name: internal-shared   # share one ALB across teams
spec:
  ingressClassName: alb
  rules:
    - host: pricing.dev.acme.internal
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: pricing-api, port: { number: 80 } } }

    ExternalDNS usually creates the Route 53 record from the hostname, and ACM supplies the certificate. Each ALB costs money and takes minutes to create, so share them with ingress groups instead of one per service.

    Zero-downtime deploys behind a load balancer

    The load balancer and Kubernetes update on different clocks. Three settings close the gaps:

    • Pod readiness gates: the pod is not Ready until the target group reports it healthy, so a rollout cannot outrun target registration.
    • A preStop sleep (for example 15 seconds) so the pod keeps serving while it is being deregistered.
    • Graceful shutdown in your code: on SIGTERM stop accepting new work, finish in-flight requests, exit before terminationGracePeriodSeconds.

    DNS and egress gotchas

    • The default ndots:5 makes a lookup of an external name try several cluster suffixes first. Chatty clients multiply DNS load. Use fully qualified names with a trailing dot or lower ndots for such workloads, and consider NodeLocal DNSCache.
    • Pods in private subnets reach the internet through NAT gateways, billed per GB. Pulling images and calling S3, ECR or DynamoDB through NAT is a common hidden cost. VPC endpoints remove it.
    • Calling another AWS account or an on-premises system requires routing (Transit Gateway, peering, PrivateLink) and security group rules and often DNS. Ask for all three.

    What you control: requests, limits and scheduling

    resources:
  requests: { cpu: "500m", memory: "1Gi" }   # what the scheduler reserves, what you pay for
  limits:   { memory: "1Gi" }                # memory limit = request; usually no CPU limit
    • Requests drive everything: scheduling, autoscaling and cost. Set them from measured usage, not guesses.
    • Memory: exceeding the limit gets the container OOM-killed. Set limit equal to request for predictable behaviour.
    • CPU: a limit causes throttling even when the node is idle, which shows up as latency spikes. Many teams set CPU requests and omit CPU limits. For latency-critical services that need whole cores, Guaranteed QoS with integer CPUs and the static CPU manager policy is the tool.
    • JVM and other runtimes: make the heap container-aware (for example -XX:MaxRAMPercentage=75) and leave room for off-heap memory, or you will be OOM-killed with a heap that looks fine.
    • Recent Kubernetes versions on EKS support resizing a pod's CPU and memory in place, without a restart. Useful for vertical scaling of stateful or slow-starting services.

    Surviving node churn

    Nodes disappear: Spot interruptions, consolidation, upgrades, AMI rotation, hardware failure. Treat it as normal.

    apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: pricing-api, namespace: pricing }
spec:
  maxUnavailable: 1
  selector: { matchLabels: { app: pricing-api } }
---
# in the pod template
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector: { matchLabels: { app: pricing-api } }
    • Run at least two replicas, three for anything important, spread across zones.
    • Define a PodDisruptionBudget. A PDB that allows zero disruptions (for example minAvailable equal to replicas) blocks node upgrades and makes you unpopular.
    • Probes: startupProbe for slow starters, readinessProbe to gate traffic, livenessProbe only for deadlocks. A liveness probe that checks a downstream dependency turns one outage into a restart storm.
    • Spot is fine for stateless, replicated or batch work with two minutes of notice. Keep stateful and singleton workloads on On-Demand with node selectors or tolerations.
    • Graviton (arm64) is cheaper per unit of work for most services. Build multi-architecture images so the scheduler can use either.

    Building and shipping

    Images and Amazon ECR

    • Small, reproducible images: multi-stage builds, minimal or distroless base, non-root user, pinned base image digests.
    • Immutable tags. Tag with the Git SHA or a version, deploy by digest where you can. Turn on tag immutability in ECR.
    • Scanning on push (basic or Amazon Inspector), with CI failing on critical findings.
    • Lifecycle policies to expire old images, otherwise storage grows without bound.
    • Pull-through cache for public registries, to avoid rate limits and outages you do not control.
    aws ecr get-login-password --region eu-west-1 | \
  docker login --username AWS --password-stdin 111122223333.dkr.ecr.eu-west-1.amazonaws.com

docker buildx build --platform linux/amd64,linux/arm64 \

  --push .

    Stateful or managed?

    The usual advice holds: keep the cluster stateless where you can and use managed services for state (RDS or Aurora, DynamoDB, ElastiCache, MSK, S3). Run stateful systems on EKS when you need control over version, latency or cost, and have the operator skills. When you do, use an operator, dedicated nodes, PDBs and tested backup and restore.

    Configuration and secrets

    • ConfigMaps for non-secret configuration. Changing one does not restart pods. Kustomize's configMapGenerator adds a content hash to the name, so a config change rolls the Deployment and a rollback restores the old config.
    • Kubernetes Secrets are base64, not encryption. On EKS they are encrypted at rest with KMS, but anyone with read access to Secrets in the namespace can read them. Lock down RBAC accordingly.
    • Source of truth should be AWS Secrets Manager or SSM Parameter Store (rotation, audit trail, IAM control), not a YAML file.
    Way to get a secret into a podHowTrade-off
    External Secrets OperatorAn ExternalSecret object syncs a Secrets Manager entry into a Kubernetes Secret.Most common. Works with env vars and any chart. The value does exist as a Secret in the cluster.
    Secrets Store CSI Driver with the AWS providerMounts the secret as a file in the pod.No Secret object needed. The app must read files and handle rotation.
    SDK call at start-upThe app reads Secrets Manager directly using its pod role.Nothing stored in the cluster. Couples code to AWS and needs caching.
    apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: pricing-db, namespace: pricing }
spec:
  refreshInterval: 1h
  secretStoreRef: { name: aws-secrets-manager, kind: ClusterSecretStore }
  target: { name: pricing-db }
  dataFrom:
    - extract: { key: prod/pricing/db }

    Prefer mounting secrets as files over environment variables for anything sensitive: env vars leak into crash dumps, debug endpoints and child processes. Plan for rotation: either reload on file change or restart on Secret change (tools such as Reloader do this).

    Security for workloads

    • One IAM role per service, least privilege, scoped to named resources. Review with IAM Access Analyzer.
    • Pods run as non-root with a read-only root file system, no privilege escalation and all Linux capabilities dropped. Namespaces enforce the Pod Security Standards restricted or baseline profile.
    • Default-deny NetworkPolicy per namespace, then allow what is needed. Confirm policy enforcement is actually enabled on the cluster.
    • Pods cannot reach the node's instance metadata credentials (IMDSv2 with a hop limit of 1 on nodes).
    • Images come only from your ECR registries, are scanned, and ideally signed and verified at admission.
    • Admission policy (Kyverno, OPA Gatekeeper or built-in ValidatingAdmissionPolicy) enforces the rules above instead of relying on review.
    • Secrets come from Secrets Manager, are never committed, and RBAC to read Secrets is narrow.
    • TLS everywhere it leaves the pod: ACM at the load balancer, and a mesh or application TLS for service-to-service where required.
    • Cluster audit logs are on, and GuardDuty's EKS protections are enabled.
    • The cluster API endpoint is private or restricted by CIDR.
    securityContext:                 # container level
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }

    Versions and upgrades

    Kubernetes ships about three minor versions a year, and EKS follows each within weeks. By late 2026 EKS has reached Kubernetes 1.37. Each version gets 14 months of standard support on EKS, then 12 months of extended support at a substantially higher control-plane price, after which the cluster is upgraded automatically. In practice that means an upgrade roughly every four to six months is normal life, not an event.

    What an upgrade involves

    1. Control plane moves up one minor version (no skipping). In place, no API downtime.
    2. Add-ons are updated (CNI, CoreDNS, kube-proxy, CSI drivers). Auto Mode handles these.
    3. Nodes are replaced with the new version, draining pods while respecting PodDisruptionBudgets.

    What it asks of developers

    • No removed APIs in your manifests or charts. EKS upgrade insights and tools such as pluto or kubent flag them. Fix these ahead of time: they are the main cause of blocked upgrades.
    • Workloads that tolerate a rolling node replacement: multiple replicas, PDBs that permit disruption, graceful shutdown, no reliance on local disk.
    • Client libraries and operators compatible with the new version.
    • Images that run on the current node OS. Amazon Linux 2 AMIs are no longer published for recent versions: nodes are Amazon Linux 2023 or Bottlerocket, with cgroup v2 and containerd 2.x. Very old runtimes and agents can break on that.
    aws eks describe-cluster --name dev-euw1 --query cluster.version
aws eks list-insights --cluster-name dev-euw1          # upgrade readiness findings
kubectl get nodes -o wide                               # node versions during a rollout

    Production-readiness checklist

    • At least two replicas across zones, with a PodDisruptionBudget and topology spread.
    • CPU and memory requests based on measurement, memory limit set, runtime heap sized for the container.
    • Startup, readiness and liveness probes that test only the service itself.
    • Graceful shutdown on SIGTERM, a preStop delay behind load balancers, readiness gates enabled.
    • A dedicated service account bound to a least-privilege IAM role through Pod Identity or IRSA.
    • Config in ConfigMaps, secrets from Secrets Manager, nothing sensitive in the image or repo.
    • Restricted security context and a default-deny NetworkPolicy.
    • Immutable image tags or digests, multi-arch, scanned, from ECR.
    • Deployed through GitOps, with a tested rollback.
    • Autoscaling (HPA or KEDA) with sane minimum, maximum and stabilisation.
    • JSON logs with trace IDs, RED metrics, traces, a dashboard, and symptom-based alerts with a runbook.
    • No deprecated Kubernetes APIs. Survives a node drain in a test.
    • Timeouts, retries with backoff and jitter, and idempotency on every outbound call.
    • Resource tags and labels for ownership and cost allocation.
